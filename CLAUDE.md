# CLAUDE.md — Campertron

## Purpose
Campertron polls recreation.gov for campsite availability that matches user YAML search configs, and reports hits to the console, an HTML file, or email. A separate Avalonia GUI is a **read-only campground lookup** (find campground IDs and details). It does **not** search for availability.

## Architecture in one paragraph
Everything lives in static classes in `CampertronLibrary`. Config (`Load.GetConfig`) picks paths: `/config` + `/cache` in a container, otherwise `LocalApplicationData/CampertronConfig` + `/CampertronCache`. It loads `General.yaml` and `Email.yaml` and ensures `RecreationDotOrg.db` exists. If an installed DB has the swapped 2024 layout, or is a pre-0.1.0-beta.4 DB that still has the omitted tables, a one-time startup repair replaces it with the bundled DB (`LegacyAddressLayout.RepairIfNeeded`, business-rules §8). The trigger is a property of the DB, never the app version, and a valid DB is never replaced. Search (`Load.RunConsoleSearch` → `Preload` → `AvailabilityApi.GetAvailabilitiesByCampground` in parallel per config → `PostProcess`) fetches monthly availability JSON from recreation.gov and filters it with the rules in `AvailabilityApi.FilterData`. It renders through a `ConsoleConfigValue` list that `CampsiteConfig.ProcessConsoleConfig` writes to the console or turns into HTML and email. Static RIDB data (campsites, equipment, attributes, facilities) comes from SQLite through `sqlite/Read.cs` and is cached as per-campground JSON in the cache dir. Details: `docs/ai-context/architecture.md`.

## Conventions observed (follow when editing)
- Static classes and static methods throughout. There is no DI, no interfaces, and no logging framework. Console messages go through `ConsoleUi` (decision D34); the RIDB refresh's plain progress lines are still `Console.WriteLine`.
- PascalCase locals and parameters (`ReturnList`, `ThisConfig`) and `ref` parameters for shared state (`ref RunningData`, `ref List<ConsoleConfigValue>`).
- Model classes are in the **global namespace** (`class/**`). Functions are in `CampertronLibrary.function.*`.
- YAML uses camelCase keys (`CamelCaseNamingConvention`).
- `OutputType.UnitTest` is a production enum value used to bypass interactive and looping behavior in tests.

## Validation and logging
- There is no validation layer. YAML is deserialized directly, and invalid values surface as runtime exceptions or `Console.WriteLine` messages (see `docs/ai-context/business-rules.md`).
- There is no structured logging. Do not introduce a logging framework unless the task asks for it. Keep the existing console messages unless the task explicitly changes them.

## Preserving business logic
- The filter semantics in `AvailabilityApi.FilterData` and the `ProcessMonth`/`CalculateAvailableDates` date math are quirky but are the current contract (for example, include filters use `configValue.Contains(siteValue)`, and today's date is never matched). Do **not** "fix" them as a side effect. Change them only when asked, and record the change in `business-rules.md`.
- Keep the retry and sleep behavior (`AvailabilityApi.GetWebApiData`), the duplicate-notification markers (`Camp.History`), and the container/email loop unless the task targets them.
- `Camp.History` is the Email loop's notification history only (decision D8 as refined, business-rules §5): one `internal` policy, `Load.UsesNotificationHistory` (`OutputTo == Email`), gates both the read in `AvailabilityApi.FilterData` and the write in `Load.HasNewEntries`. Console, HtmlFile and UnitTest must neither read nor write it. Keep the marker format (`Camp.History/{yyyy}/{M}/{d}/{CampsiteID}`, directories), never delete or migrate existing markers, and keep the rule that a reported campsite and date stays suppressed for Email even if it disappears and reappears. Run `NotificationHistoryTests` after changing the search, the output or the history.
- The RIDB refresh writes rows through `RidbTableInserter` (prepared SQLite commands, one transaction, EF Core's former `SaveChanges` row order; decision D25), not EF `SaveChanges`. Its column mappings are hand-typed: when a mapped RIDB model changes, update the matching mapping; `PopulateTests` fails otherwise. Keep the row order and run the full-export comparison of build-and-test.md §M after changing the import.
- The RIDB refresh is failure-safe (decision D26, business-rules §8): it builds and validates a staging DB in `ConfigPath/RecreationDotOrg.refresh-<guid>/` and installs it with one `SqliteConnection.BackupDatabase` transaction (`RidbStagedRefresh`). Never install by renaming, replacing or deleting the installed DB. Keep the order: refresh lock → staging build and `Validate` → cache cleared → repair lock + backup → `quick_check` → `LastRidbDataRefresh` written once. The cache step clears the configured `CachePath` (`LocalApplicationData/CampertronCache` on the desktop, `/cache` in a container; TD-05 resolved, decision D27). The cache path comes only from `CampertronInternalConfig.CachePath`; never rebuild it from `LocalApplicationData`, and keep the guards in `Clear.CheckCacheDirectory`/`ClearRefreshCache` (no unset, root or config directory; only top-level files deleted). After changing it, run `AtomicRefreshTests`, the kill harness and the full-export comparison (build-and-test.md §N). The timestamp is written with `Yaml.GeneralConfigReplaceYaml` (validated temporary file renamed over `General.yaml`, `ConfigFileReplace`); don't write it in place. The culture-dependent row order (TD-36 part 2) and the other, still in-place YAML writers (TD-37) are open.
- GUI startup (R8, decision D33): `MainWindowViewModel` runs `Load.GetConfig` on a background task after the window opened and shows "Preparing campground data" or the startup error (message, settings folder, Try again). Never create or bind anything database-backed before it succeeded (`StartupTests` count EF commands on all threads), keep UI changes on the UI thread, keep the attempt/detach guards, and keep `Program.Main` waiting for a preparation still running when the window closed (extraction, repair and refresh must not be cut off). The loader is the only test seam; don't change `CampertronLibrary` for the GUI. `--smoke-test` (`SmokeTest.cs`) reports `SMOKE key=value` lines that `check_gui_smoke_report` validates: change both together. Capped elements use a capped star column (D28), never `MaxWidth` alone (centers) or left alignment (shrinks).
- GUI (beta.8, decision D28): stays a read-only lookup with three tabs, each with its own selections and details. Take colors only from Fluent theme resources (`Styles/AppStyles.axaml`, `DynamicResource`; the app follows the system Light/Dark theme). Bind each database-backed view-model property exactly once (every getter queries SQLite; `Selections_RunOneQueryEach`). The GUI owns its labels through `Read.GetCampgroundDetailsByName`; leave `Read.GetParkCampgroundByName`'s prefixed contract alone. Keep the Tab-wrap workaround in `MainWindow` for the TabControl keyboard trap reproduced with Avalonia 12.1.6 (TD-39); reassess it after any Avalonia upgrade or an upstream fix for that exact behavior. Details are looked up by name and names are not unique (TD-38, not fixed).
- Parallel searches (TD-40): `Load.RunConsoleSearch` runs the searches in `Parallel.ForEach`, and a month's availability in `RunData.SiteData` is one object shared by every search of that campground and month. Treat it as read-only once it is cached: derive per-search data into new objects (`CampsitesDataEntry.CalculateAvailableDates`, `AvailabilityApi.AvailableDatesBySite`) and never write into the cached `AvailabilityEntries`/`CampsitesDataEntry` (the kept `GenerateDates` does; the search must not call it). `RunData.FilteredAvailableData` is the run's set of every search's final hits: a search collects its own hits, filters its consecutive nights on those only, and only adds its final hits to the run's set; never read or replace it from a search (TD-04, fixed by D35). Build dates from their numbers, never by parsing culture-dependent text (TD-11, D35), and keep the Email loop's per-check date regeneration quiet and file-free (TD-46, D35). After changing the search, run `AvailableDatesTests`, `SharedMonthSearchTests`, `SearchIsolationTests`, `SearchDatesTests` and the parallel-versus-isolated comparison of build-and-test.md §Z (every search, single-night and consecutive, must equal itself run alone: 0 differences).
- HTML results page (beta.9, decision D29): `ResultsHtml` renders only from `ConsoleConfigValue.Kind`/`Metadata`; never parse console text or rebuild results from `FilteredAvailableData` (TD-04 is fixed by D35; the rule stays). When a producer changes, tag its values without changing their text: `ConsoleOutputGoldenTests` pins the producers' text byte for byte (the console no longer writes it, D34; it is the stream's contract). Encode every dynamic value; keep the page self-contained (inline CSS, no script, no external reference) and readable without CSS (it is also the email body). `HtmlFile` writes and opens one page per run (`Load.OutputResults`); `Email` sends one email per search. Tests replace the browser launch through `CampsiteConfig.OpenHtmlFile`.
- Console output (decision D34, business-rules §12): write console messages only through `ConsoleUi` (`Line`/`Status`/`Notice`/`LoopLine` on standard output, `Warning`/`Error` on standard error) and never write a control sequence yourself; `ConsoleUi.ClearScreen` is the only screen clear (interactive terminal only, never the scrollback, never over an unread message), and the Email loop never clears. Console results are rendered by `ConsoleResults` from `Kind`/`Metadata` through `ResultsHtml`'s model (internal for that; keep the page byte-identical: build-and-test.md §Y) and never from the values' text or from `FilteredAvailableData`; like the page, it shows each stream as supplied, so it never showed TD-04's orphan calendars; the cause was fixed by D35. Keep these contracts: `--version` (untouched, first in `Main`); a start with `outputTo: UnitTest` writes nothing; `Load.GetConfig` writes nothing on a clean first start unless `Load.FirstStartNotice` is set, which only `CampertronConsole` does (the GUI's `--smoke-test` output must hold only `SMOKE` lines); "Config path does not exist" and "Unsupported output type in container" stay in their messages; a handled failure exits with code 1 (`ConsoleUi.ReportFailure` in `Program.Main`), signals keep 130/143/129. Failure messages come from exceptions only: never print a value of `Email.yaml`. Don't add a terminal library, flags or a logging framework. After changing console output run `ConsoleUiTests`, `ConsoleResultsTests`, `ConsoleOutputTests`, `ConsoleFailureTests` and `ConsoleOutputGoldenTests`, and for anything touching the terminal the pseudo-terminal, redirection, signal and container checks of build-and-test.md §Y. A plain-mode golden changes only with an intended presentation change, in the same commit.
- Keep production code changes separate from documentation-only changes, in separate commits.
- Curated release notes (decision D30): each release's reviewed notes are `.github/release-notes/v<VERSION>.md`, a fragment starting with `## What's new in <VERSION>` (rules: that directory's `README.md`), merged through its own PR, ideally the last content PR before the tag. Merging approves the bytes; pushing the tag is the separate approval to publish. A publishing tag run requires that exact file and never publishes template-only notes; it puts the composed body into the draft and checks it byte for byte (tagged checkout vs artifact, draft, public). Don't add a fragment for a speculative version, don't backfill beta.4–beta.9, and never edit a published body except as recovery the maintainer explicitly approves.
- Release tags and releases are final: tag ruleset 27004221 blocks moving or deleting any `refs/tags/v*` tag (no bypass), and immutable releases are enabled. Never re-tag; release a new version instead. Releases are made only by `.github/workflows/release.yml` from a SemVer tag on `master` (first: `v0.1.0-beta.4`, 2026-11-11; latest: `v0.1.0-beta.10`, 2026-11-14 UTC). Policy and tests: `.github/release-policy/` (decision D19). Details: `docs/ai-context/build-and-test.md` §Release workflow.
- Every release output must be .NET 11 and built by one stable SDK 11 toolchain. CI and `release.yml` fail on anything else: the exact `global.json` policy and the selected SDK after every `setup-dotnet` (`check_global_json`, `check_selected_sdk`), the restored package graph (`check_package_policy`: no prerelease, no EF Core / Microsoft.Data.Sqlite / Microsoft.Extensions package of another major), project TFMs and Docker base images (verify), each of the 16 publish outputs (`check_publish_runtime`, `check_pdb_provenance`), one compiler identity across all 16 archives (`check_single_toolchain`), `--version` of the published linux-x64 apps and of the container, the PDB provenance of both container platforms (`check_oci_image`), and the GUI state data of the published library and DB (`.github/release-policy/ReleaseCheck`). - Native smoke tests (R8, D33, build-and-test.md §X): `release.yml`'s `native-smoke` runs the run's own archives on pinned standard runners (`windows-2025`, `windows-11-arm`, `macos-26-intel`, `macos-26`; no SDK, no rebuild, no screenshots) and the linux-x64 `smoke` job runs the GUI smoke test under `xvfb-run`; `docker-publish` and `release` need `native-smoke`. The generated notes claim native smoke tests only for `NATIVE_SMOKE_RIDS_DEFAULT`, which must equal the jobs (a policy test checks it). Never add a self-hosted or paid runner.
