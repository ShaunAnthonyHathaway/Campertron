## Purpose
Campertron polls recreation.gov for campsite availability that matches user YAML search configs, and reports hits to the console, an HTML file, email or, since D67, ntfy push notifications. A separate Avalonia GUI is a **campground lookup** (find campground IDs and details) that also edits the settings files (CM5), creates and edits the search files (CM6) and, since GS2, runs saved search files on request and shows their typed results in its Results tab (manual-search semantics: no `Camp.History`, no Email settings, no file written) and, since V011-2 (D60), shows the console's View Config items in Settings > System, read-only, and since V011-1 (D61) refreshes the campground data there on request, then restarts itself to load it (D62), and since D94 edits `Web.yaml` too, and since D118 controls its own monitoring in its Monitoring tab, and since D119 hosts the guided setup there.
It never runs on its own; since D94 it sends one test email or ntfy notification when the user asks for it (D86, D88, ER-39), else never; since D118 it monitors only after the user's Start, never at its start, and the monitoring ends with it (D115). Since D92 `CampertronConsole --web` is the web UI's host (its sign-in and security), with the settings pages since D94, the searches pages since D96, the results page since D97, the monitoring page since D98, the system and campgrounds pages since D99 and the guided setup since D100 (web-only in `v0.3.0`; since D119 also the desktop GUI's), its monitoring and its refresh of the campground data the web UI's.
Since D121 (`v0.4.0`'s phase 6) `CampertronConsole --interactive` opens the console's interactive foundation, line-oriented: a main menu of Status (read only), Notifications (D122, phase 7: `Email.yaml` and `Ntfy.yaml` in the shared forms, their tests, the random topic), Settings (D123, 7a: `General.yaml`, `Web.yaml` likewise), Searches (D124, 8: the search files likewise), Campgrounds (D125, 9: the lookup, the data's status and refresh, cancellable), Results (D126, 10: saved searches run now through the shared search service, cancellable), Monitoring (D127, 11: the shared controller, stopped at every end), Guided setup (D128, 12: the shared flow over its own forms), Help and Exit; nothing searched, saved, sent, refreshed or started but when the user chooses it (and, but for Start search and Stop, confirms it); `--help` lists the ways to start it. The start without arguments is unchanged, and a terminal alone never opens the interactive console.

Projects (`Campertron.sln`): `CampertronConsole`, `CampertronGUI` (Avalonia 12.1.6), `CampertronLibrary` (all business logic), `CampertronWeb` (the web UI: Razor Pages, the ASP.NET Core framework, no package), `CampertronUnitTests`, `CampertronGUITests` (headless), `CampertronWebTests` and `docker-compose.dcproj`, on .NET 11 (`net11.0`). Details: `docs/ai-context/repository-map.md` and `docs/ai-context/architecture.md`.

## Product rules
Permanent rules set by the maintainer (D76, 2026-11-22; the first extended by D84, the last added by D87); only the maintainer's explicit approval, recorded as an exception, overrides one:
- Full UI rule: every Campertron feature must be fully controllable from the desktop GUI and from the web UI, with the same files, validation and words, except for listed exceptions. Desktop-only: the theme's storage (both UIs offer System, Light and Dark, the console no theme; the web UI keeps its choice in the browser, D110), the automatic restart, window placement, opening folders. Web-only: the sign-in and the password; the monitoring's control is in both UIs since D118, the guided setup since D119. Until the web UI exists (`v0.3.0`, D79) it applies to the desktop GUI as before. What both UIs share is the library's form layer (D91, ER-37): a form's words and rules are written once, there.
- Scope lock: once a release's scope is approved, only bugs, missing GUI parity, security or data-loss fixes and documentation for that scope may be added; new features go to a later version.
- Local test before candidate: user-facing changes are tested locally from the merged `master` before any release candidate.
- The send-failure behavior is the maintainer's approved behavior: a failed send is a visible error, the monitoring stops, and a failed delivery's openings are not recorded in `Camp.History`. Don't change it.
- Website sync (D87): campertron.com (`site/`) must stay consistent with the README and docs. Any PR that changes features, setup, downloads, Docker instructions, screenshots or user-facing wording covered by the site must include or schedule the matching `site/` update. Site screenshot copies are refreshed whenever README screenshots change. The site stays version-free and unpromoted until the public announcement. Because merging `site/` changes publishes via `pages.yml`, site updates describing unreleased features are merged only after that release is published, and each site merge needs user approval (normally bundled with the release approval).

## Data safety
- Never open, list, hash, copy, inspect or query real Campertron user data, even read-only: the configuration, cache and preference folders (`CampertronConfig`, `CampertronCache`, `CampertronExtract` and `CampertronGUI` under `LocalApplicationData`, on Linux `$XDG_DATA_HOME` or `~/.local/share`), saved searches, `General.yaml`, `Email.yaml`, `Ntfy.yaml`, password and token files, `Camp.History`, `RecreationDotOrg.db` and any other real application data.
- Use only repository files, Git metadata, read-only GitHub state and isolated temporary locations: `XDG_DATA_HOME="$(mktemp -d)"` for tests and local runs; `unshare -rm` with a `tmpfs` over `/home` for released programs and screenshots (`docs/ai-context/maintainer-procedures.md` §Rules for every procedure).
- The tests never reach the network (`NoLiveNetwork`) and never send email or an ntfy notification; ntfy is tested against a loopback listener only, never ntfy.sh or a real server.

## Conventions observed (follow when editing)
- Static classes and static methods throughout (a service's own run is an instance: `MonitoringService`, D90; so is a form of the shared form layer, D91, and the monitoring controller, D116; the web host's own classes are single instances in ASP.NET Core's service container, D92; so are the interactive console's terminal, questions and session, D121, its terminal an abstract class, the tests' seam, and its settings form's host, D122, with its menus, D123, a search form's host over it, D124, and the refresh's operation and screen, D125, a search's, D126, and the console's monitoring host, D127, and its guided setup with a form's host hook, D128). There is no DI, no interfaces, and no logging framework. Console messages go through `ConsoleUi` (decision D34); the RIDB refresh's plain progress lines are still `Console.WriteLine`.
- PascalCase locals and parameters (`ReturnList`, `ThisConfig`) and `ref` parameters for shared state (`ref RunningData`, `ref List<ConsoleConfigValue>`).
- Model classes are in the **global namespace** (`class/**`). Functions are in `CampertronLibrary.function.*`.
- YAML uses camelCase keys (`CamelCaseNamingConvention`).
- `OutputType.UnitTest` is a production enum value used to bypass interactive and looping behavior in tests.

## Validation and logging
- Since D41 the settings files have a validation layer (`ConfigValidation`, business-rules §15) that produces typed, value-free diagnostics; at run time it refuses only dangerous settings, an incomplete `Email.yaml` and (since D67) an unusable `Ntfy.yaml` before the monitoring searches. Other invalid values still surface as runtime exceptions or console warnings, as before (see `docs/ai-context/business-rules.md`).
- There is no structured logging. Do not introduce a logging framework unless the task asks for it. The web host (D81, D92) has an approved exception: ASP.NET Core's log output off (the host has no logging provider), only Campertron's own fixed lines through `ConsoleUi`. Keep the existing console messages unless the task explicitly changes them.
