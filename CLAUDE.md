# CLAUDE.md — Campertron

## Purpose
Campertron polls recreation.gov for campsite availability that matches user YAML search configs, and reports hits to the console, an HTML file, or email. A separate Avalonia GUI is a **read-only campground lookup** (find campground IDs and details). It does **not** search for availability.

## Architecture in one paragraph
Everything lives in static classes in `CampertronLibrary`. Config (`Load.GetConfig`) picks paths: `/config` + `/cache` in a container, otherwise `LocalApplicationData/CampertronConfig` + `/CampertronCache`. It loads `General.yaml` and `Email.yaml` and ensures `RecreationDotOrg.db` exists. If an installed DB has the swapped 2024 layout, or is a pre-0.1.0-beta.4 DB that still has the omitted tables, a one-time startup repair replaces it with the bundled DB (`LegacyAddressLayout.RepairIfNeeded`, business-rules §8). The trigger is a property of the DB, never the app version, and a valid DB is never replaced. Search (`Load.RunConsoleSearch` → `Preload` → `AvailabilityApi.GetAvailabilitiesByCampground` in parallel per config → `PostProcess`) fetches monthly availability JSON from recreation.gov and filters it with the rules in `AvailabilityApi.FilterData`. It renders through a `ConsoleConfigValue` list that `CampsiteConfig.ProcessConsoleConfig` writes to the console or turns into HTML and email. Static RIDB data (campsites, equipment, attributes, facilities) comes from SQLite through `sqlite/Read.cs` and is cached as per-campground JSON in the cache dir. `YamlDocument` (`function/Base/YamlDocument.cs`, D39) edits a settings document's text in memory by targeted range replacement, keeping comments and formatting, and checks every result with the loaders' own deserializer (`Yaml.SettingsDeserializer`). Every settings file is read through `Yaml.ReadSettingsText`/`LoadSettingsText` within the editor's limits, and `ConfigFiles` decides which file is which (D41); `ConfigValidation` (D41) turns settings into typed, value-free diagnostics, refuses at start only dangerous settings, and checks `Email.yaml` before the Email loop searches. `ConfigFileReplace` (D40) is the only way a settings file is written: `Replace` (strict UTF-8, verified temporary file, mode, links, backup, external-change check, rename) for `General.yaml`'s refresh timestamp, which `Yaml.GeneralConfigReplaceYaml` edits with `YamlDocument`, and create-only `Create` for the sample files. The GUI's Settings tab edits `General.yaml` and `Email.yaml` through `ConfigEditSession` (D43: the bytes read, pending typed edits, `YamlDocument` steps, `ConfigValidation`, a masked preview, `ConfigFileReplace.Replace`, external-change conflicts). The GUI lists campgrounds as `CampgroundChoice` entries (`class/RecDotOrg/CampgroundChoice.cs`: FacilityID, name, optional location; D42) from `Read.CampgroundChoicesByPark`/`ByStateAndCity`/`ByState` and loads their details with `Read.GetCampgroundDetailsById`. Details: `docs/ai-context/architecture.md`.

## Conventions observed (follow when editing)
- Static classes and static methods throughout. There is no DI, no interfaces, and no logging framework. Console messages go through `ConsoleUi` (decision D34); the RIDB refresh's plain progress lines are still `Console.WriteLine`.
- PascalCase locals and parameters (`ReturnList`, `ThisConfig`) and `ref` parameters for shared state (`ref RunningData`, `ref List<ConsoleConfigValue>`).
- Model classes are in the **global namespace** (`class/**`). Functions are in `CampertronLibrary.function.*`.
- YAML uses camelCase keys (`CamelCaseNamingConvention`).
- `OutputType.UnitTest` is a production enum value used to bypass interactive and looping behavior in tests.

## Validation and logging
- Since D41 the settings files have a validation layer (`ConfigValidation`, business-rules §15) that produces typed, value-free diagnostics; at run time it refuses only dangerous settings and an incomplete `Email.yaml` before the Email loop searches. Other invalid values still surface as runtime exceptions or console warnings, as before (see `docs/ai-context/business-rules.md`).
- There is no structured logging. Do not introduce a logging framework unless the task asks for it. Keep the existing console messages unless the task explicitly changes them.

## Preserving business logic
- The filter semantics in `AvailabilityApi.FilterData` and the `ProcessMonth`/`CalculateAvailableDates` date math are quirky but are the current contract (for example, include filters use `configValue.Contains(siteValue)`, and today's date is never matched). Do **not** "fix" them as a side effect. Change them only when asked, and record the change in `business-rules.md`.
- Keep the retry and sleep behavior (`AvailabilityApi.GetWebApiData`), the duplicate-notification markers (`Camp.History`), and the container/email loop unless the task targets them.
- `Camp.History` is the Email loop's notification history only (decision D8 as refined, business-rules §5): one `internal` policy, `Load.UsesNotificationHistory` (`OutputTo == Email`), gates the reads (`AvailabilityApi.FilterData`, the Email gate `Load.HasUnreportedEntries`) and the write (`Load.RecordNotificationHistory`). Console, HtmlFile and UnitTest must neither read nor write it. A marker is written only after the email that shows the opening was delivered (TD-14, decision D36): each search's openings right after its send in `Load.OutputResults`, the run's remaining hits after every email of the check (`Load.ReportResults`); a failed email leaves its openings and those of the later emails eligible, and earlier markers stay. Only a marker write creates `Camp.History` (TD-43); never create it eagerly or write a marker before the send. Sends go through `CampsiteConfig.SendResultsEmail`, which tests replace (no test sends mail). Keep the marker format (`Camp.History/{yyyy}/{M}/{d}/{CampsiteID}`, directories), never delete or migrate existing markers, and keep the rule that a reported campsite and date stays suppressed for Email even if it disappears and reappears. Run `NotificationHistoryTests` and `EmailDeliveryHistoryTests` after changing the search, the output, the email or the history.
- The RIDB refresh writes rows through `RidbTableInserter` (prepared SQLite commands, one transaction, EF Core's former `SaveChanges` row order; decision D25), not EF `SaveChanges`. Its column mappings are hand-typed: when a mapped RIDB model changes, update the matching mapping; `PopulateTests` fails otherwise. Keep the row order and run the full-export comparison of build-and-test.md §M after changing the import.
- The RIDB refresh is failure-safe (decision D26, business-rules §8): it builds and validates a staging DB in `ConfigPath/RecreationDotOrg.refresh-<guid>/` and installs it with one `SqliteConnection.BackupDatabase` transaction (`RidbStagedRefresh`). Never install by renaming, replacing or deleting the installed DB. Keep the order: refresh lock → staging build and `Validate` → cache cleared → repair lock + backup → `quick_check` → `LastRidbDataRefresh` written once. The cache step clears the configured `CachePath` (`LocalApplicationData/CampertronCache` on the desktop, `/cache` in a container; TD-05 resolved, decision D27). The cache path comes only from `CampertronInternalConfig.CachePath`; never rebuild it from `LocalApplicationData`, and keep the guards in `Clear.CheckCacheDirectory`/`ClearRefreshCache` (no unset, root or config directory; only top-level files deleted). After changing it, run `AtomicRefreshTests`, the kill harness and the full-export comparison (build-and-test.md §N). The timestamp is written with `Yaml.GeneralConfigReplaceYaml` (since D40 only that value, edited in the current file and written by `ConfigFileReplace.Replace`); don't write it in place or re-serialize `General.yaml`. The culture-dependent row order (TD-36 part 2) is open.
- GUI startup (R8, decision D33): `MainWindowViewModel` runs `Load.GetConfig` on a background task after the window opened and shows "Preparing campground data" or the startup error (message, settings folder, Try again). Never create or bind anything database-backed before it succeeded (`StartupTests` count EF commands on all threads), keep UI changes on the UI thread, keep the attempt/detach guards, and keep `Program.Main` waiting for a preparation still running when the window closed (extraction, repair and refresh must not be cut off). The loader is the only test seam; don't change `CampertronLibrary` for the GUI. `--smoke-test` (`SmokeTest.cs`) reports `SMOKE key=value` lines that `check_gui_smoke_report` validates: change both together. Capped elements use a capped star column (D28), never `MaxWidth` alone (centers) or left alignment (shrinks).
- GUI (beta.8, decision D28): three read-only lookup tabs, each with its own selections and details, and since D43 the Settings tab (next rules). Take colors only from Fluent theme resources (`Styles/AppStyles.axaml`, `DynamicResource`; the app follows the system Light/Dark theme). Bind each database-backed view-model property exactly once (every getter queries SQLite; `Selections_RunOneQueryEach`). Keep the FacilityID exactly as stored (a string: never parsed as a number or trimmed). - Console output (decision D34, business-rules §12): write console messages only through `ConsoleUi` (`Line`/`Status`/`Notice`/`LoopLine` on standard output, `Warning`/`Error` on standard error) and never write a control sequence yourself; `ConsoleUi.ClearScreen` is the only screen clear (interactive terminal only, never the scrollback, never over an unread message), and the Email loop never clears. Console results are rendered by `ConsoleResults` from `Kind`/`Metadata` through `ResultsHtml`'s model (internal for that; keep the page byte-identical: build-and-test.md §Y) and never from the values' text or from `FilteredAvailableData`; like the page, it shows each stream as supplied, so it never showed TD-04's orphan calendars; the cause was fixed by D35. Keep these contracts: `--version` (untouched, first in `Main`); a start with `outputTo: UnitTest` writes nothing; `Load.GetConfig` writes nothing on a clean first start unless `Load.FirstStartNotice` is set, which only `CampertronConsole` does (the GUI's `--smoke-test` output must hold only `SMOKE` lines); "Config path does not exist" and "Unsupported output type in container" stay in their messages; a handled failure exits with code 1 (`ConsoleUi.ReportFailure` in `Program.Main`; since D37 also equal `StartEndDate` dates and a blocked request), signals keep 130/143/129. Failure messages come from exceptions only: never print a value of `Email.yaml`. Don't add a terminal library, flags or a logging framework. After changing console output run `ConsoleUiTests`, `ConsoleResultsTests`, `ConsoleOutputTests`, `ConsoleFailureTests` and `ConsoleOutputGoldenTests`, and for anything touching the terminal the pseudo-terminal, redirection, signal and container checks of build-and-test.md §Y. A plain-mode golden changes only with an intended presentation change, in the same commit.
- Settings safety and failure exits (decision D37, business-rules §9): create the example `ZionConfig.yaml` only when the settings folder has no search file, and never write over or re-serialize a user's search file; with search files of which none has `autoRun: true`, warn and search nothing (open question #40 for the Email loop). Report an unusable settings file by throwing inside the loader's `ConsoleUi.NoteFile` boundary (an empty `General.yaml` or search file, equal `StartEndDate` dates); never `Console.ReadKey` or `Environment.Exit` in the loader. An empty `Email.yaml` stays tolerated outside Email output (TD-51 is preview.2). A blocked request keeps its message and 5-minute wait and exits with 1 through `AvailabilityApi.BlockedWait`/`ExitProcess` (internal seams; tests replace them, production defaults `Thread.Sleep`/`Environment.Exit`). The desktop data folder comes only from `Load.DesktopDataFolder` (`SpecialFolderOption.Create`, a full path or an error): never fall back to the working directory, and leave the container's `/config` and `/cache` alone. The RIDB refresh extracts only into `LocalApplicationData/CampertronExtract` (`Compression.ExtractFolderName`); never delete a folder Campertron does not own. Run `SettingsBootstrapTests`, `DataFolderTests`, `ConsoleFailureTests`, `AtomicRefreshTests` and `CachePathTests` after changing any of this (build-and-test.md §AB).
- YAML document editor (CM1, decision D39, business-rules §13): `YamlDocument` is pure and in memory (no file, console, environment or network access; `TheEditor_NeverReachesTheFileSystemTheConsoleOrTheNetwork` scans its IL); its one production caller is `Yaml.GeneralConfigReplaceYaml` (D40). It edits by text-range replacement located by YamlDotNet's normal parser (comments skipped; never depend on YamlDotNet's comment tokens: 17.0.0 to 18.1.0 fail on a comment after a flow sequence in that mode) and its own scan of the gaps for comments; it never re-serializes a document and refuses, with a value-free diagnostic, anything it can't edit safely instead of normalizing it. Every result passes the preservation checks and a load with `Yaml.SettingsDeserializer` (the one deserializer of the three settings loaders) that must equal the caller's intended model; a failure returns no text. Keep the refusals, the locks (anchors, aliases, standard tags), the engine-only limits and the rule that no diagnostic quotes a value of the document (Email.yaml). Offsets are UTF-16 indexes into the caller's text; a leading U+FEFF is kept but not parsed. After changing it, or the loaders' deserializer, run `YamlDocumentTests`, `YamlDocumentPreservationTests` and `YamlDocumentRefusalTests` and the negative controls of build-and-test.md §AD. File access belongs to `ConfigFileReplace` (CM2), never to the editor.
- Settings validation and loading (CM3, decision D41, business-rules §15): every settings file is loaded through `Yaml.LoadSettingsFile`/`LoadSettingsText` (`ReadSettingsText`: bytes checked before reading, the former decoding; `ScanSettings`: the editor's character, event, nesting and alias limits counted by YamlDotNet's parser; then `SettingsDeserializer` on exactly those events). Never deserialize a settings text another way, never add `IgnoreUnmatchedProperties` (D20), and keep the loader, `ConfigValidation` and the editor on the same limits and deserializer. Classify files only with `ConfigFiles` (ordinal, case-insensitive; never `ToLower`). `ConfigDiagnostic` messages are fixed text, key names and numbers: never a value or an exception's message, and no unknown key of `Email.yaml` by name. At run time refuse (through `ConfigValidation.ThrowIfRefused`, inside the loaders' `NoteFile` boundary) only what would take a dangerous path; don't print warnings. `Load.CheckEmailOutputSettings` runs first in the Email branch of `Load.RunConsoleSearch`, before `Preload`: keep it there and out of `Load.GetConfig` (the GUI and other output types must start with an incomplete `Email.yaml`); it never connects or sends. Don't change open question #40's loop. After changing any of this run `ConfigFilesTests`, `SettingsLoaderLimitsTests`, `ConfigValidationTests`, `EmailOutputValidationTests`, the CM1 and CM2 suites and `ConsoleFailureTests`, then the negative controls of build-and-test.md §AF (rebuild after restoring).
- Settings file writes (CM2, decision D40, business-rules §14): every settings file write goes through `ConfigFileReplace`. `Replace` (only `General.yaml`'s refresh timestamp uses it) reads strictly (`Read`: UTF-8 only, a BOM kept as a leading U+FEFF, UTF-16/32, NUL and invalid bytes refused, links followed to a regular-file target, a SHA-256 and the metadata kept), and the caller edits the text it read with `YamlDocument` (never a re-serialization and never the settings loaded at the start) and checks it with `VerifyCandidate` before writing, on the temporary file and after the rename. Keep the order: same-directory `<name>.<32 hex>.tmp` (create-new, 0600 while written, `Flush(true)`, the file's mode, read back) → unchanged check → `<name>.bak` (one rolling backup, the source's mode, renamed) → unchanged check → rename → read-back. `Create` (the samples) writes the serializer's unchanged text and moves it into place only if the name is free; never truncate or write over a settings file, and load a file that another program created meanwhile. A Unix link stays a link (write in the target's directory); on Windows reparse points, read-only files and files with their own ACL are refused, and the temporary file and the backup must have exactly the file's access rules (DACL as SDDL) before anything is renamed. These Windows paths run only in the CI job `windows-settings-files` (now "Windows settings files (CM1 to CM3, CM5)"): keep it green, and add a test to `ConfigFileReplaceWindowsTests` for new Windows behavior. Stale cleanup removes only exact temporary names, regular files, older than `StaleTemporaryAge` (10 minutes). Messages name the file and the problem, never a value (Email.yaml). The `Step` seam is for tests and the interruption harness only. After changing it run `ConfigFileReplaceTests`, `GeneralYamlTimestampTests`, `SettingsBootstrapTests` and `AtomicRefreshTests` (and let the Windows job run), then the negative controls and the interruption harness of build-and-test.md §AE.
- Keep production code changes separate from documentation-only changes, in separate commits.
- Curated release notes (decision D30): each release's reviewed notes are `.github/release-notes/v<VERSION>.md`, a fragment starting with `## What's new in <VERSION>` (rules: that directory's `README.md`), merged through its own PR, ideally the last content PR before the tag. Merging approves the bytes; pushing the tag is the separate approval to publish. A publishing tag run requires that exact file and never publishes template-only notes; it puts the composed body into the draft and checks it byte for byte (tagged checkout vs artifact, draft, public). Don't add a fragment for a speculative version, don't backfill beta.4–beta.9, and never edit a published body except as recovery the maintainer explicitly approves.
- Release tags and releases are final: tag ruleset 27004221 blocks moving or deleting any `refs/tags/v*` tag (no bypass), and immutable releases are enabled. Never re-tag; release a new version instead. Releases are made only by `.github/workflows/release.yml` from a SemVer tag on `master` (first: `v0.1.0-beta.4`, 2026-11-11; latest: `v0.1.0-preview.1`, 2026-11-15 UTC). Every release, including a hyphenated pre-release version, is published as a normal GitHub release marked Latest; a hyphen only limits Docker tags to the exact version. Policy and tests: `.github/release-policy/` (decision D19). Details: `docs/ai-context/build-and-test.md` §Release workflow.
- Every release output must be .NET 11 and built by one stable SDK 11 toolchain. CI and `release.yml` fail on anything else: the exact `global.json` policy and the selected SDK after every `setup-dotnet` (`check_global_json`, `check_selected_sdk`), the restored package graph (`check_package_policy`: no prerelease, no EF Core / Microsoft.Data.Sqlite / Microsoft.Extensions package of another major), project TFMs and Docker base images (verify), each of the 16 publish outputs (`check_publish_runtime`, `check_pdb_provenance`), one compiler identity across all 16 archives (`check_single_toolchain`), `--version` of the published linux-x64 apps and of the container, the PDB provenance of both container platforms (`check_oci_image`), and the GUI state data of the published library and DB (`.github/release-policy/ReleaseCheck`). Keep these guards when changing the release workflow (decisions D21, D31, D32; build-and-test.md §I, §U, §W).
- Native smoke tests (R8, D33, build-and-test.md §X): `release.yml`'s `native-smoke` runs the run's own archives on pinned standard runners (`windows-2025`, `windows-11-arm`, `macos-26-intel`, `macos-26`; no SDK, no rebuild, no screenshots) and the linux-x64 `smoke` job runs the GUI smoke test under `xvfb-run`; `docker-publish` and `release` need `native-smoke`. On Windows and macOS the data folder is the runner user's real one (on macOS .NET asks the system, so `HOME` cannot redirect it): require it absent and remove what a step created. The generated notes claim native smoke tests only for `NATIVE_SMOKE_RIDS_DEFAULT`, which must equal the jobs (a policy test checks it). Never add a self-hosted or paid runner.
- The published container image is exactly the image the docker job validated (D32, build-and-test.md §W). The docker job builds both platforms once as an OCI archive, checks both, correlates the smoke-tested amd64 image by digest and uploads the archive as `container-image`. `docker-publish` pushes those bytes with `skopeo copy --all --preserve-digests`, never moves an existing tag and attests the validated digest. Never add an image build to `docker-publish`, never let the docker job contact a registry, and keep the rehearsal and digest checks.
- Windows GUI packages exclude the SkiaSharp/HarfBuzzSharp native debug symbols (`libSkiaSharp.pdb`, `libHarfBuzzSharp.pdb`, about 105 MB per RID) through the `ExcludeWindowsNativeDebugSymbols` target in `CampertronGUI.csproj`, which filters `NativeCopyLocalItems` by package ID (an SDK-internal item; decision D24). `release.yml` fails if they reappear as files or `.deps.json` entries. Don't replace it with file deletion or `ExcludeAssets="native"` (both are wrong, D24), and keep Campertron's own PDBs. TD-35 is mitigated, not fixed upstream; remove the target only when fixed packages are adopted (open question #24, build-and-test.md §L).
- `v0.1.0-beta.4` was investigated on 2026-11-11 (build-and-test.md §I). Its published artifacts are correct. The GUI that showed ZIP codes as states was a separate 2024 executable, not the one in the beta.4 archive. The console that reported .NET 9 was not established to be the beta.4 console. - `master` is protected by ruleset 26990088, with no bypass for anyone, including admins.
