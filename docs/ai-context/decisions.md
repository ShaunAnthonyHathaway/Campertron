The repository has no ADRs or design notes. The decisions below are **observable choices** in the code and config. Rationale is given only where the repository states it. Otherwise it is marked "not recorded".

| D20 | **Old-binary compatibility is handled by documentation, not by an in-app mechanism.** Every release's notes must contain a "Compatibility with older versions" section (enforced by `validate_notes`), and `--version` identifies a copy (business-rules §10–§11). Designs considered (2026-11-11): (a) an extra key in `General.yaml`: both the 2024 and the current YAML loaders reject unknown keys, so the 2024 apps would stop starting, but with a YamlDotNet exception (the 2024 GUI, a WinExe, would close silently), every user's `General.yaml` would be rewritten, and a deliberate downgrade would be blocked; (b) a new database file name per layout: the 2024 apps would then extract their own legacy DB and work, but it needs a migration of every existing DB, a second 226–328 MB file and changes to extraction, repair and refresh; (c) a marker or readme file in the data folder: nothing old reads it.
