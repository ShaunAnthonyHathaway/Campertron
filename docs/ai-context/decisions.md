# Architecture decisions

The repository has no ADRs or design notes. The decisions below are **observable choices** in the code and config. Rationale is given only where the repository states it. Otherwise it is marked "not recorded".

## Verified decisions
| # | Decision | Evidence | Stated rationale |
|---|---|---|---|
| D1 | Shared logic lives in one class library consumed by the console and GUI hosts | `ProjectReference` to `CampertronLibrary` in `CampertronConsole.csproj` and `CampertronGUI.csproj` | not recorded |
| D2 | Target .NET 10 for all projects (previously `net9.0` at commit `0e41fbf`) | `<TargetFramework>net10.0</TargetFramework>` in all four `.csproj` files; Dockerfile `sdk:10.0` / `runtime:10.0` | the maintainer asked for the migration during the 2026-11-10 audit session, with explicit instructions not to pin .NET 9. NuGet packages were deliberately left unchanged because none were required for net10.0 (build-and-test.md §B) |
| D3 | Static RIDB reference data is stored in SQLite through EF Core | `RecreationDotOrgContext` (`function/RecDotOrg/db/SqliteDb.cs`), package `Microsoft.EntityFrameworkCore.Sqlite` | not recorded |
| D4 | Ship a pre-populated DB as an embedded resource instead of running migrations (a zip until 2026-11-10, Brotli since; see D16) | `<EmbeddedResource Include="content\RecreationDotOrg.db.br" />`, `Load.ExtractEmbeddedDbTo`. No `Migrate()` call | not recorded |
| D5 | Per-campground static data is cached as JSON files to speed up searches | `Cache.CheckCache` | code comment: "we cache campsite data in local json files to make faster" (`AvailabilityApi.GetAvailabilitiesByCampground`) |
| D6 | User configuration lives in YAML files, and multiple search files are allowed | `function/Base/Yaml.cs`, README "Multiple configuration files can be used" | README: search against all configs, "grab the data it needs … once" |
| D7 | Each monthly availability URL is fetched only once per search cycle and shared across configs | `RunData.Urls.TryAdd`, `RunData.SiteData` (`AvailabilityApi.ProcessMonth`) | code comment: "overlaping config files use the same data that's only retrieved once" |
| D8 | Duplicate notifications are suppressed with filesystem marker directories | `Load.HasNewEntries`, `FilterData` comment "prevents duplicate notifications" | comment only |
| D9 | The container deployment is headless and email-only | `Menu.WriteMenu` exits in a container. `/config` and `/cache` in `Load.GetConfig`. README Docker section | not recorded |
| D10 | Output is abstracted as a list of `ConsoleConfigValue` render instructions, so one result can be rendered to console, HTML or email | `class/Base/ConsoleConfig.cs`, `CampsiteConfig.ProcessConsoleConfig` | not recorded |
| D11 | The GUI uses Avalonia + ReactiveUI (cross-platform desktop). Since D23: Avalonia 12.1.6 with the System.Reactive-compatible `ReactiveUI.Avalonia.Reactive` 12.1.6 | `CampertronGUI.csproj` packages, `Program.cs` `.UseReactiveUI(_ => { })` | not recorded |
| D12 | The GUI's role is campground lookup, not search | README: "run CampertronGUI to get the campground ID and other information about the locations" | README |
| D13 | Tests run against real environment state, with a dedicated `OutputType.UnitTest` switch in production code | `OutputType.UnitTest` in `Config.cs`. Checks in `Menu.Init`, `Load.Preload`, `Load.RunConsoleSearch`, `Load.PostProcess`, `CampsiteConfig.ProcessConsoleConfig` | not recorded |
| D14 | CI runs on GitHub Actions (`ubuntu-latest`): Release restore, build and test, plus a failing-on-any-finding NuGet vulnerability scan. It uses least-privilege `contents: read`, actions pinned to commit SHAs, no secrets and no NuGet cache | `.github/workflows/ci.yml` (commit `ec70898`, PR #14). Repo Actions setting: GitHub-owned actions only | the maintainer requested CI during the 2026-11-10 session. No cache because there are no lock files and the cache would be about 534 MB for a roughly 30 s restore (build-and-test.md) |
| D15 | `master` is protected by an active repository ruleset (ID 26990088, "Protect master"): PR required with 0 approvals, required CI check `Restore, build, test, vulnerability scan` (integration 15368) with strict up-to-date policy, resolved conversations, merge commits only, force pushes and deletion blocked, no bypass actors (admins included), no linear-history requirement | `GET /repos/…/rulesets/26990088` and `GET …/rules/branches/master`, 2026-11-10 (build-and-test.md §Branch protection) | maintainer request during the 2026-11-10 session. 0 approvals because "I am currently the only maintainer" (maintainer). Merge commits only was the maintainer's choice; no further reason recorded. A ruleset rather than classic branch protection was proposed in-session and approved by the maintainer |

| D16 | Keep only the 6 RIDB tables Campertron reads, and ship the DB Brotli-compressed (`RecreationDotOrg.db.br`, built-in `BrotliStream`). No xz, Git LFS or third-party compression package | `RidbDatabase.OmittedTables`, `RecreationDotOrgContext`, `PopulateDbFromRIDBFiles`, `Load.ExtractEmbeddedDbTo`; commits `4215b79` (slimming) and `07e786d` (Brotli) | maintainer decision 2026-11-10. The refreshed full DB zipped to 95.7 MB, close to GitHub's 100 MiB file limit. Measured alternatives: Brotli 54.2 MB (full) / 26.6 MB (slim); slim zip 57.5 MB; xz 44.8 MB (needs a package). LFS was rejected for quota, CI and Docker-context complications |
| D17 | Releases come from `.github/workflows/release.yml`. A SemVer tag on `master` is the only way to publish; the version comes from the tag. Separate console and GUI archives for 8 targets (zip for Windows, tar.gz elsewhere), self-contained, not single-file or trimmed. `SHA256SUMS.txt` plus build-provenance attestations. Checksums and release notes are assembled and validated by a read-only job on every run, dry runs included, and the tag-only release job publishes that output unchanged. Draft-first GitHub release. Image only on GHCR (amd64 + arm64), and SemVer pre-release versions never move `latest` (see D19 for the GitHub release flag). Manual runs and relevant PRs are dry runs. The publishing jobs require a `v*` tag-push event as well as the verified version. Least-privilege per-job permissions, GitHub-owned actions pinned to SHAs, no secrets beyond `GITHUB_TOKEN`. Only linux-x64 is smoke-tested natively | `release.yml`, `CampertronConsole/Dockerfile` (multi-arch), README | maintainer approval of the release design, 2026-11-10. First intended version `v0.1.0-beta.4` |
| D18 | Release tags and releases are protected. Tag ruleset 27004221 ("Protect release tags") blocks update and deletion of `refs/tags/v*` for everyone (no bypass actors); creation is allowed. Immutable releases are enabled. A published version is therefore final, and a fix means a new version | `GET …/rulesets/27004221`, `GET …/immutable-releases`, read back 2026-11-11 (build-and-test.md §Release protections) | maintainer approval of the release stage, 2026-11-11; applied before the first tag `v0.1.0-beta.4` |
| D19 | Every published version is a **normal GitHub release marked Latest**, including SemVer pre-release (hyphenated) versions, so the newest release is always shown on the repository page. A hyphen still means "pre-release" for Docker aliases (exact tag only; no `latest` or `<major>.<minor>`) and for the release-note wording. Policy and tests are in `.github/release-policy/` | `release-policy.sh` (`github_release_flags` = `--latest`, `docker_tag_args`), `release.yml` post-publish check | maintainer decision, 2026-11-11. GitHub cannot mark a prerelease as Latest (REST `make_latest`: "Drafts and prereleases cannot be set as latest"), so the maintainer chose full releases over the Pre-release label. `v0.1.0-beta.4` was converted accordingly, and the two 2024 release entries were deleted (tags kept) |
| D20 | **Old-binary compatibility is handled by documentation, not by an in-app mechanism.** Every release's notes must contain a "Compatibility with older versions" section (enforced by `validate_notes`), the README has an upgrade note, and `--version` identifies a copy (business-rules §10–§11). Designs considered (2026-11-11): (a) an extra key in `General.yaml`: both the 2024 and the current YAML loaders reject unknown keys, so the 2024 apps would stop starting, but with a YamlDotNet exception (the 2024 GUI, a WinExe, would close silently), every user's `General.yaml` would be rewritten, and a deliberate downgrade would be blocked; (b) a new database file name per layout: the 2024 apps would then extract their own legacy DB and work, but it needs a migration of every existing DB, a second 226–328 MB file and changes to extraction, repair and refresh; (c) a marker or readme file in the data folder: nothing old reads it. None can make a 2024 binary warn, because it can't be changed. (a) and (b) change normal behavior or add migration complexity, so they were rejected | `render_notes`/`validate_notes` (`release-policy.sh`), README "Versions from 2024", `RuntimeInfo` | maintainer request 2026-11-11: add a safe mechanism only "if that can be done without adding significant migration complexity or changing normal application behavior", and choose the smallest robust solution |
| D21 | **Every release output is verified to be .NET 10**, statically and at run time, and the workflow fails otherwise: project files and Docker base images (verify), each of the 16 self-contained publish outputs (runtimeconfig, deps.json runtime pack, CoreLib), `--version` of both published linux-x64 apps against the bundled runtime, and the container (`DOTNET_VERSION`, runtimeconfig, `--version`). The GUI state data is validated with the **published** library against the DB the published apps extracted (`ReleaseCheck`). `--version` was added to both apps for this | `release.yml` (verify, binaries, smoke, docker), `release-policy.sh` guards and their tests, `.github/release-policy/ReleaseCheck/`, `RuntimeInfo.cs` | maintainer request 2026-11-11 after the beta.4 investigation (build-and-test.md §I). beta.4 itself was correct; the guards make a wrong runtime or wrong state data a failed release instead of a user report |
| D22 | **Installed databases are repaired by their own properties, not by app version.** The one-time startup repair replaces a DB only for the swapped 2024 layout or for a corrected-layout DB that still contains any of the 15 omitted RIDB tables, which only pre-0.1.0-beta.4 code created. Non-normalized GUI states are reported but don't trigger a replacement by themselves. The bundled replacement must pass `RidbDatabase.Validate` and need no repair itself, so the repair is final without a marker file. A successful replacement also deletes the DB-derived JSON cache files | `LegacyAddressLayout.DetectRepairReason`, `RepairIfNeeded`, `ClearDerivedCache`; `LegacyAddressLayoutTests`, `StartupRepairTests` | maintainer request 2026-11-11 (beta.6): repair affected upgrades automatically and once, never replace a valid or newer manually refreshed DB, and don't use the version as the trigger. A state-value trigger was rejected because the current importer passes unmappable values (`STATE MAPPING BROKEN`) through, so a future valid refresh could be downgraded on every start. Running full validation at every start was rejected because it includes `integrity_check`; the chosen check adds about 0.3 ms to the existing 13 ms layout scan (business-rules §8) |
| D23 | **The GUI runs on Avalonia 12.1.6 with `ReactiveUI.Avalonia.Reactive` 12.1.6, the System.Reactive-compatible ReactiveUI flavor.** All Avalonia packages are aligned on one version. `Avalonia.Diagnostics` was removed without a replacement (the app never attached DevTools; no `AvaloniaUI.DiagnosticsSupport`, no paid tooling). The view models keep System.Reactive semantics (`Subscribe(Action<T>)` from System.Reactive 7.0.0), and `WhenAnyValue` is source-generated by ReactiveUI.Binding. Migrating to the lean, ReactiveUI.Primitives-based `ReactiveUI.Avalonia` is a separate possible future project. GUI behavior is guarded by headless tests (`CampertronGUITests`) that use a tiny test-owned DB instead of extracting the 226 MB RIDB DB. The 8 RIDs, artifacts, release workflow and release policy are unchanged | `CampertronGUI.csproj`, `Program.cs`, `ViewModels/*.cs`, `CampertronGUITests/` (commits `bd35f88`, `7a3db44`; build-and-test.md §K) | maintainer decisions 2026-11-11 (Phase 1 investigation approval): Avalonia 12.1.6; remove Avalonia.Diagnostics; deliberately use the `.Reactive` flavor so the PR migrates Avalonia while preserving the existing ReactiveUI/System.Reactive behavior, without mixing in a System.Reactive → Primitives migration; record the Avalonia 12 platform tiers in the AI docs only |
| D24 | **Windows GUI packages exclude the SkiaSharp and HarfBuzzSharp native debug symbols by package-specific item filtering.** A target running after `ResolvePackageAssets` removes from `NativeCopyLocalItems` only items with extension `.pdb` whose `NuGetPackageId` is `SkiaSharp.NativeAssets.Win32` or `HarfBuzzSharp.NativeAssets.Win32`. Removing the items (instead of setting `CopyToPublishDirectory=false`) also keeps them out of `.deps.json`, because the publish reuses the build `.deps.json` generated from these items. Rejected: deleting files by name after publish (leaves the `.deps.json` entries; upstream reports such deletion breaking the IIS in-process host); filtering by file name alone (could remove another package's file); `ExcludeAssets="native"` and the packages' `ShouldIncludeNative*` properties (also remove the native DLLs); `CopyDebugSymbolFilesFromPackages=false` (covers only `lib/` symbols, not `runtimes/*/native`). No official opt-out exists. The target depends on SDK item and metadata names, so `release.yml` guards the result (no native PDB file or `.deps.json` entry; Skia, HarfBuzz and ANGLE DLLs present). Campertron's own managed PDBs are deliberately kept (maintainer requirement). When fixed upstream packages arrive (through Avalonia), the target matches nothing and can be removed (open question #24) | `CampertronGUI/CampertronGUI.csproj`, `.github/workflows/release.yml` "Check package contents" (build-and-test.md §L; TD-35) | maintainer approval 2026-11-11 (TD-35 Phase 1 investigation): package-specific filtering, permanent guard, Windows runtime validation before merge |

## Recommendations (not decisions; nothing below has been adopted)
- R1. Isolate the test environment: let `Load.GetConfig` accept the config and cache paths, so tests can use a temp dir. This would address TD-01.
- R2. Use the `CampertronInternalConfig.CachePath` consistently for HTML output and in `Clear.All` (TD-05).
- R3. ~~Remove the unused MailKit and MimeKit references~~ **Done in `d20e1ad`** (they caused Dependabot alerts). Still open: whether to migrate email off `System.Net.Mail.SmtpClient`, which Microsoft marks obsolete for new development [I]. That would mean re-adding MailKit at a patched version (≥ 4.16.0).
- R4. Introduce a seam (an interface or delegate) for HTTP and the clock so the filter and date rules can be unit-tested (technical-debt.md §Missing tests).
- R5. Before any GUI search work, extract the search pipeline away from `Console` and `Menu` calls (`Load.PostProcess` → `Menu.Init`) so a non-console host can reuse it.
- R6. ~~Evaluate `ReactiveUI.Avalonia` before the next Avalonia update.~~ **Done in D23 (2026-11-11):** `Avalonia.ReactiveUI` was replaced by `ReactiveUI.Avalonia.Reactive` 12.1.6 with the Avalonia 12 migration. Original text: `Avalonia.ReactiveUI` is frozen: Avalonia published no release after 11.3.8 (11.3.9 unlisted), so it stays at 11.3.3 while the other Avalonia packages are on 11.3.14 (`21c08eb`). Before the next Avalonia minor or major update, evaluate moving to the separate `ReactiveUI.Avalonia` package (12.x/14.x on nuget.org). That is a package swap plus code changes (`Program.cs` `.UseReactiveUI()`), and is unverified.
