## RIDB refresh (TD-36, decision D26)
25. ~~Should `General.yaml` be written atomically (TD-37)?~~ **Resolved for the refresh timestamp 2026-11-11** (maintainer decision: fix it on `fix/ridb-atomic-refresh`): validated temporary file + rename (`ConfigFileReplace`). Still open: should the other YAML writers (sample `General.yaml`, `Email.yaml`, `ZionConfig.yaml`) use it too, and is the Windows `MoveFileEx` replacement acceptable without a Windows test?
26. How does the failure-safe refresh behave on Windows, macOS and in Docker? Only Linux x64 (btrfs, local NVMe) was run. Not verified: Windows (GUI holding pooled connections while the console refreshes; a competing writer; `FileShare.None` lock files, which are mandatory there and advisory `flock` locks on Unix), macOS (APFS; SQLite does not use `F_FULLFSYNC` by default, so power-loss durability may be weaker [I]), Docker on other hosts and with named volumes (a Linux x64 bind-mount run passed, §N), and a full disk during the installation (SQLite should roll back with `SQLITE_FULL` [I]). The procedures are in build-and-test.md §N.
27. ~~Does a container ever reach the refresh's cache step?~~ **Answered 2026-11-11 by a real Docker run (build-and-test.md §N):** yes. Without `/home/app/.local/share/CampertronCache` the step throws `DirectoryNotFoundException` and the refresh aborts before the installation (DB unchanged); with it, the refresh succeeds but leaves `/cache` stale. The cache part was fixed by TD-05 (decision D27, build-and-test.md §O): the step now clears `CachePath` (`/cache`), and a container without `/home/app/.local/share` refreshes successfully (reconfirmed with the published `0.1.0-beta.7` amd64 image, build-and-test.md §Release history). **Still open:** where the RIDB download and `Extract` should go in a container. They use `LocalApplicationData`, which in the image is `""`, so they land in `/app` in the container layer (about 570 MB zip, then the extracted files, both removed during the refresh). Not changed by TD-05, because they are not cache.
