# Test coverage

Authority: current. This file is the only current authority for Campertron's tests: the test projects, every test class with its discovered numbers of tests and cases, the tests that skip on a platform, which tests cover each feature and what each test checks, and how the unit, GUI, release-policy, documentation-policy and platform validation differ. Other current documents name test classes only as pointers to this file; earlier counts are historical and stay in the validation records (`history/validation/`). The commands and test warnings, the validation baseline and the checks to run after a change are `build-and-test.md`'s; the test projects' packages and helper files are `repository-map.md`'s.

Roadmap step 9, Phase 4 (2026-11-17) built this file from the test tables and lists of `feature-inventory.md` and `repository-map.md` (moved here, `history/README.md` §Phase 4 migration map) and from a new discovery of the tests.

## How the counts were derived
Discovered at `6ad651d` (2026-11-17 UTC) on Linux x64 with the .NET SDK 11.0.100: a Debug build of `Campertron.sln`, then `dotnet test` of each test project with a TRX logger and an isolated `XDG_DATA_HOME`. A **test** is a test method (`[Test]`, `[TestCase]`, `[TestCaseSource]` or Avalonia's `[AvaloniaTest]`); a **case** is one executed test case, so a method with several `[TestCase]`s or `[Values]` has several. A parse of the test attributes in the source found the same test methods in the same 69 classes.
Roadmap step 10, Phase A (2026-11-18 UTC) recounted the same way on its branch (`feat/v011-2-current-configuration`): 1,033 and 239 cases in 53 and 18 classes, and 13 and 9 new test methods by the source's attributes. Roadmap step 10, Phase B (2026-11-18 UTC) recounted on its branch (`feat/v011-1-refresh-database`): 1,095 and 269 cases in 54 and 19 classes, and 45 and 24 new test methods; then, with the automatic restart of D62 on the same branch, 1,095 and 357 cases in 54 and 20 classes (43 new test methods). In §What each test checks a bare number after a class is its number of cases. The release-policy number is the number of `PASS` lines of `test-release-policy.sh`. When a change adds or removes tests, update the counts here in the same pull request. The validation records that added or changed tests are §K, §M, §N, §O, §P, §Q, §R, §T, §X, §Y, §Z, §AA, §AB, §AD to §AL, §AN to §AZ , §BB to §BD (`history/README.md` §Validation record index).
The documentation-policy number is the number of `PASS` lines of `.github/docs-policy/test-check-docs.sh`, counted at `fbffad6` (2026-11-18 UTC: the 89 of `6df374c` and the nine tests of the `ci.yml` steps added with PR #91), under GNU awk and under mawk; where `unshare -rn` is not available, as on the CI runner, its network-namespace test prints `SKIP` instead and 97 pass.

## Platforms: what runs where and what skips
- **Linux** (`ci.yml`'s Ubuntu job and `release.yml`'s `verify` job): every test of both projects; 20 cases skip, all Windows-only: the 18 cases of `ConfigFileReplaceWindowsTests`, `ConfigFileReplaceTests.OnWindows_AReparsePoint_IsRefused` and `ConfigEditEmailTests.TheAccessRulesOnWindows_AreNeverBroadened`.
- **Windows** (`ci.yml`'s job `Windows settings files (CM1 to CM3, CM5, CM6)` on `windows-2025`): only the settings-file suites of `CampertronUnitTests`, 15 classes: `YamlDocumentTests`, `YamlDocumentPreservationTests`, `YamlDocumentRefusalTests`, `ConfigFileReplaceTests`, `ConfigFileReplaceWindowsTests`, `GeneralYamlTimestampTests`, `SettingsBootstrapTests`, `ConfigFilesTests`, `SettingsLoaderLimitsTests`, `ConfigValidationTests`, `EmailOutputValidationTests`, `ConfigEditSessionTests`, `ConfigEditEmailTests`, `SearchFileSessionTests`, `SearchFilesTests`. The Windows-only tests run there, the job fails unless `ConfigFileReplaceWindowsTests` and `ConfigEditEmailTests.TheAccessRulesOnWindows_AreNeverBroadened` passed, and its summary lists each skipped test with its reason (`build-and-test.md` §Continuous integration).
- **macOS:** no test suite runs (`ci.yml` has no macOS job).
- **`Assert.Ignore`:** 30 sites in 15 files skip a test when its platform or environment is missing; on Linux they skip exactly the Windows-only cases above. `CampertronGUITests` runs only on Linux: its fixture `GuiTestEnvironment` ignores every GUI test on Windows and macOS (`build-and-test.md` §Test warnings, item 8).
- **The release policy** (482 tests of `release-policy.sh`: Docker tags and, since D59, the container publication's tag rules against a stub registry, release flags, release notes, the .NET 11 guards, the workflow's structure) runs in `release.yml`'s `verify` job on Ubuntu.
- **The documentation policy** (98 tests of `.github/docs-policy/test-check-docs.sh`) tests the documentation checker `check-docs.sh`, not the application. Each test copies a small fixture repository (documents, a test project and a Git history with tags and a merged pull request) into a temporary directory and requires either a clean pass or the expected finding of one negative control; the last tests run the checker on this repository. It needs no .NET SDK, no network and no user-data folder, and it is separate from the unit, GUI and release-policy tests. Nine of its tests run the documentation-policy steps of `ci.yml` with a stub checker. Since PR #91 it runs in `ci.yml`'s required Ubuntu job, before the build, with the runner's GNU awk (mawk, the fallback, gives the same result), and locally with `bash .github/docs-policy/test-check-docs.sh` (`.github/docs-policy/README.md` §In CI).
- **Platform validation outside the suites:** the release workflow's native smoke tests start the published console and GUI on real Linux, Windows and macOS runners (`release-process.md` §Platforms and what a release run shows); they are launch checks, not test cases. Manual platform checks: `maintainer-procedures.md`.
- **Network:** no test reaches the network; `NoLiveNetwork` fails the run otherwise (`repository-map.md` §CampertronUnitTests).

## Coverage by feature
Test names refer to `CampertronUnitTests/function/RecDotOrg/data/LoadUnitTests.cs` (`LoadTests.*`) and `DataUnitTests.cs` (`DataTests.*`).

### F1. Startup / first-run bootstrap
- **Tests [V]:** `LoadTests.GetConfigTest` (not null), `DbExistsTest`, `DbExistsCheckTest` (returns true; always true by construction). Every `LoadTests` test also exercises it through the field initializer `Load.Preload(Load.GetConfig())`. `DataFolderTests` (D37) cover the desktop data folder (a fresh home without `.local/share`, an existing folder, `XDG_DATA_HOME`, the container, no full path); `ConsoleFailureTests` the empty `General.yaml`.

### F2. Interactive menu
- **Tests [V]:** `ConsoleFailureTests` (the start conditions, `UnitTest` silence); since D47 `MenuKeysTests` (what each key does, a million key presses on a small stack, no call from `ProcessInput` to `WriteMenu`); the drawing has none (it is checked on a pseudo-terminal, history/validation/x-ac_preview.1.md §Y and history/validation/ad-ax_preview.2.md §AL). `OutputType.UnitTest` makes `Menu.Init` skip everything.

### F3. Search, console output (`outputTo: Console`)
- **Tests [V]:** `ConsoleResultsTests` and `ConsoleOutputTests` cover the rendering and the status lines (D34). `LoadTests.RunConsoleSearchTest` calls `RunConsoleSearch(config, true)` with `OutputType.UnitTest`. This runs the real search path; since D45 its months are answered through `AvailabilityApi.ConsoleDownload` (before, it hit the network, TD-01). `LoadTests.PreloadTest` and `LoadTests.PostProcessTest` cover the pieces. `NotificationHistoryTests` run the search and output repeatedly against one `Camp.History` (every match each time, no marker read or written). `AvailableDatesTests` cover the availability-date calculation and `SharedMonthSearchTests` one single-night and one two-night search over a built month (TD-40). Since D35 `SearchIsolationTests` run several searches with one shared `RunningData` (in both orders and in parallel)
  and require each to get what it gets alone (TD-04), and `SearchDatesTests` cover the search dates and the requested month in ten cultures and their regeneration (TD-11, TD-46). There are **no** tests of the calendar or `GetConsecutiveDays` on its own; the eight include and exclude lists are tested since D51 (`SearchFiltersTests`, `FilterSemanticsTests`).

### F4. Search, HTML file output (`outputTo: HtmlFile`)
- **Tests:** `NotificationHistoryTests` (complete pages on repeated runs and after mode switches, history untouched), `ResultsHtmlTests` (the page), `HtmlResultsOutputTests` (one file and one launch per run, name order, each section with only its own stream's results, one email page per search), `CachePathTests` (location).

### F5. Headless email notification loop (`outputTo: Email`)
- **Tests:** `HtmlResultsOutputTests.EmailRun_…` and `CachePathTests` write the page of the first search and fail at SMTP on a closed loopback port (nothing is sent); `ResultsEmail_BodyIsTheResultsPage`. `NotificationHistoryTests` run Email cycles (first, unchanged, new, removed, reappearing, fresh history, existing marker layout, around manual runs) through the real gate and output (`Load.ReportResults`) with the send recorded. `EmailDeliveryHistoryTests` (D36) cover the order of sends and markers: markers only after a send, a first or later failure, the next check, existing history, and no `Camp.History` before the first marker. No test sends mail (the send is replaced by a recorder or a thrower, `CampsiteConfig.SendResultsEmail`).

### F6. Refresh RIDB data
- **Tests:** `RidbDatabaseTests` (validation and `Clear.ClearDatabase`), `AddressStateTests` (import of the 6 files), `PopulateTests` (equivalence with the previous EF import, culture order, model drift, failures), `EmbeddedDatabaseTests` (the shipped DB passes the validation), `AtomicRefreshTests` (the failure-safe refresh through `RefreshData`, since D61 its adapter of the refresh service); since D61 `RidbRefreshServiceTests` (the service, the download and the extraction against an in-memory RIDB server, the console's adapter) and, in the GUI, `CampgroundDataTests` (below). ## What is not covered
The console's behavior on a real terminal (the menu's keys and cursor, Ctrl+C, redirection, the container) is not covered by unit tests; it is checked with the pseudo-terminal matrix of history/validation/x-ac_preview.1.md §Y, on Linux only. On Windows the maintainer reviewed the D34 output manually before PR #49 was merged and reported that it looked good (a maintainer-reported manual visual review, not an automated or comprehensive check); macOS was not run (open question #38).

There are no tests for: `AvailabilityApi`'s other filter conditions one by one (since D51 `SearchFiltersTests` and `FilterSemanticsTests` test the eight include and exclude lists; people, dates and weekdays are checked through the search suites), `GetConsecutiveDays` on its own (since D35 `SearchDatesTests` cover `CampertronConfig.GenerateSearchDates`/`GetMonthsOut`, and `SearchIsolationTests` consecutive filtering in shared runs), `Calendar`, `Yaml`, `Read` (other than the address/state queries and the details lookups above), `Cache` beyond the cache-path tests above, the download of the real RIDB export (since D61 the download and extraction are tested against an in-memory server, `RidbRefreshServiceTests`), actually sending email or how email clients show the page, or the menu's drawing (its keys: `MenuKeysTests`, D47).
