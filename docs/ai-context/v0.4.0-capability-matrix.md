# `v0.4.0` capability matrix (Phase 0 audit)

Authority: current for what `CampertronConsole`, `CampertronGUI` and the web UI (`CampertronWeb`) let a user do at `f8a1471`, capability by capability, and for the parity gaps `v0.4.0` (D114) must close. It plans nothing by itself: the plan, the threat model, the phases and the open questions are `v0.4.0-plan.md`'s; the behavior of each feature stays the business rules' (`business-rules.md` §Section index). Its record is §DG. Since `v0.4.0`'s phase 2 (D116, §DI) the monitoring rows' code column names the library's monitoring controller and words; no capability cell changed, and the desktop GUI and the console still have no monitoring control. Since its phase 3 (D117, §DJ) the guided setup's rows name the library's orchestration (`GuidedSetupFlow`); no capability cell changed, and the desktop GUI and the console still have no guided setup.
Since its phase 4 (D118, §DK) the desktop GUI has the monitoring: §9's GUI column was re-derived from the code (`DesktopMonitoring`, the Monitoring tab), 18 of its rows now Complete and Auto-start N/A by D115; the console still has no monitoring control (phase 11).
Since its phase 5 (D119, §DL) the desktop GUI has the guided setup: §10's GUI column and §1's first-run, guided setup and readiness rows were re-derived from the code (`GuidedSetupViewModel`, the Monitoring tab's Guided setup): 16 of §10's rows Complete, the campground data Partial as in the web UI, Console suitability N/A; the console still has no guided setup (phase 12).

Legend: **[V]** verified in the code at `f8a1471` · **[I]** inference · **[A]** assumption, not executed (as in `build-and-test.md`).
Every class below is [V] unless marked: each was read in the code (the entry points, the forms, the pages, the console's flows) and its tests, not in the documentation alone.

## How to read it

The three columns are the three application types of D114: **Console** (`CampertronConsole` without `--web`: the menu of `Menu.cs`, email or ntfy mode of `MonitoringConsole`, the container's start), **GUI** (`CampertronGUI`) and **Web** (`CampertronConsole --web`, the pages of `CampertronWeb`).
Each cell starts with one class:
- **Complete:** the application has a practical workflow with its validation, persistence, failure handling and tests.
- **Partial:** a workflow exists but misses part of the capability (named in the cell).
- **Read-only:** the application shows it and cannot change it.
- **Indirect:** the application acts on it only as a side effect of another workflow (a start that refuses, a warning).
- **File-only:** the user can do it only by editing a settings or search file in a text editor (or with another application).
- **Missing:** no workflow at all.
- **N/A:** not applicable, by an approved rule (named) or because Campertron has no such setting (said).

A shared library service alone never makes a cell Complete: the application must expose it. For example, `ConfigEditSession` and the settings forms exist in `CampertronLibrary`, but the console reaches none of them, so its settings cells are File-only.

**Dimensions:** 15 categories, 236 capability rows, 3 application columns: 708 classified cells. The counts by class are in §Summary by application.
