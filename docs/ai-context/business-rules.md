# Business rules

Legend: **[V]** verified in source · **[I]** inference (usually standard .NET semantics applied to the code) · **[?]** unknown

These rules describe **current behavior**, including the quirks. Do not change them unless the task asks for it (see CLAUDE.md).

## 1. Search config (`CampertronConfig`, `CampertronLibrary/class/Base/Config.cs`)
YAML keys are camelCase (`Yaml.CampertronConfigConvertFromYaml` uses `CamelCaseNamingConvention`) [V].

| Key | Type | Rule [V] |
|---|---|---|
| `displayName` | string | Shown in the header (`Cache.WriteProgress`). Output is sorted by it (`PostProcess` `OrderBy(p => p.Name)`) |
| `autoRun` | bool | Only `true` configs are loaded (`Yaml.CampertronConfigGetConfigs`) |
| `campgroundID` | string | RIDB `FacilityID`. If null, the search for that config is skipped (`GetAvailabilitiesByCampground`) |
| `totalHumans` | int? | Must satisfy `min_num_people ≤ totalHumans ≤ max_num_people`. [I] Lifted comparisons return false if any side is null, so null excludes everything |
| `searchBy` | `SearchTypes` | `DaysOut`, `MonthsOut`, `SpecificDates`, `Until`, `StartEndDate` |
| `searchValue` | int | Used by `DaysOut` and `MonthsOut` |
| `searchValueDates` | string list | Used by `SpecificDates`, `Until`, `StartEndDate` |
| `showMonday`…`showSunday` | bool | Day-of-week filter (`CampertronConfig.ShowThisDay`, matched on English `DayOfWeek.ToString()`) |
| `filterMatching` | `FilterMatchMode?` (`Exact`, `Contains`) | Since D51: how the eight lists below match (§3). Missing (every file written before D51): `Contains`, the matching before D51. A new search (the start's example and the GUI's New search) is written with `Exact`. Written as anything but `Exact` or `Contains` (in any case, plain or quoted) or more than once: an Error refused at start (§15, `FilterMatchingInvalid`). `CampertronConfig.EffectiveFilterMatching` is the value the search uses; the serializer leaves a null `filterMatching` out |
| `includeEquipment`/`excludeEquipment` | string list | §3 (permitted equipment names) |
| `includeSites`/`excludeSites` | string list | §3 (`CampsiteName`, exact in both modes) |
| `includeAttributes`/`excludeAttributes` | string list | §3 (`"AttributeName:AttributeValue"` strings) |
| `includeCampsiteType`/`excludeCampsiteType` | string list | §3 (`CampsiteType`) |
| `consecutiveDays` | int | `1` = single nights. `>1` = runs of N consecutive nights per campsite. See §4 for other values |

## 2. Search date generation (`CampertronConfig.GenerateSearchDates`, `GetMonthsOut`)
| SearchBy | Dates produced [V] |
|---|---|
| `DaysOut` | today … today+`searchValue` days, inclusive |
| `MonthsOut` | every day from today … today+`searchValue` months, inclusive |
| `StartEndDate` | `searchValueDates[0]` … `[1]`, inclusive. If start == end: throws `ArgumentException("search "{displayName}": Start date and End date cannot be the same.")` (since D37, TD-45 resolved), so the search file is reported like any other unusable one (§12): "Error: {file} could not be used: search "{displayName}": Start date and End date cannot be the same.", the file and what to do, no key wait, exit code 1, on a terminal and in a log alike. Equal dates stay an error (treating them as one night would be a product change). Before D37 it wrote the error, waited for a key and called `Environment.Exit(0)`; with redirected input the key wait threw and a second error followed (exit 1). [I] Fewer than 2 entries → `ArgumentOutOfRangeException` from the list indexer |
| `SpecificDates` | Each parseable entry (`Convert.ToDateTime`; failures write "Warning: search "{displayName}": "{x}" in searchValueDates is not a date and is ignored."; before D34 "Error converting {x} to DateTime"). An empty list or zero parseable entries → today only. These dates are **not** normalized with `ConvertToZeroHour` |
| `Until` | today … `searchValueDates[0]`. If that date is ≤ now → today only. [I] Empty list → `ArgumentOutOfRangeException` |
| other | `default:` branch switches to `SpecificDates`. [I] Unreachable for valid enum values |

- [V] Since D35 (TD-11) every date the search builds itself is built from numbers, independent of the culture and its calendar: `ConvertToZeroHour` returns `new DateTime(year, month, day)` (midnight, `DateTimeKind.Unspecified`: the same values the former parse of `"{M}/{d}/{yyyy} 0:00:00 AM"` gave in en-US), the requested month is `AvailabilityApi.MonthStart` (the first of the month) and its URL is written with the invariant culture (`AvailabilityApi.MonthUrl`). Before, both were parsed from text with the current culture: under en-GB, en-AU, de-DE, fr-FR and es-MX every `DaysOut`, `MonthsOut`, `Until` and `StartEndDate` search failed with `FormatException`, the month became January, and fa-IR wrote the month of its Persian calendar into the URL.
- [V] **User-written `searchValueDates` are still parsed with `Convert.ToDateTime` and the current culture, including its calendar** (unchanged contract). Measured 2026-11-14: `2026-11-20` is read as 20 November 2026 in en-US, en-GB, en-AU, de-DE, fr-FR, es-MX, ja-JP and the invariant culture, but as a date of the Thai Buddhist calendar in th-TH and of the Persian calendar in fa-IR; `11/20/2026` fails in en-GB, en-AU, de-DE, fr-FR and es-MX, and `11/5/2026` is 11 May there. So `yyyy-MM-dd` is the spelling to recommend (examples/0.1/README.md).
- [V] The search dates are generated when `Load.Preload` loads the searches (a menu Search does that every time). **The Email loop regenerates them before every check after the first** (since D35, TD-46: `Load.RegenerateSearchDates` → `CampertronConfig.RegenerateSearchData` with the current time), so its `DaysOut`, `MonthsOut` and `Until` windows (and the "today only" fallbacks) roll forward while it runs; written dates keep their meaning. The search files are still read once per start, and a search's warnings (12-month cap, invalid dates) are written only when it is loaded. Before D35 the dates stayed those of the start, so a `DaysOut 30` window was empty after 30 days of uptime.
- [V] `GetMonthsOut` returns the number of months from now to the last search date and caps it at 12, writing "Warning: search "{displayName}": results are limited to 12 months out." (before D34 "Results limited to 12 months out").
- [V] Months are queried for `i = 0..GetMonthsToCheck()`, and a month is skipped unless it contains a search date (`HasDatesDuringThisMonth`).

## 3. Availability filtering (`AvailabilityApi.ProcessMonth` + `FilterData`)
Availability parsing:
- [V] `CampsitesDataEntry.CalculateAvailableDates` (until the TD-40 fix the search used `GenerateDates`, which still exists with the same math): a day counts as available only if the status string is exactly `"Available"`.
- [V] A month's availability (`AvailabilityEntries`) is downloaded once per run and cached in `RunData.SiteData` by its URL (campground + month); every search of that campground and month gets **the same objects**. They are read-only after they are cached: each search derives its own dates into a new list (`AvailabilityApi.AvailableDatesBySite`, in the cached campsite order, entries with the same `campsite_id` kept as separate rows) and nothing writes back into the cached month (TD-40, fixed). Before the fix every search rewrote `CampsitesDataEntry.AvailabilityDates` on the shared objects, which could throw or silently drop results in parallel runs.
- [V] Day offsets assume the API's `availabilities` list covers the **last N days of the month**: `counter = DaysInMonth - availabilities.Count`.

Per day of the month, the campsites available that day are joined with the cached campsite list on `campsite_id == CampsiteID`. Then these rules apply, **in order** [V]:

**The eight include and exclude lists** (`SearchFilters`, decision D51, 2026-11-16; an intentional correction of the search rules). [V]
- **OR semantics for every list.** An include list keeps a campsite when **any** of its values matches **any** of the campsite's values; an exclude list drops a campsite when **any** of its values matches. A missing (null) or empty list is no filter. Duplicates and the order of the values change nothing. An include value that nothing has hides every campsite of that list's kind (as before); an exclude value that nothing has removes nothing.
- **Before D51** (every release through `v0.1.0-preview.1`): `excludeEquipment` and `excludeAttributes` dropped a campsite only when **every** value matched (`Any(s1 => !equipment.Any(s1.Contains))`), and `includeCampsiteType` kept one only when its type matched **every** value (`All(y => type.Contains(y))`), so two types never matched together; the other five lists were already OR. Open questions #5 and #6 asked whether that was intended; the maintainer answered no (D51). A file that listed several values in one of those three lists finds different campsites since D51: more for `includeCampsiteType`, fewer for the two exclude lists.
- **The values are matched by the search's `filterMatching`** (§1), always ordinally: case, spaces and punctuation count, nothing is trimmed or normalized.
  - **`Exact`:** the value equals the campsite's equipment name, campsite name, `"Name:Value"` attribute or campsite type, character for character.
  - **`Contains`** (also a file without `filterMatching`): the matching before D51, in its direction per list. An equipment or attribute value **contains** the campsite's equipment name or `"Name:Value"` (the list value is the longer one: `RV/MOTORHOME` matches a campsite that permits `RV`, `Shade:Yes` matches one whose `Shade` value is blank, `"Shade:"`); a campsite type **contains** the value (`GROUP` matches `GROUP STANDARD NONELECTRIC`); a campsite name **equals** the value, as it always did. Campsite names stay exact because a `Contains` reading of names would change what every existing file finds (`1` would match `10` to `19`), and existing files are read with `Contains`.
  - A null value on either side matches nothing (the search no longer throws on one; the validation still refuses an empty item of the six lists other than the campsite names, §15). The campground data has no null names, types, equipment or attribute names or values (shipped data, 2026-11-16).

1. **excludeCampsiteType** and **includeCampsiteType** (if either is non-empty): `SearchFilters.KeepsCampsiteType`, the campsite's `CampsiteType` against both lists as above.
2. `FilterData`. Every condition must hold:
   - `totalHumans` within `[Minppl, Maxppl]`.
   - `CampsiteAvailableDate >= DateTime.Now`. Availability dates are local midnight, so **today is never matched** (except exactly at midnight) [I from the values].
   - The date is in `GetSearchDates()` (exact `DateTime` equality).
   - `ShowThisDay(date.DayOfWeek)`.
   - **The equipment, campsite-name and attribute lists** (`SearchFilters.KeepsCampsite`), as above: `includeEquipment`/`excludeEquipment` against the campsite's permitted equipment names (a campsite with no permitted equipment fails a non-empty include and is never excluded), `includeSites`/`excludeSites` against its `CampsiteName`, `includeAttributes`/`excludeAttributes` against its `AttValuePairStr` (`"Name:Value"`, built by `Cache.ConvertAttributeValuePairToString`; a null value gives `"Name:"`).
   - Duplicate check, **`outputTo: Email` only**: `Directory.Exists(ConfigPath/Camp.History/{yyyy}/{M}/{d}/{CampsiteID})` must be false (§5). Console, HtmlFile and UnitTest skip this check.
3. Matches are added to the search's own hits (`AvailableData`, a per-search `ConcurrentBag` since D35). After the search, and after its consecutive filter (§4), its final hits are added to `RunData.FilteredAvailableData`, the run's set that the Email gate and the markers use (§5, §6); no search reads or replaces another search's hits (TD-04, fixed). Check-in and check-out are taken from the attributes `"Checkin Time"` and `"Checkout Time"`.

## 4. Consecutive days
- [V] `consecutiveDays == 1`: hits are written immediately, with a month header and a calendar (`Calendar.GenerateCalendar`, only when `OutputTo == Console`) or "No entries found on {M}/{yyyy}".
- [V] `consecutiveDays > 1`: `FilterConsecutiveDays` groups **this search's own hits** (since D35; before, `RunData.FilteredAvailableData`, the hits of every search of the run so far: TD-04, which gave false two-night openings, other campgrounds' campsites, removed hits and a missed Email notification) by `CampsiteID`, keeps groups with at least N entries, and uses `EnumerableExtensions.GetConsecutiveDays(N)` (`Calendar.cs`) to keep only dates that belong to runs of N or more consecutive days. Each campsite is printed once, followed by its dates and a calendar (Console only).
- [V] `GetConsecutiveDays` throws `ArgumentNullException` for null input and `ArgumentException("can't compare against less than 2")` for limits below 2. It is only called when the limit is above 1.
- [V] `consecutiveDays <= 0`: neither the `== 1` output branch nor the `> 1` filter runs. Hits go into `FilteredAvailableData` (so with `outputTo: Email` they can trigger email and, since D36 only after every email of the check was sent, create markers), but nothing is written to the output list.

## 5. Duplicate-notification suppression (`AvailabilityApi.FilterData`, `Load.ReportResults`, `Load.OutputResults`, `Load.RecordNotificationHistory`)
`Camp.History` is the notification history of the Email loop, the only periodic mode (`outputTo: Email`; feature-inventory F5). One policy decides both sides: `Load.UsesNotificationHistory` (`internal`), true only when `GeneralConfig.OutputTo == Email` (a missing config or `GeneralConfig` is not Email). Since branch `fix/manual-search-notification-history` (2026-11-14):
- [V] Markers are **directories** at `ConfigPath/Camp.History/{yyyy}/{M}/{d}/{CampsiteID}`, with `/` hard-coded as the separator and no zero padding. The format is unchanged, so existing markers stay valid (`NotificationHistoryTests.EmailReadsAndWritesTheExistingMarkerLayout`).
- [V] **Email** (`FilterData`) drops any hit whose marker exists, and the Email loop writes the markers of what it reported, only after delivery (next bullet). A campsite and date is therefore reported once; later cycles and later processes suppress it (the markers are on disk, so this survives restarts). The scope is global: date + campsite ID, shared by every search, every search file and every output type.
- [V] **Markers only after delivery** (since D36, branch `fix/email-history-after-delivery`; TD-14 resolved). The invariant: an opening is recorded in `Camp.History` only after its notification email was delivered, which means that the send (`CampsiteConfig.SendResultsEmail`, `SmtpClient.Send`) returned: the SMTP server accepted the message; Campertron cannot know whether it reached the inbox. The Email gate (§6) only reads the history (`Load.HasUnreportedEntries`). `Load.OutputResults` sends one email per search; right after a search's email was sent it records the openings that email shows (the date and campsite of its `Availability` and `ConsecutiveDate` values; `Load.RecordNotificationHistory`). After every email of the check was sent, `Load.ReportResults` records the rest of the run's final hits (`RunData.FilteredAvailableData`: hits no email shows, such as those of a search with `consecutiveDays` below 1, §4), so a fully successful check writes exactly the markers it wrote before D36. A search with nothing new still gets its email (one per search, TD-06) and records nothing.
- [V] **Partial success:** when an email fails, the emails sent before it keep their markers (nothing is rolled back); the failed email's openings, those of the emails after it (not attempted) and the run's remaining hits stay unrecorded, so they are reported again by the next check, which, because the failure still ends the process (exit 1, "Error: the email could not be sent: …", §12; no retry), is the next start. [V from the code] An opening shown by a delivered email is recorded even if another search's email that also shows it failed: the scope is global and it was reported.
- [V] **Console, HtmlFile and UnitTest** (manual menu Search; tests) neither read nor write `Camp.History`: every run shows every current match, whatever ran before (an earlier Email, HtmlFile or UnitTest run, or markers already on disk), and leaves the markers exactly as they were. Since D36 (TD-43 resolved) they also create no `Camp.History` directory.
- [V] **Interactive searches** (GS1, D45, §19) are manual searches too: they never read or write `Camp.History` and create no directory, whatever `General.yaml`'s output type is (they do not read it); markers on disk hide nothing from them, and they leave the Email loop's history exactly as it was. Since GS2 (D46, §20) the GUI's Results tab runs them: a marked opening is shown there like any other (checked by `ResultsViewTests.EmailSettingsAndCampHistory_AreNeitherUsedNorChanged`).
- [V] **The `Camp.History` directory appears with its first marker** (since D36): only a marker write creates it (`Directory.CreateDirectory` of the marker path), so it exists once Email has delivered an email that showed an opening (or completed a check whose remaining hits it records). Reading the history (`HasUnreportedEntries`, `FilterData`) creates nothing; a missing directory means nothing was reported yet. `Load.HasNewEntries` (public; the Email loop no longer calls it) keeps its contract: it returns whether a hit has no marker and, for Email only, writes the missing markers. Before D36 it created the empty root directory for every output type (a manual Console or HtmlFile search left one; TD-43).
- [V] Availability that disappears is not reported (it is not in the month); its marker stays. If it reappears, Email keeps suppressing it: once reported, a campsite and date is never reported again (current rule, unchanged).
- [V] Before D36 (through `master` `fcff731`): `PostProcess` called `HasNewEntries` first, which wrote every marker of the check before the first email was attempted, so a failed or partly failed check (for example the default first setup with the sample `Email.yaml`, TD-51) permanently hid every opening it found (TD-14).
- [V] Markers are never deleted by any code. Deleting the `Camp.History` directory resets the Email notification history; Campertron never does that itself.
- [V] Before this fix (from `15ffc1d`, 2024-01-21, through `v0.1.0-beta.9`): `HasNewEntries` wrote markers unless `OutputTo == Console` (since `87874a8`, 2024-09-14; before that for every type), and `FilterData` dropped marked hits for **every** output type. So a manual HtmlFile Search (or a UnitTest or Email run) hid those campsites and dates from every later manual Console and HtmlFile Search, which then reported "No entries found" / "No new matching availability to display." Markers written that way are left in place; they now affect only Email. Before `15ffc1d` (the 2023 JSON history), history applied to Email only.

## 6. Output and email gating (`Load.PostProcess` → `Load.ReportResults`, `CampsiteConfig.ProcessConsoleConfig`)
- [V] Output runs if `OutputTo != Email`, or if (`Email` and a hit of the run has no marker and `FilteredAvailableData.Count() > 0`). The gate is `Load.ReportResults` (called by `PostProcess`; separate since D36 so that tests run the gate and the sends without the loop's sleep); it reads the history with `Load.HasUnreportedEntries`, which writes nothing. For Email the markers follow the sends (§5).
- [V] `Load.OutputResults` takes the searches ordered by name (`OrderBy(Name)`, as before). **`HtmlFile`** (since beta.9, D29): one page for the whole run, written once and opened once (`CampsiteConfig.WriteAndOpenHtmlResults`). **`Email`, `Console`, `UnitTest`:** `ProcessConsoleConfig` once per search; for `Email` each call writes that search's page and sends one email with it as body and attachment (`CreateResultsEmail`). Each write deletes the old `*.html` directly in `CachePath` and writes a new `{guid}.html` there (`CampsiteConfig.WriteHtmlResults`). `CachePath` is `CampertronInternalConfig.CachePath` (`/cache` in a container; before the TD-05 fix always `LocalApplicationData/CampertronCache`). An unset `CachePath` throws `InvalidOperationException` before anything is written or opened; a missing cache directory is created, as before. Console and UnitTest output write no file.
- [V] **The HTML results page** (`ResultsHtml.Render`, D29) is built only from the values' presentation metadata (architecture.md §Search pipeline), so it shows the results the console would show for the same output streams, in the same order:
  - One HTML5 document: `lang="en"`, UTF-8, viewport, `color-scheme`, title "Campertron results", inline CSS, no script, no external reference. A header with the title and the number of searches ("2 searches") and, for several searches, a navigation list; no generation time, so the same streams always give the same page; one `section` with an `h2` per search (its display name, else the item name, else "Search N"), the campground, park and campground ID.
  - Single nights: an `h3` per month header and, within it, an `h4` per run of consecutive results with the same date (`<time datetime="yyyy-MM-dd">`, shown as "{weekday}, {short date}" in the current culture), each with a list of site cards: site, loop and type, equipment, booking link `https://www.recreation.gov/camping/campsites/{CampsiteID}` ("Book {site} on recreation.gov"). A bare site name is shown as "Site {name}".
  - Consecutive days (`consecutiveDays > 1`): one card per campsite in stream order, with an `h3`, the site details, its dates and the booking link. The dates of a card are sorted by date: `FilterConsecutiveDays` writes them in `ConcurrentBag` order, which is not chronological (since D35 it is the same in every run of a search, because the bag holds only that search's hits). A date entry without its site part (possible with TD-04 before D35) still gets a card from the date's own metadata.
  - Counts are computed from the results shown: "N availability entries for M sites on K dates" (an entry is one site on one date). Check-in/out are shown once for the search when every result has the same values, otherwise per site.
  - Empty states read "No new matching availability to display.": under each month that has "No entries found", and once per search that shows no result and no such month (for example consecutive days, or no search date in range). The page does not say why (no availability or filters; for Email also `Camp.History` markers from earlier cycles, §5).
  - Every dynamic value is HTML-encoded (`WebUtility.HtmlEncode`); the campsite ID in links is URL-escaped first. Untyped values (`Kind == Text`): consecutive `Write` values are joined up to the next line end and shown as one encoded paragraph (`p.note`, muted and smaller than the results) when nonblank; blank or whitespace-only lines are dropped. Untyped text is never parsed for structure and never interpreted as markup. The console decorations (emoji, `***`, "Searching for entries", "No entries found", `Date:`/`URL:` labels) are not used. The console calendar is not part of the page.
  - Email: each email's body is the page of that one search only: a complete document with one `section`, no navigation list (it would link to searches that are not in the email), the header reading "1 search". The attachment is the file `WriteHtmlResults` wrote from the same string, so its bytes are the body as UTF-8 without a byte order mark (`HtmlResultsOutputTests`).
  - **Search attribution:** `ResultsHtml` renders the output streams it is given, one section per stream; it never rebuilds results from the shared `FilteredAvailableData` and does not move a value from one stream to another, so the combined page creates no new cross-search attribution. It cannot correct a stream that is wrong when it arrives. Until D35, TD-04 (consecutive-day filtering on state shared across parallel searches) could drop, add or misattribute results upstream; since D35 (TD-04 fixed) each stream holds only its own search's results, the same as when the search runs alone. Dropping blank untyped lines removed TD-04's blank-line symptom from the page; it did not fix TD-04, D35 did.
- [V] Email settings (the send is `CampsiteConfig.SendResultsEmail`, an internal replaceable step since D36: `SendWithSmtp` in production, a recorder in tests; the client code is unchanged): `SmtpClient` with `EnableSsl = true`, `DeliveryMethod = Network`, `UseDefaultCredentials = false`, `NetworkCredential(SmtpUsername, SmtpPassword)`, subject `"Campertron Auto-Email"`, `IsBodyHtml = true`, HTML file attached as `application/octet-stream`.
- [V] Console (since D34, §12): the results are rendered by `ConsoleResults` from the values' metadata, for the whole run at once (`CampsiteConfig.WriteConsoleResults`), not by writing the values' text. Before D34 `ProcessConsoleConfig` wrote each value as its `ConfigType` said (consecutive `WriteEmptyLine` items collapsed to one blank line; no producer creates `WriteEmptyLine`).

## 7. Retry, back-off and termination (`AvailabilityApi.GetWebApiData`, `Data.DynamicDeserialize`)
| Condition | Behavior [V] |
|---|---|
| Any exception during fetch or parse | `catch` writes "Warning: the request to recreation.gov for {campground, month} failed (attempt N: {reason}); retrying in 30 seconds." (since D34; silent before), then `Thread.Sleep(30000)` and retries **without limit** |
| Response body contains `REQUEST BLOCKED` (case-insensitive) | writes "Error: Blocked by API for exceeding request limit, try again later ({campground, month}). Campertron waits 5 minutes and then exits." (the first sentence is the text before D34), then waits 5 minutes and ends the process with exit code 1 (since D37, TD-44 resolved: before, `Environment.Exit(0)`, so a supervisor that restarts only on failure stopped polling). The wait (`AvailabilityApi.BlockedWaitTime`, 300,000 ms) and the exit go through internal seams whose defaults are `Thread.Sleep` and `Environment.Exit`; the cursor and color are restored by the exit handlers as before |
| Body contains "We are currently experiencing heavy traffic on our site" | writes "Warning: Heavy traffic at recreation.gov ({campground, month}); retrying in 1 second." (written by `GetWebApiData` since D34; before, "Heavy traffic...retrying in 1 second" by `Data.DynamicDeserialize`), then `Thread.Sleep(1000)` and a **recursive** re-fetch, without limit |
| Another thread is already fetching the same URL | polls `RunData.SiteData` every 500 ms **without limit** (`ProcessMonth`) |
| Email mode, between cycles | `Thread.Sleep(60000)` |
| HTTP status code | never checked. The body is read whatever the status [V] |

- [V] D34 changed only what is written (and that the "Get: {url}" line per request is gone): the conditions, waits, retries and exits above are unchanged. `AvailabilityApi.DescribeRequest` turns the URL into "{campground name or "campground {id}"}, {month year}".
- [I] If a JSON response has no top-level property other than `count`, `ReceivedData` never becomes true and the `while (ReceivedData == false)` loop in `GetWebApiData` spins forever.
- [V] **This table is the console's.** An interactive search (GS1, D45) has its own bounds: at most three requests per month in all, a 30 s request timeout, cancellable waits, HTTP 429 and the block page as a block without a wait or an exit, the answers above classified and bounded (§19). Since D45 the console's download is the internal `AvailabilityApi.ConsoleDownload` (production: the code before it, a new `HttpClient` per request); nothing in the table changed.

- [V] **Failure-safe refresh** (`RefreshRidbRecreationData.RefreshData` → `RidbStagedRefresh`, decision D26; TD-36 part 1, branch `fix/ridb-atomic-refresh`, 2026-11-11). The installed `RecreationDotOrg.db` stays usable and unchanged unless a complete new DB has been built, populated, validated, finalized and installed. Steps:
  1. **Refresh lock.** `ConfigPath/RecreationDotOrg.refresh.lock`, opened with `FileShare.None` and never deleted (no `DeleteOnClose`). If another process or refresh holds it, `RefreshData` prints "Another RIDB refresh is running (…). Nothing was changed." and returns `false` before downloading anything.
  2. **Stale staging cleanup** (under the lock, at refresh start only, never at startup): removes directories in `ConfigPath` named exactly `RecreationDotOrg.refresh-` + 32 lowercase hex digits (`Guid.ToString("N")`). Look-alikes (other GUID formats, upper case, suffixes, `RecreationDotOrg.repair-*`, files) are never touched; a link with a staging name is removed as a link, not followed. A directory that can't be removed is reported and left: each refresh uses a new path that must not exist yet, so a leftover can't be reused.
  3. Download and extraction, unchanged (`Web.Download`, `Compression.Unzip`). Both use `LocalApplicationData` directly. Since D37 (TD-48 resolved) the export is extracted into `LocalApplicationData/CampertronExtract` (`Compression.ExtractFolderName`), a folder of Campertron's own next to `CampertronConfig` and `CampertronCache`, which `Compression.Unzip` first deletes recursively if it exists (a link with that name is removed, not followed) and `Populate` deletes recursively afterwards. Nothing else in `LocalApplicationData` is cleared; before D37 the folder was the generic `LocalApplicationData/Extract`, which could be another program's. In a container `LocalApplicationData` is `""` unless `/home/app/.local/share` exists, so the folder is `CampertronExtract` relative to `/app` (open question #27, unchanged).
  4. **Staging DB** `ConfigPath/RecreationDotOrg.refresh-<guid N>/RecreationDotOrg.db` (same directory, so the same filesystem, also in Docker `/config`). Template: an online backup (`SqliteConnection.BackupDatabase`, dedicated non-pooled connections) of the installed DB, which is only read; if no DB is installed, the bundled DB (`Load.ExtractEmbeddedDbTo`). An installed DB that can't be opened or copied (corrupt, unreadable) makes the refresh throw; it is not modified, and there is no new repair fallback.
  5. `Clear.ClearDatabase`, `PopulateDbFromRIDBFiles.Populate` (parsing, normalization, `RidbTableInserter`), since D51 `RidbIndexes.Create` ("Indexing the campsite attributes") and `RidbDatabase.Validate`, against the staging directory. The EF contexts' idle pooled staging connections are released with a targeted `SqliteConnection.ClearPool` after each step (`Validate` still calls `ClearAllPools`, as before). Then `PRAGMA wal_checkpoint(TRUNCATE)` finalizes the staging file.
  6. **Cache invalidation, before the installation:** every file directly in the configured `CachePath` is deleted (`Clear.ClearRefreshCache(InternalConfig.CachePath)`; TD-05 fixed, decision D27): `LocalApplicationData/CampertronCache` on the desktop (the same directory as before) and `/cache` in a container (before the fix, a container cleared `LocalApplicationData/CampertronCache` instead, so a refresh aborted there or left stale derived files in `/cache`; build-and-test.md §N). Subdirectories, the directory itself and anything outside it are kept; a link is unlinked, never followed. If deleting fails (a missing directory, a permission error), the refresh throws before the installation; there is no fallback directory. A crash after this step leaves the old DB with an empty cache, which is rebuilt on demand, and no path leaves the new DB with cache files derived from the old one, on the desktop and in a container (kill harness, §N; Docker kills, §O). **Guards** (nothing deleted, `InvalidOperationException`): `RefreshData` checks `CachePath` right after `ConfigPath`, before the refresh lock and the download (`Clear.CheckCacheDirectory`: unset or whitespace, a filesystem root, or the same directory as `ConfigPath` after full-path normalization); `ClearRefreshCache` re-checks the path and refuses a directory that contains `RecreationDotOrg.db` or `General.yaml`, which catches a config directory reached through a link or the same bind mount.
  7. **Installation** under `ConfigPath/RecreationDotOrg.repair.lock` (the startup repair's lock, opened with `FileShare.None`; if held, the refresh throws `IOException` and nothing is installed): `BackupDatabase` from the staging DB into the installed DB on dedicated non-pooled connections, with `PRAGMA busy_timeout` = `RidbStagedRefresh.InstallBusyTimeoutMilliseconds` (30,000 ms) on the destination. This is one SQLite write transaction: it commits completely or leaves the installed DB as it was, also after a crash. If no DB was installed, the bundled DB is first extracted to the installed path (the same write-then-move as on a first start, so the path never holds an empty or partial file) and removed again, with any `-wal`/`-shm`/`-journal` files, if the backup into it fails. The installed DB is never renamed, replaced or deleted otherwise.
  8. Best-effort `PRAGMA wal_checkpoint(TRUNCATE)`. A reader that still uses the previous snapshot keeps it from completing ("Another connection is still reading the previous data; …"); that is not a failure, and SQLite completes it later. WAL and SHM files are never touched by hand.
  9. `PRAGMA quick_check` on a new connection. If it is not `ok`, `RefreshData` reports it, keeps the staging DB for inspection, does not update `General.yaml` and returns `false`; there is no automatic rollback.
  10. The staging directory is removed (best effort, after its connections are closed), the lock released.
  11. **`LastRidbDataRefresh`** is set and `General.yaml` written **once**, only now, with `Yaml.GeneralConfigReplaceYaml` (TD-37 fix; since D40, CM2, only the timestamp changes, §14): the file is read as it is now (strict UTF-8), loaded with the loaders' deserializer, and the CM1 editor (`YamlDocument`, §13) changes or adds only `lastRidbDataRefresh`, so comments, blank lines, order, indentation, quoting, line breaks and a byte-order mark stay byte for byte, and other values of the in-memory `GeneralConfig` are never written; a file that already holds the timestamp is not written. `ConfigFileReplace.Replace` then writes the result through a verified same-directory temporary file, keeps the previous bytes in `General.yaml.bak` and renames the new file over `General.yaml` unless `General.yaml` changed meanwhile (§14); `General.yaml` is never truncated or deleted first. Before D40 the complete document was re-serialized from the in-memory settings, which dropped every comment and blank line. On any failure the old `General.yaml` stays as it was and the temporary files are removed on a best-effort basis (a cleanup failure is reported without hiding the original exception). If the write fails (I/O, permission, encoding, an external change, a file the editor refuses or the loader rejects), the refresh still returns `true` with the warning "The RIDB database refresh succeeded, but General.yaml could not be updated (…). The next start may refresh again.", whose reason names the file and the problem, never a value of it; the installed DB is kept. The in-memory `GeneralConfig` (shared with View Config) gets the new timestamp either way, because the installed data is new. Temporary files left by a killed process are never read (the loaders read `General.yaml` and `*.yaml`); those older than 10 minutes are removed at the start of the next refresh (reported) and before every write (quietly), exact names only (§14). On Unix, a `General.yaml` without write permission (0400, 0444) is still replaced, keeping its mode (the rename needs write permission on the directory, as before D40); on Windows a read-only file is refused (§14).

  **Lock order:** the refresh lock first (whole refresh), the repair lock second (installation only). `LegacyAddressLayout.RepairIfNeeded` takes only the repair lock and runs in `DbExistsCheck` before the auto-refresh, after releasing it; nothing takes the refresh lock while holding the repair lock. While a refresh holds the repair lock, a startup repair in another process fails to open it, reports "Could not check or repair …" and leaves the DB unchanged (checked again on the next start).

  **Busy installation** [V]: `BackupDatabase` performs one `sqlite3_backup_step(-1)` and does not apply Microsoft.Data.Sqlite's `Default Timeout` (that applies to commands); SQLite's busy timeout on the destination connection does apply. A competing write transaction makes the installation wait up to the busy timeout and then throw `SqliteException` with `SqliteErrorCode` 5 (`SQLITE_BUSY`); the installed DB stays byte for byte unchanged. `SQLITE_LOCKED` arises only within one connection or a shared cache, which the installation does not use.

  **Failures** keep the existing behavior: exceptions propagate (as before), and only validation, a held refresh lock and a failed `quick_check` return `false`. On every failure before the installation, the installed DB, `General.yaml` and (before step 6) the cache are unchanged and the staging directory is removed. Readers in other processes keep a consistent snapshot during the installation and see the new data with their next transaction; pooled idle connections (the GUI's) need no closing.

  **Replacement guarantees** (`ConfigFileReplace`, TD-37, D40; details in §14): .NET implements `File.Move(…, overwrite: true)` with `rename(2)` on Linux and macOS (`FileSystem.Unix.cs`; the copy-and-delete fallback is only for `EXDEV`, impossible within one directory). POSIX requires that the destination name always refers to the old or the new file and is unaffected if `rename` fails (except `EIO`). `Flush(true)` is `fsync`, `F_FULLFSYNC` on macOS (`pal_io.c`). On Windows it is `MoveFileExW(MOVEFILE_COPY_ALLOWED | MOVEFILE_REPLACE_EXISTING)` without `MOVEFILE_WRITE_THROUGH`; Microsoft documents no atomicity for it. **Verified:** process termination at every tested point of the write (Linux x64, btrfs; kill harness, build-and-test.md §N for D26's writer, §AE for D40's) left the complete old or complete new `General.yaml` and a working next start. **Not guaranteed:** power loss (the directory is not fsynced after the rename, so the old file may reappear; acceptable, it is valid), macOS behavior (not run natively); Windows runs the deterministic tests natively in CI (§14), not the kill harness. Since D40 the sample writers (`General.yaml`, `Email.yaml`, `ZionConfig.yaml`) no longer truncate or write in place either (§9, §14).

## 12. Console output (decision D34; `ConsoleUi`, `ConsoleResults`, `CampertronConsole/Program.cs`)
- [V] **Streams.** Results, status lines, notices and prompts go to standard output. Warnings and errors go to standard error and start with `Warning: ` or `Error: `, so their meaning depends on neither the stream nor color. (The RIDB refresh's plain progress lines are still `Console.WriteLine` on standard output.)
- [V] **Exit codes.** 0: `--version`, menu Exit and an `outputTo: UnitTest` start. Since D37 the two former exceptions, equal start and end dates (§2, TD-45) and a blocked request (§7, TD-44), exit with 1 too. Since D41 a settings file refused by the validation at start (§15) and the Email output's start check (an incomplete `Email.yaml` with `outputTo: Email`) exit with 1 through the same path. 1: any failure `Main` reports (`ConsoleUi.ReportFailure`: a settings file that cannot be read or used, a missing container folder, an email or download failure, any other exception; before D34 an unhandled exception with 134, or 139 in a container), a non-Email output type in a container, and the menu without a terminal. Signals are unchanged: Ctrl+C 130, SIGTERM 143, SIGHUP 129.
- [V] **Failure messages** (`ConsoleUi.DescribeFailure`). A settings file: "{file} could not be read: {reason} (line N, column M)" (or "could not be used" when the failure is not a YAML error), "File: {path}", and "Fix the file, or delete it and Campertron creates a new one." for `General.yaml` and `Email.yaml` or "Fix the file, or move it out of the settings folder." for a search file. The loaders record the file on the exception with an exception filter (`ConsoleUi.NoteFile`), so the exception that travels is unchanged (the GUI's own messages are too). "Config path does not exist" / "Cache path does not exist" keep their text and add the mount advice. An email failure: "the email could not be sent: …" and "Check the server, port, user name and password in Email.yaml."; a download failure: "a download failed: …". Anything else: "Campertron stopped because of an unexpected problem: {type}: {message}" followed by the exception's details for a report.
- [V] **Secrets.** Messages come from exceptions only; no settings value is read for them. For `Email.yaml` the inner exception messages are left out, because they can quote a value of the file, and the SMTP password, when it is known, is replaced by `[hidden]` in every line. The Email loop's lines name searches and counts only, never addresses or the server.
- [V] **Capabilities** (`ConsoleUi.Detect`, once per process). Color: standard output is a terminal, `NO_COLOR` is unset or empty, and `TERM` is not `dumb` (and, except on Windows, not missing). Width: `Console.WindowWidth` on a terminal when it is 20 to 500, else 80; redirected output has no width and is never wrapped. Interactive: standard input and output are both terminals. If detection fails, the output is plain and nothing is interactive. No flag and no other environment variable is read.
- [V] **Color.** Foreground only: green (search names), cyan (dates and the calendar's open days), dark yellow (`Warning:`), red (`Error:`), dark green (the logo) and red (the menu's arrow); never blue, dark gray or dark red. It is reset after the text it colors, also when writing fails. Nothing is told by color alone: the calendar's open days carry `*`.
- [V] **Screen and cursor.** The only clear is `ConsoleUi.ClearScreen`: `ESC[H ESC[2J` (the visible screen; never `ESC c`, never the scrollback), written only to an interactive terminal that understands control sequences, and never while a notice, warning or error has not been acknowledged by a key press (`ConsoleUi.Unacknowledged`). It is used by the menu, View Config, a manual refresh and the start of a menu search. The Email loop and redirected output never get a control sequence. The cursor is hidden only on an interactive terminal and restored, with the color, on Exit, on a failure and on Ctrl+C ("Stopped." on standard error). Cursor addressing exists only in the interactive menu; there is no animation.
- [V] **Text.** ASCII punctuation around the data; no tabs, no emoji (the window title keeps its robots). Names and other data are written as stored, with UTF-8 output set by the menu and at the start of the Email loop. On a terminal, lists and status lines wrap at spaces or between items, with indented continuation lines; a link or path is never broken and nothing is truncated.
- [V] **Results** (`ConsoleResults.Render`): built from the model `ResultsHtml.Build` returns, so the console and the HTML page group the same streams the same way (§6): `== {search} ==`; the campground, park and ID; "N openings at M sites on K dates" (an opening is one site on one date), preceded by "at least N consecutive nights" and followed by check-in/out when every result shares them; "Equipment (all sites): …" when every result has the same list, otherwise per site. Single nights: "{weekday} {short date} - N sites", each site with its loop and type and its booking link on its own line, then the month's calendar. Consecutive nights: each site with its dates in date order and a calendar per month. An empty search says "No matching availability." once; an empty month within a search that has results says "{Month Year}: no matching availability.". The run ends with "Done: N searches, X openings at Y sites." and the number of searches without availability. Dates and month names follow the current culture. Untyped nonblank text is written as a plain line; the stream's own calendar values are skipped.
- [V] **Search attribution.** Like the page, the console shows each stream as supplied. Skipping the stream's calendar values hid one symptom of TD-04 (another search's calendar without a campsite); the cause, consecutive filtering on the run's shared set, is fixed since D35, so each stream holds only its own search's results.
- [V] **Before and during a search.** "Running N searches:" lists each search (by name) with its campground, dates, weekdays, "at least N consecutive nights", people and number of non-empty filters. Warnings follow for a search without `campgroundID`, with a campground ID that is not in the campground list, without `totalHumans`, with `consecutiveDays` below 1, or without search dates; the search still runs exactly as before. Each finished search writes "Checked "{name}" at {campground}: {months} ({seconds}s)".
- [V] **The Email loop** writes for logs: a start line and each check and email line carry the local time (`yyyy-MM-dd HH:mm:ss`); nothing else is timestamped. One line per check ("nothing new. Next check HH:mm:ss." or "N new openings; sending M emails."), one "Email sent: {search} ({n} openings)" per email.
- [V] **Unchanged contracts.** `--version` (§11) is handled first and is byte-identical. An `outputTo: UnitTest` start writes nothing. `Load.GetConfig` writes nothing on a clean first start unless `Load.FirstStartNotice` is set, which only the console does (the GUI's `--smoke-test` report must hold only `SMOKE` lines). "Config path does not exist" and "Unsupported output type in container" remain in their messages.
- [?] Windows and macOS (open question #38). Windows: the maintainer reviewed the D34 output manually before PR #49 was merged and reported that it looked good; that is a maintainer-reported manual visual review, not an automated or comprehensive check, and the individual cases of #38 stay unverified. macOS: not run. The release workflow's native smoke jobs have run on D34 code since Release runs #30 and #31 (build-and-test.md §AC); they cover `--version` and the silent `outputTo: UnitTest` start only, so the menu, also its loop of D47 (below), has not run on Windows or macOS in a workflow.
- [V] **The menu's keys** (decision D47, TD-12; `Menu.WriteMenu`, `Menu.ProcessInput`). The loop in `WriteMenu` draws the four options, clears the six lines below them, places the cursor and reads a key; `ProcessInput` handles it and returns to that loop. Up and Down move the selection one step (Up at Search and Down at Exit stay), Enter runs the selected option, any other key changes nothing; after each key the options are drawn again. The console calls and their order are the same as before D47, so the terminal gets the same bytes for the same keys (compared on a pseudo-terminal, build-and-test.md §AL). Before D47 `ProcessInput` called `WriteMenu` for every key, also for keys the menu does not use, so every key press went one level deeper and the console ended with a stack overflow (SIGABRT) after 17,231 key presses with an 8 MB stack and 4,202 with 1 MB. **Still nested, by design of the search loop:** each Search, Refresh and View Config starts a new menu inside the one that ran it (`Load.PostProcess` → `Menu.Init`, or `Menu.Draw`); that is one level per Enter action, bounded by what the user does, and unchanged (the rest of TD-12).

## 13. YAML document editor (decision D39; `YamlDocument`, internal; used by the `General.yaml` timestamp write since D40 and by the GUI's editing session since D43)
- [V] **Two callers.** Since D40 (CM2) `Yaml.GeneralConfigReplaceYaml` uses `Edit` to change only `lastRidbDataRefresh` after a RIDB refresh and `VerifyCandidate` on the text before writing, on the temporary file read back and on the file read back after the rename (§8 step 11, §14). Since D43 and D44 the GUI's editing session (`ConfigEditSession`, §17 and §18) uses `Analyze` and `Edit` for every edit of `General.yaml`, `Email.yaml` and the search files. Nothing else calls it: the loaders, the sample writers and the search don't. It is pure: no file, console, environment or network access (CM2's file handling is in `ConfigFileReplace`). Under D39 alone nothing called it.
- [V] **Input.** The text of one settings file as a string; offsets are UTF-16 indexes into it (the units of YamlDotNet's `Mark.Index`); lines and columns are 1-based. A leading U+FEFF counts as the file's byte-order mark: it is not parsed (`File.ReadAllText` drops it before the loader sees the text, and YamlDotNet would read it as part of the first key) and stays at the start of the result.
- [V] **Supported documents.** One YAML document whose root is a plain block mapping (no anchor, tag or flow style) of plain or quoted scalar keys, each at the start of its line; directives, `---` and `...` may be present. Values may be anything YAML allows; only those below are edited. Refused (no edit at all): malformed text, an empty or comment-only document (Campertron reports such a file as unusable, §9), more than one document, any other root, a complex key (`?`, a collection or block scalar as key), a key that appears twice in one mapping (the loader would silently take the last), a merge key `<<` (the loader rejects it), a tag that is not a standard YAML tag (`tag:yaml.org,2002:`), a lone UTF-16 surrogate, a NEL, line separator or paragraph separator character (YamlDotNet reads them as line breaks), a `#` that can't be told apart from content, a line outside the properties that holds anything but a comment, the opening directives and `---` or the closing `...`, and anything over the editor's limits (1 Mi UTF-16 units, 100,000 parser events, 32 nesting levels, 100 aliases). Malformed text includes what YamlDotNet 16.3.0's scanner rejects with an `InvalidOperationException` (an unclosed flow list followed by another line), refused since D41 instead of thrown. Since D41 the same limits bound the settings loader and the validation (§15).
- [V] **Comments.** A `#` at the start of a line or after a space or tab, outside every scalar, alias, anchor, tag and directive (the parser reports where those are), runs to the end of its line; a block scalar's header can end with one. A `#` directly after a quoted value or a flow mapping, which YamlDotNet reads as a comment although YAML requires a space before it, is refused.
- [V] **What belongs to what.** A property's own lines run from its key's line through the line of its value's last character; for a block scalar that is its last content line, not the line break and blank lines the parser's range includes. A list item owns the comment lines directly above it (after the previous item or the key's line, without a blank line between) and its end-of-line comment.
- [V] **Edits** (one per key per call, planned against the text that was passed in and applied together): `SetScalar` replaces a scalar value (an empty value is filled in after the colon) or adds a missing key; `RemoveProperty` removes the property's own lines and nothing else (a comment above the key stays); `SetSequence` replaces a list's items (a block list's lines after the key, or the inside of a flow list's brackets) or creates the list; `SetItem`, `InsertItem`, `RemoveItem` and `ReorderItems` change items of a list whose items are single-line plain or quoted scalars without anchors or tags (a block list with every `-` at the start of its line and the same indentation, nothing but comments and blank lines between the items; or a flow list on one line). A removed or reordered item takes its own comments along; comments after the last item stay where they are. Removing the only item of a block list writes ` []` after the colon (an empty list, not a missing one) and removes the list's lines.
- [V] **Locked and kept.** A property whose key or value uses an anchor, an alias or a standard tag is kept exactly and can't be edited or removed. A block scalar (literal or folded) is kept and can be removed but not rewritten; a list with any other kind of item is kept and can be removed but not edited item by item. Keys Campertron does not know (and their sections) are kept exactly and can be removed.
- [V] **Writing a value.** An edited scalar keeps its style (plain, single-quoted, double-quoted) when the new value can be written in it and reads back unchanged; a text value is never written plain as `null`, `~` or empty, which the loader reads as null. A new text value is written plain only when YAML can't read it as anything but text: nothing YAML reads as a null or a boolean (YAML 1.1's `yes`/`no`/`on`/`off`/`y`/`n` included), nothing that starts like a number, a date, an infinity or NaN (a digit, `+`, `-` or `.`), and no character that would change its meaning, otherwise single-quoted (a `'` doubled), otherwise double-quoted (`\\`, `\"`, `\n`, `\r`, `\t`, and `\uXXXX` for other non-printable characters; an astral character is written as itself). Inside a flow list, a plain value also may not hold `:` or `,[]{}`. A null is written `null`. Booleans, numbers, dates and enum values are written as Campertron's writer writes them (the same YamlDotNet serializer configuration), in the old value's quotes if it had them.
- [V] **Where new lines go.** A new property goes after the last property's last line (before any comment lines, blank lines and `...` after it), with the top-level keys' indentation, as `key: value`; several in the order of the edits. A new list is a one-line flow sequence `[a, b]` with `, `. A new block list item goes before the item at its index (before that item's comment lines) or after the last item's line, with the first item's indentation and the text between its `-` and its value; a new flow item uses the list's separator (`, ` if it had fewer than two items). New lines end with the document's most frequent line break (ties: LF, then CRLF, then CR; LF in a document without one); a document with mixed line breaks gets the `MixedLineEndings` warning. After a last line without a line break, the break goes before the new line, so the file still ends without one; removing a last line removes the break before it for the same reason.
- [V] **The check before any text is returned.** The text outside the replacements is unchanged; the result parses as a supported document; its keys are the original ones less the removed and plus the inserted, in order; every untouched property's lines are identical; edited values and items read back as written, kept and moved items with their own text and comments; the comments are the original ones less those the losses name; line breaks, the final line break and a leading U+FEFF are kept. Then `Yaml.SettingsDeserializer`, the deserializer of the three settings loaders, loads the result, which must equal the model the caller intends property by property (strings ordinal, doubles bit for bit, dates with their kind, lists item by item, null not equal to empty). Keys the loader rejects (D20) are left out of that load (the same parsed events without them) and named in an `UnknownKeys` warning: the loader still rejects the file until they are removed. A failure returns no text and the reason.
- [V] **Losses.** A removed property, item or list reports the exact range it removed from the text, its lines and the comments in it.
- [V] **Diagnostics** hold a code, a severity, the key, a position and fixed text: never a value of the document or an exception's message, so nothing of `Email.yaml` (the SMTP password) reaches one (§12, Secrets).

## 14. Writing settings files (decision D40; `ConfigFileReplace`, `Yaml.GeneralConfigReplaceYaml`, the sample writers)
- [V] **One writer, three kinds of write, nothing else.** Campertron changes an existing settings file only to set `General.yaml`'s refresh timestamp (`ConfigFileReplace.Replace`, §8 step 11), since D43 when the user saves `General.yaml` or `Email.yaml` in the GUI's Settings tab (§17, the same `Replace`) and since D44 when the user saves a search file in the GUI's Searches tab (§18, the same `Replace`); it creates only the sample files (`ConfigFileReplace.Create`: the three at a start, §9, and `General.yaml` or `Email.yaml` from the Settings tab's Create, §17) and, since D44, a search file by the Searches tab's New search or Save As (§18, the same create-only `Create`). The console, the Email loop, the start, the RIDB refresh and the validation never write a search file (§9). The loaders read with `File.ReadAllText`'s decoding, since D41 within the editor's limits (§15). A `General.yaml` that no longer exists when the refresh writes its timestamp is not recreated ("General.yaml does not exist." in the refresh's warning; the next start creates the sample): before D40 the in-memory settings were written as a new file.
- [V] **Strict UTF-8.** A file read for editing (`ConfigFileReplace.Read`) must be UTF-8: invalid bytes are refused ("General.yaml is not valid UTF-8"), never replaced with U+FFFD; a UTF-16 or UTF-32 byte-order mark and NUL bytes (UTF-16 text without a mark) are refused, never converted. A UTF-8 byte-order mark is kept: it is decoded as a leading U+FEFF, which the editor keeps without parsing it (§13), and encoded back as `EF BB BF`; a file without one gets none. The new text is encoded, decoded again and compared before anything is written, so the text that is verified is exactly the text that is written. Files over 3,145,731 bytes (the editor's 1 Mi UTF-16 units, 3 bytes each, plus a byte-order mark) are refused.
- [V] **Replacement**, in this order; every failure before the rename leaves the file exactly as it was and removes the temporary files: (1) the editor's result is checked by the caller's check (`YamlDocument.VerifyCandidate` against the bytes read and the intended settings); (2) on Windows, a read-only file and a file with an access control list of its own are refused; (3) a temporary file `<name>.<32 hex digits>.tmp` is created in the directory of the file (of the link's final target) with create-new semantics, owner-only (0600) on Unix, written and flushed to disk (`Flush(true)`: `fsync`, `F_FULLFSYNC` on macOS), then given the file's mode, which is checked (on Windows: its access rules must equal the file's, compared as SDDL, or nothing is renamed); (4) it is read back: exact bytes, and the caller's check again; (5) the file is compared with what was read (§External changes); (6) the backup is written; (7) the file is compared again; (8) the temporary file is renamed over the file (`File.Move(…, overwrite: true)`: `rename(2)`; `MoveFileExW` on Windows); (9) the file is read back through the path the caller gave: exact bytes, the caller's check and the mode (on Windows its access rules). A mismatch there (after the rename) is reported: "General.yaml was replaced, but reading it back did not give what was written; the previous content is in General.yaml.bak."
- [V] **Backup.** One rolling `<name>.bak` next to the file (next to the link's target), holding exactly the bytes that were read, the content just before the replacement. It is written like the new file (a temporary file with the source's mode, so never wider, read back) and renamed over the previous backup, never written in place or through a link. If it can't be written or checked, nothing is replaced. It is never loaded (it is not `*.yaml`). There is one backup, no history, and none for a created sample. A backup of `Email.yaml` holds its previous SMTP password (the GUI's Settings tab saves `Email.yaml` since D43, §17); like every backup it gets the source's mode, never a broader one.
- [V] **Permissions.** On Unix the new file and the backup get exactly the file's mode (0600, 0640, 0644, 0400 and 0444 tested); the temporary file is owner-only until it gets that mode, so nothing is readable by others while it is written, and a restrictive file never becomes broader. A file without write permission (0400, 0444) is still replaced, keeping its mode (as before D40). The owner and group, POSIX ACLs and extended attributes are not carried over: the new file belongs to the user that runs Campertron (a container's `app` user, or the host user when the host updates the file). The created samples get the permissions any new file gets in that directory, as before (their content holds no secret). On Windows the new file and the backup take the access rules their folder gives new files; they must equal the file's own exactly (its DACL compared as SDDL, inheritance flags included) before anything is renamed, and are checked again after the rename, so a replacement never gets different, possibly broader rules. A file with access rules of its own (explicit entries or a protected DACL) is refused before anything is written, and so is a read-only file; `Hidden`, `System`, `Archive` and `NotContentIndexed` are copied (a hidden file and its backup stay hidden). **Windows facts** [V, CI on `windows-2025`]: a new file in the runner user's LocalApplicationData has only inherited rules (`D:(A;ID;FA;;;SY)(A;ID;FA;;;BA)(A;ID;FA;;;LA)`, not protected, owner BUILTIN\Administrators), so an ordinary settings file is updated with exactly its rules; a file moved in from another folder, and a file whose folder's DACL was rewritten with `SetFileSecurityW`, end up with a protected DACL of explicit copies (`D:P(A;;FA;;;SY)(A;;FA;;;BA)(A;;FA;;;LA)`) and are refused as files with rules of their own. The owner is not carried over (on Windows the default owner of a new file, BUILTIN\Administrators for an administrator).
- [V] **Links and special files.** On Unix a chain of symbolic links is followed to its final target (at most 40 links); the temporary file and the backup go to the target's directory, the target is replaced and every link stays a link. A cycle, a dangling link, a directory (also through a link) and an empty or non-regular file (a FIFO, socket or device reports size 0 and is refused before it is opened) are refused. On Windows any reparse point (symbolic link, junction, cloud placeholder) is refused ("…is a symbolic link, junction or other reparse point, which Campertron does not update on Windows; it was left as it is."); a junction with the file's name is refused as a directory and not followed; neither is ever replaced or written through. A created sample never replaces anything: a dangling link of that name counts as an existing file. A backup name that is a link is replaced by the new backup, never written through (Linux and Windows).
- [V] **External changes** (optimistic concurrency, no lock file). The edit is planned on the bytes read at the start of the write, not on the settings loaded when Campertron started, so an edit saved before the write is kept. Before the backup and again right before the rename, the file is read again and compared with what was read: the link chain and each link's text, the final target, the SHA-256 of the bytes, the length, the last write time, the mode, the attributes and, on Windows, the access rules. Any difference stops the update: "General.yaml was changed by another program while Campertron was updating it; it was left as it is and can be updated again." (the next refresh updates it). **Residual race:** an edit saved after the last comparison and before the rename, a window of a few system calls, is lost (an in-place write goes to the replaced file; a program that saves by renaming replaces Campertron's file instead). No portable API offers a conditional rename: `File.Replace` checks nothing either, and Linux's `renameat2` is Linux-only and needs native calls.
- [V] **Creation** (the samples, §9): the text is checked to load as the settings it is, written to a temporary file (create-new, default permissions), flushed, read back and checked, then moved into place only if the name is free (`File.Move(…, overwrite: false)`: `link(2)` and `unlink(2)` on Unix, which fails if the name exists; on a file system without hard links .NET copies with create-new semantics instead, which an interruption can leave partial; `MoveFileExW` without replacement on Windows). A name that exists, also one that appears during the write, is never written over; the caller then loads the file that is there.
- [V] **Temporary files and their cleanup.** Names are `<name>.<32 lowercase hex digits>.tmp` and `<name>.bak.<32 lowercase hex digits>.tmp` (a new GUID each time); no loader picks them up (they are not `*.yaml`). A write removes its own temporary files after any failure; a removal that fails is reported without hiding the failure. Files left by a killed process are removed only if they have exactly such a name for the file being written, are regular files (never a link or a directory) in that file's directory, and were last written more than 10 minutes ago (a write takes well under a second; a younger file may belong to a write in another process, for example the GUI and the console starting together): quietly before every write, and with a message ("Removed …, left by an interrupted update of General.yaml") at the start of a RIDB refresh, as before D40. Nothing else in the folder is touched.
- [V] **Messages** name the file and the problem, never a value of the file; the editor's reasons are its codes and fixed texts (§13), and a YAML error from loading the file is reported by its position only. The refresh shows them inside its existing warning (§8 step 11).
- [V] **What is established.** On Linux x64 (btrfs) a process killed at each of 12 points of a replacement and 6 points of a creation (two passes), and at 100 random moments, left the complete old or the complete new file (a creation: no file or the complete file), never a partial or empty one; the next start loaded it, the next write completed, and old temporary files were removed (build-and-test.md §AE). **Not established:** power loss (the directory is not fsynced after the rename or link, so the old file or no file may reappear), process interruption on Windows (no kill harness ran there), macOS (not run), a file system without hard links for creation. **Windows** [V, the CI job `Windows settings files (CM1, CM2)`, build-and-test.md §AE]: the deterministic suites pass natively: replacement and creation through `MoveFileExW`, read-backs, backup, CRLF and BOM, strict decoding, external changes (content, deletion, recreation, access rules), injected failures at every step (the file intact, only the operation's own temporary files removed), read-only and hidden files, access rules, a file or backup held open without delete sharing and a file held open for writing (refused cleanly), a locked temporary file (the rename fails, the file is intact, only that temporary file is left and the stale cleanup removes it later), symbolic links and junctions.

## 15. Configuration validation (decision D41; `ConfigValidation`, `ConfigFiles`, the bounded loader)
- [V] **Which file is which** (`ConfigFiles`). `General.yaml` and `Email.yaml` are recognized by an ordinal, case-insensitive comparison of the file name (`EMAIL.yaml` is `Email.yaml` in every culture; a dotted or dotless Turkish I is never a match); every other top-level `*.yaml` file of the settings folder is a search file. The search loader, View Config, the failure messages and the validation all use this rule. Before D41 the search loader lower-cased the path with the current culture, so in Turkish `EMAIL.yaml` became `emaıl.yaml` and was loaded (and refused) as a search file. Discovery is unchanged: `Directory.GetFiles(ConfigPath, "*.yaml", TopDirectoryOnly)` (no `.yml`, no subfolder; case-sensitive on Linux as before); CM2's `<name>.bak` and `<name>.<32 hex>.tmp` never match. On Linux `File.Exists("General.yaml")` stays case-sensitive (a file named `general.yaml` is not read as the general settings and is not a search file either), as before.
- [V] **Bounded loading** (TD-52). Every settings file is read by `Yaml.ReadSettingsText` and `Yaml.LoadSettingsText` within the editor's limits (§13): at most 3,145,731 bytes (`ConfigFileReplace.MaxBytes`, checked from the file's length before it is read, and again while reading), 1,048,576 characters (`YamlDocument.MaxDocumentLength`; a byte-order mark counts as one, as in the editor), 100,000 YAML events, 32 nested collections (the root mapping is level 1) and 100 aliases. YamlDotNet's own parser counts them before anything is deserialized, and the deserializer reads exactly the counted events, so the recursive deserializer never sees a document over a limit. Rationale: settings files are a few hundred characters and 2 levels deep (the sample search is about 700 characters); the limits are the editor's, so the loader, the validation and the editor accept and refuse the same documents at the same boundaries. Over a limit the file is "could not be used" with a message that names the limit, never the content ("The file is larger than Campertron reads (at most 1048576 characters and 3145731 bytes).", "The file has more than 100000 YAML events.", "The file nests lists or mappings more than 32 levels deep.", "The file has more than 100 aliases."), exit code 1. **Aliases**: an alias is a reference to the object already read, never a copy, so a document within the alias limit can't expand; YamlDotNet reads an alias to a list or mapping, used where a text is expected, as the text `(Collection)` (no error), which the validation reports as a warning. **Decoding** is unchanged (`File.ReadAllText`'s rules: a byte-order mark selects UTF-8, UTF-16 or UTF-32; otherwise UTF-8 with invalid bytes read as U+FFFD); the validation warns about a file that is not strict UTF-8, which the CM2 writer and the editor can't update. **YamlDotNet 16.3.0's scanner** throws `InvalidOperationException` for an unclosed flow list followed by another line; the loader reports it as the `YamlException` ("Exception during deserialization") its deserializer gave before D41, and the editor refuses it as `Malformed` (before D41 the editor threw it).
- [V] **Diagnostics** (`ConfigDiagnostic`): a stable code (below), a severity, the file kind, the file's name (never its folder), the top-level key, the 0-based list item and the 1-based line and column of the key or item (0 when there is none). Messages are fixed text, key names and numbers only: never a value of the file and never an exception's message (YamlDotNet's messages can quote the file); an unknown key of `Email.yaml` is not named (it could be a mistyped value). **Severity**: Error, Campertron refuses the file (for `Email.yaml` with `outputTo: Email`, the Email loop refuses to start); Warning, it uses the file but probably not as intended; Info, a fact. An Error about the YAML (limits, syntax, unknown keys, unreadable values) is exactly what the loader refuses: the validation runs the loader's deserializer on the same events, and when the whole document fails it runs each top-level key alone to report every refused key (not in a document with aliases, where only the loader's first error is reported).
- [V] **At run time** the loaders refuse, through `ConfigValidation.ThrowIfRefused` (the failure path of §12, exit 1), only the errors marked "refused at start" below: they would otherwise take a dangerous path. The other errors were refused by the loaders before D41 and keep their messages; warnings and information are not printed (they are for a caller that shows settings: the GUI's Settings and Searches tabs since D43 and D44, §17 and §18).
- [V] **Unknown keys** stay refused (D20; no `IgnoreUnmatchedProperties`): "Campertron can't use the file until the key is removed or corrected". Keys are case-sensitive as the loader reads them (`searchby` is unknown). The editor keeps unknown text when it edits (§13); nothing is deleted or normalized.
- [V] **`General.yaml`**: `outputTo` must be `Console`, `Email` or `HtmlFile` (any case; a defined number such as `1` still loads; an undefined number is an error refused at start); `UnitTest` loads and is reported as test-only (Info), so the GUI's Settings tab keeps it but does not offer it (§17). `refreshRidbDataDayInterval` must be a number; a non-finite one (`.nan`, `.inf`) or one too large to count back from today is an error refused at start when `autoRefresh: true` (with `.nan` the refresh ran on every start, with `.inf` the start failed) and a warning otherwise (the value is unused); 0 or less with `autoRefresh: true` is a warning (the campground data is downloaded and rebuilt on every start). With `autoRefresh: true` a missing `lastRidbDataRefresh` (never refreshes automatically) and one in the future are warnings. Missing settings take their defaults. An empty or comment-only file is an error (as since D37).
- [V] **`Email.yaml`**: what sending needs (`CampsiteConfig.SendWithSmtp`, `CreateResultsEmail`): `smtpServer` not empty, `smtpPort` from 1 to 65535, `sendFromAddress` not empty and accepted by `MailAddress`, `sendToAddressList` with at least one entry and every entry accepted by `MailAddressCollection.Add` (as sending adds it; one entry may hold several comma-separated addresses). These are **errors with `outputTo: Email` and warnings otherwise**, so a file that is incomplete for a mode that doesn't send never stops a start; an empty `Email.yaml` is likewise an error only with `outputTo: Email`. An empty `smtpUsername` or `smtpPassword` is always a warning (a relay may accept mail without signing in). **The Email output's start check** (TD-51): `Load.RunConsoleSearch` calls `Load.CheckEmailOutputSettings` first in its Email branch, before the start line, `Preload` (search files, the example search, the campground data) and any request; it refuses with "Email.yaml could not be used: the Email output can't start: {each problem}." (for example "smtpServer is empty. smtpPort is not between 1 and 65535. sendFromAddress is empty. sendToAddressList has no address."), "File: …" and "Fix the file, or delete it and Campertron creates a new one.", exit code 1. Nothing is connected, signed in or sent. Before D41 the sample `Email.yaml` failed only at the first send, after a whole search ("unexpected problem: ArgumentException"). Other output types, `Load.GetConfig` and the GUI do not check it.
- [V] **Search files** (business-rules §1 to §4). A disabled search (`autoRun: false`) is reported (Info) and its problems are only warnings (it never runs). For an enabled search: **errors refused at start**: `searchValue` below 0 for `DaysOut` or `MonthsOut` (the dates ran toward the end of the calendar, about 2.9 million days, then failed), a `DaysOut`/`MonthsOut` window past the last date of the calendar, an empty (null) item of `includeEquipment`, `excludeEquipment`, `includeAttributes`, `excludeAttributes`, `includeCampsiteType` or `excludeCampsiteType` (`FilterData` threw on it during the search; since D51 the search no longer throws, a null value matches nothing, and the item stays refused as the mistake it is), an undefined numeric `searchBy`, and (since D51, in an enabled or a disabled search, like a value the loader can't read) `filterMatching` written as anything but `Exact` or `Contains` or written twice (`FilterMatchingInvalid`, below). **Errors the loader already refused**: `StartEndDate` with no date or one date, `Until` with an empty list, an unreadable `StartEndDate` or `Until` date, equal `StartEndDate` dates (§2). **Warnings**: an empty `campgroundID` (the search is skipped), a campground ID that is not a number (whether it is in the campground data is checked when the search runs, by its scope lines, and is CM4's), `totalHumans` missing or not positive, an empty `displayName`, no day of the week, `consecutiveDays` below 1 (no result is shown; with `outputTo: Email` its openings are recorded as reported although no email shows them, §4), `searchValue` 0 (today only, never matched), a search reaching 12 months or more (results limited to 12 months out), a missing or empty date list, an empty `StartEndDate`/`Until` date, extra dates, a reversed range, dates in the past, an unreadable `SpecificDates` date (ignored), a date not written `yyyy-MM-dd` (read with the computer's date format), a `yyyy-MM-dd` date the current calendar reads as another day (th-TH, fa-IR), an empty item of `includeSites`/`excludeSites` or a blank item of any filter. Missing (null) lists are no filter. Nothing changes the date generation or the filters.
- [V] **The settings folder** (`ValidateFolder`): `General.yaml` (its `outputTo` decides how `Email.yaml` is judged), `Email.yaml`, each search file, then whether any search runs: no search file is Info (the example is created at the next start); search files of which none is usable and enabled is `NoEnabledSearch` (Warning; with `outputTo: Email` the message says the Email loop checks 0 searches every minute). **Open question #40 stays open**: the loop is unchanged.

## 16. GUI campground identity (decision D42; `CampgroundChoice`, `Read.CampgroundChoicesBy*`, `Read.GetCampgroundDetailsById`)
- [V] **A campground is its FacilityID.** The GUI's campground lists hold `CampgroundChoice` entries (`class/RecDotOrg/CampgroundChoice.cs`, global namespace): the FacilityID exactly as `FacilitiesEntries` stores it (its TEXT primary key, a `string`; never trimmed, parsed as a number or converted, so a leading zero stays; a blank ID is refused), the trimmed name (null for a blank or whitespace-only name) and the City and State of an address (null when there is none). Equality and the hash code use the FacilityID only (ordinal); the label is display text and is never parsed back. Selecting an entry selects that FacilityID; the details are loaded with `Read.GetCampgroundDetailsById`, never by name. The search files' `campgroundID` is a string too; the configuration model is unchanged.
- [V] **Why names were unsafe** (TD-38, resolved). In the shipped database (2026-11-10 export) 4,966 reservable, enabled campgrounds have 4,966 distinct FacilityIDs but 4,936 distinct names (trimmed, case-insensitive): 24 names belong to more than one campground (30 extra rows), one of them the empty name (8 campgrounds), the other 23 pairs; two names are also used by a reservable, enabled facility of another type. On the shipped data, for example, `GetCampgroundDetailsByName("FISH CREEK CAMPGROUND")`, the lookup the GUI used, returns Utah's campground (10241505) also when Montana's (232493, West Glacier) was selected on the By State tab; since D42 the GUI shows 232493 for it (real-window review, build-and-test.md §AG).
- [V] **Labels** (`CampgroundChoice.Label`, also the item's `ToString()`, accessible name and tooltip): `<Name> — <City>, <State> — ID <FacilityID>`; `<Name> — <State> — ID <FacilityID>` without a city; `<Name> — ID <FacilityID>` without a state (a city without a state is not shown; the queries never return one); `Unnamed campground` replaces a blank or whitespace-only name, followed by the location if there is one (all 8 blank-name campgrounds of the shipped data have none: "Unnamed campground — ID <FacilityID>"). Only the ends of the name, city and state are trimmed for display; stored values are unchanged. - [V] **Order** (`CampgroundChoice.ListOrder`, in managed code): by name (trimmed, case-insensitive ordinal), then state, then city (both case-insensitive, missing first), then FacilityID (shorter first, then ordinal, so digit IDs sort numerically); unnamed campgrounds last. - [V] **The lists** (each one parameterized query, one entry per FacilityID; a campground with two qualifying addresses is listed once, by its Physical address, else its Default address, then by state and city):
  - **By State** (`CampgroundChoicesByState`) and **By City** (`CampgroundChoicesByStateAndCity`, an empty city included) keep their location filters exactly (the meaning of `UniqueParksByState` and `UniqueParks(state, city)`): a reservable, enabled campground with a Physical or Default address in that state (and city), located by that address, so a campground with addresses in two states shows the one of the selected state.   - **By Park** is not a location filter: `ParksWithCampgrounds` lists every recreation area name with a reservable, enabled campground, and `CampgroundChoicesByPark` lists every such campground of the park, also one without a qualifying address (an outer join; it is then shown without a location). Shipped data: 522 parks instead of 463 and 4,937 campgrounds instead of 3,330 (1,607 newly listed, for example Zion's Lava Point Campground, 10138237). A park name shared by two recreation areas (Sardis Lake, 154 and 577) lists the campgrounds of both, as before, each with its own location and ID.
  - **Not listed in the lookup tabs:** 22 reservable, enabled campgrounds of the shipped data have neither a recreation area nor a qualifying address, among them all 8 blank-name ones. ## 17. GUI settings editing (decision D43; `ConfigEditSession`, the Settings tab)
- [V] **What is edited.** The GUI's Settings tab (since D50 Settings > Campertron, §21; every rule of this section unchanged) edits `General.yaml` and `Email.yaml` in the settings folder `Load.GetConfig` uses (`CampertronInternalConfig.ConfigPath`), each through one `ConfigEditSession` (`function/Base/ConfigEditSession.cs`, internal; the GUI sees the library's internals since D43). Search files are edited by the Searches tab (§18, CM6); deleting files is not part of either. Nothing in it searches, refreshes the campground data, connects to an SMTP server or sends an email (checked from the IL and with an HTTP listener).
- [V] **Opening.** The file's exact bytes and their SHA-256 are read by `ConfigFileReplace.Read` (strict UTF-8, links, size limit; §14), its structure by `YamlDocument.Analyze` (§13) and its settings by `Yaml.LoadSettingsText` (§15). States: **Missing** (Create offered); **Unreadable** (`ConfigFileReplace.Read` refuses it: empty, not UTF-8, too large, a link it can't follow; its message); **ReadOnly** (the editor refuses the document, for example a comment-only file, malformed YAML, a duplicate key, a flow-mapping root, or the loader can't read its settings, for example an unknown key, which stays refused (D20) and is shown as the validation's diagnostic; nothing is changed or normalized to make it editable; Reload after correcting it in a text editor); **Editable**. In an editable file a key whose value uses an anchor, alias or tag, a multi-line text, or a list layout the editor can't edit item by item is locked (shown with the reason); a missing key can be added.
- [V] **Editing.** Values are typed (`OutputType`, numbers, `true`/`false`, a UTC date and time, texts, the recipients as rows). A value equal to the file's is no edit, so a field changed back is clean again; no edit means no write. Every change is applied to the text read by the YAML document editor, step by step (the scalars in one step, then each list operation: removals from the last, one reordering, changed values, insertions), each verified against the settings it should give (§13): comments, blank lines, order, quoting, indentation, a byte-order mark, the line breaks and the final line break stay; nothing is re-serialized. A step the editor refuses is an error at its field, with the editor's reason, and blocks the save.
- [V] **Validation.** `ConfigValidation` (§15) checks the changed text as the loader would read it; its diagnostics are shown at their field (list items at their row), with the severity written out ("Error:", "Warning:", "Info:"), also as the field's accessible help text. Errors block the save, warnings and information don't. `Email.yaml`'s severity follows the outputTo the General form shows (edited or as the file has it): with `Email` what sending needs is an error, otherwise a warning. `outputTo: UnitTest` is kept and shown with its Info diagnostic, but not offered as a choice. Text that is not a value of the field's type (a port that is not a whole number, a date that is not ISO 8601) is the GUI's own error at the field.
- [V] **The preview** (read-only): the lines a save changes, with one line of context (a single unchanged line between two changes is shown instead of the gap marker), line markers `-` and `+`, and a summary of the changed keys. The SMTP password is masked (always six bullets, whatever its length): its value range in the file as it is and as it will be, and any other occurrence of the old or new password in a shown line (a whitespace-only password only by its range); the summary says "smtpPassword (hidden)". A removed recipient that takes comments with it is announced ("Removing item 2 of sendToAddressList also removes 2 comments that belong to it."); mixed line breaks are announced (new lines get the most frequent one).
- [V] **Saving.** Only an editable, edited, verified file without blocking problems and without a conflict is saved. The file is first compared with what was read (a change becomes a conflict); `ConfigFileReplace.Replace` then writes it (temporary file, one rolling `<name>.bak` with the exact previous bytes and the file's mode or access rules, the external-change checks, the rename, the read-back; §14), and the file is read again: only when it is exactly the reviewed text are the edits cleared ("Saved Email.yaml. The previous version is in Email.yaml.bak."). Any failure keeps the edits and shows the writer's message, which names the file and the problem, never a value.
- [V] **External changes** (optimistic, `CheckForExternalChange`; when the Settings tab is shown, when the window is activated, and before every save). The file is read again and compared with what was read: no change; only the permissions, time or links changed (kept as the file's state, the edits stay); the content changed or the file disappeared. A clean editor then shows the new version (or Missing); an edited one keeps its edits and opens a **conflict**: nothing can be saved and the fields are locked until the user chooses. If the other program changed other settings, "Apply my changes to the new version" applies the edits to the new version (the editor proves they apply; a byte-order mark or line-break change is a content change and is kept); if it changed the same setting, the button names it ("Keep my values for smtpServer") and the user's values replace the other program's; "Discard my changes and use the file on disk" reloads. A deleted file can be created again with the edits (create-only: a file another program created meanwhile is never written over). A version the editor can't edit can only be taken as it is. Neither version is ever lost silently: until the user chooses, the other program's version stays on disk and the edits stay in the form. Before a save the writer itself checks the file again (§14).
- [V] **The password.** The password box masks the password (`PasswordChar`); its accessibility value is always the mask (`SecretTextBox`: Avalonia's own text-box peer reports the real text once it is revealed), and copying is disabled. "Show password" reveals it on screen only until the next save, revert, reload, conflict resolution, switching files, leaving the tab or deactivating the window; the reveal is never stored. An unchanged password stays byte for byte; a changed one is written only through the editor and the writer. No diagnostic, preview line, status, conflict message, smoke line or exception text holds it (sentinel tests search all of them and the window's texts, tooltips, accessible names, help texts and accessibility values).
- [V] **Backups and permissions.** One rolling `<name>.bak` (no history): for `Email.yaml` it holds the previous password, as an exact backup does, with exactly the file's mode (Unix) or access rules (Windows), never broader. A saved file keeps its mode or access rules (§14). An `Email.yaml` the GUI creates (Create, or created again after a deletion) is owner-only (0600) on Unix; on Windows it takes its folder's inherited access rules, as every new file there does. An existing `Email.yaml` that other users can read keeps its mode; the editor says so (Info, "Other users of this computer may be able to read Email.yaml…"); TD-49.
- [V] **Missing files.** The start still creates the samples (§9); a file removed later can be created from the Settings tab with exactly the start's sample (`Yaml.CreateSampleSettingsFile`, the same sample settings as the start, create-only); if another program created it meanwhile it is opened as it is. No search file is created.
- [V] **Open settings folder** shows the settings folder in the platform's file manager through Avalonia's launcher (`LaunchDirectoryInfoAsync`: a directory to show, no command line, no shell); a failure is shown ("Campertron couldn't open the settings folder. It is …"), never thrown.

## 18. GUI search-file editing (decision D44; `ConfigEditSession<CampertronConfig>`, `SearchFiles`, `SearchFileName`, the Searches tab)
- [V] **Write policy (D37 narrowed).** A search file is written only by an explicit action in the GUI's Searches tab: **Save** (the editing session of §17 and `ConfigFileReplace.Replace`: verified temporary file, one rolling `<name>.bak` with the exact previous bytes and the file's mode or access rules, the external-change checks, the read-back), **Save As** and **New search** (`ConfigFileReplace.Create`: create-only, never over a file, also not over one another program created meanwhile; no backup for a new file). Every write is the YAML document editor's targeted text (§13), checked by the validation (§15) and the editor's own verification; no edit, no write. The console, the Email loop, the start, the RIDB refresh and the validation never write a search file, and nothing deletes one.
- [V] **Which files.** Exactly the console's search files (`ConfigFiles.SearchFiles`: the top-level `*.yaml` files except `General.yaml` and `Email.yaml` in any case, §15), listed by name ignoring case, then ordinally (`ConfigFiles.SortedSearchFileNames`; the same in every culture). Backups (`<name>.bak`) and temporary files (`<name>.<32 hex>.tmp`) never match; `.yml` files and subfolders are not search files. Each file shows its name, its search's `displayName`, whether it runs (`autoRun`), its campground (label, or the ID) and its state (no problems, warnings, errors, read-only, can't be read; unsaved changes; changed on disk while edited). A file that can't be edited (malformed, unknown key, unsupported layout, not UTF-8, empty) is listed and opens read-only with a reason that holds no value (§17's states). The list is read when the tab is first shown and compared with the disk when the tab is shown, the window is activated and on "Look for changes on disk": a new file is listed, a removed clean file leaves the list, a removed edited file stays with its edits (a conflict); the chosen file stays chosen while it is listed.
- [V] **Settings.** Every setting of `CampertronConfig` (§1): `displayName`, `autoRun` ("Run this search"), `campgroundID`, `totalHumans` (empty is no number), `searchBy` (a value that is no search type is kept as the file has it, shown as not a valid choice, until the user picks one), `searchValue`, `searchValueDates`, `showMonday` to `showSunday`, the eight include and exclude lists and `consecutiveDays` (since D51 also `filterMatching`; since D52 the equipment and campsite-type lists are database-backed selectors, §23). Numbers are whole numbers (the GUI's error otherwise); dates are text as the search reads them (`yyyy-MM-dd` recommended; the validation reports other forms). A missing setting stays missing and a null list stays null (not `[]`) until edited. Lists are edited item by item (insert, remove, reorder, change) with the comments that belong to each item; an empty item written `- ~` stays exactly as it is until the user types in it; a list written in a form the editor can't edit item by item (for example a bare `-` item) is locked with its reason and the other settings stay editable. New list items that would read as another type (a date) are quoted, as are flow-list items with a colon. Undefined content is never normalized: unknown keys keep the file read-only (D20).
- [V] **Validation.** The search validation (§15, `ValidateSearch`) of the changed text, at its setting and list item, the severity written out; errors (in an enabled search: equal or unreadable `StartEndDate`/`Until` dates, a negative or out-of-range `searchValue`, an empty item in an equipment, attribute or campsite-type filter, an undefined `searchBy`) block Save and Save As, warnings and information don't. The search rules (§1 to §4, the date generation, the filters) are unchanged; the GUI only shows what the validation says. The days-of-the-week warning is shown with the check boxes. Its message about `consecutiveDays` follows the outputTo the General form shows.
- [V] **The campground.** Identity is the FacilityID, a string kept exactly (§16). The picker lists every reservable, enabled campground (`Read.CampgroundPickerEntries`, one query when the tab is first shown: 4,966 in the shipped database, also the 22 without a named park and without a qualifying address, TD-53 resolved, and the 8 unnamed ones), each with its label (name, location if known, ID) and park if it has one; nothing is invented. A filter narrows it to the campgrounds whose name, city, state or park contains each word (ordinal, ignoring case), or whose FacilityID is exactly the text (listed first); part of an ID never matches. A typed ID is used only if a reservable, enabled campground has exactly that ID: blank, surrounding spaces, a partial ID, a number form of another ID and a name are refused with a message that does not repeat the input. A label is never parsed. A campgroundID of the file that the campground data does not have is a warning (the data may be older than the file); an entered one is an error.
- [V] **New search** asks for a name and creates `<name>.yaml` in the settings folder with the example search's settings (`Yaml.SearchSampleConfig`, the start's example; since D51 with `filterMatching: Exact`, §9) and `autoRun: false` (a new search runs only once the user enables and saves it), in the serializer's text, create-only, then opens it. **Save As** writes the chosen search, with its edits (the reviewed text; without edits an exact copy), to a new file with the source's mode on Unix (on Windows the folder's inherited access rules), create-only; the source file is not changed and shows what is on disk again; the new file is opened.
- [V] **Names** (`SearchFileName`): `.yaml` is added when it is left out (an upper-case `.YAML` becomes `.yaml`); `.yml` is refused (the console reads `*.yaml` only); the name part has at most 100 characters of letters, digits, spaces and `- _ . ( )`, does not start or end with a space or a dot, has no `/`, `\` or `..`, is not a Windows device name (`CON`, `NUL`, `COM1`, …, also before an extension) and is not `General` or `Email` in any case; a name that a file, folder or link in the settings folder has in any case is refused (one file on Windows and macOS). The file is always directly in the settings folder; no folder is created and no shell is involved.
- [V] **The enabled toggle** edits `autoRun` alone: the preview and the save change exactly that value. The tab warns when no search file on disk runs at a start (`ConfigValidation.SearchFolderDiagnostic` with `RunsAtStart`, the counting of the folder validation: `autoRun: true` and no error), with the Email loop's consequence when the General form's output is Email; open question #40 (the loop then checks 0 searches every minute) is unchanged, nothing is enabled or created automatically.
- [V] **Not part of it:** deleting search files, running a search, showing availability or results, a general YAML or raw-text editor, multi-provider work. The tab's code refers to no availability, download or email code (checked from the IL and with an HTTP listener).

## 19. Interactive searches: the host-neutral search service (decision D45; `CampsiteSearch`, `SearchHost`, `class/Base/SearchRunModel.cs`)
- [V] **What it is.** `CampertronLibrary.function.RecDotOrg.search.CampsiteSearch` (internal) lets a host other than the console (the GUI, GS2) search saved search files and get typed results. `Plan(SearchRunRequest, Now)` reads and checks the chosen files; `Run(Plan, IProgress<SearchProgress>?, CancellationToken, SearchHostOptions?)` searches them, blocking (the caller owns the thread), and returns a `SearchRunResult`. Since GS2 (D46) the GUI's Results tab calls it (§20); nothing else in the GUI does. The console's search, its Email loop and its output are unchanged (below, *Compatibility*).
- [V] **Plan: one file at a time, read once, never written.** The request names the settings folder, the cache folder and the search files by name (as `ConfigFiles.SortedSearchFileNames` lists them). The folders must be full paths, the settings folder must exist and the cache folder must pass the RIDB refresh's guard (`Clear.CheckCacheDirectory`: not unset, not a root, not the settings folder); otherwise every entry is `Invalid` with `InvalidRequest`. Names are taken once each (the first of exact duplicates), in the order asked for. A name must be a file directly in the settings folder that the console would read as a search file (`.yaml`, no folder part, not `General.yaml` or `Email.yaml` in any case): otherwise `NotASearchFile`, and the file is not read. A missing file is `FileMissing`, one that can't be read `FileUnreadable`. The file is read once with the loaders' bounded reader (`Yaml.ReadSettingsText`, D41) and never written: no file of the settings folder is created, changed or deleted, `autoRun` included.
- [V] **Plan: checked as a start checks an enabled search, whatever `autoRun` says.** Choosing a file is the explicit request to search it, so a file with `autoRun: false` is searched too. Its diagnostics are the configuration validation's (`ConfigValidation.ValidateSearch`, CM3) for the text read, with their positions, each with the severity it has in an enabled search (the validation run on the same settings with `autoRun` set in memory only); `SearchDisabled` ("this search does not run", about a start) is left out and `SearchPlanEntry.AutoRun` keeps what the file has. An Error (what a start refuses: YAML errors, limits, unknown keys, equal, too few or unreadable `StartEndDate`/`Until` dates, a negative or out-of-range window, an empty item of the six filters `FilterData` calls `Contains` on, an undefined `searchBy`) makes the entry `Invalid` (`FileInvalid`, with the diagnostics); warnings never block and reach the result. A blank `campgroundID` is `Skipped` (`CampgroundIdMissing`; the console would search a campground with an empty ID). The dates are generated for `Now` as a start generates them (`CampertronConfig.RegenerateSearchData`: the same dates, without the console's warnings, which the diagnostics already hold). No network, no database, no console output. Discovery at a start, the example search and `Yaml.CampertronConfigGetConfigs` are not involved.
- [V] **Run: the console's own search.** Each ready search runs through `AvailabilityApi.GetAvailabilitiesByCampground`, the operation `Load.RunConsoleSearch` runs for each search: the same months (0 to `GetMonthsToCheck` from now that hold a search date), the same month URLs and sharing (one request per campground and month for the whole run, `RunningData.Urls`/`SiteData`), the same availability parsing (`Data.DynamicDeserialize`, `CalculateAvailableDates`), the same filters (§3), the same consecutive nights (§4) and the same output values. Searches run in parallel (`Parallel.ForEach`, as the console). Stages: validating (the months and URLs each search needs; the cache folder created if missing, as a start creates it), preparing campsite details, checking availability, building results.
- [V] **The run's configuration is its own** (the manual-search policy, D8 as refined, §5): `GeneralConfig.OutputTo = HtmlFile`, `EmailConfig = null`, the request's two folders. On the search path that means no calendar values in the output and no notification history (`Load.UsesNotificationHistory` is false, so `FilterData` never looks at `Camp.History`). `Run` never calls `PostProcess`, `ReportResults` or `OutputResults`: nothing is rendered, written, opened or sent. It never reads `General.yaml` or `Email.yaml`, so an Email output setting or an SMTP secret never enters it; it never reads or writes `Camp.History` and never creates it; markers on disk hide nothing, and a later Email check is unaffected (its markers are exactly as they were).
- [V] **Campsite details** (the JSON cache): each campground of the run is prepared once, silently, cancellably and before any request (`Cache.PrepareCampground`, the code `Cache.PreCheckCache` runs for the console, with no status line). A campground whose cache is not complete is built from the campground data only if `RecreationDotOrg.db` exists in the settings folder (opening a missing SQLite file would create an empty one); otherwise its searches fail with `CampsiteDataMissing` and no request is made. A failure to build is `CampsiteDetailsUnavailable` for its searches. **Completion protocol** (unchanged for the console): `{CampgroundID}-Cached.json`, the only file `Cache.CacheExist` looks at, is written last and only after every other file was written; a build that stops (a cancellation between campsites, an exception, a killed process) leaves no cache that looks complete, and the next search builds it again. The search itself never builds a cache in an interactive run (`Cache.CheckCache` with `MayBuild` false). A campground ID that is not a reservable campground of the campground data is a warning (`CampgroundNotFound`); the search still runs, as the console's.
- [V] **The per-run host** (`SearchHost`, carried by `RunningData.Host`; null for the console) adds only what an interactive search needs: the run's `CancellationToken`, the transport, the bounds below, the signal of each shared month, the months each search checked, and the progress. `ProcessMonth` asks it for a month (`GetMonth`) instead of the console's fetch-or-poll; the day and campsite loops, the month loop and the consecutive filter check the token (`Host?.ThrowIfCanceled()`, a no-op for the console).
- [V] **Requests of an interactive run**:

| Answer or failure | Interactive run | Console (unchanged, §7) |
|---|---|---|
| A month: JSON with `campsites` (an empty object too) | the month is checked | the same |
| Network failure (`HttpRequestException`, `IOException`, socket, TLS) | `NetworkFailure`, tried again | retried every 30 s without limit |
| No answer within `RequestTimeout` (30 s) | `Timeout`, tried again | no timeout of its own (HttpClient's 100 s, then the 30 s retry) |
| The heavy-traffic message | `HeavyTraffic`, tried again after 1 s | retried every second without limit |
| HTTP 408 or 5xx | `HttpStatus` (the status kept), tried again | the status is not read; the body is parsed |
| Other HTTP errors (4xx) | `HttpStatus`, not tried again | as above |
| Not JSON, empty | `MalformedResponse`, tried again | retried every 30 s without limit |
| JSON of another shape: `{"count":0}`, `{}`, `[]`, `{"error":…}` | `UnexpectedResponse`, tried again | spins (`{"count":0}`, `{}`, `[]`) or retried without limit |
| Body over `MaxResponseBytes` (32 MiB) | `ResponseTooLarge`, not read, not tried again | read whole |
| The block page (`REQUEST BLOCKED`, any case) | `RequestBlocked`: the run is blocked | "Error: Blocked by API …", 5-minute wait, exit code 1 (§7) |
| HTTP 429 | `RateLimited`: the run is blocked | the body is parsed (429 is not read) |
| Cancellation | the request is canceled at once | Ctrl+C ends the process (§12) |

  **At most three requests per month in all** (`SearchHostOptions.MaxAttempts`, a constant), whatever mix of failures, timeouts, heavy traffic and other answers worth another request; there is no separate heavy-traffic path. The wait before another request is the console's (30 s, 1 s after heavy traffic), but it ends at once when the run is canceled or blocked. **A block** (the block page or HTTP 429) is never tried again and stops the run's requests: no request is started after it (a month not yet requested is not checked, with the block as its reason; one already in flight may finish), and what was received before it is kept. The run then ends `Blocked`; it never waits five minutes, never ends the process and writes nothing to the console. The answers are classified as the console reads them (the block page first, then `Data.DynamicDeserialize`), and the status is read as well.
- [V] **Shared months.** The first search that needs a campground's month fetches it (`RunningData.Urls`), the others wait for it. Whoever fetches it always releases every search waiting for it (`finally`): with the month, a final failure, a block or cancellation; a defect in the fetch itself is contained to that month (`InternalError`) and kept. A waiting search waits on that signal, cancellably; nothing polls. The month's outcome is each waiting search's outcome for it.
- [V] **The transport** (`SearchTransport`: a delegate that takes a `SearchRequest`, the URL, campground, month and attempt, and a token that ends at the request timeout or the run's cancellation, and returns a `SearchResponse`, the status, the body as text and whether it was too large). Production is `HttpSearchTransport`: one `HttpClient` for the whole run, created by `Run` when no transport is given and disposed when it ends; no header of its own and the system's proxy settings, like the console; `HttpCompletionOption.ResponseHeadersRead`, a `Content-Length` over the limit refused unread, a body without one read only up to the limit; decoded as the console's `StreamReader` decodes (UTF-8, a byte-order mark honored). Tests give their own transport (`SearchHostOptions.Transport`); no test reaches the network (build-and-test.md §AJ).
- [V] **Cancellation** is observed before any request, during a request (the request's token), during the wait before another request, while waiting for a shared month, while the campsite details are prepared (between campsites; no completion marker is written), in each month's day and campsite loops, in the consecutive filter, and while the results are built (a search not built yet is `Canceled`). Measured in the tests: well under one second from the cancellation to `Run` returning, at every one of these points (build-and-test.md §AJ).
- [V] **Run never throws** for a file, network, block, timeout, retry, response or cancellation outcome, and never for a failing progress handler. An unexpected exception on a search's path ends that search (`InternalError`, with the exception's type name; the exception itself in `SearchRunResult.Defects`, for tests and diagnostics only, never shown) and the others go on. `ArgumentNullException` for a null plan is the only exception it throws.
- [V] **Results** (`SearchRunResult`, immutable: records and read-only lists over arrays of its own; no `RunningData` collection, no `ConsoleConfigValue`): the run's status (`Completed`: every search complete; `CompletedWithProblems`; `Blocked`; `Canceled`; `Failed`: nothing could be searched), its start (UTC) and elapsed time, the unique campground-month requests planned, finished (with data or a final failure) and failed, the run's issues (the block, a cancellation, a defect of the run itself) and one `SearchResult` per plan entry, in the plan's order: the file name, display name, `autoRun` as in the file, campground ID, campground and park name, consecutive nights, its state (`Complete`: every month it needed was checked, with or without availability; `Incomplete`: some were; `Failed`: none, or it stopped; `Canceled`; `Skipped`; `Invalid`), its requests planned and finished, its months (`SearchMonthResult`: the month's first day, checked or not, and why not), its openings and sites, its issues and its configuration diagnostics.
  - **A month that was not checked is never a month without availability**: it adds nothing to the output (no month header, no "No entries found"), it is listed as not checked with its reason (`NetworkFailure`, `Timeout`, `HttpStatus`, `HeavyTraffic`, `MalformedResponse`, `UnexpectedResponse`, `ResponseTooLarge`, `RequestBlocked`, `RateLimited`, `CampsiteDataMissing`, `CampsiteDetailsUnavailable`, `InternalError` or `Canceled`), and each one except a cancellation is an issue of the search with the month, the requests made and the HTTP status. No availability is a `Complete` search with no opening.
  - **Openings** (`SearchOpening`): one campsite on one night, with the campsite's ID, name, loop, type, equipment, its check-in and check-out times (the campsite's attributes, as the console shows them), its minimum and maximum occupancy (the month's data), and its booking link (`ResultsHtml.BookingUrlPrefix` and the campsite ID escaped with `Uri.EscapeDataString`). They are built from the search's output values by `CampsiteSearch.OpeningsOf`, from their typed metadata only (`Kind` and `Metadata`: the `Availability` values of single nights, the `ConsecutiveDate` values of runs; never `ConfigValue`, the console text, and never the HTML page), so they are exactly what the console and the results page show for the same search: a search with `consecutiveDays` above 1 has only the nights of its runs, one below 1 has none. One opening per campsite and night: the same campsite listed twice for a night (the console lists it twice) is one opening. **Order:** by night, then by campsite ID (shorter first, then ordinal, so numeric IDs sort as numbers in every culture); the same in every run. **Sites** (`SearchSite`): the openings by campsite, in the same ID order, with the campsite's details (those of its first night), its nights in date order and their runs of consecutive nights (`SearchStay`: the first night, the number of nights, the checkout date).
  - **Problems are value-free** (`SearchIssue`): a code, a severity, fixed text (`CampsiteSearch.Message`), the file name, the month, the HTTP status, the requests made and, for a defect, the exception's type name. Never a response body, an exception's message, a folder or a value of a settings file; the configuration diagnostics keep CM3's rules (§15).
- [V] **Progress** (`SearchProgress`, immutable snapshots, a sequence number): reported when something changes (a stage, a search's state, a prepared campground, a finished request, the start or end of a wait before another request, a block), never per campsite or day, in order and under one lock; a handler that throws is a defect, never the run's end. Stages: `Validating`, `PreparingCampsiteDetails`, `CheckingAvailability` (`Retrying` while a request waits to be tried again), `BuildingResults`, then the run's status. Counts only where the total is known: campgrounds planned and prepared; unique campground-month requests planned (all of the run's at its start), finished, failed and waiting to be tried again. Each search: `Waiting`, `Searching`, then its state. No percentage. The library does not depend on Avalonia; throttling progress for a window is GS2's.
- [V] **Compatibility** (the console path, `RunningData.Host` null): the stream of every search is the same value for value (kind, write type, color, text, metadata) and the HTML page, each Email page and the console rendering byte for byte as on `master` (build-and-test.md §AJ); the retries, waits, block handling, exit codes, `Camp.History`, the Email loop and the container are unchanged. Two changes on the console path, both without an observable effect: `ProcessMonth` adds a month's header after the month's fetch instead of before it (nothing is added to the output while a month is fetched, so the output is the same), and the console's download is a replaceable internal step (`AvailabilityApi.ConsoleDownload`, production the former code: a new `HttpClient` per request, the body read whatever the status) so the tests run the console's search without recreation.gov. `OutputMetadata` gained `MinOccupancy` and `MaxOccupancy` (nullable, set by `AvailabilityValues`); no renderer reads them.
- [V] **Not part of GS1:** any GUI change (the Results tab is GS2, §20), throttling progress for a window and the GUI's shutdown with a run in progress (both GS2), the console's own bounds (TD-09 stays for the console), the menu (TD-12, TD-15), the parser's fragility (TD-55) and the cache race between processes (TD-54).

## 20. GUI campsite searches and results (decision D46; the Results tab, `ResultsViewModel`, `ResultRows.cs`, `ProgressGate`, `ResultsView`)
- [V] **What it is.** The GUI's sixth tab, Results, after Searches (since D50 the second of four top-level tabs, still right after Searches; §21): it runs saved search files on request through GS1's service (§19: `CampsiteSearch.Plan` and `Run`, the console's own search with manual-search semantics) and shows the typed results. It is the only part of the GUI that searches; the Searches tab has no Run button, and the lookup tabs search nothing (checked from the IL and at run time). It never calls the console pipeline, `AvailabilityApi`, an HTTP client of its own, `Camp.History` or `Email.yaml`, never parses console text or the results page, never writes a file and never sends email.
- [V] **Folders.** The settings folder and the cache folder are the ones `Load.GetConfig` returned at the GUI's start (`MainWindowViewModel.ConfigPath`/`CachePath`, carried through the startup's completion; nothing rediscovers them). Without a cache folder nothing can start ("Campertron couldn't find its cache folder, so it can't search. Restart Campertron."). The folders are never shown in the results.
- [V] **The list.** Exactly the console's search files (`ConfigFiles.SortedSearchFileNames`: the same discovery and order as the Searches tab), each read as GS1's plan reads it (`CampsiteSearch.LoadEntry`: the bounded reader and CM3's diagnostics with an enabled search's severities; never written). Each file shows its search's name (else the file name), the file, the campground (the Searches tab's campground data, one query for both tabs: name, location and ID; else "Campground ID …"), "Runs at startup" or "Not run at startup", warnings (`Warning: …`) and, for a file that can't run, the reason in words: "Can't be searched: …" with the plan's issue and the first error (fixed text, key names, line numbers; never a value), or "Save or revert the changes in the Searches tab first." for a file the Searches tab holds unsaved changes to (`SearchesViewModel.IsUnsaved`; per file: the other files stay runnable; the Results tab never saves, discards or synthesizes a search from the editor). The list is read when the tab is shown, when the window is activated while it is shown, and at Start; there is no file watching.
- [V] **The choice.** A runnable file that runs at startup is selected by default; a disabled one is listed unselected and runs only when the user selects it (its `autoRun` is never changed: the run's `SearchResult.AutoRun` and the file keep `false`). A file that can't run can't be selected and is unselected when it stops being runnable; a file that stops running at startup is unselected unless the user selected it. Select enabled, Select all that can run and Clear selection change the choice; all of them, and the check boxes, are locked while a run goes on.
- [V] **Start** (enabled only when no run goes on, at least one file is selected, Start is not waiting after a block and both folders are known; the command checks the same again): the disk is read again first. If that unselects a selected file (it can no longer run, or it no longer runs at startup and the user did not select it), nothing starts and the tab says which files changed; a file that appeared meanwhile is listed unselected. A selected file deleted since it was listed is asked for anyway, so the run reports it as a typed missing file while the others are searched. Then GS1's plan reads each selected file once (the bytes searched are those read now) and checks it; if no file can be searched, nothing starts and the previous results stay. Otherwise the run is accepted: the previous results are cleared and `CampsiteSearch.Run` runs on a background thread of its own (`TaskCreationOptions.LongRunning`: never a foreground thread, never the UI thread); one file and several files go through the same entry point.
- [V] **One operation at a time.** Each accepted Start is an operation with its own increasing ID, `CancellationTokenSource`, plan, progress gate, start time (the monotonic `TimeProvider`) and task. Every progress publication, the run's end and the elapsed-time ticker check that their operation (or ticker) is still the current one; a callback of an earlier or abandoned run changes nothing. The token is disposed only after the run has ended (Cancel and Dispose are serialized).
- [V] **Cancel** (enabled while a run goes on and not yet canceled): cancels the operation's token; GS1 stops at its next checkpoint (during a request, the wait before another request, while waiting for a shared month, while campsite details are prepared or results filtered; measured: well under a second, 143 to 148 ms by keyboard in the real window). The button reads "Canceling…" until the run ended; repeating it does nothing; it never starts anything or ends the process. Searches that finished keep their results; a month that was not checked is listed as not checked, never as a month without availability.
- [V] **Progress.** GS1's snapshots reach the UI through `ProgressGate`: `Report` (on GS1's threads, under its lock) only keeps the newest snapshot and queues one job for the UI thread if none is queued or waiting; the UI publishes at most once per 100 ms (a later snapshot waits for the rest of the interval on a one-shot timer), so at most ten publications a second and never more than one job or timer waiting. The run's end is shown at once from its result (the gate is closed and its timer stopped). Shown: the stage ("Reading the searches", "Preparing campsite details", "Checking availability at recreation.gov", "Checking availability; N requests are waiting to be tried again (each month is asked for at most three times)", "Building the results"), the campgrounds ready of planned and the month requests finished of planned (with those not checked and those waiting to be tried again), each file's state in the list (Waiting, Searching, then its end) and the elapsed time (every second). The bar is determinate only with GS1's totals (campgrounds while their details are prepared, month requests while availability is checked), otherwise indeterminate; no percentage is shown. GS1 reports no attempt number or wait duration, so none is shown (open question #42 unchanged).
- [V] **A block** (the block page or HTTP 429, `SearchRunStatus.Blocked`): the run is over at once; the searches that completed keep their results, the blocked one is "Stopped: recreation.gov limited the requests…", its months are listed as not checked ("recreation.gov blocked the requests" or "asked for fewer requests"); no answer text or exception message is shown; the application keeps running. Start is disabled for five minutes from the blocked result in this GUI process only ("recreation.gov limited Campertron's requests. Start is available again in m:ss.", every second), measured with the monotonic `TimeProvider`; nothing is written, another window or a restart does not wait, and the console's own block handling (§7) is unchanged.
- [V] **The results** (`ResultSearchViewModel`, `ResultRow` and its kinds), directly from the immutable `SearchRunResult`: the run's status ("Finished: …", "Finished with problems: …", "Stopped: …", "Canceled. …", "Nothing could be searched.") with the openings found and the elapsed time, the run's issues, and a choice of the search to show (the first with openings is shown first). Per search: its status in words, distinct for each end (complete with openings "Complete: N openings found", complete without "Complete: no matching availability in the months checked", "Incomplete: some months were not checked…", "Failed: no month could be checked", "Stopped: recreation.gov limited the requests…", "Canceled before it finished…", "Not searched: no campground is set (campgroundID)" or "Not searched: the file can't be searched"), its counts (openings, campsites, nights; for consecutive nights the campsites with runs and the nights in all), "Months checked: …" and "Not checked: <month> (<reason>)" (a month not checked is never shown as without availability), its campground, park and ID, and its issues and warnings with their severity written out ("Error:", "Warning:"), the month, the HTTP status and the requests made (never a response body or an exception's message). Single nights: a heading per night in date order with the number of campsites, then GS1's openings of that night in GS1's order (campsite ID, shorter first); consecutive nights: each campsite in GS1's order with its stays (arrive, leave, nights) in date order. A campsite row shows its name as the results page names it ("Site 086"; a name starting with "Site" as it is), its ID and only the details it has: loop and type as stored, equipment, check-in, checkout, occupancy ("1 to 6 people", "4 people", "up to 6 people"); no empty label. Nothing is truncated in the model; long text is trimmed on screen with the whole text in a tooltip and the accessible name.
- [V] **Large results.** The rows of a search are built once, when it is first shown; the list is a `ListBox` with a `VirtualizingStackPanel` in a bounded star row, so only the rows on screen exist (12,030 rows: under 100 realized, also after scrolling to the end; 17,280 openings from a stand-in run shown in 2.5 s in the real window).
- [V] **Booking links and copies.** The selected campsite's booking link is opened (Avalonia's `ILauncher.LaunchUriAsync`: no shell, no command line, no process) or copied only if it is exactly the link GS1 builds for that campsite (`CampsiteSearch.BookingUrl`: https, host `www.recreation.gov`, the default port, no user information, query or fragment, the path `/camping/campsites/<the escaped campsite ID>`); otherwise "Campertron did not open (copy) this link: it is not a recreation.gov campsite page.". Copy campsite ID and Copy booking link write to the clipboard only on the user's action. A launcher or clipboard failure is reported without its message ("Campertron couldn't open the booking page. …", "Campertron couldn't copy …"). No configuration value is ever copied.
- [V] **Accessibility.** Every interactive control has an accessible name (Start search, Cancel search, the check boxes "<search> (<file>), runs at startup / not run at startup / can't be searched now" with the reason as help text, the selection buttons, the result choice, the list "Openings found", the actions); the status is a polite live region read as its text; the progress bar is "Search progress" with its value when determinate; each result row reads its date and campsite with its details; every state and problem is said in words, never by color alone. Keyboard: Tab goes Start, the check boxes, the selection buttons (Cancel and disabled buttons skipped), then the result choice, the list (arrow keys choose a row) and the actions, and wraps to the tab header (TD-39's workaround); Enter toggles a check box and presses a button.
- [V] **Window close.** Closing the window detaches the tab (no later callback changes anything), cancels the run and stops its timers; the UI thread never waits for the run. `Program.Main` (and the smoke test) then waits at most `App.SearchShutdownWait` (10 s) for the canceled run to end (measured: a few milliseconds), so a campsite-details build stops at a checkpoint; the run's thread is a background thread either way. No `Environment.Exit`.
- [V] **Layout.** The tab keeps the capped, left-aligned column. The run card (Start and Cancel in its heading, the files, the selection buttons, the status, the progress) stays at the top; the list of files gets smaller in a low window and once there are results; the results card takes the rest with the list in a bounded star row. When the window is too low for the run card and a usable results card (a wide font at 720×540), the tab scrolls instead of letting the list run under the actions. Colors only from theme resources (Light and Dark).

## 21. GUI navigation and the theme preference (decision D50; `MainWindow`, `ThemePreferenceStore`, `AppTheme`, `SystemSettingsViewModel`, Settings > System)
- [V] **The tabs.** The window's top-level tabs are, in this order, **Searches**, **Results**, **Settings** and **Campsites** (`MainWindow.SearchesTabIndex` 0, `ResultsTabIndex` 1, `SettingsTabIndex` 2, `CampsitesTabIndex` 3). **Settings** holds its own row, **Campertron** (the `General.yaml` and `Email.yaml` editors of §17, unchanged) then **System** (the theme, below). **Campsites** holds the lookup's row, **By Park**, **By City** and **By State** (beta.8, §16, unchanged). The window opens on Searches; each nested row opens on its first tab and keeps its chosen tab, and every tab keeps its own state (the lookup's selections and details, the chosen settings file and unsaved edits, the chosen search file, the Results tab's choice and results) while the user moves between tabs. Before D50 the six tabs were By Park, By City, By State, Settings, Searches and Results in one row, and the window opened on By Park.
- [V] **When the tabs read.** Searches is shown at the start, so as soon as the startup is ready the Searches tab reads the search files and the campground data (`SearchesViewModel.Show`: one campground query, shared with the Results tab; before D50 this happened when the tab was first clicked). The Results tab reads its list when it is shown; the lookup tabs bind their lists when Campsites (and the lookup tab) is first shown, still one query per binding; Settings > Campertron looks at its two files whenever it is shown, from System as well as from another top-level tab, and when the window is activated while it is shown. Leaving Settings > Campertron, for System or another top-level tab, or the window masks a revealed password again (§17). Moving between tabs writes nothing.
- [V] **Keyboard.** The arrow keys on a header switch that row's tabs. Tab moves from a top-level header into its tab: for Settings and Campsites to the row's selected header, then into that tab's content. Because Avalonia 12.1.6 traps Tab and Shift+Tab inside a tab's content and on a nested header (TD-39), `MainWindow` corrects only plain Tab and Shift+Tab when focus did not move or skipped a header: Tab at the last stop wraps to the selected top-level header; Shift+Tab at the first stop goes to the innermost row's selected header, and from a nested header to the top-level one; a Tab from a header that went past the nested row's header goes to that header. Other keys and modified Tab combinations are Avalonia's.
- [V] **The theme.** Settings > System offers exactly **System** (the default), **Light** and **Dark**. System is Avalonia's `ThemeVariant.Default`: the window follows the operating system's light or dark setting and its changes while Campertron runs (Avalonia reads it from the platform; on Linux the settings portal's `org.freedesktop.appearance color-scheme`); Light and Dark always use that theme. A choice applies at once, through `Application.RequestedThemeVariant` (`AppTheme.Apply`), and is saved; the tab says what is shown ("Campertron is shown in its Dark theme, as the system asks.") and whether the save worked. At the start `App.PrepareTheme` reads the saved theme and applies it before the window is created. Campertron has no theme detection of its own; the console's appearance is unchanged.
- [V] **Where it is kept.** A preference of the GUI, not a Campertron setting: `<LocalApplicationData>/CampertronGUI/preferences.json` (`ThemePreferenceStore.ForCurrentUser`: the per-user folder that holds `CampertronConfig` and `CampertronCache`, looked up without being created; a lookup that is not a full path means no store, never the working directory). The file is a UTF-8 JSON object whose `"theme"` is `"System"`, `"Light"` or `"Dark"` (read ignoring case; a byte-order mark is skipped); other members are allowed and kept. It is never in `General.yaml`, `Email.yaml`, a search file or the settings folder, it is not a `.yaml` file (so never a search file), and the console never reads it.
- [V] **Reading and fallback.** Reading creates nothing. No file, or an object without `"theme"`, is System (the default). A file that can't be read (permissions, a folder in its place), is larger than 64 KiB, is not JSON (also with comments or a trailing comma), is not an object, has a duplicate member, or names a theme that is not one of the three (another word, a number, null, an object, surrounding spaces) gives System, and Settings > System says that the saved preference couldn't be used until the user chooses a theme; the file is not rewritten by reading it.
- [V] **Saving.** Only a user's choice in Settings > System writes the file: the existing object (if it is one) with `"theme"` set, its other members kept in their order, indented, through a new temporary file `preferences.json.<32 hex>.tmp` in the same folder (created if needed), flushed, then moved over the file; a file that is not an object is replaced. A save that fails (for example a file where the folder should be) leaves no temporary file, throws nothing, keeps the theme applied until Campertron closes and says so ("Campertron couldn't save the theme for the next start (…). It applies until Campertron is closed."). The smoke test's theme probe uses a temporary folder and never writes the user's file.

## 22. Filter choices from the campground data (decision D51; `Read.FilterChoicesByCampground`, `CampgroundFilterChoices`, `FilterChoice`)
- [V] **What it is.** The values a search's eight include and exclude lists can be set to for one campground, read from the local campground database only (no network): the permitted equipment names, the campsite types, the campsite names and the attributes (`"Name:Value"`, composed exactly as the search composes them, `Cache.ConvertAttributeValuePairToString`) of the campground's **own campsites** (`CampsitesEntries.FacilityID`, the exact string; never trimmed or parsed: `0232445`, ` 232445` and `2324` give nothing). Each `FilterChoice` holds the value exactly as stored (never trimmed or case-changed; blank names, surrounding spaces, colons in attribute values and case variants are kept as separate values), the number of the campground's campsites that have it (for a campsite name: the campsite records that carry it), and for an attribute its name and value. Lists are ordered by `FilterChoice.ListOrder` (ignoring case, then ordinal: case variants are next to each other; the same in every culture). The search editor's selectors use it (§23).
- [V] **How.** Three parameterized queries in one context: the campground's campsite records, then the equipment and the attribute rows of exactly those campsite IDs (an `IN` list of parameters, which Campertron's attribute index serves, §8). Equipment and attribute rows whose campsite is not in `CampsitesEntries` (the shipped data has 4,850 and 1,200 such rows) are never offered, and neither are rows of another campground's campsites: the search never sees them either. A blank ID runs no query (no database is opened or created); an unknown ID and a campground without campsites give no choices after one query. Null names and types are left out (the shipped data has none). Read-only; it reads no settings file and makes no web request.
- [V] **The shipped data** (RIDB export of 2026-11-10; measured 2026-11-16 with read-only SQL, build-and-test.md §AQ): 130,948 campsite records, 441,779 equipment rows, 2,407,137 attribute rows; 15 equipment names, 39 campsite types, 336 attribute names and 3,489 distinct `Name:Value` pairs overall; per campground at most 14 equipment names, 10 types, 92 attribute names and 270 pairs, and at most 360 campsite records (258830; 232490 has 357). 4,966 reservable, enabled campgrounds, 10 of them without campsite records. 1,115 campsite names occur more than once within their campground (in 120 campgrounds), 3 pairs of names differ only by case within a campground; 14 names are blank and 260 untrimmed; 43,862 attribute rows have a blank value and 48 a whitespace-only one, 376 an untrimmed value (17 distinct pairs); 142 pairs have a colon in the value; 28 groups of pairs differ only by case (35 when also trimmed). No equipment name, type or attribute name differs from another only by case. A copy of a real data folder's database refreshed on 2026-11-11 has exactly the same equipment names, types and `Name:Value` pairs, but 130,949 campsite records, 541 of which differ from the shipped ones (`EXCEPT`): the choices of a campground can change with a refresh.
- [V] **Cost** (the product's code, medians of 15): 22 to 34 ms per campground with Campertron's index (Watchman 27 ms, 258830 22 ms, 232490 34 ms), 0.19 to 0.35 s without it.

## 23. GUI filter selectors (decisions D51, D52; `FilterSelectorField`, `FilterChoiceSource`, `FilterSelectorView`, the Searches tab)
- [V] **Which lists.** Since D52 the search editor's `includeEquipment`, `excludeEquipment`, `includeCampsiteType` and `excludeCampsiteType` are database-backed selectors, since D53 also `includeSites` and `excludeSites`, since D54 `includeAttributes` and `excludeAttributes`: all eight lists (the rows of D44 remain for the dates). Include and exclude are separate selectors.
- [V] **Attributes** (D54). A heading per attribute name (ignoring case, then ordinal; "Shade", "4 values"), which checks nothing (no check box; Space and a click do nothing; "Attribute Shade, 4 values" for a screen reader); its values under it by their value part ("(blank)", "2:00 PM", a padded value quoted), each the value `Name:Value` exactly as the search composes it, written exactly (the editor quotes `'Shade:'` and `'Shade: Yes'`); spellings of a value that differ only by case grouped under the name; a screen reader hears "Shade: Yes, 2 campsites, checked". With Contains matching a value shows the campground's values it also matches, notably the blank value of its name (`Shade:Yes` contains `Shade:`, so it also matches campsites whose `Shade` is blank). Find matches name and value and keeps the heading above the shown values.
- [V] **Campsite names** (D53). Names compare exactly in both modes (§3): a kept name says "Not a campsite name of this campground; campsite names always match exactly, so it matches no campsite here.", and no name shows what it "also matches". A name several campsite records of the campground carry is one value, "N campsites share this name"; checking it adds the name once. Names are shown in their natural order (`NaturalOrder`: digits by number, 2 before 10; other runs ignoring case; then ordinal; display only). A validation message about an item is shown with its checked value too (a checked blank name: "Warning: includeSites item N is blank, …").
- [V] **Responsiveness** (measured, §AS). The selector's own work is linear (one set of the list's values per rebuild): 1.2 ms for a change in a list of 360 checked names. The editing session (§17, §18, unchanged) replans the list's unsaved item edits from the file on every change, one verified editor step per item: with 360 names added and not saved, a further change took 0.74 to 0.97 s; saved, 10 ms; with 9 checked names, 10 ms.
- [V] **The list is the YAML list.** A selector holds the list's items exactly as the editing session gives them (each with the item it was in the file), and gives them back the same way (§18): saving is the editing session's item edits, so comments, order, quoting, duplicates and an empty (`- ~`) item stay unless the user changes that item. **Checking** a campground value adds one item at the end; **unchecking** removes every item that is exactly that value; a **typed value** is added as typed (never trimmed or case-changed; not added again when the list holds exactly it, "The list already holds exactly this value."; an empty box is refused, "Type a value first."; a campground value typed in is checked in the list); **Remove** removes one kept item. A list the editor can't edit item by item (§18) is shown with its lock reason and takes no change. Unchanged lists are no edit; checking and unchecking the same value is no edit.
- [V] **The campground's values** (§22) are what the selector offers, checked when the list holds exactly the value. Values that differ only by case (`OrdinalIgnoreCase`) are one group row ("Tent (2 spellings that differ only by case)", the sum of their campsites) with each spelling under it: the group is checked when every spelling is in the list, partly checked when some are; checking it adds every missing spelling, unchecking it removes them all; each spelling is its own value for the search in both modes, so the group never implies more than the spellings it adds. Blank, whitespace-only and space-padded values are shown visibly ("(blank)", "(2 spaces)", "“ A1” (with spaces at its start or end)") and kept exactly as stored.
- [V] **Values the campground does not have** (typed, of another campground, stale after a refresh, a case or space variant, an empty item) are listed under the selector as "Other values in <key>", in the list's order with their position, each with what it does: with Exact "Not among this campground's … it matches none of them with Exact matching."; with Contains which of the campground's values it matches ("… with Contains matching it matches one of them: “GROUP STANDARD NONELECTRIC”."), or none; a value equal to a campground value but for case also "It differs only in upper and lower case from “Tent”, which is a different value."; an empty item "An empty item in the file. It is kept until you remove it." with the validation's message. They are never dropped: a campground change, a refresh or a failed read keeps them.
- [V] **Exact and Contains in the selectors.** With Contains matching a campground value shows the campground's other values it also matches (equipment and attributes: values that are part of it, `RV/MOTORHOME` also matches `RV`; campsite types: values that contain it, `STANDARD NONELECTRIC` also matches `GROUP STANDARD NONELECTRIC`); with Exact nothing (it matches itself only). The matching choice (`filterMatching`): a file without it shows "Contains (not set in this file: a search file without filterMatching uses Contains)", which is no edit; Exact or Contains writes the key (§13: a new key goes after the last property); choosing "not set" again is no edit; a file whose value is refused (§15) shows "Not Exact or Contains in the file (kept as it is until you choose)" and either choice writes over the refused text (`ConfigEditSession.MustRewrite`, also when the value it loads as is chosen).
- [V] **Include and exclude together.** The same value (exactly) in an include list and its exclude list is allowed, as the search allows it, with "Warning: also in includeEquipment: … A campsite that has it is left out, because an exclude list wins over an include list." under the exclude list; nothing resolves it.
- [V] **Loading** (`FilterChoiceSource`, one per Searches tab, made on the UI thread when the tab is first shown): `Read.FilterChoicesByCampground` on a worker thread (`Task.Run`), never the UI thread; the answer is posted to the dispatcher captured on the UI thread (D49). Only the file shown in the editor reads its campground's values (`SearchesViewModel.SelectedFile` activates it; a listed file reads nothing). States: no campground ("Choose a campground to pick from its equipment types. Values typed below are kept either way."), reading ("Reading this campground's equipment types…", an indeterminate bar), loaded ("11 equipment types at this campground, 3 checked."), failed (fixed text, the list kept, **Read the campground's values again** retries; a failure is not retried by edits). A newer request wins: each request has a number and an answer for an older one is ignored (choosing campgrounds quickly never shows an earlier campground's values). Values are kept per campground (FacilityID, ordinal) while `RecreationDotOrg.db` and its `-wal` file have the same length and write time; when the tab is shown again or the window activated, a changed database (a refresh by the console) is read again. Short lists (at most 16 rows) are shown whole; longer lists are bounded (320) and virtualized, with a find box (every word, ignoring case) and **Select all shown** / **Clear shown**, which change only the shown campground values.
- [V] **Keyboard and accessibility.** Each list is one tab stop (a `ListBox`): arrow keys move, Space checks or unchecks the focused value; the list's selection is only its keyboard cursor and has no fill (the focus outline shows it); a row's check box is not focusable and hidden from accessibility, and the row's accessible name is the value, its campsites and "checked", "not checked" or "partly checked", with what it also matches under Contains. The find box, the typed-value box, Add and each Remove name their list's key. The TD-39 workaround is unchanged and still holds with the selectors (`NavigationTests`, `MainWindowUsabilityTests`).
- [V] **Not part of it:** a database write (only reads), a search or availability request, a web request, normalizing or sorting a list, a per-list matching setting.
