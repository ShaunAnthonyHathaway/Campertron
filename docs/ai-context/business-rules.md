# Business rules

Legend: **[V]** verified in source · **[I]** inference (usually standard .NET semantics applied to the code) · **[?]** unknown

These rules describe **current behavior**, including the quirks. Do not change them unless the task asks for it (see CLAUDE.md).

## 1. Search config (`CampertronConfig`, `CampertronLibrary/class/Base/Config.cs`)
YAML keys are camelCase (`Yaml.CampertronConfigConvertFromYaml` uses `CamelCaseNamingConvention`) [V].

| Key | Type | Rule [V] |
|---|---|---|
| `displayName` | string | Shown in the header (`Cache.WriteProgress`). Output is sorted by it (`PostProcess` `OrderBy(p => p.Name)`) |
| `autoRun` | bool | Only `true` configs are loaded (`Yaml.CampertronConfigGetConfigs`) |
| `campgroundID` | string | RIDB `FacilityID`. If null, the search for that config is skipped (`GetAvailabilitiesByCampground`) |
| `totalHumans` | int? | Must satisfy `min_num_people ≤ totalHumans ≤ max_num_people`. [I] Lifted comparisons return false if any side is null, so null excludes everything |
| `searchBy` | `SearchTypes` | `DaysOut`, `MonthsOut`, `SpecificDates`, `Until`, `StartEndDate` |
| `searchValue` | int | Used by `DaysOut` and `MonthsOut` |
| `searchValueDates` | string list | Used by `SpecificDates`, `Until`, `StartEndDate` |
| `showMonday`…`showSunday` | bool | Day-of-week filter (`CampertronConfig.ShowThisDay`, matched on English `DayOfWeek.ToString()`) |
| `includeEquipment`/`excludeEquipment` | string list | §3 |
| `includeSites`/`excludeSites` | string list | Exact `CampsiteName` match |
| `includeAttributes`/`excludeAttributes` | string list | Matched against `"AttributeName:AttributeValue"` strings |
| `includeCampsiteType`/`excludeCampsiteType` | string list | §3 |
| `consecutiveDays` | int | `1` = single nights. `>1` = runs of N consecutive nights per campsite. See §4 for other values |

## 2. Search date generation (`CampertronConfig.GenerateSearchDates`, `GetMonthsOut`)
| SearchBy | Dates produced [V] |
|---|---|
| `DaysOut` | today … today+`searchValue` days, inclusive |
| `MonthsOut` | every day from today … today+`searchValue` months, inclusive |
| `StartEndDate` | `searchValueDates[0]` … `[1]`, inclusive. If start == end: prints "Start date and End date cannot be the same", waits for a key, then `Environment.Exit(0)`. [I] Fewer than 2 entries → `ArgumentOutOfRangeException` from the list indexer |
| `SpecificDates` | Each parseable entry (`Convert.ToDateTime`; failures print "Error converting {x} to DateTime"). An empty list or zero parseable entries → today only. These dates are **not** normalized with `ConvertToZeroHour` |
| `Until` | today … `searchValueDates[0]`. If that date is ≤ now → today only. [I] Empty list → `ArgumentOutOfRangeException` |
| other | `default:` branch switches to `SpecificDates`. [I] Unreachable for valid enum values |

- [V] `ConvertToZeroHour` builds the string `"{M}/{d}/{yyyy} 0:00:00 AM"` and parses it with `Convert.ToDateTime`. `ProcessMonth` builds `CheckDt` the same way. [I] Both parse with the current culture, so they assume a US-style M/d date format.
- [V] `GetMonthsOut` returns the number of months from now to the last search date and caps it at 12, printing "Results limited to 12 months out".
- [V] Months are queried for `i = 0..GetMonthsToCheck()`, and a month is skipped unless it contains a search date (`HasDatesDuringThisMonth`).

## 3. Availability filtering (`AvailabilityApi.ProcessMonth` + `FilterData`)
Availability parsing:
- [V] `CampsitesDataEntry.CalculateAvailableDates` (until the TD-40 fix the search used `GenerateDates`, which still exists with the same math): a day counts as available only if the status string is exactly `"Available"`.
- [V] A month's availability (`AvailabilityEntries`) is downloaded once per run and cached in `RunData.SiteData` by its URL (campground + month); every search of that campground and month gets **the same objects**. They are read-only after they are cached: each search derives its own dates into a new list (`AvailabilityApi.AvailableDatesBySite`, in the cached campsite order, entries with the same `campsite_id` kept as separate rows) and nothing writes back into the cached month (TD-40, fixed). Before the fix every search rewrote `CampsitesDataEntry.AvailabilityDates` on the shared objects, which could throw or silently drop results in parallel runs.
- [V] Day offsets assume the API's `availabilities` list covers the **last N days of the month**: `counter = DaysInMonth - availabilities.Count`.

Per day of the month, the campsites available that day are joined with the cached campsite list on `campsite_id == CampsiteID`. Then these rules apply, **in order** [V]:

1. **excludeCampsiteType** (if non-empty): keep the site only if `CampsiteType` contains **none** of the values (`All(y => !type.Contains(y))`, case-sensitive substring).
2. **includeCampsiteType** (if non-empty): keep the site only if `CampsiteType` contains **all** of the values (`All(y => type.Contains(y))`). Several values act as AND.
3. `FilterData`. Every condition must hold:
   - `totalHumans` within `[Minppl, Maxppl]`.
   - `CampsiteAvailableDate >= DateTime.Now`. Availability dates are local midnight, so **today is never matched** (except exactly at midnight) [I from the values].
   - The date is in `GetSearchDates()` (exact `DateTime` equality).
   - `ShowThisDay(date.DayOfWeek)`.
   - **includeEquipment**: passes if empty, or if some include value `s` and some permitted equipment `e` satisfy `s.Contains(e)`. Note the direction: the **config string contains the RIDB name**, ordinal and case-sensitive. A site with no permitted equipment fails a non-empty include.
   - **excludeEquipment**: passes if empty, or if **some** exclude value contains none of the site's equipment names. So the site is dropped only when **every** exclude value matches.
   - **includeSites** / **excludeSites**: exact `List.Contains(CampsiteName)`.
   - **includeAttributes** / **excludeAttributes**: same shapes as equipment, against `AttValuePairStr` (`"Name:Value"`, built by `Cache.ConvertAttributeValuePairToString`).
   - Duplicate check, **`outputTo: Email` only**: `Directory.Exists(ConfigPath/Camp.History/{yyyy}/{M}/{d}/{CampsiteID})` must be false (§5). Console, HtmlFile and UnitTest skip this check.
4. Matches are added to `RunData.FilteredAvailableData` (`AvailableData`). Check-in and check-out are taken from the attributes `"Checkin Time"` and `"Checkout Time"`.

## 4. Consecutive days
- [V] `consecutiveDays == 1`: hits are written immediately, with a month header and a calendar (`Calendar.GenerateCalendar`, only when `OutputTo == Console`) or "No entries found on {M}/{yyyy}".
- [V] `consecutiveDays > 1`: `FilterConsecutiveDays` groups `RunData.FilteredAvailableData` by `CampsiteID`, keeps groups with at least N entries, and uses `EnumerableExtensions.GetConsecutiveDays(N)` (`Calendar.cs`) to keep only dates that belong to runs of N or more consecutive days. Each campsite is printed once, followed by its dates and a calendar (Console only).
- [V] `GetConsecutiveDays` throws `ArgumentNullException` for null input and `ArgumentException("can't compare against less than 2")` for limits below 2. It is only called when the limit is above 1.
- [V] `consecutiveDays <= 0`: neither the `== 1` output branch nor the `> 1` filter runs. Hits go into `FilteredAvailableData` (so with `outputTo: Email` they create markers and can trigger email), but nothing is written to the output list.

## 5. Duplicate-notification suppression (`Load.HasNewEntries`, `AvailabilityApi.FilterData`)
`Camp.History` is the notification history of the Email loop, the only periodic mode (`outputTo: Email`; feature-inventory F5). One policy decides both sides: `Load.UsesNotificationHistory` (`internal`), true only when `GeneralConfig.OutputTo == Email` (a missing config or `GeneralConfig` is not Email). Since branch `fix/manual-search-notification-history` (2026-11-14):
- [V] Markers are **directories** at `ConfigPath/Camp.History/{yyyy}/{M}/{d}/{CampsiteID}`, with `/` hard-coded as the separator and no zero padding. The format is unchanged, so existing markers stay valid (`NotificationHistoryTests.EmailReadsAndWritesTheExistingMarkerLayout`).
- [V] **Email** (`FilterData`) drops any hit whose marker exists, and `HasNewEntries` creates the markers of the run's filtered hits. A campsite and date is therefore reported once; later cycles and later processes suppress it (the markers are on disk, so this survives restarts). The scope is global: date + campsite ID, shared by every search, every search file and every output type.
- [V] **Console, HtmlFile and UnitTest** (manual menu Search; tests) neither read nor write `Camp.History`: every run shows every current match, whatever ran before (an earlier Email, HtmlFile or UnitTest run, or markers already on disk), and leaves the markers exactly as they were. `HasNewEntries` still returns whether a hit has no marker; only the Email gate (§6) uses that result.
- [V] Availability that disappears is not reported (it is not in the month); its marker stays. If it reappears, Email keeps suppressing it: once reported, a campsite and date is never reported again (current rule, unchanged).
- [V] Markers are created **before** the email is attempted (`PostProcess` calls `HasNewEntries` first), so a failed email does not leave the hit eligible for the next run (TD-14).
- [V] Markers are never deleted by any code. Deleting the `Camp.History` directory resets the Email notification history; Campertron never does that itself.
- [V] Before this fix (from `15ffc1d`, 2024-01-21, through `v0.1.0-beta.9`): `HasNewEntries` wrote markers unless `OutputTo == Console` (since `87874a8`, 2024-09-14; before that for every type), and `FilterData` dropped marked hits for **every** output type. So a manual HtmlFile Search (or a UnitTest or Email run) hid those campsites and dates from every later manual Console and HtmlFile Search, which then reported "No entries found" / "No new matching availability to display." Markers written that way are left in place; they now affect only Email. Before `15ffc1d` (the 2023 JSON history), history applied to Email only.

## 6. Output and email gating (`Load.PostProcess`, `CampsiteConfig.ProcessConsoleConfig`)
- [V] Output runs if `OutputTo != Email`, or if (`Email` and `HasNewEntries` and `FilteredAvailableData.Count() > 0`).
- [V] `Load.OutputResults` takes the searches ordered by name (`OrderBy(Name)`, as before). **`HtmlFile`** (since beta.9, D29): one page for the whole run, written once and opened once (`CampsiteConfig.WriteAndOpenHtmlResults`). **`Email`, `Console`, `UnitTest`:** `ProcessConsoleConfig` once per search; for `Email` each call writes that search's page and sends one email with it as body and attachment (`CreateResultsEmail`). Each write deletes the old `*.html` directly in `CachePath` and writes a new `{guid}.html` there (`CampsiteConfig.WriteHtmlResults`). `CachePath` is `CampertronInternalConfig.CachePath` (`/cache` in a container; before the TD-05 fix always `LocalApplicationData/CampertronCache`). An unset `CachePath` throws `InvalidOperationException` before anything is written or opened; a missing cache directory is created, as before. Console and UnitTest output write no file.
- [V] **The HTML results page** (`ResultsHtml.Render`, D29) is built only from the values' presentation metadata (architecture.md §Search pipeline), so it shows the results the console would show for the same output streams, in the same order:
  - One HTML5 document: `lang="en"`, UTF-8, viewport, `color-scheme`, title "Campertron results", inline CSS, no script, no external reference. A header with the title and the number of searches ("2 searches") and, for several searches, a navigation list; no generation time, so the same streams always give the same page; one `section` with an `h2` per search (its display name, else the item name, else "Search N"), the campground, park and campground ID.
  - Single nights: an `h3` per month header and, within it, an `h4` per run of consecutive results with the same date (`<time datetime="yyyy-MM-dd">`, shown as "{weekday}, {short date}" in the current culture), each with a list of site cards: site, loop and type, equipment, booking link `https://www.recreation.gov/camping/campsites/{CampsiteID}` ("Book {site} on recreation.gov"). A bare site name is shown as "Site {name}".
  - Consecutive days (`consecutiveDays > 1`): one card per campsite in stream order, with an `h3`, the site details, its dates and the booking link. The dates of a card are sorted by date: `FilterConsecutiveDays` writes them in `ConcurrentBag` order, which is not stable. A date entry without its site part (possible with TD-04) still gets a card from the date's own metadata.
  - Counts are computed from the results shown: "N availability entries for M sites on K dates" (an entry is one site on one date). Check-in/out are shown once for the search when every result has the same values, otherwise per site.
  - Empty states read "No new matching availability to display.": under each month that has "No entries found", and once per search that shows no result and no such month (for example consecutive days, or no search date in range). The page does not say why (no availability or filters; for Email also `Camp.History` markers from earlier cycles, §5).
  - Every dynamic value is HTML-encoded (`WebUtility.HtmlEncode`); the campsite ID in links is URL-escaped first. Untyped values (`Kind == Text`): consecutive `Write` values are joined up to the next line end and shown as one encoded paragraph (`p.note`, muted and smaller than the results) when nonblank; blank or whitespace-only lines are dropped. Untyped text is never parsed for structure and never interpreted as markup. The console decorations (emoji, `***`, "Searching for entries", "No entries found", `Date:`/`URL:` labels) are not used. The console calendar is not part of the page.
  - Email: each email's body is the page of that one search only: a complete document with one `section`, no navigation list (it would link to searches that are not in the email), the header reading "1 search". The attachment is the file `WriteHtmlResults` wrote from the same string, so its bytes are the body as UTF-8 without a byte order mark (`HtmlResultsOutputTests`).
  - **Search attribution (TD-04, not fixed):** `ResultsHtml` renders the output streams it is given, one section per stream; it never rebuilds results from the shared `FilteredAvailableData` and does not move a value from one stream to another, so the combined page creates no new cross-search attribution. It cannot correct a stream that is already wrong when it arrives: if TD-04 (consecutive-day filtering on state shared across parallel searches) drops, adds or misattributes results upstream, the page shows that stream as it is. Dropping blank untyped lines removes the visible blank-line symptom of TD-04 from the page; it does not fix TD-04.
- [V] Email settings: `SmtpClient` with `EnableSsl = true`, `DeliveryMethod = Network`, `UseDefaultCredentials = false`, `NetworkCredential(SmtpUsername, SmtpPassword)`, subject `"Campertron Auto-Email"`, `IsBodyHtml = true`, HTML file attached as `application/octet-stream`.
- [V] Console: consecutive `WriteEmptyLine` items collapse to one blank line (`LastConfigType` check). No producer creates `WriteEmptyLine`.

## 7. Retry, back-off and termination (`AvailabilityApi.GetWebApiData`, `Data.DynamicDeserialize`)
| Condition | Behavior [V] |
|---|---|
| Any exception during fetch or parse | `catch` swallows it, then `Thread.Sleep(30000)` and retries **without limit** |
| Response body contains `REQUEST BLOCKED` (case-insensitive) | prints "Blocked by API for exceeding request limit, try again later", then `Thread.Sleep(300000)` and `Environment.Exit(0)` |
| Body contains "We are currently experiencing heavy traffic on our site" | prints "Heavy traffic...retrying in 1 second", then `Thread.Sleep(1000)` and a **recursive** re-fetch, without limit |
| Another thread is already fetching the same URL | polls `RunData.SiteData` every 500 ms **without limit** (`ProcessMonth`) |
| Email mode, between cycles | `Thread.Sleep(60000)` |
| HTTP status code | never checked. The body is read whatever the status [V] |

- [I] If a JSON response has no top-level property other than `count`, `ReceivedData` never becomes true and the `while (ReceivedData == false)` loop in `GetWebApiData` spins forever.

  The model classes (`class/RecDotOrg/*.cs`) and JSON loaders (`LoadJsonFromFile`) are kept but unused. Measured on the 2026-11-10 data, omitting the tables shrinks the DB from 345 MB to 226 MB; Media alone was about 92 MB including its index.
- [V] **Restoring an omitted table for a future feature:**
  1. Add its `DbSet<…>` back to `RecreationDotOrgContext` (`function/RecDotOrg/db/SqliteDb.cs`), and its composite key in `OnModelCreating` if the table above lists one.
  2. Add its import block back to `PopulateDbFromRIDBFiles.Populate`. The pre-removal version is in git history before commit `4215b79`.
  3. Add a `DELETE FROM` line for it to `Clear.ClearDatabase`.
  4. Remove it from `RidbDatabase.OmittedTables`. The validation then requires it to exist instead of being absent.
  5. Refresh and re-embed the DB (build-and-test.md §Refreshing the embedded database).

  The repair's `LegacyAddressLayout.KnownTables` keeps all 21 names on purpose, so it needs no change.
- [V] **Clearing before an import** (`Clear.ClearDatabase`, called during a refresh on the **staging** copy of the installed DB since TD-36, see *Failure-safe refresh* below): empties the 6 imported tables, runs `DROP TABLE IF EXISTS` for each omitted table, then `VACUUM`. A refresh of an older full DB therefore removes the omitted tables. Verified 2026-11-10 by refreshing a full 2024 DB.
- [V] **Writing the imported rows** (`RidbTableInserter`, decision D25, build-and-test.md §M). All six tables are inserted in one transaction, committed only after the last one. Rows go in EF Core's former `SaveChanges` order: tables by ordinal name, rows by the complete primary key (model key order, `Comparer<T>.Default` per component, so culture-sensitive for strings). The resulting database is byte-identical to the former EF import on the same export and culture; several queries have no `ORDER BY`, so this order is part of the observable behavior. A null row, a null key or a duplicate key fails the import and rolls back every insert. Since TD-36 part 1 was fixed (branch `fix/ridb-atomic-refresh`), the import runs on a staging copy, so a failed import leaves the **installed** DB unchanged (below); the extract directory remains, as before.
- [V] **Refresh-time validation** (`RidbDatabase.Validate`). It runs at the end of every `RefreshRidbRecreationData.RefreshData`, and in CI against the shipped DB (`EmbeddedDatabaseTests`). It checks that:
  - `PRAGMA integrity_check` returns `ok`
  - every table and column mapped by the EF model exists
  - none of the 15 omitted tables exists
  - `Read.UniqueStates` is non-empty and contains only two-letter codes (`^[A-Z]{2}$`)
  - `WATCHMAN CAMPGROUND` is returned by `Read.UniqueParks("UT", "SPRINGDALE")`.

  Since TD-36 part 1 was fixed, it runs against the **staging** DB, before anything installed is touched. If any check fails, `RefreshData` prints the problems in red, then "The installed database was not changed.", and returns `false`. It waits for a key only in an interactive console (`OutputTo` Console or HtmlFile, not in a container, input not redirected), so container, email and unit-test runs never block. The installed DB, the derived cache and `LastRidbDataRefresh` stay unchanged (before TD-36, the failed data was kept and the timestamp still updated). `RefreshData` changed from `void` to `bool`; no existing caller uses the result.
- [V] **Failure-safe refresh** (`RefreshRidbRecreationData.RefreshData` → `RidbStagedRefresh`, decision D26; TD-36 part 1, branch `fix/ridb-atomic-refresh`, 2026-11-11). The installed `RecreationDotOrg.db` stays usable and unchanged unless a complete new DB has been built, populated, validated, finalized and installed. Steps:
  1. **Refresh lock.** `ConfigPath/RecreationDotOrg.refresh.lock`, opened with `FileShare.None` and never deleted (no `DeleteOnClose`). If another process or refresh holds it, `RefreshData` prints "Another RIDB refresh is running (…). Nothing was changed." and returns `false` before downloading anything.
  2. **Stale staging cleanup** (under the lock, at refresh start only, never at startup): removes directories in `ConfigPath` named exactly `RecreationDotOrg.refresh-` + 32 lowercase hex digits (`Guid.ToString("N")`). Look-alikes (other GUID formats, upper case, suffixes, `RecreationDotOrg.repair-*`, files) are never touched; a link with a staging name is removed as a link, not followed. A directory that can't be removed is reported and left: each refresh uses a new path that must not exist yet, so a leftover can't be reused.
  3. Download and extraction, unchanged (`Web.Download`, `Compression.Unzip`).
  4. **Staging DB** `ConfigPath/RecreationDotOrg.refresh-<guid N>/RecreationDotOrg.db` (same directory, so the same filesystem, also in Docker `/config`). Template: an online backup (`SqliteConnection.BackupDatabase`, dedicated non-pooled connections) of the installed DB, which is only read; if no DB is installed, the bundled DB (`Load.ExtractEmbeddedDbTo`). An installed DB that can't be opened or copied (corrupt, unreadable) makes the refresh throw; it is not modified, and there is no new repair fallback.
  5. `Clear.ClearDatabase`, `PopulateDbFromRIDBFiles.Populate` (parsing, normalization, `RidbTableInserter`) and `RidbDatabase.Validate`, all unchanged, against the staging directory. The EF contexts' idle pooled staging connections are released with a targeted `SqliteConnection.ClearPool` after each step (`Validate` still calls `ClearAllPools`, as before). Then `PRAGMA wal_checkpoint(TRUNCATE)` finalizes the staging file.
  6. **Cache invalidation, before the installation:** every file directly in the configured `CachePath` is deleted (`Clear.ClearRefreshCache(InternalConfig.CachePath)`; TD-05 fixed, decision D27): `LocalApplicationData/CampertronCache` on the desktop (the same directory as before) and `/cache` in a container (before the fix, a container cleared `LocalApplicationData/CampertronCache` instead, so a refresh aborted there or left stale derived files in `/cache`; build-and-test.md §N). Subdirectories, the directory itself and anything outside it are kept; a link is unlinked, never followed. If deleting fails (a missing directory, a permission error), the refresh throws before the installation; there is no fallback directory. A crash after this step leaves the old DB with an empty cache, which is rebuilt on demand, and no path leaves the new DB with cache files derived from the old one, on the desktop and in a container (kill harness, §N; Docker kills, §O). **Guards** (nothing deleted, `InvalidOperationException`): `RefreshData` checks `CachePath` right after `ConfigPath`, before the refresh lock and the download (`Clear.CheckCacheDirectory`: unset or whitespace, a filesystem root, or the same directory as `ConfigPath` after full-path normalization); `ClearRefreshCache` re-checks the path and refuses a directory that contains `RecreationDotOrg.db` or `General.yaml`, which catches a config directory reached through a link or the same bind mount.
  7. **Installation** under `ConfigPath/RecreationDotOrg.repair.lock` (the startup repair's lock, opened with `FileShare.None`; if held, the refresh throws `IOException` and nothing is installed): `BackupDatabase` from the staging DB into the installed DB on dedicated non-pooled connections, with `PRAGMA busy_timeout` = `RidbStagedRefresh.InstallBusyTimeoutMilliseconds` (30,000 ms) on the destination. This is one SQLite write transaction: it commits completely or leaves the installed DB as it was, also after a crash. If no DB was installed, the bundled DB is first extracted to the installed path (the same write-then-move as on a first start, so the path never holds an empty or partial file) and removed again, with any `-wal`/`-shm`/`-journal` files, if the backup into it fails. The installed DB is never renamed, replaced or deleted otherwise.
  8. Best-effort `PRAGMA wal_checkpoint(TRUNCATE)`. A reader that still uses the previous snapshot keeps it from completing ("Another connection is still reading the previous data; …"); that is not a failure, and SQLite completes it later. WAL and SHM files are never touched by hand.
  9. `PRAGMA quick_check` on a new connection. If it is not `ok`, `RefreshData` reports it, keeps the staging DB for inspection, does not update `General.yaml` and returns `false`; there is no automatic rollback.
  10. The staging directory is removed (best effort, after its connections are closed), the lock released.
  11. **`LastRidbDataRefresh`** is set and `General.yaml` written **once**, only now, with `Yaml.GeneralConfigReplaceYaml` (TD-37 fix): the complete document (same serializer, same bytes as `GeneralConfigConvertToYaml`) is written to `General.yaml.<32 hex>.tmp` in `ConfigPath`, flushed (`StreamWriter.Flush`, `FileStream.Flush(flushToDisk: true)`), closed, read back and validated (identical text, deserializes, re-serializes identically), and only then moved over `General.yaml` with `File.Move(…, overwrite: true)` (`ConfigFileReplace.Replace`); `General.yaml` is never truncated or deleted first. On any failure the old `General.yaml` stays as it was and the temporary file is removed on a best-effort basis (a cleanup failure is reported without hiding the original exception). If the write fails (I/O, permission, validation or YAML error), the refresh still returns `true` with the warning "The RIDB database refresh succeeded, but General.yaml could not be updated (…). The next start may refresh again."; the installed DB is kept. The in-memory `GeneralConfig` (shared with View Config) gets the new timestamp either way, because the installed data is new. Temporary files left by a killed process are never read (the loaders read `General.yaml` and `*.yaml`) and are removed at the start of the next refresh, under the refresh lock (exact names only). On Unix, a read-only `General.yaml` *file* no longer blocks the update (the rename needs write permission on the directory); on Windows, `MoveFileEx` refuses to replace a read-only file [I, not tested].

  **Lock order:** the refresh lock first (whole refresh), the repair lock second (installation only). `LegacyAddressLayout.RepairIfNeeded` takes only the repair lock and runs in `DbExistsCheck` before the auto-refresh, after releasing it; nothing takes the refresh lock while holding the repair lock. While a refresh holds the repair lock, a startup repair in another process fails to open it, reports "Could not check or repair …" and leaves the DB unchanged (checked again on the next start).

  **Busy installation** [V]: `BackupDatabase` performs one `sqlite3_backup_step(-1)` and does not apply Microsoft.Data.Sqlite's `Default Timeout` (that applies to commands); SQLite's busy timeout on the destination connection does apply. A competing write transaction makes the installation wait up to the busy timeout and then throw `SqliteException` with `SqliteErrorCode` 5 (`SQLITE_BUSY`); the installed DB stays byte for byte unchanged. `SQLITE_LOCKED` arises only within one connection or a shared cache, which the installation does not use.

  **Failures** keep the existing behavior: exceptions propagate (as before), and only validation, a held refresh lock and a failed `quick_check` return `false`. On every failure before the installation, the installed DB, `General.yaml` and (before step 6) the cache are unchanged and the staging directory is removed. Readers in other processes keep a consistent snapshot during the installation and see the new data with their next transaction; pooled idle connections (the GUI's) need no closing.

  **Replacement guarantees** (`ConfigFileReplace`, TD-37): .NET implements `File.Move(…, overwrite: true)` with `rename(2)` on Linux and macOS (`FileSystem.Unix.cs`; the copy-and-delete fallback is only for `EXDEV`, impossible within one directory). POSIX requires that the destination name always refers to the old or the new file and is unaffected if `rename` fails (except `EIO`). `Flush(true)` is `fsync`, `F_FULLFSYNC` on macOS (`pal_io.c`). On Windows it is `MoveFileExW(MOVEFILE_COPY_ALLOWED | MOVEFILE_REPLACE_EXISTING)` without `MOVEFILE_WRITE_THROUGH`; Microsoft documents no atomicity for it. **Verified:** process termination at every tested point of the write (Linux x64, btrfs; kill harness, build-and-test.md §N) left the complete old or complete new `General.yaml` and a working next start. **Not guaranteed:** power loss (the directory is not fsynced after the rename, so the old file may reappear; acceptable, it is valid), Windows and macOS behavior (not tested). The other YAML writers (`Email.yaml`, search configs, the sample `General.yaml`) still truncate and rewrite in place (TD-37).

- [V] **One-time startup repair of installed DBs** (`LegacyAddressLayout.RepairIfNeeded(ConfigPath, CachePath)`, called from `Load.DbExistsCheck` whenever `RecreationDotOrg.db` already exists, before the auto-refresh check; console and GUI both start through `Load.GetConfig`). It replaces a DB that no current Campertron would produce with the bundled DB, keeping the old one as a backup. Generalized from the legacy-layout repair on branch `fix/repair-stale-ridb-on-upgrade` (2026-11-11).
  - **Layout detection** looks only at DB contents (`FacilityAddressesEntries.PostalCode` and `AddressStateCode`, trimmed and uppercased; empty values ignored), with at least 100 non-empty values in each column:
    - **Legacy:** at least 95% of `PostalCode` values are 2-letter codes (`^[A-Z]{2}$`) and at least 95% of `AddressStateCode` values are ZIP codes (`^[0-9]{5}(-?[0-9]{4})?$`).
    - **Corrected:** at least 95% of `AddressStateCode` values are 2-letter codes and at most 5% of `PostalCode` values are.
    - **Unknown:** anything else (too few rows, mixed layouts, other values).
    - Measured 2026-11-10: the 2024-11-18 DB has 15,924 of 15,933 `PostalCode` values as 2-letter codes and 6,738 of 6,757 `AddressStateCode` values ZIP-like (**Legacy**). The 2026-11-10 DB has 0 of 7,248 and 0 of 16,353 (**Corrected**).
  - **Repair reasons** (`DetectRepairReason`). Anything else is **never** replaced, including Unknown layouts and any valid DB, however much it differs from the bundled one:
    - **LegacyLayout:** the layout is Legacy (the swapped 2024-11-18 export).
    - **ObsoleteTables:** the layout is Corrected **and** at least one of the 15 `RidbDatabase.OmittedTables` exists. Only code from before PR #17 created those tables (every release before 0.1.0-beta.4, and every 2024 importer), and every current refresh drops them (`Clear.ClearDatabase`). So their presence marks a DB that no current version writes, and a later "Refresh Ridb Data" with a current version can never trigger this reason.
    - **Why not a state-value trigger:** non-normalized GUI states are reported (`NonNormalizedGuiStates`, in the message) but **don't trigger a replacement by themselves**. The current importer passes unmappable values through unchanged: 8 × `STATE MAPPING BROKEN` and 1 × `ILE-DE-FRANCE` in the 2026-11-10 data, which aren't listed today only because none belongs to a reservable campground. A future export could list one. A state-based trigger would then replace that user's newer refresh with the older bundled DB on every start.
  - **The DB must contain only objects Campertron creates:** the 21 RIDB tables, `__EFMigrationsHistory`, `sqlite_sequence` and SQLite's automatic primary-key indexes on them (`LegacyAddressLayout.KnownTables`). Any other table, view, trigger or index means the DB was changed outside Campertron. It is then **not** replaced, and a message tells the user to run "Refresh Ridb Data". Campertron itself stores no user data in this DB: the only writers are the embedded-DB extraction, `Clear.All` and `PopulateDbFromRIDBFiles`.
  - **Replacement steps.** Every step happens in `ConfigPath`, so all moves stay on one filesystem:
    1. Take an exclusive lock file, `RecreationDotOrg.repair.lock` (deleted on close). If another process holds it, skip.
    2. Re-run the detection; the reason must be unchanged.
    3. Extract the bundled DB to `RecreationDotOrg.repair-<guid>/`. **It must pass `RidbDatabase.Validate`, be Corrected, contain only known objects and need no repair itself**; otherwise skip, and remember the result for the rest of the process. "Needs no repair itself" guarantees the replacement is final, so the repair can't loop.
    4. `PRAGMA wal_checkpoint(TRUNCATE)` on the old DB. If another connection prevents it, or the DB can't be opened for writing, skip.
    5. Rename the old DB (and any `-wal`/`-shm` files) to `RecreationDotOrg.db.legacy-layout-<yyyyMMddHHmmss UTC>.bak` (LegacyLayout) or `RecreationDotOrg.db.pre-0.1.0-beta.4-<yyyyMMddHHmmss UTC>.bak` (ObsoleteTables).
    6. Move the extracted DB into place. If this fails, the backup is moved back.
    7. Remove the derived cache files (below), then remove the temporary directory.
  - **One-time by construction.** No marker file and no version comparison are used. After a replacement, the installed DB is the bundled one, which needs no repair. After any later refresh with a current version there are no omitted tables either. So the next start does nothing.
  - **Cache.** The JSON cache (`CachePath`) holds per-campground files derived from the DB: `{CampgroundID}-CampInfo.json`, `-Campsites.json`, `-CampsitesByPark.json`, `-Cached.json`, and `{CampsiteID}-Equipment.json` and `-Attributes.json`. `Cache.CacheExist` only checks for `-Cached.json`, so these files would otherwise keep serving the old data indefinitely. After a **successful** replacement (either reason), exactly the files with these suffixes are deleted (`LegacyAddressLayout.ClearDerivedCache`), and searches rebuild them. Other files in the cache directory (for example `{guid}.html` results) and everything in `ConfigPath` are left alone. A file that can't be deleted is reported and left; the repair stands. *Before this change, the legacy repair left the cache in place.*
  - **Data-loss considerations:**
    - Nothing in `ConfigPath` is deleted. The old DB is kept byte for byte as the `.bak` file (about 328–355 MB), which the user can delete. `General.yaml`, `Email.yaml`, search YAML files and `Camp.History` are never touched.
    - I/O, permission and SQLite errors are caught. The DB is then left unchanged and a message is printed. The console shows these messages; the GUI (`WinExe`) does not.
    - [I] If the move back after a failed swap also fails, `RecreationDotOrg.db` is missing. The next start then extracts the bundled DB as on a first run, and the `.bak` file is still present.
  - **Cost** [V] (2026-11-11, Release library, median of 15 calls on real DBs): the layout scan that the repair has always done takes 12.9 ms (current DB) / 13.9 ms (stale DB). The new omitted-table check adds 0.25 / 0.29 ms, for 14.0 / 14.3 ms in total. The first call in a process takes about 70 ms, which includes one-time SQLite setup. A whole normal start of the published console (`outputTo: UnitTest`) took 148–151 ms. Only an actual repair pays for extracting and validating the bundled DB (`integrity_check` included): 2.45 s for the whole first start of the published console.

## 9. Config bootstrap rules
- [V] If no `autoRun: true` search YAML exists, `ZionConfig.yaml` is generated, **overwriting** any existing file with that name (`Yaml.CampertronConfigGenerateSampleConfig` uses `StreamWriter`).
- [V] Auto-refresh condition: `AutoRefresh && UtcNow - RefreshRidbDataDayInterval days > LastRidbDataRefresh` (`Load.DbExistsCheck`). The sample sets `LastRidbDataRefresh` to 50 years ago, so enabling `autoRefresh` triggers a refresh on the next start. Since TD-36 part 1 was fixed, `DbExistsCheck` no longer writes `LastRidbDataRefresh` before the refresh; only a successful installation writes it (§8). A refresh that fails, or is skipped because another refresh holds the lock, is therefore retried on the next start (before, the pre-write suppressed retries for the whole interval).
- [V] Container detection relies on `DOTNET_RUNNING_IN_CONTAINER` or `DOTNET_RUNNING_IN_CONTAINERS`. [I] The official .NET container images set the first of these.

## 10. Compatibility with versions before 0.1.0-beta.4
- [V] All versions use the same data folder (`LocalApplicationData/CampertronConfig`, or `/config` in a container) and the same `RecreationDotOrg.db` file name. A newer version does not keep a separate database.
- [V] The 2024 versions (`v0.1-beta1`/`v0.1-beta3` downloads, code up to `e96bc7c`; `v0.1-beta3` is `net9.0`) read the state from `FacilityAddresses.PostalCode`. In the corrected address layout (§8), `PostalCode` holds ZIP codes. That layout is in the DB that 0.1.0-beta.4 and later extract or install by repair, and in any DB refreshed from current RIDB data, whichever version ran the refresh. **A 2024 GUI reading such a DB lists ZIP codes as states** (for example `01005` → city BARRE; MA lists nothing). Measured 2026-11-11 with the 2024 library: 1,185 ZIP-like "states" on the beta.4 DB, and 1,171 on a copy of a real data folder's refreshed DB. The 2024 console shows `Framework => .NET 9.x` in View Config (`.NET 9.0.0` for the self-contained `v0.1-beta3` download).
- [V] Nothing in a newer version can prevent this: the 2024 binaries can't be changed, and they don't check anything a newer version could write (decisions D20). The protection is documentation: the required "Compatibility with older versions" section of every release's notes (`render_notes`/`validate_notes`) tells users not to keep or run old copies, and `--version` (§11) identifies a copy. The README carried the same warning until 2026-11-11, when it was rewritten for current users and the note was removed at the maintainer's request.
- [V] Running a 2024 version first and a newer version afterwards is handled at startup (§8): a DB with the swapped 2024 layout is replaced by 0.1.0-beta.4 and later. A DB refreshed by a 2024 version (corrected layout, 15 omitted tables, un-normalized states) is replaced since branch `fix/repair-stale-ridb-on-upgrade`. Before that, beta.4 and beta.5 kept it until a manual refresh.
- [I] A 2024 version's in-app "Refresh Ridb Data" re-imports all 21 tables with its old normalization (states un-normalized in `AddressStateCode`). A newer version classifies that DB as Corrected and doesn't repair it; how a newer version then shows it is measured in §8.

- [V] `RuntimeInfo.IsVersionRequest(args)` is true only for exactly one argument, `--version` (case-sensitive). Any other arguments are ignored as before, and the normal startup runs.
