## 2. Search date generation (`CampertronConfig.GenerateSearchDates`, `GetMonthsOut`)
| SearchBy | Dates produced [V] |
|---|---|
| `DaysOut` | today … today+`searchValue` days, inclusive |
| `MonthsOut` | every day from today … today+`searchValue` months, inclusive |
| `StartEndDate` | `searchValueDates[0]` … `[1]`, inclusive. If start == end: throws `ArgumentException("search "{displayName}": Start date and End date cannot be the same.")` (since D37, TD-45 resolved), so the search file is reported like any other unusable one (§12): "Error: {file} could not be used: search "{displayName}": Start date and End date cannot be the same.", the file and what to do, no key wait, exit code 1, on a terminal and in a log alike. Equal dates stay an error (treating them as one night would be a product change). Before D37 it wrote the error, waited for a key and called `Environment.Exit(0)`; with redirected input the key wait threw and a second error followed (exit 1). [I] Fewer than 2 entries → `ArgumentOutOfRangeException` from the list indexer |
| `SpecificDates` | Each parseable entry (`Convert.ToDateTime`; failures write "Warning: search "{displayName}": "{x}" in searchValueDates is not a date and is ignored."; before D34 "Error converting {x} to DateTime"). An empty list or zero parseable entries → today only. These dates are **not** normalized with `ConvertToZeroHour` |
| `Until` | today … `searchValueDates[0]`. If that date is ≤ now → today only. [I] Empty list → `ArgumentOutOfRangeException` |
| other | `default:` branch switches to `SpecificDates`. [I] Unreachable for valid enum values |

- [V] Since D35 (TD-11) every date the search builds itself is built from numbers, independent of the culture and its calendar: `ConvertToZeroHour` returns `new DateTime(year, month, day)` (midnight, `DateTimeKind.Unspecified`: the same values the former parse of `"{M}/{d}/{yyyy} 0:00:00 AM"` gave in en-US), the requested month is `AvailabilityApi.MonthStart` (the first of the month) and its URL is written with the invariant culture (`AvailabilityApi.MonthUrl`). Before, both were parsed from text with the current culture: under en-GB, en-AU, de-DE, fr-FR and es-MX every `DaysOut`, `MonthsOut`, `Until` and `StartEndDate` search failed with `FormatException`, the month became January, and fa-IR wrote the month of its Persian calendar into the URL.
- [V] **User-written `searchValueDates` are still parsed with `Convert.ToDateTime` and the current culture, including its calendar** (unchanged contract). Measured 2026-11-14: `2026-11-20` is read as 20 November 2026 in en-US, en-GB, en-AU, de-DE, fr-FR, es-MX, ja-JP and the invariant culture, but as a date of the Thai Buddhist calendar in th-TH and of the Persian calendar in fa-IR; `11/20/2026` fails in en-GB, en-AU, de-DE, fr-FR and es-MX, and `11/5/2026` is 11 May there. So `yyyy-MM-dd` is the spelling to recommend (examples/0.1/README.md).
- [V] The search dates are generated when `Load.Preload` loads the searches (a menu Search does that every time). **The Email loop regenerates them before every check after the first** (since D35, TD-46: `Load.RegenerateSearchDates` → `CampertronConfig.RegenerateSearchData` with the current time), so its `DaysOut`, `MonthsOut` and `Until` windows (and the "today only" fallbacks) roll forward while it runs; written dates keep their meaning. The search files are still read once per start, and a search's warnings (12-month cap, invalid dates) are written only when it is loaded. Before D35 the dates stayed those of the start, so a `DaysOut 30` window was empty after 30 days of uptime.
- [V] `GetMonthsOut` returns the number of months from now to the last search date and caps it at 12, writing "Warning: search "{displayName}": results are limited to 12 months out." (before D34 "Results limited to 12 months out").
- [V] Months are queried for `i = 0..GetMonthsToCheck()`, and a month is skipped unless it contains a search date (`HasDatesDuringThisMonth`).

## 3. Availability filtering (`AvailabilityApi.ProcessMonth` + `FilterData`)
Availability parsing:
- [V] `CampsitesDataEntry.CalculateAvailableDates` (until the TD-40 fix the search used `GenerateDates`, which still exists with the same math): a day counts as available only if the status string is exactly `"Available"`.
- [V] A month's availability (`AvailabilityEntries`) is downloaded once per run and cached in `RunData.SiteData` by its URL (campground + month); every search of that campground and month gets **the same objects**. They are read-only after they are cached: each search derives its own dates into a new list (`AvailabilityApi.AvailableDatesBySite`, in the cached campsite order, entries with the same `campsite_id` kept as separate rows) and nothing writes back into the cached month (TD-40, fixed). Before the fix every search rewrote `CampsitesDataEntry.AvailabilityDates` on the shared objects, which could throw or silently drop results in parallel runs.
- [V] Day offsets assume the API's `availabilities` list covers the **last N days of the month**: `counter = DaysInMonth - availabilities.Count`.

Per day of the month, the campsites available that day are joined with the cached campsite list on `campsite_id == CampsiteID`. Then these rules apply, **in order** [V]:

**The eight include and exclude lists** (`SearchFilters`, decision D51, 2026-11-16; an intentional correction of the search rules). [V]
- **OR semantics for every list.** An include list keeps a campsite when **any** of its values matches **any** of the campsite's values; an exclude list drops a campsite when **any** of its values matches. A missing (null) or empty list is no filter. Duplicates and the order of the values change nothing. An include value that nothing has hides every campsite of that list's kind (as before); an exclude value that nothing has removes nothing.
- **Before D51** (every release through `v0.1.0-preview.1`): `excludeEquipment` and `excludeAttributes` dropped a campsite only when **every** value matched (`Any(s1 => !equipment.Any(s1.Contains))`), and `includeCampsiteType` kept one only when its type matched **every** value (`All(y => type.Contains(y))`), so two types never matched together; the other five lists were already OR. Open questions #5 and #6 asked whether that was intended; the maintainer answered no (D51). A file that listed several values in one of those three lists finds different campsites since D51: more for `includeCampsiteType`, fewer for the two exclude lists.
- **The values are matched by the search's `filterMatching`** (§1), always ordinally: case, spaces and punctuation count, nothing is trimmed or normalized.
  - **`Exact`:** the value equals the campsite's equipment name, campsite name, `"Name:Value"` attribute or campsite type, character for character.
  - **`Contains`** (also a file without `filterMatching`): the matching before D51, in its direction per list. An equipment or attribute value **contains** the campsite's equipment name or `"Name:Value"` (the list value is the longer one: `RV/MOTORHOME` matches a campsite that permits `RV`, `Shade:Yes` matches one whose `Shade` value is blank, `"Shade:"`); a campsite type **contains** the value (`GROUP` matches `GROUP STANDARD NONELECTRIC`); a campsite name **equals** the value, as it always did. Campsite names stay exact because a `Contains` reading of names would change what every existing file finds (`1` would match `10` to `19`), and existing files are read with `Contains`.
  - A null value on either side matches nothing (the search no longer throws on one; the validation still refuses an empty item of the six lists other than the campsite names, §15). The campground data has no null names, types, equipment or attribute names or values (shipped data, 2026-11-16).

1. **excludeCampsiteType** and **includeCampsiteType** (if either is non-empty): `SearchFilters.KeepsCampsiteType`, the campsite's `CampsiteType` against both lists as above.
2. `FilterData`. Every condition must hold:
   - `totalHumans` within `[Minppl, Maxppl]`.
   - `CampsiteAvailableDate >= DateTime.Now`. Availability dates are local midnight, so **today is never matched** (except exactly at midnight) [I from the values].
   - The date is in `GetSearchDates()` (exact `DateTime` equality).
   - `ShowThisDay(date.DayOfWeek)`.
   - **The equipment, campsite-name and attribute lists** (`SearchFilters.KeepsCampsite`), as above: `includeEquipment`/`excludeEquipment` against the campsite's permitted equipment names (a campsite with no permitted equipment fails a non-empty include and is never excluded), `includeSites`/`excludeSites` against its `CampsiteName`, `includeAttributes`/`excludeAttributes` against its `AttValuePairStr` (`"Name:Value"`, built by `Cache.ConvertAttributeValuePairToString`; a null value gives `"Name:"`).
   - Duplicate check, **the unattended monitoring only** (`outputTo: Email` or, since D67, `Ntfy`): `Directory.Exists(ConfigPath/Camp.History/{yyyy}/{M}/{d}/{CampsiteID})` must be false (§5). Console, HtmlFile and UnitTest skip this check. Since D104 (TD-61) a search with `consecutiveDays` above 1 skips it too: its stays are checked whole after they are built (§4).
3. Matches are added to the search's own hits (`AvailableData`, a per-search `ConcurrentBag` since D35). After the search, and after its consecutive filter (§4), its final hits are added to `RunData.FilteredAvailableData`, the run's set that the Email gate and the markers use (§5, §6); no search reads or replaces another search's hits (TD-04, fixed). Check-in and check-out are taken from the attributes `"Checkin Time"` and `"Checkout Time"`.

## 4. Consecutive days
- [V] `consecutiveDays == 1`: hits are written immediately, with a month header and a calendar (`Calendar.GenerateCalendar`, only when `OutputTo == Console`) or "No entries found on {M}/{yyyy}".
- [V] `consecutiveDays > 1`: `FilterConsecutiveDays` groups **this search's own hits** (since D35; before, `RunData.FilteredAvailableData`, the hits of every search of the run so far: TD-04, which gave false two-night openings, other campgrounds' campsites, removed hits and a missed Email notification) by `CampsiteID`, keeps groups with at least N entries, and uses `EnumerableExtensions.GetConsecutiveDays(N)` (`Calendar.cs`) to keep only dates that belong to runs of N or more consecutive days. Each campsite is printed once, followed by its dates and a calendar (Console only).
- [V] **Stays and the notification history** (since D104, 2026-11-24; TD-61 fixed): in the unattended monitoring, a search with `consecutiveDays` above 1 builds its stays from every night it keeps, notified or not (`FilterData` skips the history for it, §3); a stay is a longest run of consecutive nights of one campsite (`GetConsecutiveDays`: every run of N or more nights, whole). `FilterConsecutiveDays` keeps a stay whole when any of its nights has no `Camp.History` marker and drops it when every night has one (§5).
  So a stay notified before stays suppressed while it stays available; a longer stay with a night never notified, a stay whose middle night was booked and freed again (re-armed, §5), a stay that disappeared and came back, and another search's stay over nights a one-night search notified are notified, each shown whole. The markers of every night it shows are written after delivery, as for any opening (§5).
  Before D104 `FilterData` dropped the notified nights before the stays were built, so such a stay was never notified, even a night of it that never was (TD-61). Manual searches (no history) and `consecutiveDays` of 1 or below are unchanged.
- [V] `GetConsecutiveDays` throws `ArgumentNullException` for null input and `ArgumentException("can't compare against less than 2")` for limits below 2. It is only called when the limit is above 1.
- [V] `consecutiveDays <= 0`: neither the `== 1` output branch nor the `> 1` filter runs. Hits go into `FilteredAvailableData` (so with `outputTo: Email` they can trigger email and, since D36 only after every email of the check was sent, create markers; since D67 likewise in ntfy mode, which sends no message for them, after a check that no provider failed, §28), but nothing is written to the output list.

## 5. Duplicate-notification suppression (`AvailabilityApi.FilterData`, `Load.ReportResults`, `Load.OutputResults`, `Load.RecordNotificationHistory`)
`Camp.History` is the notification history of the Email loop, the only periodic mode (`outputTo: Email` and, since D67, `outputTo: Ntfy`, the unattended monitoring; feature-inventory F5). One policy decides both sides: `Load.UsesNotificationHistory` (`internal`), true only when `GeneralConfig.OutputTo` is `Email` or, since D67, `Ntfy` (`Notifications.IsMonitoring`; a missing config or `GeneralConfig` is neither). Since branch `fix/manual-search-notification-history` (2026-11-14):
- [V] Markers are **directories** at `ConfigPath/Camp.History/{yyyy}/{M}/{d}/{CampsiteID}`, with `/` hard-coded as the separator and no zero padding. The format is unchanged, so existing markers stay valid (`NotificationHistoryTests.EmailReadsAndWritesTheExistingMarkerLayout`).
- [V] **The monitoring** (`FilterData`) drops any hit whose marker exists (a search of consecutive nights: whole stays, §4), and writes the markers of what it reported, only after delivery (next bullet). A campsite and date is therefore reported once while it stays available; later checks and later processes suppress it (the markers are on disk, so this survives restarts) until a check sees it unavailable (re-arming, below). The scope is global: date + campsite ID, shared by every search, every search file and every output type.
- [V] **Markers only after delivery** (since D36, branch `fix/email-history-after-delivery`; TD-14 resolved). The invariant: an opening is recorded in `Camp.History` only after its notification email was delivered, which means that the send (`CampsiteConfig.SendResultsEmail`, `SmtpClient.Send`) returned: the SMTP server accepted the message; Campertron cannot know whether it reached the inbox. The Email gate (§6) only reads the history (`Load.HasUnreportedEntries`). `Load.OutputResults` sends one email per search; right after a search's email was sent it records the openings that email shows (the date and campsite of its `Availability` and `ConsecutiveDate` values; `Load.RecordNotificationHistory`). After every email of the check was sent, `Load.ReportResults` records the rest of the run's final hits (`RunData.FilteredAvailableData`: hits no email shows, such as those of a search with `consecutiveDays` below 1, §4), so a fully successful check writes exactly the markers it wrote before D36. A search with nothing new still gets its email (one per search, TD-06) and records nothing.

With email only, everything above is unchanged.
- [V] **Partial success:** when an email fails, the emails sent before it keep their markers (nothing is rolled back); the failed email's openings, those of the emails after it (not attempted) and the run's remaining hits stay unrecorded, so they are reported again by the next check, which, because the failure still ends the process (exit 1, "Error: the email could not be sent: …", §12; no retry), is the next start. [V from the code] An opening shown by a delivered email is recorded even if another search's email that also shows it failed: the scope is global and it was reported.   - **Evidence only from what the check fetched and read.** A month is in `RunData.SiteData` once its answer was received and read; a request that failed, was blocked or was stopped leaves nothing there, and a check that did not complete (a stop, a block, a failed search) never reaches its report. If another process or refresh holds it, `RefreshData` prints "Another RIDB refresh is running (…). Nothing was changed." and returns `false` before downloading anything.

Look-alikes (other GUID formats, upper case, suffixes, `RecreationDotOrg.repair-*`, files) are never touched; a link with a staging name is removed as a link, not followed. In a container `LocalApplicationData` is `""` unless `/home/app/.local/share` exists, so until D99 the folder was `CampertronExtract` relative to `/app`; since D99 (D85 point 5, open question #27) a refresh in the container downloads and extracts into the cache folder, the mounted `/cache` (`RidbRefreshRequest.InContainer`, `RidbRefreshService.DefaultWorkRoot`; below).

Template: an online backup (`SqliteConnection.BackupDatabase`, dedicated non-pooled connections) of the installed DB, which is only read; if no DB is installed, the bundled DB (`Load.ExtractEmbeddedDbTo`). An installed DB that can't be opened or copied (corrupt, unreadable) makes the refresh throw; it is not modified, and there is no new repair fallback.

The EF contexts' idle pooled staging connections are released with a targeted `SqliteConnection.ClearPool` after each step (`Validate` still calls `ClearAllPools`, as before). Then `PRAGMA wal_checkpoint(TRUNCATE)` finalizes the staging file.
  6. **Cache invalidation, before the installation:** every file directly in the configured `CachePath` is deleted (`Clear.ClearRefreshCache(InternalConfig.CachePath)`; TD-05 fixed, decision D27): `LocalApplicationData/CampertronCache` on the desktop (the same directory as before) and `/cache` in a container (before the fix, a container cleared `LocalApplicationData/CampertronCache` instead, so a refresh aborted there or left stale derived files in `/cache`; history/validation/a-w_2026-11-10_to_beta.10.md §N). Subdirectories, the directory itself and anything outside it are kept; a link is unlinked, never followed. If deleting fails (a missing directory, a permission error), the refresh throws before the installation; there is no fallback directory. A crash after this step leaves the old DB with an empty cache, which is rebuilt on demand, and no path leaves the new DB with cache files derived from the old one, on the desktop and in a container (kill harness, §N; Docker kills, §O). **Guards** (nothing deleted, `InvalidOperationException`): `RefreshData` checks `CachePath` right after `ConfigPath`, before the refresh lock and the download (`Clear.CheckCacheDirectory`: unset or whitespace, a filesystem root, or the same directory as `ConfigPath` after full-path normalization); `ClearRefreshCache` re-checks the path and refuses a directory that contains `RecreationDotOrg.db` or `General.yaml`, which catches a config directory reached through a link or the same bind mount.
  7. **Installation** under `ConfigPath/RecreationDotOrg.repair.lock` (the startup repair's lock, opened with `FileShare.None`; if held, the refresh throws `IOException` and nothing is installed): `BackupDatabase` from the staging DB into the installed DB on dedicated non-pooled connections, with `PRAGMA busy_timeout` = `RidbStagedRefresh.InstallBusyTimeoutMilliseconds` (30,000 ms) on the destination. This is one SQLite write transaction: it commits completely or leaves the installed DB as it was, also after a crash. If no DB was installed, the bundled DB is first extracted to the installed path (the same write-then-move as on a first start, so the path never holds an empty or partial file) and removed again, with any `-wal`/`-shm`/`-journal` files, if the backup into it fails. The installed DB is never renamed, replaced or deleted otherwise.
  8. Best-effort `PRAGMA wal_checkpoint(TRUNCATE)`. A reader that still uses the previous snapshot keeps it from completing ("Another connection is still reading the previous data; …"); that is not a failure, and SQLite completes it later. WAL and SHM files are never touched by hand.
  9. `PRAGMA quick_check` on a new connection. If it is not `ok`, `RefreshData` reports it, keeps the staging DB for inspection, does not update `General.yaml` and returns `false`; there is no automatic rollback.
  10. The staging directory is removed (best effort, after its connections are closed), the lock released.
  11. **`LastRidbDataRefresh`** is set and `General.yaml` written **once**, only now, with `Yaml.GeneralConfigReplaceYaml` (TD-37 fix; since D40, CM2, only the timestamp changes, §14): the file is read as it is now (strict UTF-8), loaded with the loaders' deserializer, and the CM1 editor (`YamlDocument`, §13) changes or adds only `lastRidbDataRefresh`, so comments, blank lines, order, indentation, quoting, line breaks and a byte-order mark stay byte for byte, and other values of the in-memory `GeneralConfig` are never written; a file that already holds the timestamp is not written. `ConfigFileReplace.Replace` then writes the result through a verified same-directory temporary file, keeps the previous bytes in `General.yaml.bak` and renames the new file over `General.yaml` unless `General.yaml` changed meanwhile (§14); `General.yaml` is never truncated or deleted first. Before D40 the complete document was re-serialized from the in-memory settings, which dropped every comment and blank line. On any failure the old `General.yaml` stays as it was and the temporary files are removed on a best-effort basis (a cleanup failure is reported without hiding the original exception). If the write fails (I/O, permission, encoding, an external change, a file the editor refuses or the loader rejects), the refresh still returns `true` with the warning "The RIDB database refresh succeeded, but General.yaml could not be updated (…). The next start may refresh again.", whose reason names the file and the problem, never a value of it; the installed DB is kept. The in-memory `GeneralConfig` (shared with View Config) gets the new timestamp either way, because the installed data is new. Temporary files left by a killed process are never read (the loaders read `General.yaml` and `*.yaml`); those older than 10 minutes are removed at the start of the next refresh (reported) and before every write (quietly), exact names only (§14). On Unix, a `General.yaml` without write permission (0400, 0444) is still replaced, keeping its mode (the rename needs write permission on the directory, as before D40); on Windows a read-only file is refused (§14).

  **Lock order:** the refresh lock first (whole refresh), the repair lock second (installation only). `LegacyAddressLayout.RepairIfNeeded` takes only the repair lock and runs in `DbExistsCheck` before the auto-refresh, after releasing it; nothing takes the refresh lock while holding the repair lock. While a refresh holds the repair lock, a startup repair in another process fails to open it, reports "Could not check or repair …" and leaves the DB unchanged (checked again on the next start).

  **Busy installation** [V]: `BackupDatabase` performs one `sqlite3_backup_step(-1)` and does not apply Microsoft.Data.Sqlite's `Default Timeout` (that applies to commands); SQLite's busy timeout on the destination connection does apply. A competing write transaction makes the installation wait up to the busy timeout and then throw `SqliteException` with `SqliteErrorCode` 5 (`SQLITE_BUSY`); the installed DB stays byte for byte unchanged. `SQLITE_LOCKED` arises only within one connection or a shared cache, which the installation does not use.

  **Failures** keep the existing behavior: exceptions propagate (as before), and only validation, a held refresh lock and a failed `quick_check` return `false`. On every failure before the installation, the installed DB, `General.yaml` and (before step 6) the cache are unchanged and the staging directory is removed. Readers in other processes keep a consistent snapshot during the installation and see the new data with their next transaction; pooled idle connections (the GUI's) need no closing.

  **Replacement guarantees** (`ConfigFileReplace`, TD-37, D40; details in §14): .NET implements `File.Move(…, overwrite: true)` with `rename(2)` on Linux and macOS (`FileSystem.Unix.cs`; the copy-and-delete fallback is only for `EXDEV`, impossible within one directory). POSIX requires that the destination name always refers to the old or the new file and is unaffected if `rename` fails (except `EIO`). `Flush(true)` is `fsync`, `F_FULLFSYNC` on macOS (`pal_io.c`). On Windows it is `MoveFileExW(MOVEFILE_COPY_ALLOWED | MOVEFILE_REPLACE_EXISTING)` without `MOVEFILE_WRITE_THROUGH`; Microsoft documents no atomicity for it. **Verified:** process termination at every tested point of the write (Linux x64, btrfs; kill harness, history/validation/a-w_2026-11-10_to_beta.10.md §N for D26's writer, history/validation/ad-ax_preview.2.md §AE for D40's) left the complete old or complete new `General.yaml` and a working next start. **Not guaranteed:** power loss (the directory is not fsynced after the rename, so the old file may reappear; acceptable, it is valid), macOS behavior (not run natively); Windows runs the deterministic tests natively in CI (§14), not the kill harness. Since D40 the sample writers (`General.yaml`, `Email.yaml`, `ZionConfig.yaml`) no longer truncate or write in place either (§9, §14).

With search files of which none has `autoRun: true`, every file stays exactly as it is (no example is written, nothing is re-serialized), the warning "No search file has autoRun: true, so no search runs. Set autoRun: true in a search file to run that search." is written and the list of searches is empty; each output type then does what it does with no search: Console and UnitTest show "Done: 0 searches, no matching availability.", HtmlFile opens the empty results page, and email mode stops at its start with one error and exit code 1 (since D64, next rule; before, it checked 0 searches every minute, "Check N: 0 searches, nothing new.", open question #40). Before D37 the example was written over a user's `ZionConfig.yaml` (its comments and values lost) and run; D34 had changed only the message. **Narrowed by D44 (CM6) for explicit GUI actions only:** the GUI's Searches tab writes a search file when the user saves it, saves it under a new name or creates one (§18); the console, the Email loop, the start, the RIDB refresh and the validation still never write a search file, and nothing deletes one.
- [V] **Email mode starts its checks only with a search to check** (since D64, answering open question #40; history/validation/ba_v0.1.1.md §BJ). Its start reads the search files once, as before, and before it prepares anything asks `Load.CheckSearchesToCheck`. A search to check is a search the start loaded (`autoRun: true`, not refused by the validation) whose `campgroundID` is not blank: the search plan's rule (`CampsiteSearch.LoadEntry`'s `Ready`). With none, email mode writes one error on standard error (§12) and the console exits with code 1: no check, wait, request, email, `Camp.History` or file write. The error tells apart search files none of which is Enabled (autoRun), enabled searches none of which has a `campgroundID`, and a settings folder without a search file, which since D65 email mode leaves exactly as it is (no example search; until D65 it created `ZionConfig.yaml` and checked it).
  An enabled search with an error still stops the start with its own message (business-rules-settings §15), and an incomplete `Email.yaml` before that. Before every check `Load.RequireSearchesToCheck` throws if the plan has no search to check (a defect; `Program.Main` reports it, exit code 1). Since D73 the reading and the rule are one function, `Load.LoadMonitoringSearches`, which the GUI's check of the same calls too (business-rules-settings §15, "The monitoring's search check"); the start's messages and exit code are unchanged. A folder with a search to check starts as before, also when other enabled searches have no `campgroundID` (they are skipped at every check with their warning; TD-59 for an empty or blank ID). The console's Search, HtmlFile and UnitTest output are unchanged. Before D64 email mode wrote the warning above, "Running 0 searches:" and "Check N: 0 searches, nothing new." every minute for as long as it ran, and with only searches without a `campgroundID` it checked them every minute without a result. Searches whose dates have all passed still count as searches to check (open question #44). Since D67 ntfy mode has the same gate, its words naming "ntfy mode" (§28).
- [V] **The example search matches exactly** (since D51): `Yaml.SearchSampleConfig` (the start's `ZionConfig.yaml` and the GUI's New search) has `filterMatching: Exact` (written after `showSunday`, the serializer's property order) and exact values of Watchman's data: `excludeCampsiteType` is `GROUP TENT ONLY AREA NONELECTRIC`, Watchman's only group type, instead of the part `GROUP` that a `Contains` search uses; the equipment and attribute values were already exact names. It finds exactly the campsites the example of before D51 found on Watchman's data (`FilterSemanticsTests.TheExampleSearch_FindsWhatItFoundBefore_NowWithExactValues`). An existing `ZionConfig.yaml` is never rewritten (D37), so it keeps `GROUP` and, without `filterMatching`, `Contains`.
- [V] **The sample files are created atomically and never written over** (since D40, CM2; §14). A missing `General.yaml` or `Email.yaml`, and the example `ZionConfig.yaml` when there is no search file, are written with the serializer's text exactly as before (same values, order and bytes; the permissions a new file gets) to a temporary file, flushed, read back and checked to load as settings, and moved into place only if no file, directory or link of that name exists (`ConfigFileReplace.Create`). An interrupted creation leaves no file (or the complete one) and at most a temporary file, which is never loaded; there is no backup. If another program creates the file meanwhile, it is kept: `General.yaml` and `Email.yaml` are then loaded like any existing file, and a `ZionConfig.yaml` created meanwhile is loaded like a search file that was there (run if it has `autoRun: true`). Before D40 a truncating `StreamWriter` wrote them, so a kill could leave an empty or partial file, and a file created meanwhile was written over.
- [V] **An empty settings file is an unusable file** (since D37, the empty-file part of TD-37 resolved). An empty `General.yaml` or search file, or one with only comments or blank lines, deserializes to null; it is now reported inside the file-context boundary (`ConsoleUi.NoteFile`) as "{file} could not be used: The file has no settings: it is empty or contains only comments.", with the file and what to do, exit code 1, and the file is left as it is (an empty search file is not replaced by the example). Before, a `NullReferenceException` followed ("unexpected problem" for `General.yaml`, "Object reference not set …" for a search file). An empty `Email.yaml` is still loaded as no settings and tolerated outside Email output; since D41 the Email output refuses to start with it (§15, TD-51 resolved).
- [V] **The desktop data folder** (since D37, TD-47 resolved): `Load.GetConfig` resolves `LocalApplicationData` with `SpecialFolderOption.Create` (`Load.DesktopDataFolder`), so a missing `~/.local/share` or a missing `$XDG_DATA_HOME` folder is created, and stops with an error if the result is still not a full path. Existing folders, `XDG_DATA_HOME`, Windows (`%LOCALAPPDATA%`), macOS (`~/Library/Application Support`) and the container's `/config` and `/cache` resolve as before.
- [V] Auto-refresh condition: `AutoRefresh && UtcNow - RefreshRidbDataDayInterval days > LastRidbDataRefresh` (`Load.DbExistsCheck`). The sample sets `LastRidbDataRefresh` to 50 years ago, so enabling `autoRefresh` triggers a refresh on the next start. A refresh that fails, or is skipped because another refresh holds the lock, is therefore retried on the next start (before, the pre-write suppressed retries for the whole interval).

## 10. Compatibility with versions before 0.1.0-beta.4
- [V] All versions use the same data folder (`LocalApplicationData/CampertronConfig`, or `/config` in a container) and the same `RecreationDotOrg.db` file name. A newer version does not keep a separate database.
- [V] The 2024 versions (`v0.1-beta1`/`v0.1-beta3` downloads, code up to `e96bc7c`; `v0.1-beta3` is `net9.0`) read the state from `FacilityAddresses.PostalCode`. In the corrected address layout (§8), `PostalCode` holds ZIP codes. That layout is in the DB that 0.1.0-beta.4 and later extract or install by repair, and in any DB refreshed from current RIDB data, whichever version ran the refresh. **A 2024 GUI reading such a DB lists ZIP codes as states** (for example `01005` → city BARRE; MA lists nothing). Measured 2026-11-11 with the 2024 library: 1,185 ZIP-like "states" on the beta.4 DB, and 1,171 on a copy of a real data folder's refreshed DB. The 2024 console shows `Framework => .NET 9.x` in View Config (`.NET 9.0.0` for the self-contained `v0.1-beta3` download).
- [V] Nothing in a newer version can prevent this: the 2024 binaries can't be changed, and they don't check anything a newer version could write (decisions D20). The protection is documentation: the required "Compatibility with older versions" section of every release's notes (`render_notes`/`validate_notes`) tells users not to keep or run old copies, and `--version` (§11) identifies a copy. The README carried the same warning until 2026-11-11, when it was rewritten for current users and the note was removed at the maintainer's request.
- [V] Running a 2024 version first and a newer version afterwards is handled at startup (§8): a DB with the swapped 2024 layout is replaced by 0.1.0-beta.4 and later. A DB refreshed by a 2024 version (corrected layout, 15 omitted tables, un-normalized states) is replaced since branch `fix/repair-stale-ridb-on-upgrade`. Before that, beta.4 and beta.5 kept it until a manual refresh.
- [I] A 2024 version's in-app "Refresh Ridb Data" re-imports all 21 tables with its old normalization (states un-normalized in `AddressStateCode`). A newer version classifies that DB as Corrected and doesn't repair it; how a newer version then shows it is measured in §8.

## 12. Console output (decision D34; `ConsoleUi`, `ConsoleResults`, `CampertronConsole/Program.cs`)
- [V] **Streams.** Results, status lines, notices and prompts go to standard output. Warnings and errors go to standard error and start with `Warning: ` or `Error: `, so their meaning depends on neither the stream nor color. (The RIDB refresh's plain progress lines are still `Console.WriteLine` on standard output.)
- [V] **Exit codes.** 0: `--version`, menu Exit and an `outputTo: UnitTest` start. Since D37 the two former exceptions, equal start and end dates (§2, TD-45) and a blocked request (§7, TD-44), exit with 1 too. Since D41 a settings file refused by the validation at start (§15) and the Email output's start check (an incomplete `Email.yaml` with `outputTo: Email`) exit with 1 through the same path. Since D64 email mode exits with 1 after its one error when its start has no search to check (§9), since D65 also without a search file, since D66 when the SMTP password's configured source can't be used (business-rules-settings §27; it comes before the search files), and since D67 when `Ntfy.yaml` or ntfy's configured token source can't be used, or `outputTo: Ntfy` has no enabled ntfy, and after a check in which a provider failed (§28), and since D90 when another monitoring holds the settings folder's monitoring lock or the lock's file can't be created (business-rules-settings §29); `Load.RunConsole` gives `Program.Main` that code. An `outputTo: UnitTest` start (the validation's `TestOutput`; the release smoke tests' silent start) is not email mode: `Menu.Init` returns at once, so it reads no search file, searches, creates, waits for and sends nothing and ends with 0 (D65). 1: any failure `Main` reports (`ConsoleUi.ReportFailure`: a settings file that cannot be read or used, a missing container folder, an email or download failure, any other exception; before D34 an unhandled exception with 134, or 139 in a container), an output type other than Email or, since D67, Ntfy in a container, and the menu without a terminal. Signals are unchanged: Ctrl+C 130, SIGTERM 143, SIGHUP 129. Since D121 the interactive console's own (§43): 0 for Exit and the end of the input, 130 for Ctrl+C at its main menu, 1 without a terminal, for a refused `--interactive` or `--help` command line and for its unexpected problem; `--help` exits with 0.
- [V] **Failure messages** (`ConsoleUi.DescribeFailure`). A settings file: "{file} could not be read: {reason} (line N, column M)" (or "could not be used" when the failure is not a YAML error), "File: {path}", and "Fix the file, or delete it and Campertron creates a new one with the default settings (outputTo: Console)." for `General.yaml`, since D71 "Fix the file in a text editor or in the GUI (Settings > Campertron > Email.yaml). Don't delete it to start over: Campertron would create an empty one, without your email settings or smtpPasswordFile." for `Email.yaml` and "Fix the file in a text editor or in the GUI (Settings > Campertron > Ntfy.yaml). To turn ntfy off, set enabled: false (with outputTo: Ntfy, choose another outputTo too); don't delete the file, which holds the server, the topic and tokenFile." for `Ntfy.yaml` (before D71 both advised deleting the file, which loses its settings and secret files' paths), or "Fix the file, or move it out of the settings folder." for a search file. The loaders record the file on the exception with an exception filter (`ConsoleUi.NoteFile`), so the exception that travels is unchanged (the GUI's own messages are too). "Config path does not exist" / "Cache path does not exist" keep their text and add the mount advice. An email failure: "the email could not be sent: …" and "Check the server, port, user name and password in Email.yaml." (since D66, for a password from a file or the variable, "Check the server, port and user name in Email.yaml, and the password in the file that smtpPasswordFile names." or "… in CAMPERTRON_EMAIL_PASSWORD."); a password source that can't be used: "email mode can't start: the SMTP password can't be used: …" with what to do and the order of the sources (business-rules-settings §27); since D67 ntfy's "the ntfy notification could not be sent: …" with what to check, "ntfy mode can't start: the ntfy access token can't be used: …" and, when both providers failed, "the notifications could not be sent: both the email and the ntfy notification failed." with an "Email:" and an "ntfy:" line (§28); a download failure: "a download failed: …". Anything else: "Campertron stopped because of an unexpected problem: {type}: {message}" followed by the exception's details for a report.
- [V] **Secrets.** Messages come from exceptions only; no settings value is read for them. For `Email.yaml` the inner exception messages are left out, because they can quote a value of the file, and the SMTP password, when it is known, is replaced by `[hidden]` in every line; since D66 `Program.Main` reports with the email settings (`ConsoleUi.ReportFailure(Exception, EmailConfig)`), so every password the process knows (the one resolved from `smtpPasswordFile`'s file, `CAMPERTRON_EMAIL_PASSWORD` or `smtpPassword`, and `smtpPassword` itself) is hidden, and no message names the password file's path or the variable's value. Since D67 `Program.Main` reports with all the run's settings (`ConsoleUi.ReportFailure(Exception, CampertronInternalConfig)`), which also hides ntfy's token and topic, and `Ntfy.yaml`'s inner exception messages are left out like `Email.yaml`'s (§28). The Email loop's lines name searches and counts only, never addresses, the server or the topic.
- [V] **Capabilities** (`ConsoleUi.Detect`, once per process). Color: standard output is a terminal, `NO_COLOR` is unset or empty, and `TERM` is not `dumb` (and, except on Windows, not missing). Width: `Console.WindowWidth` on a terminal when it is 20 to 500, else 80; redirected output has no width and is never wrapped. Interactive: standard input and output are both terminals. If detection fails, the output is plain and nothing is interactive. No flag and no other environment variable is read.
- [V] **Color.** Foreground only: green (search names), cyan (dates and the calendar's open days), dark yellow (`Warning:`), red (`Error:`), dark green (the logo) and red (the menu's arrow); never blue, dark gray or dark red. It is reset after the text it colors, also when writing fails. Nothing is told by color alone: the calendar's open days carry `*`.
- [V] **Screen and cursor.** The only clear is `ConsoleUi.ClearScreen`: `ESC[H ESC[2J` (the visible screen; never `ESC c`, never the scrollback), written only to an interactive terminal that understands control sequences, and never while a notice, warning or error has not been acknowledged by a key press (`ConsoleUi.Unacknowledged`). It is used by the menu, View Config, a manual refresh and the start of a menu search. The Email loop and redirected output never get a control sequence. The cursor is hidden only on an interactive terminal and restored, with the color, on Exit, on a failure and on Ctrl+C ("Stopped." on standard error). Cursor addressing exists only in the interactive menu; there is no animation.
- [V] **Text.** ASCII punctuation around the data; no tabs, no emoji (the window title keeps its robots). Names and other data are written as stored, with UTF-8 output set by the menu and at the start of the Email loop. On a terminal, lists and status lines wrap at spaces or between items, with indented continuation lines; a link or path is never broken and nothing is truncated.
- [V] **Results** (`ConsoleResults.Render`): built from the model `ResultsHtml.Build` returns, so the console and the HTML page group the same streams the same way (§6): `== {search} ==`; the campground, park and ID; "N openings at M sites on K dates" (an opening is one site on one date), preceded by "at least N consecutive nights" and followed by check-in/out when every result shares them; "Equipment (all sites): …" when every result has the same list, otherwise per site. Single nights: "{weekday} {short date} - N sites", each site with its loop and type and its booking link on its own line, then the month's calendar. Consecutive nights: each site with its dates in date order and a calendar per month. An empty search says "No matching availability." once; an empty month within a search that has results says "{Month Year}: no matching availability.". The run ends with "Done: N searches, X openings at Y sites." and the number of searches without availability. Dates and month names follow the current culture. Untyped nonblank text is written as a plain line; the stream's own calendar values are skipped.
- [V] **Search attribution.** Like the page, the console shows each stream as supplied. Skipping the stream's calendar values hid one symptom of TD-04 (another search's calendar without a campsite); the cause, consecutive filtering on the run's shared set, is fixed since D35, so each stream holds only its own search's results.
- [V] **Before and during a search.** "Running N searches:" lists each search (by name) with its campground, dates, weekdays, "at least N consecutive nights", people and number of non-empty filters. Warnings follow for a search without `campgroundID`, with a campground ID that is not in the campground list, without `totalHumans`, with `consecutiveDays` below 1, or without search dates; the search still runs exactly as before. Each finished search writes "Checked "{name}" at {campground}: {months} ({seconds}s)".
- [V] **The Email loop** writes for logs: a start line and each check and email line carry the local time (`yyyy-MM-dd HH:mm:ss`); nothing else is timestamped. One line per check ("nothing new. Next check HH:mm:ss." or "N new openings; sending M emails."; since D67 "sending M emails and K ntfy notifications.", "sending K ntfy notifications." or "nothing to send."), one "Email sent: {search} ({n} openings)" per email and, since D67, one "ntfy notification sent: {search} ({n} openings)" per ntfy message. The start line ends with "output Email", "output Email and ntfy" or "output Ntfy".
- [V] **Email mode's start without a search to check** (D64, §9): after the start line, one `ConsoleUi.Error` of three lines on standard error, plain ASCII, with no file name, path, search name or settings value: "Error: email mode has no search to check, so it stopped: {reason}", the fix, and "Email mode reads the search files only when it starts.". The reasons: "the search file is not Enabled (autoRun)." or "none of the {n} search files is Enabled (autoRun)."; "the Enabled (autoRun) search has no campgroundID, so it would never be checked." or "none of the {n} Enabled (autoRun) searches has a campgroundID, so none would ever be checked."; "the settings folder has no search file." (since D65 for every folder without one). The fixes: "Enable at least one valid search (set autoRun: true in its file, or check Enabled (autoRun) in CampertronGUI's Searches tab and save it), then start Campertron again, or restart its container."; "Set the campgroundID of at least one enabled search (CampertronGUI's Searches tab can choose the campground), then …"; "Add a search file and enable it (set autoRun: true in it, or use New search and Enabled (autoRun) in CampertronGUI's Searches tab), then …". The console's warning about no enabled search is not written there (the error replaces it). Since D67 ntfy mode writes the same lines with "ntfy mode" and "Ntfy mode" (`Load.EmailStartProblemText`'s mode).
- [V] **Unchanged contracts.** `--version` (§11) is handled first and is byte-identical. An `outputTo: UnitTest` start writes nothing. `Load.GetConfig` writes nothing on a clean first start unless `Load.FirstStartNotice` is set, which only the console does (the GUI's `--smoke-test` report must hold only `SMOKE` lines). "Config path does not exist" and "Unsupported output type in container" remain in their messages.
- [?] Windows and macOS (open question #38). Windows: the maintainer reviewed the D34 output manually before PR #49 was merged and reported that it looked good; that is a maintainer-reported manual visual review, not an automated or comprehensive check, and the individual cases of #38 stay unverified. macOS: not run. The release workflow's native smoke jobs have run on D34 code since Release runs #30 and #31 (history/validation/x-ac_preview.1.md §AC); they cover `--version` and the silent `outputTo: UnitTest` start only, so the menu, also its loop of D47 (below), has not run on Windows or macOS in a workflow.
- [V] **The menu's keys** (decision D47, TD-12; `Menu.WriteMenu`, `Menu.ProcessInput`). The loop in `WriteMenu` draws the four options, clears the six lines below them, places the cursor and reads a key; `ProcessInput` handles it and returns to that loop. Up and Down move the selection one step (Up at Search and Down at Exit stay), Enter runs the selected option, any other key changes nothing; after each key the options are drawn again. The console calls and their order are the same as before D47, so the terminal gets the same bytes for the same keys (compared on a pseudo-terminal, history/validation/ad-ax_preview.2.md §AL). Before D47 `ProcessInput` called `WriteMenu` for every key, also for keys the menu does not use, so every key press went one level deeper and the console ended with a stack overflow (SIGABRT) after 17,231 key presses with an 8 MB stack and 4,202 with 1 MB. **Still nested, by design of the search loop:** each Search, Refresh and View Config starts a new menu inside the one that ran it (`Load.PostProcess` → `Menu.Init`, or `Menu.Draw`); that is one level per Enter action, bounded by what the user does, and unchanged (the rest of TD-12).

## 43. The interactive console (decisions D115, D121, D122, D123, D124; `ConsoleArguments`, `InteractiveConsole`, `InteractivePrompts`, `InteractiveNotifications`, `InteractiveSettings`, `InteractiveSettingsForm`, `InteractiveSearches`, `InteractiveSearchForm`)
`v0.4.0`'s phase 6 (D121, record §DO): the console's interactive foundation, in `CampertronLibrary/function/Interactive/`, beside the start without arguments, which is unchanged (§11, §12, ER-21). Its phase 7 (D122, record §DP) adds Notifications: `Email.yaml` and `Ntfy.yaml` in the shared forms (below); its phase 7a (D123, record §DQ) Settings: `General.yaml` and `Web.yaml` in the shared forms (below); its phase 8 (D124, record §DR) Searches: the search files in the shared forms (below). No capability of a later phase exists in it yet.
- [V] **Its arguments** (`ConsoleArguments`, `Program.Main`): `--version` (exactly one argument, §11) and web mode's `--web`, `--healthcheck`, `--listen` and `--port` (business-rules-settings §31) are read first, unchanged; a command line with one of web mode's arguments is web mode's to refuse, in its own words, also when it holds `--interactive` or `--help`. Then `--interactive` opens the interactive console and `--help` writes how to start CampertronConsole.
  Each is the whole command line: given with another argument, twice or with a value (`--interactive=yes`), it is refused with "Error: --interactive opens the interactive console and takes no value and no other argument." (or "--help shows how to start CampertronConsole and takes no value and no other argument.") and the usage line on standard error, exit code 1, before anything is read or created. Names are case-sensitive.
  Every other argument (`-h`, `/?`, `--Interactive`, a word) is still ignored, as before D121, and the console starts as without arguments (open question #66). The decision is made from the arguments alone: no terminal, environment variable or file takes part, so a terminal never opens the interactive console and a script or container that passes no new argument sees no change.
- [V] **`--help`** writes the usage of each start (without arguments, `--interactive`, `--web`, `--healthcheck`, `--version`, `--help`) and what it does on standard output, exit code 0; on a terminal each description is wrapped at its width under its own indentation, redirected it is written as it is. Like `--version` it reads, creates and starts nothing.
- [V] **The terminal:** the interactive console needs standard input and output both a terminal (`ConsoleUi.Capabilities.Interactive`, as the menu does); otherwise "Error: the interactive console needs an interactive terminal. Start CampertronConsole --interactive in a terminal, without redirecting its input or output." and exit code 1, with nothing read or created (in a container too: `docker run -it` has a terminal). It reads no setting to start and needs none to be valid.
- [V] **The screen:** plain lines only, through `ConsoleUi` (§12): no cursor movement, no screen clear, no full-screen drawing, no window title, no escape sequence of its own; its headings are colored only where `ConsoleUi` colors (a color terminal, without `NO_COLOR`, not dumb). Long lines are wrapped at spaces at the terminal's width (20 to 500 columns, else 80), continuation lines indented; a path is never broken. A question's text ends without a line break and the answer is written back after it as it is typed (`ConsoleUi.Prompt`, `Echo`).
- [V] **The main menu:** the title "Campertron interactive console", one sentence on how to choose and cancel, then "Main menu" with its numbered choices, Status, Notifications (since D122), Settings (since D123), Searches (since D124), Help and Exit, and "Choose a number from 1 to 6: ". A choice is its number typed and Enter (spaces around it allowed; ASCII digits only); an empty answer says "Type the number of a choice, from 1 to 6, then press Enter.", another "That is not one of the choices. Type a number from 1 to 6.", and the menu is shown again (the answer is never repeated back).
  After a choice the menu comes again. The main menu asks until it has an answer; each answer needs a key, and a choice's unexpected problem is told as "That could not be done because of an unexpected problem (<the exception's kind>)." on standard error, never the exception's text or a stack, before the menu comes again. A later phase adds its choices to `InteractiveConsole.MainMenu`, before Help.
- [V] **Status** (read only: "Status (read only: nothing is changed)"): Version (the first line of `--version`); Settings folder (its path, as View Config shows it, from `Load.FolderLocations`, which creates nothing: a missing folder says "not created yet: a start without arguments, or the desktop app, creates it", in a container "not found: in a container, mount the settings folder at /config"; without a folder for the settings on this computer it says so and shows nothing else);
  General.yaml ("not found: …", "found, but it can't be used as it is: a start stops with its problem", or "found; outputTo: <value>", read with `CurrentConfiguration.ReadGeneral`, which never creates it); Email.yaml, Ntfy.yaml and Web.yaml ("found" or "not found", never opened); Search files (their number, names only); Campground data ("prepared" or "not prepared yet: …", the database file's existence, never opened). Nothing else: no other value of a file, no secret, no environment variable; a fact that can't be found is "unknown".
- [V] **Help:** how the interactive console is opened, how to choose, how a default is shown (`[y/N]`), that Esc or Ctrl+C cancels a question and returns to the main menu, how to leave (Exit, Ctrl+C at the main menu, Ctrl+D or on Windows also Ctrl+Z on an empty line), that the start without arguments is unchanged and `--help` lists every start, and that missing or incomplete settings can limit what Campertron can do; since D122 what Notifications holds (the two files, the tests and the random topic; nothing saved or sent until chosen and confirmed; passwords never shown, the topic only on request); since D123 what Settings holds (`General.yaml`: where results go and the campground data's automatic update; `Web.yaml`: the web UI's settings; nothing saved until chosen and confirmed, a save starts, stops and restarts nothing; the web UI's password set and changed in the web UI only); since D124 what Searches holds (the search files with the desktop app's and the web UI's choices, checks and words: list, New search, every setting, save, Save As, revert, reload; nothing written until chosen and confirmed, no search run, no file deleted or renamed; a campground needs the prepared campground data); it names no capability the console does not have.
- [V] **The questions** (`InteractivePrompts`, the foundation of later phases' screens): a numbered choice; yes or no with an explicit default shown as the capital letter (`[y/N]`, `[Y/n]`; `y`, `yes`, `n`, `no` in any case; Enter alone is the default); text, trimmed, required (an empty answer: "An answer is needed here. Type it, or press Esc to cancel.") or optional (" (optional, Enter leaves it empty): "), with a check that returns fixed words, and since D124 optionally the answer exactly as typed (`Trim: false`, for a form that judges its spaces itself); and a secret.
  Each asks in a loop, never by calling itself, says what was wrong and asks again (a choice with its choices shown again); below the main menu five unusable answers end it as cancelled ("No usable answer after several tries, so the question was cancelled."). Esc ends it as cancelled, Ctrl+C as interrupted (below the main menu both cancel the question: "Cancelled.", and since D122 the choices of the screen it was asked from come again, the main menu for a choice of the main menu), the end of the input at once; nothing is read after any of them.
- [V] **Keys** (`KeyLineReader`, on the terminal through `Console.ReadKey`): Enter ends the answer; Backspace removes the last character (written back as backspace, space, backspace; a character outside the Basic Multilingual Plane whole); Esc and Ctrl+C end the read; Ctrl+D on an empty line, on Windows also Ctrl+Z, is the end of the input, elsewhere ignored; every other control character and key without a character (arrows, function keys, Tab) is ignored and moves no cursor; an answer has at most 4,096 characters.
  Ctrl+C is read as a key only while an answer is read (`Console.TreatControlCAsInput`, restored after every read, however it ended); a Ctrl+C while no answer is read is `ConsoleUi`'s handler's, as in every start ("Stopped." and the process ends). An Esc followed at once by another key can be read as that key with Alt, as the terminal sends them together.
- [V] **The ends and exit codes:** Exit ends it with 0; the end of the input (Ctrl+D, or a terminal that is gone) with "The input ended, so the interactive console ended." and 0; Ctrl+C at the main menu with "Stopped." on standard error and 130, the code a Ctrl+C gives the console's other starts on Linux and macOS; Esc at the main menu has nothing to cancel ("There is nothing to cancel here. Choose Exit to leave.") and the menu comes again, as often as it is pressed. Its own unexpected problem: "Error: the interactive console stopped because of an unexpected problem (<kind>)." and 1.
- [V] **Secrets:** a secret is typed without being shown, not even as a mask (only the line break is written back), its value is a `SecretText` whose text is `[hidden]` in every string, and it is never written, logged or kept by the question; on a terminal that can't hide what is typed nothing is read, no question claims it would be hidden, and "This needs a terminal that can hide what you type, and this one can't, so nothing was read." is said. Since D122 `Email.yaml`'s plain-text password is asked through it (below); nothing writes a secret file.
- [V] **Notifications** (D122, phase 7; `InteractiveNotifications`): "Notifications (nothing is saved or sent until you choose to)", a summary in the console's words (`Email.yaml` and `Ntfy.yaml`: "not found", "found, but it can't be used as it is", or found and whether the monitoring's start would accept it as it is saved, by `GuidedSetupStatus.NotificationsReady`, the start's own checks; for `Ntfy.yaml` whether ntfy is on; `General.yaml`'s outputTo, and since D123 "… choose it in Settings > General settings." where phase 7 said that the console does not change it), then Email, ntfy and Back to the main menu. It creates, saves and sends nothing by itself; without the settings folder it says where it comes from and offers nothing (the console never creates it). Since D123 its loop is shared with Settings (`InteractiveSettingsMenu`); its screens are otherwise the same, byte for byte.
- [V] **A form at the terminal** (`InteractiveSettingsForm`): the shared `SettingsViewModel`'s Email or Ntfy form (their checks follow `General.yaml`'s saved outputTo, D71), new each time it is opened, its title, its state, conflict and notices, each field with its value, "(changed)", its message in its severity's words and why it is locked; the changes' summary, the last action's result and the test's result or why it can't be sent, every word the form's (business-rules-settings §32, business-rules-gui §17).
  Its choices: Change each editable field, the form's own actions at their fields (Remove smtpPasswordFile, Remove the plain-text password, Generate a random topic, Show the topic, Remove tokenFile), Show the changes Save would write, Save (with changes), Revert changes (with changes or a field's own input error), Reload from disk (without changes), the test (when the form offers it) and Back to Notifications (Back to Settings for Settings' forms); for a missing `Email.yaml` or `General.yaml` only Create, for a conflict the session's resolutions, for a file that can't be used only Reload. Each time the choices come, the file on disk is looked at: a clean form follows it, an edited one opens a conflict, never overwritten.
  A field's question: text, trimmed (Enter alone empties it, Esc keeps it); the plain-text password through the hidden question, the form's words saying only what is set or what Save will do; a switch as yes or no with its value as the default; a choice by number; a list's own choices (add, change, remove, move up, move down, Done). The answer goes to the field as if typed; the form parses and judges it (a port that is not a number, a timeout outside 1 to 120, a relative password file: the form's own errors). Save, Revert, Create, Create the file again, Discard my changes, Send a test and Show the topic ask once, No by default; leaving with unsaved changes asks, and leaving keeps only what was saved.
  The topic is shown only by Show the topic and a yes, and `Ntfy.yaml`'s preview only after a yes (its lines can hold the topic); a random topic is the form's `NtfyTopic` (an unsaved change, never shown unless asked for). A value from a file is shown with its control characters replaced by U+FFFD. Whether `CAMPERTRON_EMAIL_PASSWORD` and `CAMPERTRON_NTFY_TOKEN` are set in the console's process is said yes or no only, never their values; the password and token files are paths only, never opened.
  The test email and notification are the form's (`TestNotificationForm`: the saved file, the monitoring's resolvers and transports, fixed words; ER-39), sent on the console's thread after a yes while the console waits; nothing is written, `Camp.History` and the monitoring lock untouched. At a screen's choices Esc and Ctrl+C go back one level (a form with changes asks first); the end of the input ends the console with nothing saved; a Ctrl+C while a test is sent is `ConsoleUi`'s ("Stopped."). `Email.yaml` has no switch: outputTo (in `General.yaml`, since D123 in Settings) decides whether emails are sent.
- [V] **Settings** (D123, phase 7a; `InteractiveSettings`): "Settings (nothing is saved until you choose to)", a summary in the console's words (`General.yaml`: "not found: a start without arguments, or the desktop app, creates it (outputTo: Console); choose General settings to create it now", "found, but it can't be used as it is: choose it to see why", or "found; outputTo: <value>" and, for Email or Ntfy, "; the monitoring's start would accept the saved settings" or "; the monitoring's start would refuse the saved settings: choose General settings to see why", by `GuidedSetupStatus.FilesReady`, the start's own checks, which read no secret; `Web.yaml`: "not found; web mode uses the defaults shown in Web UI settings, and Save creates the file", unusable, or "found; passwordProtection: on|off; networkListening: on|off"),
  a sentence that a save starts, stops and restarts nothing (each start reads `General.yaml`, a monitoring when it starts, web mode `Web.yaml` when it starts) and that the web UI's password is set in the web UI only, then General settings, Web UI settings (the forms' own titles) and Back to the main menu.
  Each opens a new shared form of `SettingsViewModel` in `InteractiveSettingsForm`, as Notifications does, with every choice, question, save, revert, reload, conflict and leave above. `General.yaml`'s form: its four settings (Output, the automatic refresh, its interval, the last refresh); a missing file only Create (the start's sample, `Yaml.CreateSampleSettingsFile`, asked once, No by default); the form's outputTo choices (a file's `outputTo: UnitTest` kept, never offered); outputTo's message, the monitoring start's own checks of the saved `Email.yaml`, `Ntfy.yaml`, secret files and search files (D71, D73, D77), read again whenever the choices come, so Save is refused in the form's words while the start would refuse; the ntfy line (`NtfyStatus`) at outputTo and the refresh's explanation at the switch; the console's own sentence that a saved change applies from the next start.
  `Web.yaml`'s form: its four settings (Require a password, Listen on the network, the allowed host names, the trusted reverse proxies, their rows the form's), a missing file a new one with the defaults that only Save creates (owner-only, 0600 on Unix), the form's explanation and the command line's precedence (`--listen`, `--port`); a save that leaves the password off while it listens on the network (`WebAccessRule`, D81) is asked at once, "Save without a password?", the warning and two choices, "Save without a password, reachable from the network" (saved) and "Don't save" (Esc, Ctrl+C and five unusable answers too; nothing written, the changes kept), the end of the input ending the console with nothing written; a later save of the confirmed state asks nothing. The web UI's password, `Web.password`, the setup code, the sessions and `Web.keys` are never read, shown or written, and no password is typed (web-only, D84). Nothing starts a monitoring, a web host or a test.
- [V] **Searches** (D124, phase 8; `InteractiveSearches`, `InteractiveSearchForm`, `InteractiveSearchesWording`): "Searches (nothing is saved until you choose to)", a note that nothing there runs a search, deletes or renames a file and that the words are the desktop app's and the web UI's (the Results tab theirs, the console's Search the menu of the start without arguments), the folder's notice of the shared `SearchesViewModel` (`FolderNoticeText`; `General.yaml`'s saved outputTo handed to it as the web UI hands it, D73), "The campground data is not prepared yet, …" when the database file does not exist, then "Search files": each file as the form lists it ("<name>, <ListDetails>, <ListStatus>": the console's own search files, never a backup, a `.yml` or a settings file), New search file, Look for changes on disk and Back to the main menu. The list is a new form each time it is shown: entering it creates, saves and sends nothing; the settings folder must exist (never created).
  New search is the form's (its help and note, the name as typed, then "Create the search file now? [y/N]"): the form's name rules, today's example search not enabled (`autoRun: false`), create-only and checked again at the creation; its result in the form's words, the new file's form at once; a name it refuses, an existing name in any case and No, Esc, Ctrl+C or the end of the input write nothing. D120's TD-66 changes it later for every host at once.
  A file's form is the shared `SearchFileViewModel` in phase 7's adapter (every choice, question, save, revert, reload, conflict and leave above; its title and file name shown with control characters replaced): its fields in the form's order, the days of the week as one line and the campsite filters (filterMatching and the eight lists, their values named, the first eight of each) as one group; Change for each editable setting, "Change Days of the week" (each day checked or unchecked by number), "Change Campsite filters" (Matching and each list, grouped as both UIs group them: equipment, campsites, campsite types, attributes; "Read the campground's values again" when they could not be read), Show the changes, Save, Revert, Reload, "Save as a new search file" (the form's help, note and name rules, asked once, No by default; the new file's form follows, the edited file keeps what is on disk) and Back to Searches.
  The campground: its current text, "Find a campground" (the form's find, its summary, its first 25 matches by number, the form's words when there are more) and "Or enter a campground ID" (exactly as typed: the form uses it only when a reservable, enabled campground has exactly that ID, and says why not). A list: its status, its values (the campground's checked values and its other values, as the form names them), "Check or uncheck values" (the campground's values by number, each as the form names it, with Find, Select all shown and Clear shown for a long list; a find lasts only on that screen), "Add the value to <key>" (exactly as typed: the form refuses an empty value and one the list holds) and "Remove a value that is not the campground's".
  A search form's text answers go to the form as typed (the form trims a number, keeps a name as entered and refuses an ID or a file name with spaces around it). The form's own messages, the weekdays' message, the include and exclude conflict and D73's warning (with the monitoring's outputTo, a change that would leave it no search to check; never blocking Save) are shown in its words. A file that can't be loaded, or holds a setting search files do not have, is shown read-only with the form's reason (Reload and Back only, nothing written). Each time a form's choices come the Searches form looks at the disk: a clean file follows a change, an edited one opens a conflict, a clean file deleted on disk leaves the list with the form's words.
  The campground data is read through the library's own queries only when it is prepared (the database file exists): it is never prepared, repaired, refreshed or opened when missing; without it the picker and the lists say so in their own words, and the console says where it comes from. A campground's values are read on the console's thread while it waits (a Ctrl+C meanwhile is `ConsoleUi`'s). Nothing in Searches runs a search, reads availability, starts the monitoring, sends, or touches `Camp.History`, the lock or the cache; no file is deleted or renamed.
- [V] **What it never does** (`InteractiveConsoleTests`' and, since D122 and D123, `InteractiveNotificationsTests`' and `InteractiveSettingsTests`' IL checks): start or reach the monitoring, a search, web mode, the refresh or the results' renderers; reach a settings writer, a YAML loader, an editing session, a sender, a secret's resolver or the random topic's generator but through the shared Email, Ntfy, General and Web forms (since D124 also the search forms, `InteractiveSearchesTests`' IL check); reach the web UI's access, password, setup code, sessions, keys or host (`function/WebAccess`, `CampertronWeb`), cryptography, a thread or the network; create or change the database (never prepared or opened when missing), the cache, `Camp.History` or a lock, or a settings or search file but by a form's Save, Create, Save As or New search the user confirmed; delete or rename a search file; read an environment variable of its own (the two variables' yes or no are their resolvers' own `VariableIsSet`).
- [?] Run on Linux only: the unit tests, the process tests (redirected, and on a pseudo-terminal through util-linux `script`, `TERM=dumb`) and the checks of §DO, §DP, §DQ and §DR (phase 7's: a test terminal answering by label, the shared form as the oracle, canary secrets, a pseudo-terminal run of the hidden password, negative controls; phase 7a's: the same for `General.yaml` and `Web.yaml`, a pseudo-terminal run of `Web.yaml`'s confirmation, Notifications compared byte for byte with phase 7's build; phase 8's: the search forms with an in-memory campground data, a pseudo-terminal run of Searches, the settings forms compared byte for byte with phase 7a's build, a real campground data in an isolated folder). Windows (`Console.TreatControlCAsInput`, Ctrl+Z, a console window's keys) and macOS were not run: the Windows CI job's class list does not name the new tests (a workflow change with its own approval), and the release workflow's native smoke tests run `--version` only. No screen reader was used.
- **Left to later phases** (D121 point 6, D122 point 7, D123 point 6, D124 point 5): a `FormHost` instance with the first operation that runs on a worker thread (phase 8's filter choices needed none: read on the console's thread, as the web UI reads them); an operation's cancellation (the first Ctrl+C cancels it through its token, a second ends the process), with the first operation; every capability of D114 point 4 in its own phase (`v0.4.0-plan.md` §Implementation phases).
