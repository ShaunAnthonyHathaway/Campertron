# Maintainer procedures

Authority: current. This file is the current authority for hands-on maintainer procedures: refreshing the README screenshots and the embedded database, downloading and inspecting a candidate, verifying a published release, the manual platform checks of the database refresh, the reusable validation harnesses and the tooling problems they meet. What a release must satisfy is in `release-process.md`; what to run after a change in each area is in `build-and-test.md` §Recommended verification after changes.

Roadmap step 9, Phase 2 (2026-11-17) moved the two "Refreshing …" procedures here from `build-and-test.md` with their text; lines over 1,000 characters were broken at sentence boundaries (`history/README.md` §Phase 2 migration map). The other sections are current procedures written then from validation records, which stay unchanged in `history/validation/`. Each section names its sources, and `history/README.md` §Label index resolves the labels. The harnesses and launchers named here were scratch programs, never in the repository: rebuild one from its description. Legend: **[V]** verified (command run or file read) · **[A]** assumption, not executed · **[R]** recommendation.

## Rules for every procedure
- Never open, list, hash, copy, inspect or query real Campertron user data, even read-only (`CLAUDE.md` §Data safety). Several validation records compared, hashed or copied the real data folders (for example §E, §N, §AD and §AQ); that was the practice then and is never a procedure now.
- Tests and local runs use a new `XDG_DATA_HOME="$(mktemp -d)"`, which redirects all of Campertron's data on Linux (`build-and-test.md` §Test warnings). On Windows and macOS it redirects nothing (`%LOCALAPPDATA%`, `~/Library/Application Support`): use a separate user account or a virtual machine there (§N, §X).
- Released or candidate programs, screenshots and any run that shows paths run inside `unshare -rm` with a `tmpfs` mounted over `/home` and `HOME=/home/camper`, so the real home, its data and the SDK under it are not visible; such a program must be published self-contained (§AW, §AX, §AZ).
- Work in the session's scratch directory and remove what you made. Build from a `git archive` export when uncommitted files must not matter (§AZ). Put each download in a new empty directory.
- Nothing may reach recreation.gov, send email, open a browser or push an image unless the procedure says so; use the stand-ins of §Validation harnesses.
- A step that needs a manual dispatch, a rerun, a tag or a release waits for the maintainer's separate approval (`CLAUDE.md` §Approval boundaries).

### Refreshing the embedded database (maintainer procedure)
Verified 2026-11-10 for `07e786d`. All steps run in a scratch directory, never in the user's data dirs.
1. `dotnet build Campertron.sln -c Release`
2. Create an empty `X=$(mktemp -d)` and write `$X/CampertronConfig/General.yaml` with `outputTo: UnitTest`, `autoRefresh: false`, `refreshRidbDataDayInterval: 30` and any `lastRidbDataRefresh`. Then run `XDG_DATA_HOME=$X CampertronConsole/bin/Release/net11.0/CampertronConsole` (`net10.0` when this procedure was recorded, before D31). This extracts the bundled DB and exits without a menu.
3. Set `autoRefresh: true` and a `lastRidbDataRefresh` older than 30 days, then run the console again. It downloads the RIDB export (about 573 MB), imports the 6 used files and validates the result (about 15 s after the download since §M; the download itself took about 50 s in one sample). **The output must not contain "failed validation".**
4. `sqlite3 $X/CampertronConfig/RecreationDotOrg.db "VACUUM; PRAGMA integrity_check;"` must print `ok`.
5. Compress with .NET's built-in encoder, not a CLI tool, so the output matches what `BrotliStream` reads. Use `new System.IO.Compression.BrotliEncoder(11, 24)`, feed the file through `Compress(..., isFinalBlock: false)` and finish with `isFinalBlock: true`. Then verify that decompressing through `BrotliStream` gives the same SHA-256 as the DB. This takes about 6 minutes.
6. Replace `CampertronLibrary/content/RecreationDotOrg.db.br`, then run the full isolated test suite. `EmbeddedDatabaseTests` checks the shipped DB with the same validation as step 3.
7. GitHub rejects files over 100 MiB; the file is currently 26.6 MB. Record the export date, ETag, sizes and hashes in this file.
8. Since D51 (§AQ) the refresh of step 3 builds Campertron's index `IX_CampsiteAttributesEntries_EntityID` (about 35 MB more before compression), so a database embedded after this procedure has it; `RidbDatabase.Validate` and `EmbeddedDatabaseTests` do not require it, and every start builds it on a database without it.

Step 7's "this file" was `build-and-test.md` when the procedure was written. Record a refresh of the embedded database as a new validation record with the next free label, §BG or later (the router `README.md` §Maintaining these documents).

## Candidate download and inspection
Sources: §AC, §AN, §AX, §AZ. What a candidate is and how it differs from a release: `release-process.md` §Versions, candidates and publication. Downloading a finished run's artifacts reads GitHub state only; starting a dry run by hand is a manual dispatch and needs its own approval.
1. List the run's artifacts with their IDs: `gh api 'repos/ShaunAnthonyHathaway/Campertron/actions/runs/<run id>/artifacts?per_page=100'`. A dry run has 18: the 16 archives, `container-image` and `release-metadata`.
2. Download each archive into a new empty directory with `gh api repos/ShaunAnthonyHathaway/Campertron/actions/artifacts/<artifact id>/zip > <artifact name>`. The archives are uploaded as they are (`archive: false`), so `gh run download` fails on them; the run's page in a browser offers the same files. `release-metadata` is an ordinary artifact (`gh run download <run id> -n release-metadata`); it holds the run's `SHA256SUMS.txt` and, for a dry run, the template `RELEASE_NOTES.md`.
3. Check every archive:
   - its SHA-256 equals its GitHub artifact digest; `sha256sum --check --strict SHA256SUMS.txt` passes 16/16, and a local recomputation agrees;
   - it has exactly one top-level folder `campertron-<app>-<version>-<rid>` and the host executable (with the executable bit in a tar archive);
   - `CampertronLibrary.dll` and the app's DLL embed `<version>+<commit>`, here `0.0.0-dryrun.<n>+<commit>`;
   - the runtime config is self-contained `net11.0` on .NET 11;
   - Campertron's own PDBs are present, and the three Windows GUI archives carry no `libSkiaSharp.pdb` or `libHarfBuzzSharp.pdb` (TD-35);
   - all 16 name one compiler identity (the run's assemble summary lists it).
4. ## Manual platform validation of the database refresh
Source: §N, "Manual validation procedures for platforms not run here" (2026-11-11, D26), unchanged in its record; adapted here only where it pointed at that record's own results. Use these for a change to the refresh on the platforms the automated runs do not cover (`build-and-test.md` §Recommended verification after changes, "RIDB refresh changes").

Use a published build of the branch and an isolated data folder: on Linux a new `XDG_DATA_HOME`; on Windows and macOS a separate user account or virtual machine, because `XDG_DATA_HOME` does not redirect `%LOCALAPPDATA%` or `~/Library/Application Support`. Never the maintainer's own account or data. Before each check, set that folder's `General.yaml` to `outputTo: Console` and note the SHA-256 of its `RecreationDotOrg.db` and its `lastRidbDataRefresh`.
1. **Windows, GUI holding pooled connections while the console refreshes:** start `CampertronGUI.exe`, select a park, state and city so it has queried the DB. 2. **Windows, competing writer:** while the console refresh is validating, open the DB in `sqlite3.exe` and run `BEGIN IMMEDIATE;` (keep it open for more than 30 s). Expected: after "Installing the refreshed database", about 30 s later, an unhandled `SqliteException` with error 5; the DB hash and `lastRidbDataRefresh` unchanged; then `ROLLBACK;`. Repeat and `ROLLBACK;` after 10 s: the refresh succeeds.
3. **macOS** (osx-arm64 and osx-x64): run the console refresh with the GUI open, as in 1. Then run it again and force-quit the console (`kill -9 <pid>`) right after "Installing the refreshed database" is printed. Expected: the next start works and the DB is either the previous or the new one (`sqlite3 RecreationDotOrg.db "PRAGMA quick_check;"` prints `ok`).
4. **Docker with `/config`** (§N ran it on Linux x64; repeat on other hosts): `docker run` the image with `-v <dir>:/config -v <dir2>:/cache` (scratch folders) and a `General.yaml` with `autoRefresh: true` and an old `lastRidbDataRefresh` (container mode still auto-refreshes, TD-03). Repeat with `docker kill` during "Installing the refreshed database": the next container start works.
5. **Insufficient disk space** (Linux): put the data folder on a small filesystem, for example a 600 MiB loop-mounted ext4 image, with the 226 MB DB installed (the staging copy, its WAL and the installation's WAL needed about 700 MB more in 2026-11; Campertron's index adds about 35 MB since D51). Run the refresh with an extracted export. Expected: an `SqliteException` (`SQLITE_FULL`, "database or disk is full") during staging or the installation, the installed DB hash unchanged, `lastRidbDataRefresh` unchanged.
6. **Forced termination during the installation:** the kill harness (§Validation harnesses, Linux). On Windows: Task Manager → End task on the console right after "Installing the refreshed database"; expected as in 3.
7. **The GUI's refresh (since D61) on Windows and macOS:** in the isolated account, Settings > System > Campground data: Refresh campground data…, Start refresh, and let it finish (expected since D62: "Restarting Campertron…", then a new window where the old one was, at Settings > System with "The campground data was refreshed and Campertron restarted successfully." and a new "Last refreshed"; no `CampertronDownload-*` or `CampertronExtract` folder left in `LocalApplicationData`, and the `CampertronGUI/restart` folder empty; repeat with the window maximized, on a second monitor if there is one, and with an unsaved change in Settings, which keeps the window with a manual-restart message).
   Again with Cancel while it downloads (expected: "The refresh was canceled. The campground data was not changed.", the DB hash and `lastRidbDataRefresh` unchanged, the folders removed); and once more closing the window while it downloads (the process ends within a second, nothing changed) and while it installs (the process stays until the installation finished). 8. **All 8 publish targets:** the release workflow's publish, contents and `check_publish_runtime` steps, which every Release dry run runs (`release-process.md`). ## Validation harnesses

### RIDB refresh interruption (kill harness)
Source: §N (D26), including its `General.yaml` points.
- A .NET console that references `CampertronLibrary` runs the production refresh, `RefreshRidbRecreationData.RefreshData(false, <config>, () => <an extracted export>)`, in an isolated `XDG_DATA_HOME`. `CampertronConfig/` holds the embedded database, marked in its first facility to tell old from new, and a `General.yaml` with `outputTo: UnitTest`, `autoRefresh: false` and an old `lastRidbDataRefresh`; `CampertronCache/` holds a few files, or 150,000 for the cache points. The console timestamps every line it prints.
- A Python driver (`python3 -I`, `ctypes` inotify, no packages) sends `SIGKILL` at each point, triggered by a console message plus a delay or by an inotify event in the settings folder. Then it checks the database after recovery (`PRAGMA quick_check`; old or new by the marker and the row counts), the WAL size before recovery, staging directories, remaining cache files, the timestamp in `General.yaml`, the next start (`Load.GetConfig`, then `Read.UniqueStates` and `Read.UniqueParks("UT", "SPRINGDALE")`) and that the next refresh's stale cleanup removes a staging directory.
- Pass rules: `quick_check` ok and the database wholly old or wholly new; a new database leaves no old cache file; an old one leaves the timestamp unchanged; the next start works; stale staging is removed; `General.yaml` is never empty or partial.
- Points (§N's tables, 31 on the code of 2026-11-11): template creation, staging clear, population, after the staging validation, during the cache step, before, during and around the commit of `BackupDatabase`, after the installation, during the cleanup, and the `General.yaml` points from the temporary file's creation to the replacement.
- Cross-process scenarios with the same harness: a competing writer holding a write transaction (`BEGIN IMMEDIATE`) longer and shorter than the 30 s wait, an idle connection across the refresh, two refreshes 0.3 s apart, the refresh or repair lock held by another process, and a startup repair in another process during the installation.
- **The whole refresh, download included** (§BD, D61): the published console's automatic refresh at start (`autoRefresh: true`, an old `lastRidbDataRefresh`, `outputTo: UnitTest`, so it exits after the refresh) downloads a generated export (§Full-export comparison of the RIDB import) from the RIDB stand-in (§Stand-ins for recreation.gov, email and the browser), the console and the stand-in in one network namespace. The driver also kills at points that only the folders show (half the archive downloaded, the first extracted file), checks that a killed refresh's `CampertronDownload-<32 hex>` folder is removed by the next refresh ("Removed …, left by an interrupted RIDB refresh") and that no archive is left at `LocalApplicationData`'s root. §BD's 18 points passed (one, inside the `General.yaml` write, is shorter than the driver's 5 ms polling and was not hit); an uninterrupted run, sampled every 5 ms, gives the data folder's peak size.

### The real RIDB refresh, isolated
Source: §BD (2026-11-18, D61 and D62). Only with the maintainer's explicit approval for that run (`CLAUDE.md` §Approval boundaries); it downloads the whole export (about 574 MB) from `ridb.recreation.gov`.
- The GUI (or the console) runs inside `unshare -rmn`: a tmpfs mounted over `/home` (check that only the new home is there and the real one is not visible), `HOME` on that tmpfs, every Campertron path in a new scratch folder through `XDG_DATA_HOME`, and loopback as the only interface. A self-contained build is needed: the per-user .NET under `/home` is hidden.
- The only way out: a relay inside forwards `127.0.0.1:<port>` to a Unix socket file outside (its path under 108 bytes, in an owner-only folder), where a proxy tunnels only `CONNECT ridb.recreation.gov:443`, a fixed number of times, and refuses anything else before contacting a host. `HTTPS_PROXY` points the program at the relay; a direct connection fails at once.
- One `curl -I` through the same proxy first (size, ETag, Last-Modified; any answer but 200, such as a redirect to another host, stops the run); then the program's one GET. A sampler outside measures the data folder every 100 ms by component, stops the program (`SIGKILL`) below a free-space guard or on any abort flag, and checks the program's open files for paths outside the scratch folder.
- Afterwards: check the folders for leftovers, query the installed database in the scratch folder, keep only the numbers, and delete the whole folder, the build and the socket folder.

### Full-export comparison of the RIDB import
Sources: §M (D25), §N, §O, §AQ.
- Download one RIDB export and use it for both builds: the live export changes over time (the records name its ETag). Refresh with the previous build and with the new one, each in its own isolated `XDG_DATA_HOME` that starts from the extracted embedded database, in the same culture (the row order of text keys follows the current culture, TD-36).
- Checkpoint each result (`PRAGMA wal_checkpoint(TRUNCATE)`) and compare: `PRAGMA integrity_check` and `foreign_key_check`; `sqlite_master` and `pragma table_info`; per table the row count, `EXCEPT` in both directions and with `rowid`; per-column `typeof` counts; the SHA-256 of the file. Then run `ReleaseCheck` on the result.
- Byte equality excludes SQLite's three header counters (file change counter, schema cookie, version-valid-for), which depend on the template's history; since D51 both results also carry Campertron's index (business-rules §8; §O, §AQ).
- **Without the network** (§BD): a generated export from the bundled database (a scratch Python script writes its six tables as the RIDB files, `{"RECDATA": [...]}`, booleans as JSON booleans, optionally a marker in the first facility's name) served by the RIDB stand-in to both builds' consoles. The two results were identical, SHA-256 included. The real export is downloaded only with the maintainer's approval (it contacts `ridb.recreation.gov`).

### Settings-file interruption harness
Source: §AE (D40).
- A scratch console program references the library, sets the internal `ConfigFileReplace.Step` seam by reflection to print each step and pause at a chosen one, and runs `Yaml.GeneralConfigReplaceYaml` on a commented `General.yaml` (a replacement) or `Yaml.EmailConfigGetConfig` on an empty folder (a creation), in a new temporary folder.

### Stand-ins for recreation.gov, email and the browser
Sources: §Q, §T, §Y, §Z, §AA, §AB, §AJ, §AK.

It answers `CONNECT` only for the hosts it stands in for (`www.recreation.gov`; for a refresh also `ridb.recreation.gov`), terminates TLS with a throwaway CA given in `SSL_CERT_FILE` (with `SSL_CERT_DIR=/nonexistent`) and never connects anywhere. ## Tooling problems and their fixes
- **`release-policy.sh` needs bash.** Sourcing it in zsh fails, because its functions' local `path` is zsh's `PATH`. Run it as `bash -c 'source .github/release-policy/release-policy.sh && …'`, as CI does (§AP).
- **A full `/tmp`.** When `/tmp` is a tmpfs, isolated runs that each extract the database (226 MB, 261 MB with Campertron's index) fill it, and tests then fail within milliseconds. Remove the session's own isolated folders and watch the free space (§AR).
- **A restored negative control** still needs a rebuild before any later `--no-build` run, or that run tests the mutated build (§AF).
- **Artifacts uploaded with `archive: false`:** `gh run download` 2.104.0 fails on them ("error extracting zip archive: zip: not a valid zip file"); download them with `gh api …/actions/artifacts/<id>/zip` (§AN; §Candidate download and inspection).
- **Release bodies:** extract a body with `jq -j`, never with gh's `--jq`, which appends a newline (`release-process.md` §Release workflow, the `release` job).
- **`gh attestation verify`** (gh 2.104.0) prints nothing on success when its output is not a terminal; add `--format json` (`release-process.md`, "Release procedure" step 5).
- **`tr: write error: Broken pipe`** lines in release logs come from `pdb_option` and are harmless (§V, §AZ).
- **Nested sessions:** with D-Bus service activation, `xdg-desktop-portal-kde` and `ksecretd` aborted and dumped core, so use a session-bus configuration without service directories (§X). The Wayland socket path must stay below 108 bytes, hence a short `XDG_RUNTIME_DIR` (§Refreshing the README screenshots).
- **Keys into a GUI window:** XTest key events did not reach an XWayland window under KWin (again in §BD); inject them through the window's platform input (§P, §X) or invoke the controls' automation peers (§BD).
- **ImageMagick 7.1.2's `import -window <id> <file>`** failed in the nested session with "missing an image filename"; capture the X11 window with `XGetImage` through `ctypes` and write the PNG yourself (§BD).
- **`pkill -f <pattern>`** also kills the shell that runs it when the shell's own command line contains the pattern (exit code 144); select the PIDs with `ps` and `awk` excluding `awk` itself (§BD).
- **Hover in captures:** KWin centers a new window, under a pointer resting at the output's center; move the window to 0,0 once the startup is ready (§AW).
- **`RenderTargetBitmap`** misdraws Campertron's window (borders and text at different offsets): capture the real window (§Refreshing the README screenshots).
- **Headless Chrome's `--screenshot`** cannot scroll to a section of a large page; drive Chrome over the DevTools protocol (§Refreshing the README screenshots).
- **The console through a pipe:** it queries the cursor position, so a plain pipe hangs it; use raw mode and `cat` around `script`. Through the pipe `script` cannot learn the terminal's size: set `stty cols … rows …` inside it, or the console wraps at 80 columns (§Refreshing the README screenshots).
