## Behavior intent
Questions of this group that are still open (#7, #9, #10, #11, #31) are in `../open-questions.md`.

### #5
~~Are the equipment and attribute include/exclude semantics intentional? The config value contains the RIDB value (substring), and an exclude only drops a site when **all** exclude values match (business-rules §3).~~ **Answered 2026-11-16 by the maintainer (D51):** the AND of the exclude lists was not intended; every include and exclude list is OR since D51. The containment direction is kept as the `Contains` matching (a file without `filterMatching`, and an explicit `filterMatching: Contains`); `Exact` (new searches) compares whole values (business-rules §3).

### #6
~~Is `includeCampsiteType` meant to be AND (`All`) across values, while the other include filters are OR (`Any`)?~~ **Answered 2026-11-16 by the maintainer (D51):** no; it is OR since D51, like every list.

### #8
~~Should `Camp.History` markers be created for `HtmlFile` output (they are), and should they ever expire or be cleaned up?~~ **Closed 2026-11-14 (owner decision, branch `fix/manual-search-notification-history`):** no. Markers are the Email loop's notification history only: Console, HtmlFile and UnitTest neither read nor write them, so manual searches show every current match. They never expire and Campertron never deletes them; deleting `Camp.History` resets the Email history. Existing markers are left as they are, and a reported campsite and date stays suppressed for Email even if it disappears and reappears (business-rules §5, D8).

### #37
**Closed 2026-11-14 by the consolidated deferred-work audit: no application defect found; the cause remains an inference, not an established fact.** The evidence below shows no application-controlled shutdown path, no recurrence in 10 isolated reproductions, and a concurrent manual close of a separately launched copy on the same desktop as the most likely explanation; the maintainer has not confirmed it. ## Answered by the email-mode repair (2026-11-21, decision D64)
### #40
~~Should the Email loop stop when no search is enabled?~~ **Answered by D64 (2026-11-21 UTC, the email-mode repair, approved by the maintainer after `v0.1.1`; `validation/ba_v0.1.1.md` §BJ):** email mode starts its checks only when its start produced a search to check (an enabled search the load did not refuse, with a `campgroundID`); otherwise it writes one error that says why and what to do, and the console exits with code 1, without a check, wait, request, email or file write. The concern recorded below, that a supervisor which restarts on failure would start it again and again, is answered by stopping visibly and by the README's warning about restart policies, not by a restart design. Not in `v0.1.1`. Moved here from `../open-questions.md` on 2026-11-21 (`README.md` here, the notes of the email-mode repair).
Original record, kept for history:
Should the Email loop stop when no search is enabled? Since D37 (TD-13), search files of which none has `autoRun: true` are left as they are and nothing is searched; the Email loop then writes the warning once and checks 0 searches every minute ("Check N: 0 searches, nothing new."), because that is what every output type does with no search. The search files are read only at the start, so enabling a search needs a restart anyway. Alternatives: end with the warning and exit code 1 (a restart-on-failure supervisor would then restart it repeatedly), or with 0. Product direction; default: keep the current behavior until stable readiness. **Still open after CM3 (D41):** the folder validation reports it (`NoEnabledSearch`, a warning, with the Email loop's consequence in its message) for a later GUI to show; the loop itself is unchanged. **Still open after CM6 (D44):** the GUI's Searches tab shows that warning (with the Email loop's consequence when the General form's output is Email)
and never enables or creates a search by itself; the loop is unchanged (by the maintainer's CM6 brief), for stable readiness. **Reconciliation (2026-11-15, D47):** not a blocker of preview.2: the behavior is safe and bounded (one warning, then a check of 0 searches every minute), and ending the process instead would make a supervisor that restarts on failure start it again and again. Default until stable readiness: keep it. **Still open after V011-3 (D63, 2026-11-18):** the warning's words changed ("No usable search file is enabled (autoRun: true), so email mode checks 0 searches every minute until a search is enabled and email mode is started again.", then that the Results tab still runs a search that is not enabled); the loop is unchanged.
