### D81
**Decision:** **The web UI's access protection and security defaults (2026-11-22; the maintainer's choice of reachability differs from §CB's recommendation of loopback only).**
(1) A password is required by default. On the first start without one, Campertron prints a one-time setup code on its console (in a container: `docker logs`), and the setup page needs that code to set the password. The password is kept as a PBKDF2-SHA256 hash in an owner-only file in the settings folder, never in a YAML settings file.
(2) Reachable from the network by default: on the desktop and in the container web mode listens on all interfaces; the Docker documentation publishes `-p 8790:8790` and names `-p 127.0.0.1:8790:8790` as the local-only option.
(3) Both can be turned off: the password (no sign-in) and the network listening (local only).
(4) A save that leaves the password off while network listening is on shows a clear warning at that save and asks for confirmation. After it nothing warns again and nothing blocks: no lasting banner, no refusal to start.
(5) Kept from §CB's section D: the session cookie (HttpOnly, SameSite=Strict, Secure over HTTPS, an idle timeout; a password change signs out every session); antiforgery tokens on every POST, and changes by POST only; Origin and Host checks; security headers with a strict Content-Security-Policy (`script-src 'self'`, `frame-ancestors 'none'`), `nosniff`, `Referrer-Policy: no-referrer`, `no-store` for signed-in pages, no `Server` header and no CORS;
ASP.NET Core's Data Protection keys in the settings folder, owner-only (its default, `~/.aspnet/DataProtection-Keys`, is outside Campertron's folders and lost in a container, §CB); forwarded headers trusted only from configured proxy addresses; HTTPS from a reverse proxy; rate limits for the sign-in, the site and the request size; one manual search or refresh at a time per process; the write-only SMTP password (D82); no request that takes a path (a search file is chosen from the folder's list or named through `SearchFileName.Check`).
(6) How the Host check works while network listening is the default (which names and addresses it accepts) is proposed with D79's PR 4.
(7) An exception to `CLAUDE.md` §Validation and logging: ASP.NET Core's log output is off; Campertron writes only its own fixed lines through `ConsoleUi`: the listening address, the setup code and the number of failed sign-ins with the client address. Never a request body, query string, cookie, header, form value or file content.

**Evidence:** §CB (section D; the probe that wrote a Data Protection key to `~/.aspnet`).

**Stated rationale:** Campertron runs on home servers and is used from other devices; a password from the first start protects it there, and after one clear warning the user decides.

### D83
**Decision:** **The unattended monitoring in web mode, and a monitoring lock (2026-11-22, as §CB proposed).**
(1) A host-neutral monitoring service in the library, in the pattern of GS1's search (D45) and the refresh service (D61), runs the monitoring's checks; the console's email and ntfy mode become its adapter, with their output, exit codes, one-minute wait, start checks and `Camp.History` rules unchanged (ER-02, ER-03, ER-13).
(2) In web mode the monitoring starts by itself when `outputTo` is Email or Ntfy and the start's checks pass (D64, D66, D67, D71, D73); otherwise the page says why, in the start's words. Start, Stop and Restart from the browser; Stop holds for the running process only (it saves nothing, and the next start of web mode starts the monitoring again); a check that is sending finishes its deliveries and records before it stops. The search files are read at each start of the monitoring, as today, and the page says when they changed since.
(3) Web mode keeps running with no search file or no search to check, waiting to be configured, and creates no example search (as email mode since D65).
(4) A failed send follows the maintainer's rule (D76): a visible error, the monitoring stops, the failed delivery's openings are not recorded in `Camp.History`; the process and the web UI stay up, and nothing restarts the monitoring by itself.
(5) A monitoring lock: one monitoring at a time per settings folder, by a lock file in it, like the refresh's (D26); a second monitoring, of web mode or of the console's email or ntfy mode, refuses to start with a clear message. ER-02 and ER-03 change with the pull request that implements it (D79's PR 2).
(6) Manual searches from the browser keep the desktop Results tab's rules (ER-19, ER-20); a refresh of the campground data pauses the monitoring.

**Evidence:** §CB (sections A and C: the loop in `Load.RunConsoleSearch` blocks, keeps static state, has no stop or status and ends the process on a failure).

**Stated rationale:** the notification-only user sets up and starts the monitoring in the browser; one monitoring per folder prevents duplicate notifications; the send-failure rule stays the maintainer's.

### D90
**Decision:** **The monitoring service and the monitoring lock as implemented (D79's PR 2, 2026-11-23 UTC, on the maintainer's instruction of 2026-11-22; D83's points (1) and (5) for the console; web mode's use of the service, points (2) to (4) and (6), comes with D79's later pull requests).**
(1) **The service.** `MonitoringService` (`CampertronLibrary/function/RecDotOrg/monitoring/`), an instance with no static state, in the pattern of D45's search service and D61's refresh service. `Start(settings)` runs the start's checks in the console's former order (the `Email.yaml` and `Ntfy.yaml` checks, the SMTP password and ntfy's token from their sources, the search files read once and D64's gate, then the monitoring lock, then each campground's cache) and returns a typed result (`MonitoringStartResult`: started, or the problem and its words; a start that threw carries its exception); then the checks run on a thread of the service's own, one minute apart (`CheckInterval`).
`Stop` asks the run to end and waits until it has: the wait between two checks ends at once; a check that is searching ends at its next checkpoint and nothing of it is sent or recorded (its openings come again); a check that is sending finishes every notification and its records in `Camp.History` first. `Restart` is `Stop` and `Start` (the search files read again, the check number from 1). A host's cancellation token stops it as `Stop` does.
`GetStatus` gives a snapshot: the state (not started, starting, checking, sending, waiting, stopped, failed), whether a stop was asked for, when it started, how many searches it checks, the last check's number and time, the next check's time, the last error with its words, the last start's result, and whether the search files changed since the start (by their names, sizes and times of writing, never their contents).
(2) **No static state.** `Load.CheckNumber` and `Load.CheckWait` are gone: the check number, the wait, the clock and the output are the service's (`MonitoringOptions`). The service writes nothing to a console and ends no process: its events (`MonitoringEvent`: starting, a status line, a warning, the searches loaded, a check's report, an email or an ntfy notification sent, the deliveries finished) go to the host. A check's searches reach the service through `RunningData.Monitoring` (`MonitoringRun`: the token, the warning and status lines, what a blocked request does).
Every start counts its checks from 1 (before, the number was the process's, which is the same for the console: one start for each process).
(3) **The console is its adapter** (`MonitoringConsole`): it writes each event through `ConsoleUi` with the calls the loop made, in their order, rethrows a start's or a check's exception unchanged for `Program.Main` to report (exit code 1), and gives the service the console's own answer to a blocked request (the error, the five-minute wait and exit code 1, TD-44). Its output, exit codes, start checks (D64 to D67, D71), one-minute wait, send-failure behavior (D76) and `Camp.History` rules (ER-03) are unchanged. Without a host's own handling a blocked request ends the monitoring as failed and the process goes on (for web mode).
(4) **The monitoring lock.** The file `Campertron.monitoring.lock` in the settings folder, kept open without sharing while a monitoring runs, as the refresh lock is (D26): one monitoring at a time for a settings folder, whether a console in email or ntfy mode, a container, or (later) web mode. The lock is the open handle: the operating system releases it when the monitoring ends in any way (a stop, a failure, a kill, a power loss), so a lock is never stale and a lock file left behind locks nothing; the file is never deleted and stays empty. It is created for its owner only (0600 on Unix; the settings folder's access rights on Windows); an existing file keeps its rights.
It is taken last of the start's checks, so a start that is refused for another reason still creates nothing (D64's promise). It is separate from the refresh lock and the repair lock.
(5) **The message and the exit code.** A start the lock refuses says one error on standard error after the start line, naming the mode ("email mode" or "ntfy mode"): "… can't start: another Campertron is already monitoring this settings folder.", then "Only one monitoring runs for a settings folder, so that every opening is notified once. Stop the other one first (another CampertronConsole in email or ntfy mode, or a container that uses the same settings folder), or give this one its own settings folder." and "Nothing was searched or sent.".
A settings folder that can't hold the lock's file says "… can't start: the monitoring's lock file can't be created or opened in the settings folder.", what the file is for and to let the user that runs Campertron write to the folder. Both end with **exit code 1**, the code of every handled failure and of every other start that is refused (D64, D66, D67): a supervisor sees a failure, never a process that seems to monitor.
(6) **What changed for a user:** a second monitoring of one settings folder is refused where it used to send every notification twice; the file `Campertron.monitoring.lock` appears in the settings folder at the first monitoring; a settings folder the monitoring can't write to is refused at the start (before, the first opening's email was sent and the marker's write then failed, at every restart again). The details of an unexpected failure (the lines after "Details, for a problem report:") name the service's functions.
(7) **Limits:** on Linux and macOS the lock is advisory (`flock`, which every .NET process takes for an open without sharing), so it holds between Campertron's processes on one host, also across containers that use the same folder; a file system without such locks (some network shares) gives no protection. Not run natively on Windows or macOS (open question #49). It does not make the campground cache safe for two processes (TD-54 stays open: a monitoring and a manual search can still build one campground's cache at once).

**Evidence:** `validation/bv_v0.2.0.md` §CC (the tests, the negative controls and the local build's check: a console in email mode against a loopback SMTP server, and the lock refusing a second instance).

**Stated rationale:** web mode needs a monitoring it can start, stop and show; the console must not change for it; one monitoring for a folder prevents duplicate notifications; and a start that is refused must stay a visible failure.

### D91
**Decision:** **The shared form layer as implemented (D79's PR 3, 2026-11-23 UTC, on the maintainer's instruction of 2026-11-22: "Move the GUI-locked logic into a shared, Avalonia-free layer (library or new project, your recommendation, justified) that both the desktop GUI and the future web UI use").**
(1) **Where: in the library**, `CampertronLibrary/function/Forms`, namespace `CampertronLibrary.function.Forms`; no new project. The library already holds what both UIs call (the editing session, D43; the search service, D45; the refresh service, D61; the monitoring service, D90), and the web host will be the console's (D80), which references the library and nothing of the GUI. The layer needs only the base class library, so no package changes. A project of its own would add a project file, a solution entry, the Dockerfile's copy step and the package policy's lists for no gain: nothing else would reference it.
(2) **Moved whole, with their names** (namespace, base class and three seams changed, nothing else): the Settings forms (`SettingsViewModel`, `GeneralSettingsViewModel`, `EmailSettingsViewModel`, `NtfySettingsViewModel`, `SettingsFileViewModel`), every field and row type of `SettingFields.cs`, `SecretFileMessages`, the Searches forms (`SearchesViewModel`, `SearchFileViewModel`, `AutoRunWording`), `CampgroundCatalog` and `CampgroundSettingField`, the filter selectors (`FilterSelectorField`, `FilterOptionRow`, `FilterCustomRow`, `FilterText`, `FilterChoiceSource`), the Results tab's rows (`ResultsSearchRow`, `ResultSearchViewModel`, the `ResultRow` types, `ResultText`, `BookingLink`), `ProgressGate`, `DataOperationGate` and `RelayCommand`. The names stay, "ViewModel" included: the desktop GUI's views and its 529 tests name them, and a web page's model is called the same.
The three seams: `FilterOptionRow.Indent` (an Avalonia `Thickness`) is gone, and the view indents by `Level` through a converter (28 pixels a level, as before); `FilterChoiceSource` takes its post to the UI thread from its host where it captured Avalonia's dispatcher; `SearchesViewModel`'s public constructor takes the host for it.
(3) **Split, not moved:** `ResultsViewModel` and `CampgroundDataViewModel` stay in the desktop GUI with the run's worker thread, the dispatcher, the timers and the automatic restart: that code is host-bound, and the GUI's tests read its IL for TD-56 (no worker asks for the dispatcher), ER-19 (only the Results tab's seams call the search service) and D61 and D62 (only the refresh's seam calls the refresh service and the restart).
Their rules and words moved into the layer, and the two classes call them: `ResultsSearchList` (the list of search files and the rules of its choice), `ResultsWording`, `BlockHold` (the five minutes after a block), `RefreshRules` and `RefreshWording` (the confirmation and cancel rules, the stages, counts and results); `SeverityBlock`'s rule is `MessageSeverity`. The confirmation's text is the layer's up to "you can cancel until the new data is being installed."; the sentences about the automatic restart stay the desktop GUI's.
(4) **`FormObject` and `FormHost`.** The moved classes derive from `FormObject`, the base class library's `INotifyPropertyChanged` with the two helper methods the code used (the same notifications, raised at once on the calling thread), in place of ReactiveUI's `ReactiveObject`; the GUI's own view models keep `ReactiveObject`. `FormHost` is the form's thread as its host gives it (a post captured on that thread, a one-shot timer, a repeating timer); the desktop GUI's is `GuiHost.Avalonia`.
(5) **Rules of the layer (ER-37):** no UI toolkit (no Avalonia, ReactiveUI or ASP.NET Core); no static state that changes (a web host runs many sessions); a form is used by one thread at a time and reaches it only through its host; a form's parsing, input errors, words, save rule and run rules belong in the layer, never in one UI.
(6) **For a user nothing changed:** no word, rule, layout, color or file. The same build's windows were compared with the build before it, side by side (`validation/bv_v0.2.0.md` §CE).

(2) **The host is built on an empty builder** (`WebApplication.CreateEmptyBuilder`): no `appsettings` file, no environment variable (`ASPNETCORE_URLS`, `ASPNETCORE_ENVIRONMENT`, the image's own `ASPNETCORE_HTTP_PORTS=8080`), no command line and no logging provider reach it, so D81's "ASP.NET Core's log output is off" holds by construction and where it listens is the command line's and `Web.yaml`'s alone. (3) **The command line.** `--web`, `--healthcheck`, `--listen` and `--port` are read only when one of them is given; then the whole line must be right (a wrong value, an unknown argument, an argument twice, `--listen` or `--port` alone, `--web` with `--healthcheck`: one error, the usage line, exit code 1, nothing created). Every other start still ignores its arguments, as it always did. `--listen` takes one IP address or `localhost`, never another name; `--port` 1 to 65535.
(4) **`Web.yaml`** is the web UI's own settings file (the "approved web-host configuration model"): `passwordProtection` and `networkListening` (both true by default, D81), `allowedHosts` and `trustedProxies`. It is a settings file like `Ntfy.yaml`: never a search file (a search can't be named so; a user's search file of that name would stop being one, as with `Ntfy.yaml` in D67), read by the bounded loader, judged by the validation with value-free errors, edited by the existing editing session (a missing file is a new file that only a save creates, owner-only), and never created by a start. `--listen` decides for its process; without it `networkListening` does. An error of the validation refuses the start: a name or a proxy silently left out would change who can reach the web UI.
(5) **The one confirmation (D81's point 4)** is `WebAccessRule`: a save asks only when it makes the settings open (the password off while the network is on) and the saved file is not open already. The confirmed state is the saved file itself, so nothing is kept beside it and nothing asks again; the validation has no finding for the open state. The state of the password file and of the keys never keeps a save from going through. The page that uses it is D79's PR 5; nothing of a settings page is in this pull request.
(6) **The password** is kept as `$pbkdf2-sha256$i=600000$<salt>$<hash>` in `Web.password` (owner-only, written whole, the first one create-only, a change in one rename, no backup of an old hash). 600,000 iterations is OWASP's number for PBKDF2-HMAC-SHA256, and PBKDF2 is what the base class library has (no package for Argon2 or scrypt). A password is 10 to 128 characters, hashed in Unicode's NFKC form; a record is read strictly, 100,000 to 10,000,000 iterations. A password file that exists but can't be used refuses the start while a password is required: the web UI never runs open, and never offers a new setup code, because its password got lost. To set a new one the owner deletes the file.
(7) **The setup code** is 12 characters without look-alikes (58 bits), in memory only, good for 30 minutes and one use; a restart makes a new one. A wrong entry does not use it up (anyone on the network could otherwise lock the owner out; the rate limit and the 58 bits hold guessing off), and a new code can be asked for only once the last one is used or expired. The setup signs nobody in.
(8) **Sessions are kept in the web UI's memory**, and the cookie (HttpOnly, SameSite=Strict, Secure when the request is HTTPS, a session cookie, named with a short random name of the settings folder's own, so that two web UIs on one computer keep their own cookies) carries only a random identifier inside its encrypted ticket. So a sign-out ends the session in the web UI itself and a copied cookie is worth nothing afterwards, a password change ends every session (D81), and a session ends after 8 idle hours, 7 days at the latest, or when the password file changes outside the web UI. **A restart of web mode ends every session:** nothing of a session is written to disk. This was chosen over sessions that survive a restart, which would need the sessions, or their revocations, in a file; the Data Protection keys are kept all the same, for the forms' tokens and because the cookie's ticket is still what authenticates the identifier.
(9) **The Host check (D81's point 6).** Every IP address is answered, and of names only `localhost`, this computer's own name (also with `.local`) and the names of `allowedHosts`. A refused name gets a fixed page that says so and repeats nothing of the request.
(10) **The Origin check** refuses a POST that does not say it comes from the web UI's own address: `Origin` decides when it is sent, else `Referer`; a POST with neither is refused, and so is one that `Sec-Fetch-Site` calls cross-site. (11) **`Referrer-Policy` is `same-origin`, not D81's `no-referrer`.** With `no-referrer` a browser sends `Origin: null` and no `Referer` with a page's own form (the Fetch standard; seen in Chrome 155, `validation/bv_v0.2.0.md` §CF), so the Origin check of the same decision would have nothing to check. (12) **Forwarded headers** are read only from `Web.yaml`'s `trustedProxies` (addresses or networks; one proxy; the address, the scheme and the host name). The framework's own defaults, which trust this computer's loopback addresses, are removed: a reverse proxy on the same computer must be listed too. HTTPS is a reverse proxy's (D81); the web UI itself speaks HTTP only and sends no `Strict-Transport-Security`.
(13) **Rate limits:** 5 POSTs with a password or a setup code a minute from a client (an IPv6 client is its /64 network), 30 a minute from all clients together (so many addresses can't keep the computer hashing), 240 requests of any kind a minute from a client; the health answer is not counted. 1 MB is the largest request.
(14) **The keys** of ASP.NET Core's Data Protection are in `Web.keys` of the settings folder, the folder 0700 and each key file 0600 on Unix (on Windows the settings folder's access rights, as for the monitoring lock), written whole, never following a link. (15) **The console** gets only the web UI's fixed lines (D81's point 7): the start, where it listens and whether a password is required, the setup code between two marks on a line of its own, a failed sign-in with the client's address (at most one line a minute for an address, with its count), an unexpected failure by its exception type's name, and the stop. ### D108
**Decision:** **The results page shows a running search's progress by itself (the maintainer's approval of 2026-11-24 UTC, after the personal test of `v0.3.0`'s web UI; a correction inside `v0.3.0`'s scope lock: a defect of the web UI found by the local test before a candidate). The exact rules are `../business-rules-settings.md` §34; this record says what was decided and why.**
(1) **The finding:** after Start the page showed "Searching…", a bar and an elapsed time and never changed; the user had to find "Show the latest progress" and select it again and again, so the page looked frozen. D97 had chosen exactly that (its point (0): "progress by reloading the page (no script, no automatic reload)").
(2) **The cause:** no part of the page asked the web UI again after it was shown. The run's progress was always there to take (`WebResultsRun`, the latest snapshot), but only a GET of the whole page took it over.
(3) **The mechanism** (the smallest that keeps the security): a small first-party script, as D80's point (2) allowed ("at most a small first-party script, served by Campertron itself and using no library, for progress"), asks a read-only GET of the page, `?handler=progress&run=<key>`, every two seconds, one request at a time, and sets text and the bar's attributes in place; once the run has ended it takes the page's results part (`#results-view`) from a GET of `/results` and puts it in place once. Rejected: an automatic reload (it flashes, loses the focus and the scroll position and announces the whole page again); Server-Sent Events (a long-lived connection per page that reverse proxies may buffer, and the session's one-request lock held or bypassed; nothing in the requirement needs push); rendering fragments in the browser (the page's words stay the server's).
(4) **Security kept:** the Content-Security-Policy is unchanged (`script-src 'self'` and `connect-src 'self'` already allowed it; no inline script, no other site, no CORS). The script is an embedded file at `/assets/results.js`, versioned by its content, for a signed-in session only (no new anonymous address). The answer passes every request check (method, Host, Origin, rate limits, the sign-in), is the session's own run only, named by a key of the web UI's random name and the run's number, and holds only what the page shows (no path, file, setting, exception or other session's run); it only looks: it never starts, repeats or cancels a search, writes nothing, notifies nobody and takes no lock. Cancel and Start stay POSTs with the antiforgery token and the revision. Each answer counts as a request of the session (the established idle time), and the asking stops at the run's end.
(5) **Order and generations:** each answer has a number that rises with every answer of the session; the page applies one only for its run and only when it is newer (canceling and ended are never replaced by running); a page of another run, of an earlier start of the web UI or of another session is told so and shown nothing, and stops asking.
(6) **What the user sees:** the stage, the counts, the elapsed time (the web UI's clock), each file's state and "This page updates by itself while the search runs. Last update: <time>."; a failed, stalled (ten seconds) or unusable answer at once as a warning that says the search goes on and the page keeps trying (tried again later and later, at most thirty seconds apart); the end, a signed-out session or an out-of-date page each said once; never the focus or the scroll position moved by an update, the focus put on the status only when the control it was on is replaced at the end; one polite announcement region outside the replaced part, for those changes only. "Show the latest progress" stays, and without a script the page is the server's as before.
(7) **Not in it:** a change of the run, its rules or words (the shared form layer is unchanged), of the desktop GUI, the console, the monitoring page (which still updates on request), the other pages, the session's lifetime, the workflows or the site.

**Evidence:** `validation/co_v0.3.0.md` §CU (the root cause, the tests in a real browser, the negative controls, the validation); the maintainer's approval of 2026-11-24.

**Stated rationale:** the maintainer's: a page that looks frozen during a search is unusable; manual refreshing was a deliberate choice of D97 and is superseded for active manual runs only, with the security and the run's rules unchanged.

*Note (2026-11-24 UTC, D109):* D109 made this mechanism the web UI's one for every page of an operation that goes on (the script renamed `Assets/live.js`, the answer's shape `WebLiveAnswer`, the results part `#live-view`) and superseded point (4)'s "each answer counts as a request of the session": a page's own requests never renew the session's idle time.

### D109
**Decision:** **Every page of a user-started operation that goes on updates by itself, and never again asks the user to show the latest state again and again (the maintainer's rule of 2026-11-24 UTC, after the personal test of the consolidated `v0.3.0` package found the system page's refresh frozen; a usability correction inside `v0.3.0`'s scope lock, not a feature). The exact rules are `../business-rules-settings.md` §39 (the rule), §34, §35 and §36 (the three pages) and `../engineering-rules.md` ER-43; this record says what was decided and why.**
(0) **The rule (applies to all later web work):** a page that shows a user-started, long-running operation updates its visible state by itself while the operation goes on: non-disruptively (focus and scroll kept, no flashing, no reload), with the current state, meaningful progress and the elapsed time where they exist, when the browser last got an update, a browser's failure to get one told apart from the operation's own failure, recovery by itself, a stop at every end (completion, failure, cancellation, a block, a replacement, a lost session), "Show the latest …" kept as the fallback; it never starts, repeats, resumes or extends the operation and weakens no protection (the sign-in, a session's ownership, the Host and Origin checks, antiforgery, the rate limits, the Content-Security-Policy, the fixed errors, a page's revision or moment).
(1) **The finding:** the system page, during a refresh of the campground data, said "This page does not update by itself: select Show the latest progress to see how the refresh is going." and stayed as it was: D108's rejected pattern again.
(2) **The audit** (§CV, every web page): two pages had it. The system page (the refresh, D99) and the monitoring page (D98: "This page does not update by itself: select Show the latest status …", frozen also while the monitoring started, stopped, restarted or paused, and "Show the latest status to see when it has" among its words). (3) **The maintainer's two decisions** (2026-11-24, asked because the monitoring runs without end): the monitoring page is corrected in the same pull request, through the same architecture; and a page's own requests never renew the session's idle time, on every live page (the results page included, which until then kept its session alive while a search ran: D108's point (4) "each answer counts as a request of the session" is superseded).
(4) **The architecture (D108's, made the web UI's one):** one first-party script, `Assets/live.js` (D108's `results.js` renamed and generalized; owner-only, versioned, no library, the Content-Security-Policy unchanged), for every live page: the page names its operation (`#live`, the partial `_Live`, with the page's words); the script asks the page's own `?handler=progress&key=` (a GET that only looks) and sets the text of the page's own elements and the bar; when the answer's view differs from the page's (a control, a section or the end changed) it takes the page itself (`?handler=view`, the page as a GET shows it, without an action's notice) and puts the changed parts in place: a part named by `data-part` whose name is unchanged stays, with the focus in it.
  One answer shape (`WebLiveAnswer`, format 2: state, key, number, rank, view, fields, bar) and one request rule (`WebLive.IsObservation`: those two GETs check the session without renewing it, `WebSessions.Check`).
  Each operation keeps its own read-only observer and key: the results page's run (the session's own, D108), the refresh (the web UI's random name and the refresh's number; every signed-in session sees it, as the page), the monitoring (the web UI's random name; every signed-in session).
(5) **Order:** each answer is numbered higher within the browser session (its workspace's counter, under its lock); a run's and a refresh's states only go forward (a rank: running, canceling, finishing for the refresh past its cache step, ended), so Cancel, the installation and an end are never replaced by an earlier state; the monitoring's states come round again (rank 0), its answers ordered by number only.
(6) **What the user sees:** "This page updates by itself while the refresh runs (the monitoring runs). Last update: <time>."; the refresh's stage, counts, elapsed time and bar in place, then Cancel's change, the cache step and the end with the card's new date and the configuration's refresh line, each announced once; the monitoring's status, each check as it begins and ends and its sending, its start, stop, restart, pause for a refresh and start after it, Start, Stop and Restart (and the focus on them) left as they are while checks go on; a failed, stalled or unusable answer said at once as the page's problem ("That does not stop the refresh (the monitoring)"), recovered from by itself; a page that can't get the end says so and keeps trying.

### D111
**Decision:** **`Email.yaml.bak` never keeps a plain-text SMTP password that a save replaced or removed (the maintainer's pre-candidate instruction of 2026-11-25 UTC, after the personal test of the consolidated package of `2adbe49` passed).**
(1) **The finding (§CX):** every save of `Email.yaml` (the desktop GUI since D43, the web UI's settings pages since D94, the guided setup's email step since D100) wrote the exact previous bytes to `Email.yaml.bak` before the replacement (D40). So replacing the plain-text password, removing it, or moving it to `smtpPasswordFile` (in one save or in two, as the README advises) left the old password in the backup, with the file's mode, until a later save of `Email.yaml` replaced the backup.
  Nothing at a start touched the backup, and Campertron never read it, so it never became a source again by itself; a user who copied it back restored the password. business-rules-settings §14 recorded it as an exact backup's property; the README's "With the password in a file or the variable, `Email.yaml` no longer holds it, so sharing, backing up or syncing your settings folder ... doesn't reveal it" was not true of the backup. Reproduced through the web UI built from `2adbe49` with synthetic passwords.
(2) **The rule:** when a save replaces or removes the plain-text password the file holds, the backup is the text that was read with `smtpPassword` cleared (`''`, as Remove clears it): the previous settings, comments and all, for a rollback, without any plain-text password (neither the removed one nor one only entered, so a save that stops after the backup was installed leaves none there either). Any other save keeps the exact previous bytes (a password the saved file still holds, or none). A backup copied back brings back the previous settings, never a removed password.
(3) **Its checks:** the backup must load as the previous settings with the password cleared, and hold the password nowhere the saved file does not hold it too outside its own password (a comment of the user's); otherwise (another value the same save changes holds the password) nothing is written, and the message says to save the password's change on its own first. `ConfigFileReplace` takes the backup's text from the caller (`SecretFreeBackup`) and checks it before anything is written and when its temporary file is read back; the order, the temporary files, the file's mode or access rules, the links and the external-change checks stay D40's.
(4) **Not chosen:** a migration of the password into a file Campertron writes (Campertron never writes, copies or chmods a password file, D66, D70, and the plain-text password stays a supported source, §27); a backup without the previous settings (a rollback of the other settings would be lost); a backup with the new password (it would hold a password never saved after a failed save); a cleanup at a start or when a file is opened (no start writes a settings file but the samples and the refresh's timestamp, and a backup can be the only copy of a lost file). A backup an earlier version left is replaced by the next save of `Email.yaml`; the curated `v0.3.0` notes are to say so.
(5) **Where:** the shared session (`ConfigEditSession.Save`), so the desktop GUI, the web UI's settings pages and the guided setup behave alike; the console, email mode, the monitoring, the test email and the validation never write `Email.yaml` or read a backup and are unchanged. (6) **Not in it:** `Ntfy.yaml.bak` and a changed ntfy topic (open question #55), `v0.8.0`'s backup and restore, the README's planned cleanup (two sentences changed), the site, the workflows.

**Evidence:** `validation/co_v0.3.0.md` §CX (the reproduction, every read and write path, the tests, the negative controls, the validation); the maintainer's instruction of 2026-11-25.

**Stated rationale:** the maintainer's: once a plain-text SMTP password has been removed, replaced or moved into a password file, Campertron must not leave it behind in an ordinary backup under its control; a routine backup must not silently become long-lived secret retention, while rollback and crash safety stay.
