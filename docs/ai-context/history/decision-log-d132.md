## Decisions after D131

### D132
**Decision:** **`v0.4.0`'s settings transfer: what it carries, where a secret goes and how a package is protected (the maintainer's decisions of 2026-11-28 UTC, relayed through a pasted instruction after Microsoft 365 Copilot's review of the read-only phase 15 investigation; recorded by the phase 15 design pull request, `validation/dz_v0.4.0.md` §ED).** It answers open questions #59, #60 and #63 and binds the design `../v0.4.0-settings-transfer.md`, which states each point in full. Nothing of it is implemented, and it authorizes no code.
(1) **The ntfy topic** (#59) is a secret: left out of a transfer by default and included only after its own opt-in; never shown in a preview, log, screenshot, transcript, evidence file or error. Omitted, the receiver's topic is kept; a receiver without one is told safely that ntfy stays incomplete. An opted-in topic is written to `Ntfy.yaml` only if the resulting file is owner-only; otherwise that secret's import is refused. No `topicFile` property is invented in `v0.4.0`; ER-34's and D112's protections stay.
(2) **`Web.yaml`** (#59) is never part of a `v0.4.0` transfer, not as an advanced or off-by-default category either: none of its values (`passwordProtection`, `networkListening`, `allowedHosts`, `trustedProxies` or another), nor `Web.password`, `Web.keys`, setup codes, session data or password records. Reconsidering it needs a later, separately reviewed decision.
(3) **outputTo** (#59) of `General.yaml` is transferred and named prominently in the preview. It is applied only when the resulting candidate folder passes the established readiness checks of D71 and D73; when it can't be, the user may apply the remaining package without changing outputTo. Campertron never chooses another notification mode silently; the preview explains which future starts would monitor; an import never starts the monitoring; `General.yaml` is applied last.
(4) **The secret's destination** (#60): an opted-in secret that has a file source is written to a new owner-only file of Campertron's own name in the receiver's settings folder: the SMTP password, referenced through `smtpPasswordFile` and never written to the plain-text `smtpPassword`; ntfy's token, referenced through `tokenFile`. A sender's or a receiver's own secret source is never written over; a change of a source's kind is shown in the preview without a path or a value where paths are forbidden. The mode on Unix is 0600; a binding owner-only access rule for Windows is defined by the design before phase 16b.
  No secure deletion is claimed; no secret goes into a rolling `.bak` file or a transfer's backup set. The topic follows point 1, because the schema has no topic file.
(5) **A secret whose only source is an environment variable** (#60, D76's phrase) is not offered for export: the option is disabled with a safe note, the export never reads the variable's value, and the receiver sets the variable itself. The established precedence of the sources is kept, and this stays outside the exception that lets a user's action read a secret.
(6) **The package's protection** (#63): a package that holds any opted-in secret must be encrypted, with .NET's own cryptography only: PBKDF2-SHA256 at the repository's established 600,000 iterations, AES-GCM, the complete header authenticated as associated data, the established passphrase normalization and length rules where they fit. The passphrase is never stored, logged, echoed or put into evidence; a wrong passphrase and a tampered package get fixed safe words. Its availability on every release target is confirmed before phase 16a is approved for merge.
  A package without a secret may be readable UTF-8 with a SHA-256 checksum, described only as corruption detection, never as authenticity or as protection against a deliberate change. The envelope must allow a secret-free package to be encrypted later without a new format.
(7) **The interfaces:** `v0.4.0`'s Export and Import exist only in the interactive console, the desktop GUI and the web UI. No noninteractive Export or Import command; open question #66 therefore does not block phase 15 and stays open.
(8) **Phase 16 is two separately reviewed phases.** Phase 16a: the package model, the strict reader and writer, the format's versioning, the limits, the hashing, the encryption, the passphrase handling and the package's validation, with no settings write. Phase 16b: the candidate state, the outputTo gate of D71 and D73, the apply service, the protected secret writer, the backup set, the rollback, the shared apply lock, the failure recovery and the settings writes.
(9) **Crash recovery:** no startup recovery journal in `v0.4.0`. Instead a protected backup set, a controlled write order with `General.yaml` last and a secret file before the settings file that names it, read-back verification, a rollback in the same process, the backup set kept when a rollback fails, and fixed safe recovery words. No application's start changes for it.
(10) **What the design binds beyond these points, from the repository's evidence and for review** (each marked so in the design): the package as one UTF-8 JSON document of at most 1 MiB, never compressed, with allow-listed entry kinds and names checked by `SearchFileName.Check`; at most 256 entries and 64 KiB a text (the web host's form limits), a secret within `SecretFile`'s 4,096 bytes; the secret files' names `Email.password` and `Ntfy.token` (the naming of `Web.password`), only ever created; the lock `Campertron.transfer.lock` and the backup folder `Campertron.transfer.backup`, one set kept; on Windows a protected access list with the current user alone for a new secret file and the backup folder.
  Left open for the phase that needs each: whether a later import may supersede an imported secret file (16b), the dry run's cipher check and `linux-arm` (16a), the web upload's request limit (19) and the user-facing names (17 to 19).
(11) **What it changes in earlier text:** the audit's recommendation (d) for `Web.yaml` (its own category, off by default) is not taken: (c), never; the plan's phase 16 is 16a and 16b; its "the set restores at the next start, or the files are each complete … the design names which" is answered by point 9; its `ConfigFiles.MaxNameLength` is `SearchFileName.MaxNameLength`. Beam's transport, discovery, port, pairing, key agreement, receiver lifecycle, timeout, replay defense, guessing limits and remote-session behavior stay undecided (phase 20; open questions #61, #62 and #64).

**Evidence:** the read-only phase 15 investigation of `a91c9c3` (2026-11-28; `validation/dz_v0.4.0.md` §EC names it) and its facts read again in the code at `5487906` (§ED): `ConfigFileReplace` (one rolling backup; `Create`'s mode Unix-only; `Replace` refusing a file with access rules of its own on Windows), `SecretFile` and `SecretFileCheck`, `WebPasswordHash` (600,000 iterations, NFKC, 10 to 128 characters), `SearchFileName`, `ConfigFiles`, `YamlDocument` and the bounded loader, `ConfigValidation.MonitoringStartErrors` and `MonitoringSearchErrors` with the search loader's unsaved-text seam, `MonitoringLock`, the web host's limits; D66, D67, D70, D71, D73, D75, D76, D94, D95, D111, D112, D114, D115; ER-14, ER-16 to ER-18, ER-33, ER-34, ER-36 to ER-39; TD-49; the questions' own records.

**Stated rationale:** the maintainer's, as the instruction gives it: the topic keeps the secret's treatment it already has; a host's web access is never changed by a transfer; outputTo moves with the notifications it belongs to, but never into a state the monitoring's start would refuse and never by starting anything; a transferred secret lands only in a file other users can't read and never in the plain-text setting, a backup or a log; an environment variable's value is not Campertron's to read for a package; a secret is never in a readable file, while a package without one stays inspectable; the package and its cryptography are reviewed before any code that writes settings; and no application's start is changed to recover an import.
