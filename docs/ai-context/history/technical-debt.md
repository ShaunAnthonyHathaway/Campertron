### TD-04
**Issue:** ~~Consecutive-day filtering operates on state shared across parallel configs~~ **Resolved on branch `fix/search-correctness` (P2, 2026-11-14, decision D35).** Each search now collects its own hits (`FilterData` adds to a per-search `ConcurrentBag`), `FilterConsecutiveDays` groups, filters and replaces only those, and `GetAvailabilitiesByCampground` adds the search's final hits to `RunData.FilteredAvailableData`, which nothing replaces any more. A search's output, including the order of its consecutive campsites, is byte-identical to what it was when it ran alone; in a shared run every search now gets exactly that, and the run's set is the union of the searches' own final hits. `consecutiveDays` below 1 still keeps its hits in the run's set and out of the output. Evidence: `SearchIsolationTests` (10; 5 fail in every run with the former filtering), and the broad parallel-versus-isolated scenario (build-and-test.md §Z:
0 differences in 100 parallel runs and both orders, against 100 of 100 runs with differences on `master`). Original entry, kept for history

**Evidence:** [V] `FilterConsecutiveDays` groups and reassigns `RunData.FilteredAvailableData`, which every config in `Parallel.ForEach` (`Load.RunConsoleSearch`) writes to. [I] One config's consecutive filter can drop or include another config's hits, and the race on reassignment can lose entries. [V] Visible symptom (2026-11-12, real run with four searches): 19 empty lines before the consecutive search's results, absent when that search ran alone; they come from other searches' hits, whose `ConsoleData` is empty. [V] Also observed (2026-11-12, same live data, `master` `da9484c` and the beta.9 branch alike): the shipped Mather example (`consecutiveDays: 2`) produced no results when run in parallel with the Zion example, but 1,284 date entries when run in a set that included a 60-day Watchman search; the cause was not investigated. **Not fixed by beta.9** (D29):
`ResultsHtml` renders each search's output stream as supplied and does not read `FilteredAvailableData`, so the combined page adds no cross-search attribution of its own, but it cannot correct a stream that TD-04 has already altered (dropped, added or misattributed results). The page drops blank untyped lines and builds a card from a date entry whose site part is missing, so the blank-line symptom no longer shows on the page; that hides a symptom and does not fix the defect. **Not fixed by the console output polish either** (D34): the console now renders each stream from its metadata, like the page, and skips the stream's calendar values, so the orphan calendars seen in the console before (2026-11-14, two example searches in parallel: the consecutive search's section showed four calendars, two of them for the other search's sites with no campsite above them) are no longer shown. That too hides a symptom; dropped, added or misattributed results are shown as the stream has them.
**Deterministic reproduction (consolidated audit, 2026-11-14)** [V]: a scratch harness outside the repository, built against the library of `7e325cd`: months built in memory with their URLs already claimed (no network), one shared `RunningData`, the searches run one after the other (one legal schedule of `Parallel.ForEach`). (1) **Missed Email notification:** search A (Watchman, single nights) found one new opening, search B (Mather, two consecutive nights) none. With A first, B's `FilterConsecutiveDays` replaced `FilteredAvailableData` with an empty set, and the production `Load.PostProcess` wrote "Check 1: 2 searches, nothing new." and then "Check 2: …, nothing new.": no email and no marker, although A's stream held the opening. With B first the opening stayed in the set. The shipped examples (Zion single nights, Mather two nights) are this combination. (2) **False-positive consecutive result:** search B (Watchman, two nights, Sundays only) alone showed "No matching availability.";
after a single-night search A of the same campground in the same run, B reported a campsite as "at least 2 consecutive nights" for a Sunday whose Monday matched only A's filters. (3) **Repeated emails** [I, from (1) and the code]: single-night hits that a consecutive search removes from the set are still in their own search's email but get no marker, so they are reported again in later checks whenever the gate opens. Disposition: **required before preview.1**, P2 (each search filters its own hits; only its final hits are added to the shared set)

### TD-11
**Issue:** ~~Culture-dependent date parsing~~ **Resolved on branch `fix/search-correctness` (P2, 2026-11-14, decision D35):** `ConvertToZeroHour` and the requested month (`AvailabilityApi.MonthStart`) build their dates from numbers (`new DateTime(y, m, d)`: the same values and `DateTimeKind` the former parse gave in en-US), and the month's URL is written with the invariant culture (`AvailabilityApi.MonthUrl`; the audit's fa-IR check also showed `ToString("MM")` writing 08 for November in the Persian calendar). Evidence: `SearchDatesTests` in en-US, en-GB, en-AU, de-DE, fr-FR, es-MX, ja-JP, the invariant culture, th-TH and fa-IR, and real console searches under `LANG=en_GB.UTF-8` and `de_DE.UTF-8` (build-and-test.md §Z; `master` ends there with "TwoNights.yaml could not be used: String '11/14/2026 0:00:00 AM' was not recognized as a valid DateTime", exit 1). **Left as it is, by design:** user-written `searchValueDates` are still parsed with the current culture, including its calendar:
`2026-11-20` reads the same in every Gregorian culture tested, but th-TH (Buddhist calendar) and fa-IR (Persian) read even that differently (business-rules §2; a product question for stable readiness). Original entry, kept for history

**Evidence:** [V] `ConvertToZeroHour` and `ProcessMonth` parse the `"M/d/yyyy 0:00:00 AM"` strings with `Convert.ToDateTime`. [I] Fails or swaps day and month under non-US cultures. **Verified (consolidated audit, 2026-11-14)** [V], .NET 11.0.0 with ICU, a `DaysOut 3` search and `ProcessMonth`'s `CheckDt` expression for the current month (2026-11): en-US, en-CA, ja-JP and the invariant culture give the expected dates and 2026-11-01; **en-GB, en-AU, de-DE, fr-FR and es-MX** throw `FormatException` ("String '11/14/2026 0:00:00 AM' was not recognized as a valid DateTime.") in `ConvertToZeroHour`, and `CheckDt` becomes **2026-01-11** (the month number read as the day, the day as January). So in those cultures every `DaysOut`, `MonthsOut`, `Until` and `StartEndDate` search fails (since D34 reported as "{file} could not be used: …", exit 1), and [I] a `SpecificDates` search requests January and finds nothing.
The tests set en-US explicitly (for example `SharedMonthSearchTests`), so the suite never exercises this. User-written `searchValueDates` are parsed with the current culture as well; that is a separate, documented contract (business-rules §2). [I] A container without a locale setting runs with the invariant culture and is unaffected. Disposition: **required before preview.1**, P2 (build the internal dates directly; the en-US values stay identical)
