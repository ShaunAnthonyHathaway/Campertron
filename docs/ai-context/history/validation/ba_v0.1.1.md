**V011-1, Refresh database** [V unless marked]:
- The console's menu entry clears the screen and runs `RefreshRidbRecreationData.RefreshData(false, config)`. The same refresh also runs automatically from `Load.GetConfig` (`DbExistsCheck`) when `autoRefresh` is on and the interval has passed, so **the GUI already runs it inside its startup's background task**.
- The chain: the cache-path check, the refresh lock, the stale staging and temporary files removed, the download, the extraction, `RidbStagedRefresh.BuildValidateAndInstall` (staging copy, clear, populate, index, validate, checkpoint, cache cleared, the installation by `BackupDatabase` under the repair lock, `quick_check`), then `Yaml.GeneralConfigReplaceYaml` for `lastRidbDataRefresh` (ER-05's order).
- It is synchronous (`Web.Download(…).Result`, a new `HttpClient` each time), writes about 17 progress lines with `Console.WriteLine` and its outcome through `ConsoleUi`, returns a `bool`, throws on download, extraction, import and installation failures, and has no cancellation. [I] `HttpClient`'s timeout covers only the headers, so a stalled body could hang.
- Cancellation is feasible at checkpoints before the cache is cleared (before and during the download, between the extracted files, before clear, populate, index and validate), not once the cache step and the installation start. A cancel there takes an existing failure's path: nothing installed changes.
- Calling `RefreshData` from the GUI is unsafe: it writes to the console, sets `ConsoleUi.Unacknowledged`, cannot report progress or be canceled. [I] A GUI started from a terminal with `outputTo` Console or HtmlFile could wait for a key after a failed refresh; this inference was not reproduced and is not recorded as a defect. The recommendation was a host-neutral library service in GS1's pattern, with `RefreshData` kept as the console's adapter.
- The download goes to `LocalApplicationData/RIDBFullExport_V1_JSON.zip`, a generic name; an existing file of that name is deleted first (TD-58). The disk space a refresh needs is unknown (open question #43).

**V011-2, View current configuration** [V]: `Menu.ProcessInput` prints `Menu.ViewConfigLines` (public): eight items (version, settings folder, cache folder, output, number of searches, the refresh age, the operating system, the .NET runtime), from `RuntimeInfo.Describe`, the values loaded at the start, `ConfigFiles.SearchFiles` and `RuntimeInformation`. None is secret; no `Email.yaml` value is shown. A GUI view must read `General.yaml` read-only and not through `Yaml.GeneralConfigGetConfig`, which creates the file when it is missing.

**V011-3, the `autoRun` and "startup" wording** [V]: the eight behaviors that `../../current-state.md` V011-3 lists were each verified in the code (the interactive console's start runs no search; Search reads the files each time; Email mode reads them once and checks every minute; the GUI runs nothing at its start; Results selects the enabled searches, `RunsAtStart` being the raw `autoRun`; a search without `autoRun` runs when selected; the example search is created only by the console's next search). The location list was incomplete; the newly found locations are now in that requirement. No single phrase is accurate in every context, so the report recommended one canonical name with context-specific explanations.

**TD-57** [V]: `docker_tag_refs` gives a stable version `<version>`, `<major>.<minor>` and `latest`, in that order, and `publish_oci_archive` refuses any existing reference with another digest, one reference at a time. With `0.1` and `latest` at `38039d81…`, a `v0.1.1` tag run would push `0.1.1` first and then fail at `0.1`, before the image attestation and the GitHub release (the release job needs `docker-publish`); a rerun of that workflow fails the same way. Git tags are not involved. The release-policy tests covered only a pre-release's exact tag and the refusal of an exact tag at another digest. Recommended: check every reference before copying any, keep the exact tag immutable, move a stable version's floating tags only forward, read every reference back; its own pull request before any `v0.1.1` tag.
