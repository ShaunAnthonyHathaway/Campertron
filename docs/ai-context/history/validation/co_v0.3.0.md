**3. `Camp.History` before D104** [V from the code at `1395e00`]:
- The format: one empty directory per campsite and night, `<settings folder>/Camp.History/{yyyy}/{M}/{d}/{CampsiteID}`, no padding, version or metadata, since `15ffc1d` (2024-01-21; before, a JSON file in the cache folder, no longer read). A marker meant "a notification showing this campsite and night was delivered at least once"; no code deleted one; deleting the folder was the documented reset.
- The path: `AvailabilityApi.GetWebApiData` fetches each campground-month once per check into `RunData.SiteData`; `Data.DynamicDeserialize` reads the statuses, never the quantities; `CalculateAvailableDates` counts a night only when its status is exactly `"Available"`; `FilterData` checks occupancy, the date, the window, the day and the filters and, in the monitoring, dropped a night with a marker, before `FilterConsecutiveDays` built the runs of nights; `MonitoringService.ReportCheck` read the history at its gate, then `Notifications.Deliver` (email, then ntfy, by search) recorded a search's openings once a provider delivered them and the run's other hits after a check no provider failed.
- The identity is the campsite and night, global for the settings folder: not the search, its file or name, the campground, the window, the number of nights, the occupancy, the equipment or the provider. All 130,948 campsite IDs of the bundled campground data are unique (none under two campgrounds; a read-only copy extracted into the investigation's isolated folder).
- The documented rule: D8 refined on 2026-11-14 (open question #8 closed), ER-03 ("stays suppressed for Email even if it disappears and reappears"), business-rules §5, README line 214 and the web page's `LastCheckNote`; `NotificationHistoryTests.EmailCycles_…_AndKeepSuppressingReappearingOnes` pinned it.
