### D17
**Decision:** Releases come from `.github/workflows/release.yml`. A SemVer tag on `master` is the only way to publish; the version comes from the tag. Separate console and GUI archives for 8 targets (zip for Windows, tar.gz elsewhere), self-contained, not single-file or trimmed. `SHA256SUMS.txt` plus build-provenance attestations. Checksums and release notes are assembled and validated by a read-only job on every run, dry runs included, and the tag-only release job publishes that output unchanged. Draft-first GitHub release. Image only on GHCR (amd64 + arm64), and SemVer pre-release versions never move `latest` (see D19 for the GitHub release flag). Manual runs and relevant PRs are dry runs. The publishing jobs require a `v*` tag-push event as well as the verified version. Least-privilege per-job permissions, GitHub-owned actions pinned to SHAs, no secrets beyond `GITHUB_TOKEN`. Only linux-x64 is smoke-tested natively (extended by D33: also win-x64, win-arm64, osx-x64 and osx-arm64)

**Evidence:** `release.yml`, `CampertronConsole/Dockerfile` (multi-arch), README

**Stated rationale:** maintainer approval of the release design, 2026-11-10. First intended version `v0.1.0-beta.4`

### D20
**Decision:** **Old-binary compatibility is handled by documentation, not by an in-app mechanism.** Every release's notes must contain a "Compatibility with older versions" section (enforced by `validate_notes`), and `--version` identifies a copy (business-rules §10–§11). The README carried an upgrade note ("Versions from 2024") until 2026-11-11, when the README was rewritten for current users at the maintainer's request (branch `docs/rewrite-readme`); the release-notes section remains the required, enforced notice. Designs considered (2026-11-11): (a) an extra key in `General.yaml`: both the 2024 and the current YAML loaders reject unknown keys, so the 2024 apps would stop starting, but with a YamlDotNet exception (the 2024 GUI, a WinExe, would close silently), every user's `General.yaml` would be rewritten, and a deliberate downgrade would be blocked; (b) a new database file name per layout:
the 2024 apps would then extract their own legacy DB and work, but it needs a migration of every existing DB, a second 226–328 MB file and changes to extraction, repair and refresh; (c) a marker or readme file in the data folder: nothing old reads it. None can make a 2024 binary warn, because it can't be changed. (a) and (b) change normal behavior or add migration complexity, so they were rejected

**Evidence:** `render_notes`/`validate_notes` (`release-policy.sh`), `RuntimeInfo` (README "Versions from 2024" until 2026-11-11)

**Stated rationale:** maintainer request 2026-11-11: add a safe mechanism only "if that can be done without adding significant migration complexity or changing normal application behavior", and choose the smallest robust solution

### D22
**Decision:** **Installed databases are repaired by their own properties, not by app version.** The one-time startup repair replaces a DB only for the swapped 2024 layout or for a corrected-layout DB that still contains any of the 15 omitted RIDB tables, which only pre-0.1.0-beta.4 code created. Non-normalized GUI states are reported but don't trigger a replacement by themselves. The bundled replacement must pass `RidbDatabase.Validate` and need no repair itself, so the repair is final without a marker file. A successful replacement also deletes the DB-derived JSON cache files

**Evidence:** `LegacyAddressLayout.DetectRepairReason`, `RepairIfNeeded`, `ClearDerivedCache`; `LegacyAddressLayoutTests`, `StartupRepairTests`

**Stated rationale:** maintainer request 2026-11-11 (beta.6): repair affected upgrades automatically and once, never replace a valid or newer manually refreshed DB, and don't use the version as the trigger. A state-value trigger was rejected because the current importer passes unmappable values (`STATE MAPPING BROKEN`) through, so a future valid refresh could be downgraded on every start. Running full validation at every start was rejected because it includes `integrity_check`; the chosen check adds about 0.3 ms to the existing 13 ms layout scan (business-rules §8)

### D24
**Decision:** **Windows GUI packages exclude the SkiaSharp and HarfBuzzSharp native debug symbols by package-specific item filtering.** A target running after `ResolvePackageAssets` removes from `NativeCopyLocalItems` only items with extension `.pdb` whose `NuGetPackageId` is `SkiaSharp.NativeAssets.Win32` or `HarfBuzzSharp.NativeAssets.Win32`. Removing the items (instead of setting `CopyToPublishDirectory=false`) also keeps them out of `.deps.json`, because the publish reuses the build `.deps.json` generated from these items. Rejected: deleting files by name after publish (leaves the `.deps.json` entries; upstream reports such deletion breaking the IIS in-process host); filtering by file name alone (could remove another package's file); `ExcludeAssets="native"` and the packages' `ShouldIncludeNative*` properties (also remove the native DLLs); `CopyDebugSymbolFilesFromPackages=false` (covers only `lib/` symbols, not `runtimes/*/native`). No official opt-out exists.
The target depends on SDK item and metadata names, so `release.yml` guards the result (no native PDB file or `.deps.json` entry; Skia, HarfBuzz and ANGLE DLLs present). Campertron's own managed PDBs are deliberately kept (maintainer requirement). When fixed upstream packages arrive (through Avalonia), the target matches nothing and can be removed (open question #24)

**Evidence:** `CampertronGUI/CampertronGUI.csproj`, `.github/workflows/release.yml` "Check package contents" (build-and-test.md §L; TD-35)

**Stated rationale:** maintainer approval 2026-11-11 (TD-35 Phase 1 investigation): package-specific filtering, permanent guard, Windows runtime validation before merge

### D25
**Decision:** **The RIDB import writes rows with prepared Microsoft.Data.Sqlite commands, not EF Core `SaveChanges`.** EF Core stays for the model, schema, connection and queries. `RidbTableInserter` inserts the six tables in one transaction on the context's connection, one prepared parameterized `INSERT` per table, in EF Core's former `SaveChanges` order (tables by ordinal name; rows by the complete primary key, `Comparer<T>.Default` per key component), so the database is byte-identical. The mappings are hand-typed per table (no reflection in the insert loop) and guarded by model-drift tests. Rejected after measurement: `AddRange`, `AutoDetectChangesEnabled = false`, per-table `SaveChanges` with `ChangeTracker.Clear()`, `MaxBatchSize` (EF's SQLite provider still sent one command per row), durability pragmas (the commit costs 0.4 s), third-party bulk-insert packages (not needed). The refresh's committed-clear failure behavior is deliberately unchanged (TD-36)

**Evidence:** `CampertronLibrary/function/RecDotOrg/sqlite/RidbTableInserter.cs`, `PopulateDbFromRIDBFiles.cs`, `PopulateTests` (build-and-test.md §M)

**Stated rationale:** maintainer approval 2026-11-11 (RIDB refresh performance, Phase 1): direct prepared commands, exact EF row order, hand-typed mappings, unchanged failure semantics; measured `Populate` 69.4–71.1 s → 12.5–12.7 s, peak 6.1 → 2.0 GB

### D26
**Decision:** **The RIDB refresh builds and validates a staging database and installs it with SQLite's online backup API (`SqliteConnection.BackupDatabase`), never by renaming or replacing files.** The staging DB lives in `ConfigPath/RecreationDotOrg.refresh-<guid N>/RecreationDotOrg.db`, so the unchanged `ConfigPath`-based `ClearDatabase`, `Populate` (D25) and `Validate` run against it. Its template is a backup of the installed DB (or the bundled DB if none is installed). The derived cache is cleared after validation and before the installation (safe on the desktop, where the cleared directory is `CachePath`; in a container the refresh still clears `LocalApplicationData/CampertronCache` while searches use `/cache`, so stale derived files can remain there: TD-05, not changed by D26); `LastRidbDataRefresh` is written once, after the installation and a passing `quick_check`. A refresh lock (`RecreationDotOrg.refresh.lock`, never deleted) serializes refreshes;
the repair lock is taken second, only around the installation. Rejected after measurement (TD-36 Phase 1): one transaction on the installed DB (no `VACUUM` in a transaction, so not byte-identical; `Validate` can't see uncommitted data); temp DB + `File.Move` (renaming an open SQLite DB is undefined, a stale WAL was replayed onto a renamed-in file, Windows can't replace an open file, .NET documents no atomicity, and the output differed in 3 header bytes); `ATTACH` + copy (different page layout); copying the staging file into place (not atomic)

**Evidence:** `RidbStagedRefresh`, `RefreshRidbRecreationData.RefreshData`, `Clear.ClearRefreshCache`, `Load.DbExistsCheck`; `AtomicRefreshTests`; kill harness and full-export comparison (build-and-test.md §N)

**Stated rationale:** maintainer approval 2026-11-11 (TD-36 Phase 1 → Phase 2): staging + `BackupDatabase` for existing and missing destinations; cache cleared before the installation; no timestamp pre-write; refresh lock without `DeleteOnClose`; repair lock around the installation only; stale staging removed at refresh start only; exceptions propagate as before. The full-export result is byte-identical to the in-place refresh; the installation costs about 1 s and the whole refresh about 1.4–2.3 s more (mean 1.8 s; performance accepted 2026-11-11 including one run 0.19 s over the provisional 17.5 s target). Follow-up the same day (TD-37): the timestamp is written through a validated temporary file renamed over `General.yaml` (`ConfigFileReplace`), not in place, so an interrupted write leaves the complete old or new file; the missing-destination path (bundled DB placed by `Load.ExtractEmbeddedDbTo`, then `BackupDatabase`, created DB removed on failure) was approved as implemented

### D27
**Decision:** **`CampertronInternalConfig.CachePath` is the only runtime cache directory (TD-05).** The RIDB refresh's cache step, the derived JSON cache and the HTML results (including the email attachment) all use it: `LocalApplicationData/CampertronCache` on the desktop (unchanged), `/cache` in a container. `RefreshData` takes the cache directory from `InternalConfig.CachePath` only (the test overload lost its separate cache-directory parameter; `Clear.RefreshCachePath` was removed; `Clear.All` takes the cache path), and `ProcessConsoleConfig` receives `config.CachePath`. No fallback to `LocalApplicationData`. Deletion guards: `Clear.CheckCacheDirectory` refuses an unset or whitespace path, a filesystem root and `ConfigPath` (after full-path normalization; case-insensitive outside Linux) before anything is downloaded or changed; `ClearRefreshCache` refuses a directory holding `RecreationDotOrg.db` or `General.yaml` (a config directory reached through a link or bind mount).
What a clear deletes is unchanged: every file directly in the directory (links unlinked, never followed; subdirectories and the directory itself kept). The HTML write and the email message were extracted unchanged into `CampsiteConfig.WriteHtmlResults` and `CreateResultsEmail` so they can be tested without a browser or SMTP. The download and extract locations (`LocalApplicationData`) and the TD-36 order are unchanged

**Evidence:** `Clear.CheckCacheDirectory`, `Clear.ClearRefreshCache`, `RefreshRidbRecreationData.RefreshData`, `CampsiteConfig.ProcessConsoleConfig`/`WriteHtmlResults`/`CreateResultsEmail`, `Load.PostProcess`; `CachePathTests`, `AtomicRefreshTests`; Docker validation (build-and-test.md §O)

**Stated rationale:** maintainer request 2026-11-11 (TD-05 project): use `CachePath` consistently for cache clearing and HTML output, keep desktop behavior and the TD-36 guarantees, no fallback, no new path abstraction, strict deletion safety

### D29
**Decision:** **The HTML results page (beta.9) is rendered by `ResultsHtml` from typed presentation metadata on the existing output values; one page per `HtmlFile` run, one email per search.** Producers tag their values (`ConsoleConfigValue.Kind`/`Metadata`) without changing their text, so the console stays byte-identical and the page shows the same results in the same order; the page never parses console text and never reads `FilteredAvailableData`. It renders each search's stream as supplied and adds no cross-search attribution of its own; it does not correct a stream that TD-04 has already altered upstream (TD-04 is not fixed). The page (business-rules §6):

Lists of cards instead of tables (they work at 320 px without restyling table semantics, and in email clients). Always expanded: native `<details>` was not used because collapsed content does not print and email clients handle it inconsistently, and the 3.4 MB test page loaded in about 0.5 s without it. Not added: a generation time (removed in review:
it made the output nondeterministic and was not needed to use the page), an HTML calendar, a filter summary, a version footer, JavaScript

**Evidence:** `class/Base/ConsoleConfig.cs`, `function/Base/ResultsHtml.cs`, `Console.cs` (`WriteAndOpenHtmlResults`, `OpenHtmlFile`), `Load.OutputResults`, the producers in `Cache.cs` and `AvailabilityApi.cs`; `ResultsHtmlTests`, `ConsoleOutputGoldenTests`, `HtmlResultsOutputTests` (build-and-test.md §Q)

### D30
**Decision:** **Curated release notes are tracked, version-specific fragments, reviewed through a PR and published in the draft (R7).** Each release has `.github/release-notes/v<VERSION>.md` (format: `.github/release-notes/README.md`), the curated part only, starting with `## What's new in <VERSION>`; it is merged to protected `master` through a PR, ideally the last content PR before the tag. Merging approves the exact bytes; pushing the tag is the separate approval to publish. A publishing tag run requires the exact fragment from the tagged commit (missing, invalid or mismatched fails in `verify`, before any build or publication;
never template-only notes), composes it unchanged between the generated title/status and the generated sections, validates it (`validate_notes`), rebuilds it from the tagged checkout in the release job and compares it byte for byte with the `release-metadata` copy, creates the draft with it, reads the draft body back byte for byte before publishing (still a draft, expected title, tag, 17 assets), then reads the public body back after publishing. A mismatch is reported, never repaired automatically. Pull requests and `workflow_dispatch` runs stay unable to publish; their synthetic `0.0.0-dryrun.<n>` version uses the template, and every real fragment is still validated and previewed (CI's required job and the release `verify` job). ### D39
**Decision:** **CM1 of GUI configuration management: a comment-preserving YAML document editor, in memory, with no production caller (2026-11-15).** (1) **Approach.** YamlDotNet 16.3.0's normal parser (`Parser` with the default scanner, which skips comments: the path `Deserialize(string)` takes) locates every top-level key, value and sequence item by its source range (`Mark.Index`, UTF-16 code units); Campertron's own scan finds comments in the gaps between those ranges (a `#` at a line start or after a space or tab, to the end of its line) and in block scalar headers. An edit is a list of non-overlapping text-range replacements applied to the original text, so everything outside them stays byte for byte: comments, blank lines, key order, indentation, quoting, line breaks, Unicode, unknown keys and sections, directives and document markers, a leading U+FEFF. Edits (one per key per call):
`SetScalar` (replace a value, or add a missing key after the last property), `RemoveProperty` (its own lines, with the exact range and comments reported as a loss), `SetSequence`, `SetItem`, `InsertItem`, `RemoveItem` (with its loss) and `ReorderItems` (an item moves with the comment lines directly above it and its end-of-line comment). (2) **Writing values** (business-rules §13): an edited scalar keeps its style when the new value can be written in it and reads back unchanged, and a text value is never written plain in a form the loader reads as null; a new text value is plain only when YAML can't read it as a null, boolean, number or date, otherwise single-quoted, otherwise double-quoted; other values are written as Campertron's writer writes them (the same serializer configuration); a new list is a one-line flow sequence; new lines take the document's indentation and its most frequent line break (ties: LF, CRLF, CR; mixed breaks give a warning);
a file without a final line break keeps none. (3) **Refusal instead of normalization:** malformed, empty or comment-only text, more than one document, a root that is not a plain block mapping, complex, duplicate or merge keys, tags other than standard YAML tags, a `#` that can't be told apart from content, a layout it does not understand, lone surrogates, NEL/LS/PS characters. Kept but locked: properties with anchors, aliases or standard tags. Kept but not rewritten: block scalars (literal and folded; they can still be removed), lists whose items are not single-line plain or quoted scalars. (4) **Verification before any text is returned:** the text outside the replacements is unchanged; the result parses as a supported document; its keys are the original ones less the removed and plus the inserted, in order; every untouched property's lines are identical; edited values and items read back as planned (moved and kept items with their own text);
the comments are the original ones less the reported losses; line breaks, the final line break and a leading U+FEFF are kept. Then `Yaml.SettingsDeserializer` (the deserializer of the three settings loaders, now defined once) loads the result and it must equal the model the caller intends, property by property; a document with keys the loader rejects is loaded from the same parsed events without them, with an `UnknownKeys` warning. `VerifyCandidate` runs the same checks on a text produced elsewhere (CM2: what was written). a temporary file `<name>.<32 hex>.tmp` in the file's directory is created with create-new semantics, owner-only (0600) on Unix while it is written, written, flushed to disk (`Flush(true)`: `fsync`, `F_FULLFSYNC` on macOS), given the file's mode (checked) and read back (exact bytes, `VerifyCandidate`); the file is compared with what was read (link chain, target, SHA-256, length, time, mode, attributes); the previous bytes go to `<name>.bak` the same way (the source's mode, read back, renamed over the previous backup; one rolling backup); the file is compared again; then `File.Move(…, overwrite: true)` (`rename(2)`; `MoveFileExW` on Windows) and the file is read back through its link (exact bytes, `VerifyCandidate`, mode; on Windows its access rules). An existing file, directory or link is never truncated or written over; a file another program created meanwhile is kept and loaded as the caller loads an existing one. No backup. (5) **Links:** on Unix a chain of symbolic links is followed to its final target (at most 40; a cycle, a dangling link, a directory and an empty or non-regular file are refused); the temporary file and the backup are written in the target's directory and the link stays a link. (7) **Cleanup:** only `<name>.<32 hex>.tmp` and `<name>.bak.<32 hex>.tmp` of the file being written, in its directory, regular files (never a link or a directory), last written more than 10 minutes ago:
quietly before every write, reported at the start of a refresh (as before). (8) **Established** [V, Linux x64, btrfs]: `SIGKILL` at each of 12 replacement and 6 creation points (two passes) and 100 random kills left the complete old or the complete new file, never a partial or empty one, and a working next start. **Windows** [V, the CI job `Windows settings files (CM1, CM2)` on `windows-2025`, added to `ci.yml` for CM2]: the CM1 and CM2 suites and 18 Windows-only tests pass natively (ordinary files in the runner user's LocalApplicationData, CRLF and BOM, access rules, attributes, read-only files, files and backups held open, a locked temporary file, symbolic links and junctions, injected failures at every step); no process-kill harness ran there. **Not established:** power loss (the directory is not fsynced; the old file may reappear), macOS (not run), process interruption on Windows.

### D59
**Decision:** **TD-57 resolved: a stable version's floating container tags move only forward, and an exact version tag never moves (roadmap step 10, Phase T, 2026-11-18 UTC).** (1) **The problem** (TD-57; §BA): `docker_tag_refs` gives a stable version `<version>`, `<major>.<minor>` and `latest`, and `publish_oci_archive` refused every existing tag with another digest, one tag at a time. Since `v0.1.0` created `0.1` and `latest`, a `v0.1.1` tag run would have pushed `0.1.1` and then failed at `0.1`, before the image attestation and the GitHub release, and a rerun would have failed the same way. Git tags were never involved.
(2) **Preflight:** every tag of the version is read before anything is copied and gets an action, or the run stops with nothing changed. (3) **The exact version** is created if absent, kept if it already serves the validated image index, and refused otherwise: it is never moved (D32's rule, kept).
(4) **Floating tags, stable versions only:** `<major>.<minor>` and `latest` are created if absent and kept if they already serve the validated index. Otherwise they move only when the image they serve carries a stable `org.opencontainers.image.version` label older than the release, compared as numbers, read from both platform images by digest (each manifest and config must hash to the digest that names it, and both labels must be equal) and, for `<major>.<minor>`, of the same `<major>.<minor>`.
A newer label (a backward move), the same version at another digest (not newer), a pre-release, malformed or missing label, platforms that disagree, or evidence that cannot be read or verified refuses the move.
(5) **Order and read-back:** the exact version is pushed and read back first, then the floating tags. Each tag is read again just before its copy and must still be what the preflight saw (or already the validated index), so a tag another publisher changed meanwhile is not overwritten; each copy is read back (the validated index listing both platform manifests), and every tag again at the end.
(6) **Pre-releases:** only their exact tag is passed (the function requires exactly `docker_tag_refs`' list for the version and its pre-release flag), so no floating tag is read or moved. (7) **Recovery:** a repetition for the same validated archive keeps what is already published and completes the rest, also after a partial failure; rerunning a tag run's failed jobs does that and, like every rerun, needs the maintainer's approval.
(8) **Consequence:** a stable version that is not newer than the version `latest` serves (a backport, such as `0.1.2` after `0.2.0`) is refused in the preflight, before anything is pushed; publishing one would need a policy change. (9) **Workflow:** `release.yml` passes `VERSION` and `PRERELEASE` to the push step; only that call and the comments on the push changed.
The same pull request corrected the stale comments above the Test steps of `ci.yml` and `release.yml` (226 MB, no network since D45, the folder created since D37), comments only. **Not changed:** the build, the validated archive, its checks, the attestation, gates, permissions, the tags each version gets, Git tags and their ruleset, releases, the application

### D72
**Decision:** **The results email shows the search's results in its body, in the layout of the results page, with a plain-text alternative; only when the HTML body, measured as sent, is over a fixed 80,000 bytes is the body a short summary with the full results page attached as `Campertron-results-yyyy-MM-dd.html` (approved by the maintainer on 2026-11-22 UTC as `v0.2.0` step 1 of 3, after the personal test of the local build of `54d3142`).**
(1) **Before:** each email (one per search, D29) had the search's results page as its HTML body (`IsBodyHtml`), the browser page with CSS variables, a grid and `rem` sizes, and the same page attached as `application/octet-stream` under the cache file's `{guid}.html` name; no plain-text part. Every email carried the results twice.
(2) **The body** (`ResultsEmail`, from `ResultsHtml.Build`'s model, never the console text): the title, the search, its campground, the consecutive-days note, the counts, check-in and check-out, the month and date headings, and each site with its loop, type, equipment and booking link; consecutive days as cards; the page's empty states and footer. Email-safe: inline light colors, each background with its text color, a `prefers-color-scheme: dark` block with the page's dark colors, `color-scheme` meta tags, no CSS variable, grid, script, image or external reference; a table wrapper, `px` sizes.
(3) **Its parts:** `multipart/alternative`, the plain text first and the HTML last (RFC 2046 §5.1.4), UTF-8, base64, CRLF; the plain text has the same facts, one per line, the booking links as URLs.
(4) **The size rule:** the full results go in the body when the HTML part's size as sent is at most 80,000 bytes (`ResultsEmail.BodyLimitBytes`). The measure (`EncodedSize`) is the base64 text System.Net.Mail writes (68-character lines with CRLF; checked against its output). Researched limits: Gmail clips an HTML body over about 102 KB (Litmus, 2024: "Gmail clips any message with a file size of over 102 kilobytes", images excluded; Email on Acid, 2021: "around 102KB" and "try to stay below 80KB"; Spam Resource, 2022: the limit applies to the HTML part, found near 105 KB, and a base64 message clipped only above 110 KB of HTML; Google documents no figure).
No other client's byte limit was found documented (iOS Mail's partial downloads are reported without a fixed size). The encoded size is about 37 % above the HTML's, so the threshold is below 102 KB under either reading of what Gmail counts. A fixed technical limit, not a setting.
(5) **Otherwise:** a summary body (the title, the search, its campground, its counts and "The full results are too large to show in this email. Open the attached file, Campertron-results-yyyy-MM-dd.html, in a web browser to see every site, date and booking link.") and the page attached from memory as `text/html; charset=utf-8` under that name, the check's local Gregorian date.
(6) **Safety:** every value HTML-encoded, the campsite ID URL-escaped in links, control characters as spaces in both parts; the booking links are the only links; no setting, secret or file path in the email (the cache file's name neither).
(7) **Not changed:** one email per search, the subject, the recipients, the page written to the cache first, the send seam and its failure behavior (approved by the maintainer: an error, the run stops, a failed email records nothing), the "Email sent" line, ntfy, `Camp.History`, provider independence, the console output, the GUI (no new setting). Part of D68's `v0.2.0`.

**Evidence:** `ResultsEmail.cs` (new), `Console.cs` (`ProcessConsoleConfig`, `CreateResultsEmail`), `ResultsHtml.cs` (helpers shared, the page unchanged); tests `ResultsEmailTests` and `ResultsEmailDeliveryTests` (new; the latter fail on `54d3142`), the `ResultsEmails` helper, five classes adapted; the negative controls and the sources (`validation/ba_v0.1.1.md` §BR).

**Stated rationale:** the maintainer's requirements of 2026-11-22: the body shows the results in the attached file's layout; without an attachment when they fit within what common mail clients display without clipping, researched and cited, with a safety margin on the measured encoded size; otherwise a short body and the attached file under a readable name; a plain-text part; readable in light and dark clients; safe, escaped links; no secrets, paths or settings; no new configuration.
