# Architecture

Legend: **[V]** verified in source · **[I]** inference · **[R]** recommendation · **[?]** unknown

## Component boundaries and dependency direction
- [V] Three-layer project graph: `CampertronConsole` and `CampertronGUI` → `CampertronLibrary`. The library has no reference back to either host. Since D92 the console also references `CampertronWeb` (the web UI's host and pages, §Web mode), which references the library; nothing references the console but `CampertronWebTests`, which starts it as a process.
- [V] Since D91 the library also holds the shared form layer (`function/Forms`, §Shared form layer): the forms the desktop GUI's views bind and the web UI will fill, free of any UI toolkit. The GUI project keeps its views, its own view models (the startup, the lookup, Settings > System) and the run of a search and of a refresh.
- [V] Inside the library there is no layering enforcement. `function/Base/Menu.cs` (UI) calls `RecDotOrg.data.Load` and `RecDotOrg.api.RefreshRidbRecreationData`. `Load` calls back into `Menu.Init`. `Cache` (data) writes to the console via `ConsoleUi`. So UI, orchestration and data access are mutually dependent.
- [V] No interfaces, no DI container, all static classes (the services' runs of D45, D61 and D90 and the forms of D91 are instances; the web host of D92 uses ASP.NET Core's service container, which its framework needs, for its own single instances). The only instantiated service-like type of the data access is `RecreationDotOrgContext` (EF `DbContext`), which every query creates with `new RecreationDotOrgContext(configPath)`.
- [V] Models in `CampertronLibrary/class/**` are declared in the global namespace (no `namespace` statement in `Config.cs`, `ConsoleConfig.cs`, `Availability.cs`, `Generic.cs`, etc.).

## Runtime modes
Determined in `Load.GetConfig()` (`CampertronLibrary/function/RecDotOrg/data/Load.cs`):

| Mode | Detection [V] | ConfigPath | CachePath |
|---|---|---|---|
| Container | env `DOTNET_RUNNING_IN_CONTAINER` or `DOTNET_RUNNING_IN_CONTAINERS` is non-null | `/config` (throws `"Config path does not exist"` if missing) | `/cache` (throws `"Cache path does not exist"` if missing) |
| Desktop | otherwise | `Environment.SpecialFolder.LocalApplicationData` + `/CampertronConfig` (created if missing) | `LocalApplicationData/CampertronCache` (created if missing) |

- [V] On the desktop `LocalApplicationData` is resolved with `SpecialFolderOption.Create` (`Load.DesktopDataFolder`, since D37): a missing `~/.local/share` or `$XDG_DATA_HOME` folder is created, and a result that is still not a full path stops the start with an error. It never falls back to the working directory (TD-47 resolved; before, a missing folder resolved to `""` and the data went into the working directory). Existing folders, `XDG_DATA_HOME`, Windows and macOS resolve as before; the container branch does not use it.

`OutputType` (`GeneralConfig.OutputTo`) then selects the behavior: `Console`, `Email`, `HtmlFile`, `UnitTest` or, since D67, `Ntfy`. `Email` and `Ntfy` are the unattended monitoring (`Notifications.IsMonitoring`, §Notification providers).

- [V] Before either mode is chosen, `Program.Main` of the console and the GUI handles `--version` (`RuntimeInfo`): it prints the version and `RuntimeInformation.FrameworkDescription` and exits without calling `Load.GetConfig` (business-rules §11). Everything after that runs inside one `try` in the console's `Main`: a failure is reported by `ConsoleUi.ReportFailure` on standard error and `Main` returns 1 (D34, business-rules §12).
- [V] Since D92 one more thing comes before `Load.GetConfig`: a command line with `--web`, `--healthcheck`, `--listen` or `--port` is web mode's (`CampertronWeb.WebMode.Run`, §Web mode), which finds the same two folders through `Load.GetFolders` (the first part of `GetConfig`, with no settings file read or created and no database extracted). Every other command line starts as before.
- [V] All versions share the data folder and DB file name. Versions before 0.1.0-beta.4 misread the current DB layout (business-rules §10).

```

 └─ Load.GetConfig()                         → CampertronInternalConfig {GeneralConfig, EmailConfig, NtfyConfig, paths, ContainerMode}
      ├─ Yaml.GeneralConfigGetConfig / EmailConfigGetConfig   (generate samples if missing)
      ├─ Yaml.NtfyConfigGetConfig   (only for the monitoring, D67; null without Ntfy.yaml, never created here)

 └─ Load.RunConsole(cfg) → RunConsoleSearch(cfg) → RunConsoleSearch(cfg, ForceSearch:false)  (Main returns its exit code, D64)
      ├─ if the monitoring (OutputTo Email or Ntfy, D67) → MonitoringConsole.Run (D90): MonitoringService.Start, then its checks (§Monitoring service)
      ├─ if ForceSearch → search loop (below)
      └─ else Menu.Init(cfg) → interactive menu (Search → RunConsoleSearch(cfg, true))

search loop (the search files are read once per start, before the first search.
Every later check of the monitoring starts with Load.RegenerateSearchDates, so relative dates follow the current time: D35, TD-46):
  [Email, Ntfy: MonitoringService.Start] Load.CheckEmailOutputSettings (email enabled), Load.CheckNtfyOutputSettings (ntfy enabled or required, D67), the start line,

          no search to check → refused the same way (D64); MonitoringLock.TryAcquire: held or unusable → refused the same way (D90); else Load.PrepareRun, the searches listed
  [menu Search, UnitTest] Load.Preload = Yaml.CampertronConfigGetConfigs(ConfigPath) + Load.Prepare
  Load.Prepare = Load.PrepareRun + Load.WriteScope
    ├─ the loaded searches  (every *.yaml except general/email with autoRun:true; the loader generates the search dates)

    └─ ConsoleResults.DescribeSearches → the searches that run and their warnings (not for UnitTest)

  [checks after the first] Load.RegenerateSearchDates → CampertronConfig.RegenerateSearchData(now)  (no file read, no warning)

      │        (the eight include/exclude lists: SearchFilters, OR semantics, the search's filterMatching, D51)

      └─ its final hits → RunData.FilteredAvailableData (added, never replaced)
  Load.PostProcess → Load.ReportResults (a console, HtmlFile or UnitTest run) | the monitoring: MonitoringService.ReportCheck, written by MonitoringConsole (D90)
    ├─ the monitoring's gate: HasUnreportedEntries (reads Camp.History, writes nothing; Email and Ntfy only: Load.UsesNotificationHistory)
    ├─ the monitoring: one timestamped "Check N: …" line (Load.CheckText; the emails and ntfy messages it will send: Notifications.Planned)
    ├─ Load.OutputResults (items ordered by name):
    │    HtmlFile → CampsiteConfig.WriteAndOpenHtmlResults: one ResultsHtml page for the run, written and opened once; its path and a summary line on the console
    │    Console / UnitTest → CampsiteConfig.WriteConsoleResults: ConsoleResults renders the whole run, with one summary line
    │    Email, Ntfy → Notifications.Deliver (D67), per item: its email if email is enabled (CampsiteConfig.ProcessConsoleConfig:
    │              the page to the cache, ResultsEmail.Compose (D72: the results in the body, or a summary and the page attached
```

- [V] `RunningData` (`class/Base/ConsoleConfig.cs`) is the shared state between parallel tasks: `AllConsoleConfigItems`, `SiteData`, `Urls`, `UniqueCampgroundIds`, `CampertronConfigFiles`, `FilteredAvailableData`, and since D45 the internal `Host`: the per-run `SearchHost` of an interactive search, null for the console (next section); since D90 also the internal `Monitoring`: the `MonitoringRun` of a monitoring's checks, null for the console's Search and an interactive search (§Monitoring service).
- [V] Output is built as a list of `ConsoleConfig.ConsoleConfigValue` (`ConfigType` = `WriteLine`/`Write`/`WriteLineColor`/`WriteColor`/`WriteEmptyLine`). Since D34 nothing writes that text to the console anymore: the console results (`ConsoleResults`), like the HTML page (`ResultsHtml`), are rendered from the values' `Kind` and `Metadata`.
- [V] Since beta.9 (decision D29) the producers also tag their values with presentation metadata: `ConsoleConfigValue.Kind` (`OutputKind`: `SearchHeader`, `MonthHeader`, `NoEntries`, `Availability`, `ConsecutiveSite`, `ConsecutiveDate`, `Detail` for the rest of a record, `Text` = untyped) and `Metadata` (`OutputMetadata`: search, campground, month or date, campsite, equipment, check-in/out). Producers: `Cache.WriteProgress` and `AvailabilityApi.MonthHeaderValues`, `NoEntriesValues`, `AvailabilityValues`. The producers' text is unchanged (`ConsoleOutputGoldenTests` pins it at the value level). Since D34 `Calendar.GenerateCalendar` tags its values `OutputKind.Calendar` (they are only in Console streams). `ResultsHtml.Render` (`function/Base/ResultsHtml.cs`) builds the HTML results page from the metadata only, never from the console text and never from `RunData.FilteredAvailableData` (business-rules §6). It renders the streams as supplied; since D35 (TD-04 fixed) each stream holds only its own search's results.
- [V] Desktop interactive flow recurses: `PostProcess` → `Menu.Init` → `WriteMenu` (infinite `while(true)` reading keys) → `ProcessInput` → `RunConsoleSearch` → `PostProcess` → `Menu.Init`, and so on. Nothing returns: each Search, Refresh and View Config starts one nested menu. Since D47 (TD-12) a key that is not Enter no longer goes deeper: `Menu.ProcessInput` moves the selection or does nothing and returns to the loop in `Menu.WriteMenu`, which draws the options again and reads the next key (before, `ProcessInput` called `WriteMenu` for every key and the stack grew with each key press).

## Notification providers (D67, business-rules-settings §28)
```
Notifications (one definition):  IsMonitoring = OutputTo Email | Ntfy;  EmailEnabled = OutputTo Email;
                                 NtfyEnabled = the monitoring and Ntfy.yaml enabled: true;  NtfyRequired = OutputTo Ntfy
start:  ConfigValidation.ThrowIfNtfyOutputRefused (CheckNtfy: server, topic, tags, priority, timeout, tokenFile's form; no connection)
        NtfyToken.ResolveOnce → NtfyConfig.ResolvedToken (SecretFile for tokenFile; never serialized)
check:  Notifications.Deliver(config, ordered searches, Record):
          per search: email (CampsiteConfig.ProcessConsoleConfig) | ntfy (NtfyMessages.Build → Notifications.PublishNtfy = NtfyPublisher.Publish)
          → Record(search) once any provider delivered;  after the loop: one failure rethrown as it is, both → NotificationException
NtfyPublisher.Publish: HttpClient(SocketsHttpHandler: no redirects, no cookies; Timeout = timeoutSeconds)
          POST <server root> application/json {topic, title, message, priority, tags, click} [+ Authorization: Bearer <token>]
          → 2xx with ntfy's JSON message id = delivered; anything else → NtfyException(NtfyFailure, status)
```
- [V] `Notifications` is the only place that decides which providers a run has; `Load` asks it for the start, the check line, the history policy (`UsesNotificationHistory` is `IsMonitoring`) and the delivery. The providers share one search per check and one result set; each search's openings are recorded once any provider delivered them (the maintainer's decision of 2026-11-22). `Notifications.PublishNtfy` is the seam tests replace (a recorder; `NtfyPublishTests` use a recording handler and a loopback listener, never ntfy.sh). Reports hide ntfy's token and topic (`ConsoleUi.ReportFailure(Exception, CampertronInternalConfig)`).

## Monitoring service (decisions D83 and D90, business-rules-settings §29)
```
MonitoringConsole.Run(cfg, wait)                      the console's adapter (email and ntfy mode)
 ├─ new MonitoringService(MonitoringOptions { Report = MonitoringConsole.Write, Now = ConsoleUi.Now, Blocked = AvailabilityApi.ConsoleBlocked })
 ├─ Start(cfg) → MonitoringStartResult                 refused: ConsoleUi.Error(lines), false | a start that threw: rethrown
 └─ WaitForEnd() → MonitoringStatus                    failed: LastError.Error rethrown to Program.Main (exit code 1)
MonitoringService (an instance: its run, check number, status and lock; no static state)
 Start: the settings checks → Starting → the secrets → the search files and D64's gate → MonitoringLock.TryAcquire
        → Load.PrepareRun → SearchesLoaded → its own thread
 thread: RequireSearchesToCheck → [RegenerateSearchDates] → Parallel.ForEach GetAvailabilitiesByCampground (RunData.Monitoring)
        → a stop asked for meanwhile: abandon (nothing sent or recorded)
        → ReportCheck: HasUnreportedEntries → CheckReported → Notifications.Deliver(DeliveryOutput: EmailSent, NtfySent) → markers → DeliveriesFinished
        → clear → wait CheckInterval (1 minute; the token ends it)
 Stop: cancel the run's token, wait for the thread's end | Restart: Stop, Start | GetStatus: a snapshot | the end: the lock released, Stopped or Failed
MonitoringLock: ConfigPath/Campertron.monitoring.lock, FileStream(OpenOrCreate, ReadWrite, FileShare.None; 0600 when created), held while a run exists
```
- [V] The service is host-neutral, in the pattern of `CampsiteSearch` (D45) and `RidbRefreshService` (D61): it writes nothing to a console, waits for no key and ends no process; a host gets its events (`MonitoringEvent`) and its status (`MonitoringStatus`). The console is its only host today (`MonitoringConsole`); web mode (D83) comes with D79's later pull requests.
- [V] A check's searches are the console's own (`AvailabilityApi`, the same requests, retries and filters). They reach the service through `RunningData.Monitoring` (`MonitoringRun`): the warnings and status lines become events, the waits (30 seconds before a retry, 1 second after heavy traffic, 500 ms for another search's month) end when the run's token is canceled, and a blocked request does what the host gave (`MonitoringOptions.Blocked`; the console's: the error, the five-minute wait and exit code 1; none: the run fails with `MonitoringBlockedException`).
- [V] The deliveries announce themselves through a `DeliveryOutput` (`Notifications.Deliver`): the service's events, or, for `Load.OutputResults` with a monitoring's settings, the console's lines (`DeliveryOutput.Console`). An email is sent by `CampsiteConfig.SendSearchEmail`, which writes nothing to the console.
- [V] The test seams that existed before stay static and are not the service's state: `CampsiteConfig.SendResultsEmail`, `Notifications.PublishNtfy`, `AvailabilityApi.ConsoleDownload`, `BlockedWait` and `ExitProcess`. The wait between two checks is `MonitoringOptions.Wait` (the tests of email and ntfy mode pass it to `Load.RunConsoleSearch`).

## Interactive search service (GS1, decision D45, business-rules §19)
```
CampsiteSearch.Plan(SearchRunRequest{ConfigPath, CachePath, SearchFileNames}, Now)          (no network, no database, no write)
  per chosen file, read once: Yaml.ReadSettingsText → ConfigValidation.ValidateSearch (CM3, with an enabled search's severities)
    → Yaml.LoadSettingsText<CampertronConfig> → CampertronConfig.RegenerateSearchData(Now)   → SearchPlanEntry (Ready | Skipped | Invalid)
CampsiteSearch.Run(plan, IProgress<SearchProgress>?, CancellationToken, SearchHostOptions?)    (blocking; never throws for an outcome)
  SearchHost (per run): token, transport (HttpSearchTransport: one HttpClient per run, or a test's), bounds, shared-month signals, months, progress
  Validating: each search's months (AvailabilityApi.HasDatesDuringThisMonth) and URLs (MonthUrl); the cache folder
  PreparingCampsiteDetails: per campground Cache.PrepareCampground (only with RecreationDotOrg.db; marker last; cancellable)
  CheckingAvailability: Parallel.ForEach search → AvailabilityApi.GetAvailabilitiesByCampground(search, RunData{Host}, own config)
      ProcessMonth → Host.GetMonth: fetch (≤ 3 requests, timeout, cancellable waits, block → no further request) or wait on the
                     month's signal → the console's parsing, filters (FilterData) and consecutive nights, with token checkpoints
  BuildingResults: CampsiteSearch.OpeningsOf(the search's values: Kind/Metadata only) → SearchResult (months, openings, sites, issues)
  → SearchRunResult (status, times, request counts, results, issues; immutable)
```
- [V] The run's configuration is its own: `OutputTo = HtmlFile` on the search path (no calendar values; `Load.UsesNotificationHistory` false, so `Camp.History` is never read; nothing writes it), `EmailConfig = null`; `Run` calls no `PostProcess`, `ReportResults` or `OutputResults`, so nothing is rendered, written, opened or sent, and it never reads `General.yaml` or `Email.yaml`. It never writes to the console (`ConsoleUi`) and never ends the process. The namespace is outside `…RecDotOrg.api`, which the GUI's tests forbid the GUI to reference; since GS2 (D46) the GUI's Results tab uses `CampsiteSearch` (§GUI data flow).
- [V] Shared with the console: `GetAvailabilitiesByCampground` and everything under it, `Cache.PrepareCampground`/`CheckCache` (their console overloads pass the status line and no token), the model types. Changed on the console path without an observable effect: `ProcessMonth` adds a month's header after its fetch; the console's download is the replaceable internal `AvailabilityApi.ConsoleDownload`; `OutputMetadata` carries the occupancy (no renderer reads it).

## RIDB refresh service (V011-1, decision D61, business-rules §8)
```
RidbRefreshService.Run(RidbRefreshRequest{ConfigPath, CachePath}, IProgress<RidbRefreshProgress>?, CancellationToken, RidbRefreshOptions?)
  Clear.CheckCacheDirectory (throws for an unusable cache folder, before anything)                 (blocking; never throws for an outcome)
  AcquiringLock: RecreationDotOrg.refresh.lock (FileShare.None) | held → AnotherRefreshRunning
  CleaningUp: stale staging folders, General.yaml's stale temporary files, stale CampertronDownload-<guid> folders
  [checkpoint] Preparing: WorkRoot/CampertronDownload-<guid>/ (WorkRoot: LocalApplicationData, or a test's)
  Downloading: Web.Download (HttpClient or a test's handler; ResponseHeadersRead; the body streamed; a 60 s stall ends it; bytes)
  Extracting: Compression.Extract → WorkRoot/CampertronExtract (entry by entry, checkpoints, entries); the download folder removed
  RidbStagedRefresh.BuildValidateAndInstall(..., Log, Reporter, Token)
    [checkpoint] PreparingDatabase → [checkpoint] Importing (Populate: a checkpoint before each RIDB file and before Saving)
    → [checkpoint] Indexing → [checkpoint] Validating (ValidationFailed) → [checkpoint] Finalizing
    → [last checkpoint] ClearingCache → Installing (repair lock + BackupDatabase) → CheckingDatabase (quick_check)
  RecordingRefresh: Yaml.GeneralConfigReplaceYaml (lastRidbDataRefresh only), while the lock is still held
  → RidbRefreshResult (Outcome, Stage, Installed, RefreshedAt, Elapsed, Problems, Detail, Error, CancelRequested)
  finally: the download folder and the extraction removed; the staging folder by BuildValidateAndInstall (kept after a failed quick_check)
Hosts: the console's RefreshRidbRecreationData.RefreshData (Log = Console.WriteLine; messages, key wait, rethrows Error)
       and the GUI's CampgroundDataViewModel (RefreshSeams.Run on a worker thread; progress through ProgressGate<T>; Cancel)
```
- [V] The service is the D26 refresh with its steps unchanged in order; what is new is the typed progress (each stage, with the bytes, ZIP entries and RIDB files counted where their number is known), the checkpoints of the token up to the cache step (never after it: from there it installs, checks and records to its end), the classification of a failure by the stage it ended (`RidbRefreshService.Classify`), the download folder of its own (TD-58) and the 60-second stall timeout. It writes nothing to the console, waits for no key and never ends the process; `Run` throws only for a request it can't start. Its seams (`RidbRefreshOptions`: the handler, the timeouts, the work folder, an extract-directory provider, the clock, the log) are production defaults; the tests replace them, and `NoLiveNetwork` still guards every `HttpClient` of the unit tests.

## Shared form layer (decision D91, business-rules-settings §30)
- [V] **Where and why.** `CampertronLibrary/function/Forms`, namespace `CampertronLibrary.function.Forms`: the forms of Settings and Searches, the Results tab's rules and the refresh's rules, for the desktop GUI and the web UI (D79; the web host will be the console's, D80, which references the library only). No new project and no package: the layer uses the base class library alone (`INotifyPropertyChanged`, `ICommand`, `ObservableCollection`, `TimeProvider`).
- [V] **The dependency direction.** A view (Avalonia XAML; later a Razor page) → a form of the layer → the library's services: `ConfigEditSession` (typed edits, validation, preview, the safe writer), `ConfigValidation` (D71's, D73's and D77's checks), `SecretFileCheck`, `SearchFiles`, `Read` (the campground list and the filter choices), `CampsiteSearch.LoadEntry` (the Results list). The layer never references a view, Avalonia, ReactiveUI or ASP.NET Core, and nothing in it is static state that changes.
- [V] **The forms.** `SettingsViewModel` owns `GeneralSettingsViewModel`, `EmailSettingsViewModel`, `NtfySettingsViewModel` and, since D94, `WebSettingsViewModel` (each a `SettingsFileViewModel<T>` over one `ConfigEditSession<T>`; `Web.yaml`'s save goes through `WebAccessRule`) and carries outputTo between them (the General form's shown and saved outputTo decide `Email.yaml`'s and `Ntfy.yaml`'s severities, D71). `SearchesViewModel` owns one `SearchFileViewModel` per search file, the `CampgroundCatalog` and the `FilterChoiceSource` (since D96 also for the web UI's searches pages, one per browser session; the Searches tab's own words are `SearchesWording`, which both UIs show). A field (`SettingField` and its kinds) holds what the user typed, its own input error, the validation's message and severity, and whether it is changed or locked; `SettingsFileViewModel<T>.Refresh` composes everything shown from the session and applies the save rule.
- [V] **The Results tab and the refresh are split.** The desktop GUI's `ResultsViewModel` and `CampgroundDataViewModel` keep the run (an operation with its ID and cancellation, the worker thread, the posts to the UI thread, the ticker, the automatic restart) and call the layer for the rest: `ResultsSearchList` (the list and its choice), `ResultsWording`, `BlockHold`, `ProgressGate`, `ResultSearchViewModel` and the `ResultRow` types (a result's summary and rows), `DataOperationGate`; `RefreshRules` and `RefreshWording`. A web host writes its own run over the same services (`CampsiteSearch.Plan`/`Run`, `RidbRefreshService.Run`) and the same rules and words.
  Since D97 a Start's checks (`ResultsStart`) and an ended run as the tab shows it (`ResultsOutcome`) are the layer's too, called by the desktop GUI's `ResultsViewModel` and the web UI's `WebResults`; `ResultsListing` cuts a search's rows into pages for a UI without a virtualized list, each booking link checked by `BookingLink` (`ResultsLink`).
- [V] **`FormObject` and `FormHost`.** `FormObject` raises `PropertyChanged` at once on the calling thread when a value changed; Avalonia's bindings listen, a page that renders once does not. `FormHost` is the form's thread as the host gives it: `CapturePost` (called on that thread; a post to it from any thread), `Delay` and `Ticker` (timers on it). The desktop GUI's host is `GuiHost.Avalonia` (`CampertronGUI/GuiHost.cs`): the UI thread's dispatcher at `Background` priority and `DispatcherTimer`. Today only `FilterChoiceSource` takes a `FormHost` (through `SearchesViewModel`'s constructor); `ProgressGate` takes the post and the timer as functions from its caller.
- [V] **A message's severity** is `MessageSeverity` (the rule and the screen readers' words); `SeverityBlock` calls it and keeps the colors, the icon and the block (D74, ER-35).
- [V] **Threads.** A form is used by one thread at a time (the desktop GUI: the UI thread; the web UI: one request at a time, D94). The layer starts work off that thread in two places: `FilterChoiceSource`'s read of a campground's values (a task; the answer is posted back through the host and ignored if a newer request was made) and, since D94, `TestNotificationForm.Start`, the desktop GUI's test email or notification (a task running the library's `TestNotification`; its result posted back through the host). The web UI calls the test form's `TryBegin`, `Send` and `End` itself.
- [V] **For a host without live updates** (the web UI, D94): `FieldList` (every field in order), `Generation` (how often the values were filled from the session, so entries apply only to the values a page showed), `ReloadUnlessChanged` and `Save` on the base class. The page hands entries over as bindings do (`WebSettingsForm`) and runs the forms' commands.

## Web mode (decisions D80, D81, D85 and D92, business-rules-settings §31; the settings pages D94, §32; the searches pages D96, §33; the results page D97, §34)
- [V] **The parts.** `CampertronConsole` (`Program.Main`) → `CampertronWeb.WebMode.Run` → `CampertronWebHost.Build` (Kestrel and Razor Pages) → the pages (`Pages/`: the start page, the setup, the sign-in, the sign-out, the password change and, since D94, the settings pages, since D96 the searches pages, since D97 the results page). What needs no ASP.NET Core is the library's `function/WebAccess`: `WebArguments` (the command line), `WebHosts` (the Host and Origin rules, a proxy's form), `WebPasswordHash` and `WebPasswordFile`, `WebSetupCode`, `WebAccessRule` (the one confirmation of a save of `Web.yaml`); `WebConfig` is `Web.yaml`'s model, read and written like every settings file (§Configuration).
  `CampertronWeb` is a Razor class library with a framework reference to `Microsoft.AspNetCore.App` and no package; the console's outputs therefore carry that framework (self-contained archives) or name it (the image, whose base is the ASP.NET Core runtime).
- [V] **An empty builder.** The host is built by hand on `WebApplication.CreateEmptyBuilder`: no configuration from files, environment variables or the command line, no logging provider, none of the framework's default middleware. Where it listens (`WebHostSettings`: the folder, the address, the port, `Web.yaml`'s settings, where its console lines go) comes from `WebMode`; no request can change any of it. ASP.NET Core's services live in its service container; the web UI's own classes (`WebHostSettings`, `WebConsoleLines`, `WebPasswordFile`, `WebSessions`, `WebSetupCode`) are single instances of one host there, with no static state, so several hosts run in one process (the tests).
- [V] **A request's way:** `WebSecurity.Failures` (fixed pages for an exception or an empty refusal; the headers on every answer) → `Methods` (GET, HEAD, POST; the size) → the forwarded headers, only with `trustedProxies` → `Hosts` → `Origins` → routing → the rate limiter → authentication (the cookie's ticket, then `WebSessions`) → authorization (the owner: a session, or no password protection; the fallback for every address) → a page (`WebPageRules`; its antiforgery token), the stylesheet (`WebAssets`, from the assembly) or `/healthz`.

## Console output (decision D34, business-rules §12)
- [V] `ConsoleUi` (`function/Base/ConsoleUi.cs`) is the console's presenter. `Line`, `Status` (wrapped at spaces on a terminal), `Notice`, `LoopLine` (timestamped) and `Write` (styled lines) go to standard output; `Warning` and `Error` go to standard error with a text prefix. One lock makes each call's lines atomic, also from the parallel searches.
- [V] Capabilities are detected once (`ConsoleUi.Current`, from `Console.IsOutputRedirected`/`IsInputRedirected`/`IsErrorRedirected`, `NO_COLOR`, `TERM`, the OS and `Console.WindowWidth`; `ConsoleUi.Detect` is the pure decision). Color needs a terminal on standard output, no `NO_COLOR` and no dumb terminal, and is reset after its text. `ClearScreen` writes `ESC[H ESC[2J` (the visible screen only) and only when both streams are a terminal that understands control sequences and no notice, warning or error is unacknowledged; it is called by the menu, by View Config, before a manual refresh and at the start of a menu search. Nothing else writes a control sequence; the menu's cursor addressing goes through `System.Console` as before.
- [V] `ConsoleResults` (`function/Base/ConsoleResults.cs`) renders the results from the model `ResultsHtml.Build` returns (the model types and `Build` are `internal` for this; nothing else in `ResultsHtml` changed), draws the calendar itself (`Calendar.Lines`, open days marked with `*`) and skips the stream's `Calendar` values. It also describes the searches before they run (`DescribeSearches`) and returns the warnings for searches that cannot find anything.
- [V] Terminal state: the cursor is hidden only on an interactive terminal (`ConsoleUi.HideCursor`), and `Console.CancelKeyPress` and `AppDomain.ProcessExit` handlers, installed on first use, restore the cursor and the color; Ctrl+C also writes "Stopped." to standard error and ends the process as before (exit code 130).
- [V] `Load.FirstStartNotice` (unset by default) is called before the bundled database is extracted, unless `outputTo` is `UnitTest`. Only `CampertronConsole` sets it, so `Load.GetConfig` writes nothing in the GUI (its `--smoke-test` output must hold only `SMOKE` lines) and nothing for `UnitTest`.
- [V] The RIDB refresh's progress lines (`RidbStagedRefresh`, `Clear`, `PopulateDbFromRIDBFiles`, `ConfigFileReplace`, the download lines) are still plain `Console.WriteLine` for the console: since D61 the steps write them to the refresh service's log sink, and only the console's adapter (`RefreshRidbRecreationData.RefreshData`) gives that sink `Console.WriteLine`. ## GUI data flow
- [V] Since D91 the forms named below (`SettingsViewModel` and its three editors, `SearchesViewModel`, `SearchFileViewModel`, the fields, the filter selectors, the Results tab's rows) are classes of the library's shared form layer (§Shared form layer); the flow is as described, with the views binding to them directly. `ResultsViewModel`, `CampgroundDataViewModel`, `MainWindowViewModel`, `ReactiveViewModel`, `SystemSettingsViewModel` and `CurrentConfigurationViewModel` are the GUI project's.
- [V] Startup (R8, decision D33): `App` creates `MainWindowViewModel` and `MainWindow`; when the window has opened, `MainWindowViewModel.Start()` runs `Load.GetConfig()` on a background task (`Task.Run`). It has the same side effects as the console: it creates dirs, writes sample YAML, extracts or repairs the DB, and may auto-refresh. The task never faults; its result is posted to the UI thread and applied only by the latest attempt of a window that is still open. Until then `StartupStatusView` shows "Preparing campground data…"; on failure it shows the message, the settings folder and Try again (`Retry()`, one attempt at a time). `Program.Main` waits for a preparation still running when the window closed, so it is never cut off.
- [V] `ReactiveViewModel` is created only after `Load.GetConfig()` succeeded, with its `CampertronInternalConfig.ConfigPath`, so no getter queries a database that is not ready. It computes its lists in property getters, each with a fresh SQLite query through `Read.*`. (Before R8 its path was hard-coded to `LocalApplicationData/CampertronConfig`; that rule remains as `ReactiveViewModel.DefaultConfigPath` for the designer, tests and the startup-error message, because `Load.GetConfig` returns no path when it fails.)
- [V] `CampertronGUI --smoke-test` (`SmokeTest.cs`, R8) runs this same startup with the real window and reports each step; the release workflow runs it natively on six platforms (linux-x64, linux-arm64, win-x64, win-arm64, osx-x64, osx-arm64) and, for win-x86, as a 32-bit process on 64-bit Windows (history/validation/x-ac_preview.1.md §X, history/validation/ad-ax_preview.2.md §AM).
- [V] Property-change chaining is done with `WhenAnyValue(...).Subscribe(RaisePropertyChanged(...))` in the constructor: each filter raises its dependent list, and each tab's filters and campground raise that tab's details property (`ParkCampgroundDetails`, `CityCampgroundDetails`, `StateCampgroundDetails`; beta.8, D28).
- [V] **Campground identity** (CM4, decision D42, business-rules §16). The three campground lists are `List<CampgroundChoice>` from `Read.CampgroundChoicesByPark`, `CampgroundChoicesByStateAndCity` and `CampgroundChoicesByState` (one parameterized query each, one entry per FacilityID, ordered by `CampgroundChoice.ListOrder`), the park list is `Read.ParksWithCampgrounds`, and the three campground selections are `CampgroundChoice?`. A filter change clears its tab's campground before the new list is raised. `MainWindow.axaml` shows an entry through `CampgroundItemTemplate` (name and location trimmed, ID never trimmed; compiled bindings to the global-namespace type through `xmlns:lib="clr-namespace:;assembly=CampertronLibrary"`), sets each item's accessible name to its label (style on `ComboBox.campground ComboBoxItem`) and caps the drop-down at its selector's width (style on the template's `Popup`).

Before D42 it was `Read.GetCampgroundDetailsByName`, the first facility of the selected name (TD-38). Because every list and details getter queries the database when read, each is bound exactly once (`MainWindowUsabilityTests.Selections_RunOneQueryEach` and `CampgroundIdentityTests.EverySelection_RunsOneParameterizedQuery_AndNoNameLookup` count EF Core commands). - [V] **The YAML document editor** (`YamlDocument`, decision D39, business-rules §13) edits a settings document's text in memory by targeted range replacement, so comments and formatting outside the edited ranges stay byte for byte, and checks every result by reparsing it and loading it with `Yaml.SettingsDeserializer` (the deserializer the three loaders share since D39) against the model the caller intends. It is pure (no file, console, environment or network access). **Its callers**: `Yaml.GeneralConfigReplaceYaml` (since D40, CM2), which changes only `lastRidbDataRefresh` after a RIDB refresh, and the GUI's editing session `ConfigEditSession` (since D43 and D44), which applies the Settings and Searches tabs' edits with it; the loaders are unchanged.
- [V] **Validation and bounded loading** (decision D41, business-rules §15). `ConfigFiles` decides which file is which (ordinal, case-insensitive; one rule for the search loader, View Config, the failure messages and the validation). Every loader reads through `Yaml.ReadSettingsText` and `Yaml.LoadSettingsText`: the editor's limits (bytes before reading, characters, YAML events, nesting, aliases) counted by YamlDotNet's parser, then `SettingsDeserializer` on exactly those events (unknown keys still refused, D20). `ConfigValidation` turns a settings text, file or folder into `ConfigDiagnostic`s (stable code, severity, file kind and name, key, list item, position; never a value), with the loader's own deserializer for what is an error. At run time the loaders refuse only settings that would take a dangerous path (`ThrowIfRefused`), and `Load.RunConsoleSearch` checks `Email.yaml` before the Email loop searches (`Load.CheckEmailOutputSettings`) and, since D67, `Ntfy.yaml` when ntfy is enabled or required (`Load.CheckNtfyOutputSettings`); warnings are not printed. The console prints none of the warnings; the GUI shows the diagnostics: the Settings and Searches tabs at their fields and rows (D43, D44) and the Results tab for the files it lists (D46).

- [V] **Filter choices and Campertron's index** (decision D51, business-rules §8 and §22). `Read.FilterChoicesByCampground` reads a campground's equipment, campsite types, campsite names and `Name:Value` attributes from the installed `RecreationDotOrg.db` (three queries: the campground's campsites, then the equipment and attribute rows of exactly those campsite IDs) into `CampgroundFilterChoices`; the GUI's filter selectors are its callers (`FilterChoiceSource`, D52 to D54, business-rules §23). `RidbIndexes` owns the database's only secondary index, `IX_CampsiteAttributesEntries_EntityID`: `Load.DbExistsCheck` ensures it at every start (best effort, after the repair and any refresh), the refresh builds it on the staging database after the import (`Clear.ClearDatabase` drops it first), and `LegacyAddressLayout.HasOnlyKnownSchemaObjects` accepts it.

## Concurrency
- [V] `Parallel.ForEach` over unique campground IDs (`Load.PrepareRun`, which `Load.Prepare` and the monitoring's start call), over campground configs (`Load.RunConsoleSearch` and, for the monitoring, `MonitoringService`), and over campsite IDs (`Cache.GenerateCacheForCampground`).
- [V] Monitorings exclude each other across processes by the monitoring lock (`Campertron.monitoring.lock`, D90): one for a settings folder. A monitoring's checks run on the service's own thread; `Start`, `Stop` and `Restart` are serialized, and the status is a snapshot taken under the service's lock. The lock does not cover the campground cache (TD-54).
- [V] Refreshes exclude each other across processes by the refresh lock (`RecreationDotOrg.refresh.lock`, D26). Within one GUI window, since D61, the Results tab's search and the refresh of the campground data also exclude each other (`DataOperationGate`, on the UI thread), because the refresh clears the cache folder a search writes; across processes a search and a refresh can still overlap (TD-54).
- [V] Monthly URL dedup: the first thread to `RunData.Urls.TryAdd(Url)` fetches. The others busy-wait in 500 ms steps on `RunData.SiteData` (`AvailabilityApi.ProcessMonth`). In an interactive run (D45) they wait, cancellably, on the month's signal in `SearchHost`, which the fetching search always sets (with the month, a final failure, a block or cancellation).
- [V] `RunData` is passed by `ref` into parallel lambdas. Since D35 a search writes into it only what it shares: a month it downloaded (`SiteData`, `Urls`) and, at its end, its final hits (`FilteredAvailableData.Add`, a thread-safe `ConcurrentBag`). Its hits during the search, and its consecutive filtering, are its own (a per-search `ConcurrentBag`), and nothing replaces `RunData.FilteredAvailableData`. Before D35 `FilterConsecutiveDays` read every search's hits in it and reassigned it (TD-04: a missed Email notification and a false-positive consecutive result, reproduced deterministically on 2026-11-14). The cached months stay read-only (TD-40).
