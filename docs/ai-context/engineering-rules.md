# Engineering rules

Authority: current. These are the rules for changing each part of Campertron: what to keep, what never to do, and which suites and negative controls to run afterwards. Read the whole rule for every area a task touches before changing it.

Origin: moved from `CLAUDE.md` §"Preserving business logic" in roadmap step 9, Phase 1 (2026-11-17 UTC; `CLAUDE.md` at `3adcc8be47a5708ebd950ee8d5b3b8448ba6263d`). The text of each rule is unchanged. Phase 1 added only the heading and ID above each rule and broke lines longer than 1,000 characters at sentence boundaries; each rule is still one Markdown list item and renders as before. `history/README.md` §Phase 1 migration map records the proof. Roadmap step 9, Phase 4 (2026-11-17) changed only the rules' `build-and-test.md` § citations, which now name the file that holds each section since Phase 2, with the same label (`history/README.md` §Phase 4 migration map).

The IDs ER-01 to ER-32 are permanent: an ID never changes meaning and is never reused, and a new rule takes the next free ID. `CLAUDE.md` §Invariant index summarizes every rule in one line, and `README.md` §Task routing names the rules each task needs. The summaries are pointers; the text below is the authority.

## Preserving business logic

### ER-01 Filter semantics and date math
- The filter semantics (`SearchFilters`, since D51) and the `ProcessMonth`/`CalculateAvailableDates` date math are the current contract (for example, `Contains` matching has the list value contain an equipment or attribute value but a campsite type contain the list value, campsite names are exact in both modes, and today's date is never matched). D51 changed the filters deliberately (OR for every list; `filterMatching`); do **not** change them further as a side effect. Change them only when asked, and record the change in `business-rules.md`.

### ER-02 Retries, notification markers and the container and email loop
- Keep the retry and sleep behavior (`AvailabilityApi.GetWebApiData`), the duplicate-notification markers (`Camp.History`), and the container/email loop unless the task targets them.

### ER-03 Camp.History, the Email notification history
- `Camp.History` is the Email loop's notification history only (decision D8 as refined, business-rules §5): one `internal` policy, `Load.UsesNotificationHistory` (`OutputTo == Email`), gates the reads (`AvailabilityApi.FilterData`, the Email gate `Load.HasUnreportedEntries`) and the write (`Load.RecordNotificationHistory`). Console, HtmlFile and UnitTest must neither read nor write it. A marker is written only after the email that shows the opening was delivered (TD-14, decision D36): each search's openings right after its send in `Load.OutputResults`, the run's remaining hits after every email of the check (`Load.ReportResults`); a failed email leaves its openings and those of the later emails eligible, and earlier markers stay. Only a marker write creates `Camp.History` (TD-43); never create it eagerly or write a marker before the send. Sends go through `CampsiteConfig.SendResultsEmail`, which tests replace (no test sends mail).
  Keep the marker format (`Camp.History/{yyyy}/{M}/{d}/{CampsiteID}`, directories), never delete or migrate existing markers, and keep the rule that a reported campsite and date stays suppressed for Email even if it disappears and reappears. Run `NotificationHistoryTests` and `EmailDeliveryHistoryTests` after changing the search, the output, the email or the history.

### ER-04 RIDB import row writer
- The RIDB refresh writes rows through `RidbTableInserter` (prepared SQLite commands, one transaction, EF Core's former `SaveChanges` row order; decision D25), not EF `SaveChanges`. Its column mappings are hand-typed: when a mapped RIDB model changes, update the matching mapping; `PopulateTests` fails otherwise. Keep the row order and run the full-export comparison of history/validation/a-w_2026-11-10_to_beta.10.md §M after changing the import.

### ER-05 Failure-safe RIDB refresh
- The RIDB refresh is failure-safe (decision D26, business-rules §8): it builds and validates a staging DB in `ConfigPath/RecreationDotOrg.refresh-<guid>/` and installs it with one `SqliteConnection.BackupDatabase` transaction (`RidbStagedRefresh`). Never install by renaming, replacing or deleting the installed DB. Keep the order: refresh lock → staging build and `Validate` → cache cleared → repair lock + backup → `quick_check` → `LastRidbDataRefresh` written once. The cache step clears the configured `CachePath` (`LocalApplicationData/CampertronCache` on the desktop, `/cache` in a container; TD-05 resolved, decision D27). The cache path comes only from `CampertronInternalConfig.CachePath`; never rebuild it from `LocalApplicationData`, and keep the guards in `Clear.CheckCacheDirectory`/`ClearRefreshCache` (no unset, root or config directory; only top-level files deleted).
  After changing it, run `AtomicRefreshTests`, the kill harness and the full-export comparison (history/validation/a-w_2026-11-10_to_beta.10.md §N). The timestamp is written with `Yaml.GeneralConfigReplaceYaml` (since D40 only that value, edited in the current file and written by `ConfigFileReplace.Replace`); don't write it in place or re-serialize `General.yaml`. The culture-dependent row order (TD-36 part 2) is open.

### ER-06 GUI startup
- GUI startup (R8, decision D33): `MainWindowViewModel` runs `Load.GetConfig` on a background task after the window opened and shows "Preparing campground data" or the startup error (message, settings folder, Try again). Never create or bind anything database-backed before it succeeded (`StartupTests` count EF commands on all threads), keep UI changes on the UI thread, keep the attempt/detach guards, post an attempt's completion to the dispatcher `Begin` captured on the UI thread and never ask for `Dispatcher.UIThread` on a worker thread (D49: between two headless tests the first thread that asks becomes the UI thread, and the next test fails before it starts), and keep `Program.Main` waiting for a preparation still running when the window closed (extraction, repair and refresh must not be cut off). The loader is the only test seam; don't change `CampertronLibrary` for the GUI. `--smoke-test` (`SmokeTest.cs`) reports `SMOKE key=value` lines that `check_gui_smoke_report` validates:
  change both together. Capped elements use a capped star column (D28), never `MaxWidth` alone (centers) or left alignment (shrinks).

### ER-07 GUI lookup tabs and theme resources
- GUI (beta.8, decision D28): three read-only lookup tabs, each with its own selections and details, since D43 the Settings tab, since D44 the Searches tab and since D46 the Results tab (next rules); since D50 the lookup tabs are the Campgrounds tab's own row (labeled Campsites until D55) and Settings holds Campertron and System (the GUI navigation and theme rule below). Take colors only from Fluent theme resources (`Styles/AppStyles.axaml`, `DynamicResource`; the app follows the system Light/Dark theme). Bind each database-backed view-model property exactly once (every getter queries SQLite; `Selections_RunOneQueryEach`). The GUI owns its labels through `Read.GetCampgroundDetailsById` (since D42; `GetCampgroundDetailsByName` is kept unchanged for its tests); leave `Read.GetParkCampgroundByName`'s prefixed contract alone. Keep the Tab-wrap workaround in `MainWindow` for the TabControl keyboard trap reproduced with Avalonia 12.1.6 (TD-39; since D50 on both tab levels);
  reassess it after any Avalonia upgrade or an upstream fix for that exact behavior. Campgrounds are identified by FacilityID, not by name (D42, next rule).

### ER-08 Campground identity
- Campground identity (CM4, decision D42, business-rules §16): a GUI campground is a `CampgroundChoice`; never select, compare or look up a campground by its name or label in the GUI (the label is display text, never parsed). Keep the FacilityID exactly as stored (a string: never parsed as a number or trimmed). One entry per FacilityID; the label shows the location when known and always the ID (`Unnamed campground` for a blank name); order by `CampgroundChoice.ListOrder`. By State and By City keep their location filters (inner joins); By Park lists a park's campgrounds also without an address (outer join); never invent a location. A filter change clears its tab's campground in `ReactiveViewModel`; the details come only from `Read.GetCampgroundDetailsById` (empty state when it returns null); still one query per selection. Keep the campground drop-down capped at its selector's width so the IDs stay visible.
  Keep the name-based `Read` methods unchanged for their callers (`RidbDatabase.Validate`, `ReleaseCheck`, tests). The search editor's picker (CM6, D44) reuses `CampgroundChoice` through `CampgroundPickerEntry` and `Read.CampgroundPickerEntries` (every reservable, enabled campground, one query). After changing any of this run `CampgroundChoiceTests`, `CampgroundIdentityTests` (library and GUI), `CampgroundDetailsTests`, `AddressStateTests`, the GUI suite and the negative controls of history/validation/ad-ax_preview.2.md §AG.

### ER-09 GUI navigation and theme
- GUI navigation and theme (decision D50, business-rules §21): the top-level tabs are exactly Searches, Results, Settings, Campgrounds (`MainWindow.*TabIndex` 0 to 3; the fourth labeled Campgrounds since D55, while its automation IDs `CampsitesTab` and `CampsitesTabControl`, the internal `MainWindow.CampsitesTabIndex` and the smoke line's key `campsites` keep the former label: they are automation IDs, keep them; never relabel campsite text, a campsite is a site within a campground), Searches is shown at the start and is shown to its view model when the startup is ready (it reads the search files and the campground data then); Settings' row is Campertron then System (`SettingsTabControl`), Campgrounds' row is By Park, By City, By State (`CampsitesTabControl`), each opening on its first tab; nested rows use `Classes="nested"` (aligned with the top level, smaller headers).
  Settings > Campertron keeps every CM5 rule (files checked when it is shown, the password masked when it is left, also for System). Keep the tabs' `x:Name`s (automation IDs), the content names and the smoke test's `navigation` line in step with `check_gui_smoke_report`. The TD-39 workaround: a trapped Tab wraps to the top-level header, a trapped Shift+Tab goes to the innermost row's header, a Tab from a header that skips a nested header goes to it. The theme: `ThemeChoice` System/Light/Dark, applied only through Avalonia (`AppTheme`: System is `ThemeVariant.Default`, never platform detection of Campertron's own), read by `App.PrepareTheme` before the window is created and kept by `ThemePreferenceStore` in `LocalApplicationData/CampertronGUI/preferences.json` (a JSON object, `"theme"`; read without creating anything, never the working directory; anything missing, unreadable, malformed, over 64 KiB, with a duplicate member or an unknown name gives System;
  a save goes through a temporary file in the same folder and keeps the object's other members). Never store it in `CampertronConfig`, a YAML file, `CampertronInternalConfig` or the console, and never write it except on the user's choice (the smoke test's `ThemeProbe` uses a temporary folder and restores the application's theme). After changing any of this run `NavigationTests`, `ThemePreferenceTests`, `MainWindowUsabilityTests`, `SettingsEditorTests`, `SearchEditorTests`, `ResultsTabTests`, `StartupTests`, `SmokeTestTests` and the release-policy tests, then the negative controls and the real-window review of history/validation/ad-ax_preview.2.md §AO.

### ER-10 GUI settings editing
- GUI settings editing (CM5, decision D43, business-rules §17): the Settings tab (since D50 Settings > Campertron) edits only `General.yaml` and `Email.yaml` (search files: the Searches tab, next rule), only through `ConfigEditSession` (never write a settings file from the GUI another way, never re-serialize, never normalize a file to make it editable: unsupported YAML stays read-only with its reason, unknown keys stay refused). Keep: no edit no write; a value equal to the file's is no edit; Save only when edited, verified by the editor, without blocking validation errors and without a conflict; the read-back must be the reviewed text before the edits are cleared; external changes reload a clean editor and open a conflict for an edited one (never overwrite, never discard silently); `Email.yaml`'s severity follows the General form's outputTo; `outputTo: UnitTest` kept but not offered. The password:
  masked (`SecretTextBox`, whose automation value is always the mask), revealed on screen only until save/revert/reload/resolution/file switch/leaving the tab or window, never in a message, preview line, status, smoke line or exception (the preview masks it with a fixed-length mask). One rolling `.bak` with the file's mode or access rules; a GUI-created `Email.yaml` 0600 on Unix (`ConfigFileReplace.Create`'s mode). No SMTP connection, test email, search, refresh or vault. `--smoke-test` runs `SettingsProbe` in a temporary folder and reports `settings-probe` and `settings-tab`; change `SmokeTest.cs`, `check_gui_smoke_report` and its policy tests together. After changing any of this run `ConfigEditSessionTests`, `ConfigEditEmailTests`, `SettingsEditorTests`, `SmokeTestTests`, the CM1 to CM3 suites and the release-policy tests, then the negative controls of history/validation/ad-ax_preview.2.md §AH.

### ER-11 Parallel searches
- Parallel searches (TD-40): `Load.RunConsoleSearch` runs the searches in `Parallel.ForEach`, and a month's availability in `RunData.SiteData` is one object shared by every search of that campground and month. Treat it as read-only once it is cached: derive per-search data into new objects (`CampsitesDataEntry.CalculateAvailableDates`, `AvailabilityApi.AvailableDatesBySite`) and never write into the cached `AvailabilityEntries`/`CampsitesDataEntry` (the kept `GenerateDates` does; the search must not call it). `RunData.FilteredAvailableData` is the run's set of every search's final hits: a search collects its own hits, filters its consecutive nights on those only, and only adds its final hits to the run's set; never read or replace it from a search (TD-04, fixed by D35). Build dates from their numbers, never by parsing culture-dependent text (TD-11, D35), and keep the Email loop's per-check date regeneration quiet and file-free (TD-46, D35).
  After changing the search, run `AvailableDatesTests`, `SharedMonthSearchTests`, `SearchIsolationTests`, `SearchDatesTests` and the parallel-versus-isolated comparison of history/validation/x-ac_preview.1.md §Z (every search, single-night and consecutive, must equal itself run alone: 0 differences).

### ER-12 HTML results page
- HTML results page (beta.9, decision D29): `ResultsHtml` renders only from `ConsoleConfigValue.Kind`/`Metadata`; never parse console text or rebuild results from `FilteredAvailableData` (TD-04 is fixed by D35; the rule stays). When a producer changes, tag its values without changing their text: `ConsoleOutputGoldenTests` pins the producers' text byte for byte (the console no longer writes it, D34; it is the stream's contract). Encode every dynamic value; keep the page self-contained (inline CSS, no script, no external reference) and readable without CSS (it is also the email body). `HtmlFile` writes and opens one page per run (`Load.OutputResults`); `Email` sends one email per search. Tests replace the browser launch through `CampsiteConfig.OpenHtmlFile`.

### ER-13 Console output
- Console output (decision D34, business-rules §12): write console messages only through `ConsoleUi` (`Line`/`Status`/`Notice`/`LoopLine` on standard output, `Warning`/`Error` on standard error) and never write a control sequence yourself; `ConsoleUi.ClearScreen` is the only screen clear (interactive terminal only, never the scrollback, never over an unread message), and the Email loop never clears. Console results are rendered by `ConsoleResults` from `Kind`/`Metadata` through `ResultsHtml`'s model (internal for that; keep the page byte-identical: history/validation/x-ac_preview.1.md §Y) and never from the values' text or from `FilteredAvailableData`; like the page, it shows each stream as supplied, so it never showed TD-04's orphan calendars; the cause was fixed by D35. Keep these contracts: `--version` (untouched, first in `Main`); a start with `outputTo: UnitTest` writes nothing;
  `Load.GetConfig` writes nothing on a clean first start unless `Load.FirstStartNotice` is set, which only `CampertronConsole` does (the GUI's `--smoke-test` output must hold only `SMOKE` lines); "Config path does not exist" and "Unsupported output type in container" stay in their messages; a handled failure exits with code 1 (`ConsoleUi.ReportFailure` in `Program.Main`; since D37 also equal `StartEndDate` dates and a blocked request), signals keep 130/143/129. Failure messages come from exceptions only: never print a value of `Email.yaml`. Don't add a terminal library, flags or a logging framework. After changing console output run `ConsoleUiTests`, `ConsoleResultsTests`, `ConsoleOutputTests`, `ConsoleFailureTests` and `ConsoleOutputGoldenTests`, and for anything touching the terminal the pseudo-terminal, redirection, signal and container checks of history/validation/x-ac_preview.1.md §Y. A plain-mode golden changes only with an intended presentation change, in the same commit.

### ER-14 GUI search-file editing

Never add a parallel editor, never re-serialize a search file, never delete one, never write one from the console, the loop, the start, the refresh or the validation (D37 holds there). Keep: no edit no write; the console's discovery (`ConfigFiles.SearchFiles`, sorted ordinally ignoring case); missing keys, null lists and `- ~` items kept until edited; list edits item by item with their comments (a list the editor can't edit item by item stays locked); undefined `searchBy` kept; unknown keys read-only.
  Names only through `SearchFileName` (`.yaml`, letters, digits, spaces and `- _ . ( )`, no folder or traversal, no reserved or settings-file name, a name in use in any case refused). Campgrounds: identity the FacilityID string; the picker lists every reservable, enabled campground (one query when the tab is first shown, no query per file), filters by name, city, state, park or exact ID, never by part of an ID; a typed ID is used only if it is exactly such a campground (never trimmed or parsed); an entered unknown ID is an error, the file's own a warning. New search: the example (`Yaml.SearchSampleConfig`, shared with the start) with `autoRun: false`. The enabled toggle edits `autoRun` alone. Open question #40 stays: show the folder's warning (`ConfigValidation.SearchFolderDiagnostic`, `RunsAtStart`), never enable or create a search by itself. No search, availability request or result control in the Searches tab (GS2 put them in the Results tab, next rule; no Run button here).

After changing any of this run `SearchFileSessionTests`, `SearchFilesTests`, `CampgroundPickerTests`, `SearchEditorTests`, `SmokeTestTests`, the CM1 to CM5 suites and the release-policy tests, then the negative controls of history/validation/ad-ax_preview.2.md §AI.

### ER-15 Settings safety and failure exits
- Settings safety and failure exits (decision D37, business-rules §9): create the example `ZionConfig.yaml` only when the settings folder has no search file, and never write over or re-serialize a user's search file (the GUI's explicit Save, Save As and New search are D44's, previous rule); with search files of which none has `autoRun: true`, warn and search nothing (open question #40 for the Email loop). Report an unusable settings file by throwing inside the loader's `ConsoleUi.NoteFile` boundary (an empty `General.yaml` or search file, equal `StartEndDate` dates); never `Console.ReadKey` or `Environment.Exit` in the loader. An empty `Email.yaml` stays tolerated outside Email output (TD-51 is preview.2). A blocked request keeps its message and 5-minute wait and exits with 1 through `AvailabilityApi.BlockedWait`/`ExitProcess` (internal seams; tests replace them, production defaults `Thread.Sleep`/`Environment.Exit`).
  The desktop data folder comes only from `Load.DesktopDataFolder` (`SpecialFolderOption.Create`, a full path or an error): never fall back to the working directory, and leave the container's `/config` and `/cache` alone. The RIDB refresh extracts only into `LocalApplicationData/CampertronExtract` (`Compression.ExtractFolderName`); never delete a folder Campertron does not own. Run `SettingsBootstrapTests`, `DataFolderTests`, `ConsoleFailureTests`, `AtomicRefreshTests` and `CachePathTests` after changing any of this (history/validation/x-ac_preview.1.md §AB).

### ER-16 YAML document editor
- YAML document editor (CM1, decision D39, business-rules §13): `YamlDocument` is pure and in memory (no file, console, environment or network access; `TheEditor_NeverReachesTheFileSystemTheConsoleOrTheNetwork` scans its IL); its production callers are `Yaml.GeneralConfigReplaceYaml` (D40) and the GUI's editing session `ConfigEditSession` (D43, D44). It edits by text-range replacement located by YamlDotNet's normal parser (comments skipped; never depend on YamlDotNet's comment tokens: 17.0.0 to 18.1.0 fail on a comment after a flow sequence in that mode) and its own scan of the gaps for comments; it never re-serializes a document and refuses, with a value-free diagnostic, anything it can't edit safely instead of normalizing it. Every result passes the preservation checks and a load with `Yaml.SettingsDeserializer` (the one deserializer of the three settings loaders) that must equal the caller's intended model; a failure returns no text.
  Keep the refusals, the locks (anchors, aliases, standard tags), the engine-only limits and the rule that no diagnostic quotes a value of the document (Email.yaml). Offsets are UTF-16 indexes into the caller's text; a leading U+FEFF is kept but not parsed. After changing it, or the loaders' deserializer, run `YamlDocumentTests`, `YamlDocumentPreservationTests` and `YamlDocumentRefusalTests` and the negative controls of history/validation/ad-ax_preview.2.md §AD. File access belongs to `ConfigFileReplace` (CM2), never to the editor.

### ER-17 Settings validation and loading
- Settings validation and loading (CM3, decision D41, business-rules §15): every settings file is loaded through `Yaml.LoadSettingsFile`/`LoadSettingsText` (`ReadSettingsText`: bytes checked before reading, the former decoding; `ScanSettings`: the editor's character, event, nesting and alias limits counted by YamlDotNet's parser; then `SettingsDeserializer` on exactly those events). Never deserialize a settings text another way, never add `IgnoreUnmatchedProperties` (D20), and keep the loader, `ConfigValidation` and the editor on the same limits and deserializer. Classify files only with `ConfigFiles` (ordinal, case-insensitive; never `ToLower`). `ConfigDiagnostic` messages are fixed text, key names and numbers: never a value or an exception's message, and no unknown key of `Email.yaml` by name. At run time refuse (through `ConfigValidation.ThrowIfRefused`, inside the loaders' `NoteFile` boundary) only what would take a dangerous path; don't print warnings.
  `Load.CheckEmailOutputSettings` runs first in the Email branch of `Load.RunConsoleSearch`, before `Preload`: keep it there and out of `Load.GetConfig` (the GUI and other output types must start with an incomplete `Email.yaml`); it never connects or sends. Don't change open question #40's loop. After changing any of this run `ConfigFilesTests`, `SettingsLoaderLimitsTests`, `ConfigValidationTests`, `EmailOutputValidationTests`, the CM1 and CM2 suites and `ConsoleFailureTests`, then the negative controls of history/validation/ad-ax_preview.2.md §AF (rebuild after restoring).

### ER-18 Settings file writes
- Settings file writes (CM2, decision D40, business-rules §14): every settings file write goes through `ConfigFileReplace`. `Replace` (`General.yaml`'s refresh timestamp and, since D43 and D44, the GUI's saves of `General.yaml`, `Email.yaml` and search files through `ConfigEditSession`) reads strictly (`Read`: UTF-8 only, a BOM kept as a leading U+FEFF, UTF-16/32, NUL and invalid bytes refused, links followed to a regular-file target, a SHA-256 and the metadata kept), and the caller edits the text it read with `YamlDocument` (never a re-serialization and never the settings loaded at the start) and checks it with `VerifyCandidate` before writing, on the temporary file and after the rename. Keep the order: same-directory `<name>.<32 hex>.tmp` (create-new, 0600 while written, `Flush(true)`, the file's mode, read back) → unchanged check → `<name>.bak` (one rolling backup, the source's mode, renamed) → unchanged check → rename → read-back. `Create` (the samples)
  writes the serializer's unchanged text and moves it into place only if the name is free; never truncate or write over a settings file, and load a file that another program created meanwhile. A Unix link stays a link (write in the target's directory); on Windows reparse points, read-only files and files with their own ACL are refused, and the temporary file and the backup must have exactly the file's access rules (DACL as SDDL) before anything is renamed. These Windows paths run only in the CI job `windows-settings-files` (now "Windows settings files (CM1 to CM3, CM5, CM6)"): keep it green, and add a test to `ConfigFileReplaceWindowsTests` for new Windows behavior. Stale cleanup removes only exact temporary names, regular files, older than `StaleTemporaryAge` (10 minutes). Messages name the file and the problem, never a value (Email.yaml). The `Step` seam is for tests and the interruption harness only.
  After changing it run `ConfigFileReplaceTests`, `GeneralYamlTimestampTests`, `SettingsBootstrapTests` and `AtomicRefreshTests` (and let the Windows job run), then the negative controls and the interruption harness of history/validation/ad-ax_preview.2.md §AE.

### ER-20 Host-neutral search service
- Host-neutral search service (GS1, decision D45, business-rules §19): `CampsiteSearch.Plan` reads each chosen search file once (the bounded reader), checks it as an enabled search whatever its `autoRun` (CM3's diagnostics with an enabled search's severities; warnings never block) and never writes a file or reads `General.yaml`/`Email.yaml`; `Run` searches only through `AvailabilityApi.GetAvailabilitiesByCampground` (never a parallel search, never `Preload`/`PostProcess`/`OutputResults`), with its own configuration (`OutputTo = HtmlFile` on the search path, `EmailConfig = null`): never `Camp.History`, never `ConsoleUi`, never `Environment.Exit`, never a settings write. Keep `RunningData.Host` null for the console and every host addition a no-op there (`Host?.ThrowIfCanceled()`; the console's fetch-or-poll, retries, 5-minute wait and exit unchanged). The interactive host:
  at most three requests per month in all (`SearchHostOptions.MaxAttempts`, a constant), the 30 s request timeout, cancellable waits, HTTP 429 and the block page a block (no further request, received months kept), 408/5xx retried, other 4xx not, the 32 MiB limit, every waiter of a shared month released in `finally`; one `HttpClient` per run (`HttpSearchTransport`). Typed results only from `Kind`/`Metadata` (`CampsiteSearch.OpeningsOf`; never `ConfigValue` or the page), a month not checked never reported as one without availability, issues fixed text only. Never build a cache without `RecreationDotOrg.db` (SQLite would create an empty one); keep the completion marker last. Tests reach recreation.gov only through `SearchHostOptions.Transport` or `AvailabilityApi.ConsoleDownload` (`NoLiveNetwork` fails the run otherwise).

### ER-29 The published container image is the validated image
- The published container image is exactly the image the docker job validated (D32, history/validation/a-w_2026-11-10_to_beta.10.md §W). The docker job builds both platforms once as an OCI archive, checks both, correlates the smoke-tested amd64 image by digest and uploads the archive as `container-image`. Since D48 `container-smoke` loads that archive's arm64 image on an arm64 runner (`skopeo copy` from `oci-archive:` into the local Docker; no registry, no rebuild) and identifies it by its config blob (read from a `docker save`, `saved_image_config`) and its layer diff_ids (`check_loaded_platform_image`), not by its image ID: a loaded image can get a manifest of Docker's own. `docker-publish` pushes those bytes with `skopeo copy --all --preserve-digests` and attests the validated digest.
  Its tags (`publish_oci_archive`, D59, which resolved TD-57): every tag of the version is checked before anything is copied; the exact version tag is created or already the validated digest and is never moved; a stable version's `<major>.<minor>` and `latest` are created, kept, or moved forward only from an image whose version label, read from both platform images by digest, is an older stable version (of the same `<major>.<minor>` for that tag), never backward; a pre-release passes only its exact tag.
  The exact tag is pushed and read back first, each tag is read again just before its copy and every tag is read back at the end; a repetition for the same archive completes a partial publication.
  Never add an image build to `docker-publish`, never let the docker job contact a registry, never move an exact version tag or a floating tag backward, and keep the rehearsal, the preflight and the digest checks.
