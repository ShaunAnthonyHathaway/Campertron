# Engineering rules

Authority: current. These are the rules for changing each part of Campertron: what to keep, what never to do, and which suites and negative controls to run afterwards. Read the whole rule for every area a task touches before changing it.

Origin: moved from `CLAUDE.md` §"Preserving business logic" in roadmap step 9, Phase 1 (2026-11-17 UTC; `CLAUDE.md` at `3adcc8be47a5708ebd950ee8d5b3b8448ba6263d`). The text of each rule is unchanged. Phase 1 added only the heading and ID above each rule and broke lines longer than 1,000 characters at sentence boundaries; each rule is still one Markdown list item and renders as before. `history/README.md` §Phase 1 migration map records the proof. Roadmap step 9, Phase 4 (2026-11-17) changed only the rules' `build-and-test.md` § citations, which now name the file that holds each section since Phase 2, with the same label (`history/README.md` §Phase 4 migration map).

The IDs ER-01 to ER-42 are permanent: an ID never changes meaning and is never reused, and a new rule takes the next free ID. `CLAUDE.md` §Invariant index summarizes every rule in one line, and `README.md` §Task routing names the rules each task needs. The summaries are pointers; the text below is the authority.

## Preserving business logic

### ER-01 Filter semantics and date math
- The filter semantics (`SearchFilters`, since D51) and the `ProcessMonth`/`CalculateAvailableDates` date math are the current contract (for example, `Contains` matching has the list value contain an equipment or attribute value but a campsite type contain the list value, campsite names are exact in both modes, and today's date is never matched). D51 changed the filters deliberately (OR for every list; `filterMatching`); do **not** change them further as a side effect. Change them only when asked, and record the change in `business-rules.md`.

### ER-02 Retries, notification markers and the container and email loop
- Keep the retry and sleep behavior (`AvailabilityApi.GetWebApiData`), the duplicate-notification markers (`Camp.History`), and the container/email loop unless the task targets them.
- Email mode enters its loop only with a search to check (decision D64, business-rules §9): keep `Load.CheckSearchesToCheck` after the search files are read and before anything is prepared, with the search plan's rule (a loaded search with a `campgroundID`; never a second model), both in `Load.LoadMonitoringSearches`, which the GUI's check calls too (D73: change the rule there, once, for both), one `ConsoleUi.Error` and `Load.RunConsole`'s exit code 1, and `Load.RequireSearchesToCheck` before every check. Never enable, create or rewrite a search to avoid the error, never send an email about it, and never wait or retry instead of stopping.
  Email mode's start never creates the example search: without a search file it stops with the same error and leaves the folder as it is (D65; the loader's `CreateExampleIfNone` false only there). An `outputTo: UnitTest` start is not email mode: it searches nothing and ends with 0, the silent start the release smoke tests use (D65). After changing it run `EmailStartTests`, `EmailOutputValidationTests`, `SettingsBootstrapTests` and `SearchFilesTests`, then the negative controls of history/validation/ba_v0.1.1.md §BJ and §BK (rebuild after restoring).
  Since D67 the unattended monitoring is `outputTo: Email` or `outputTo: Ntfy` (`Notifications.IsMonitoring`, one definition): ntfy mode shares this loop, this gate (its words name "ntfy mode") and its exit; never make a monitoring rule depend on `OutputTo == Email` alone (ER-34; `NtfyStartTests`, `NotificationDeliveryTests`).
  Since D90 that loop, its gate, its checks and its one-minute wait are the monitoring service's (`MonitoringService`, ER-36), and `Load.RunConsoleSearch` hands a monitoring's outputTo to its console adapter (`MonitoringConsole.Run`); the rules above apply to the service's start and checks as written, and the console's output, exit codes and waits stay as they were. The console's Search and the container's loop for other output types stay in `Load.RunConsoleSearch`.

### ER-03 Camp.History, the Email notification history
- `Camp.History` is the Email loop's notification history only (decision D8 as refined, business-rules §5): one `internal` policy, `Load.UsesNotificationHistory` (the unattended monitoring: `OutputTo` Email or, since D67, Ntfy), gates the reads (`AvailabilityApi.FilterData`, the Email gate `Load.HasUnreportedEntries`) and the write (`Load.RecordNotificationHistory`). Console, HtmlFile and UnitTest must neither read nor write it. A marker is written only after the email that shows the opening was delivered (TD-14, decision D36): each search's openings right after its send in `Load.OutputResults`, the run's remaining hits after every email of the check (`Load.ReportResults`); a failed email leaves its openings and those of the later emails eligible, and earlier markers stay. Only a marker write creates `Camp.History` (TD-43); never create it eagerly or write a marker before the send. Sends go through `CampsiteConfig.SendResultsEmail`, which tests replace (no test sends mail).
  Since D67 (ER-34) a delivery is that of any enabled provider: a search's openings are recorded once its email was sent or its ntfy message published (`Notifications.Deliver`, the maintainer's decision of 2026-11-22), the remaining hits only after a check that no provider failed; ntfy's publish goes through `Notifications.PublishNtfy`, which tests replace (no test reaches an ntfy server).
  Keep the marker format (`Camp.History/{yyyy}/{M}/{d}/{CampsiteID}`, directories): no version, no migration. Run `NotificationHistoryTests`, `EmailDeliveryHistoryTests` and, since D67, `NotificationDeliveryTests` after changing the search, the output, the email, ntfy or the history.
  Since D104 (2026-11-24, which replaced the rule of D8's refinement that a reported campsite and date is never reported again) a reported campsite and night is suppressed while it stays available and re-armed once a completed check saw it unavailable: only `NotificationHistory.Rearm`, at the start of `MonitoringService.ReportCheck` (before the gate), removes a marker; only from a month the check fetched and read (`RunData.SiteData`), never from a month that was not fetched, another campground's month, an unlisted campsite or a night without a status; only for a status other than exactly `Available` (the search's rule, its day offsets); only an empty marker folder, never a link, anything under a linked folder or a path from recreation.gov's answer. A removal that fails only warns in fixed words; nothing is created; a later failure of the check undoes no re-arm. Never infer an unavailable night, add an expiry or dampening, or re-arm from a manual search.
  For `consecutiveDays` above 1, `FilterData` keeps notified nights and `FilterConsecutiveDays` drops a stay only when every night of it has a marker (TD-61); 1 or below is unchanged. After changing the history, the re-arm, the search's filters or stays, or the monitoring's report, also run `NotificationHistoryRearmTests`, `NotificationReopeningTests` and `MonitoringConsoleTests`, and `MonitoringPageTests` (`CampertronWebTests`).
  Since D90 the monitoring's gate, deliveries and marker writes run in `MonitoringService.ReportCheck` (the same calls in the same order; ER-36), and one settings folder has one monitoring at a time (the monitoring lock), so two monitorings never both write `Camp.History`; also run `MonitoringServiceTests`.

### ER-04 RIDB import row writer
- The RIDB refresh writes rows through `RidbTableInserter` (prepared SQLite commands, one transaction, EF Core's former `SaveChanges` row order; decision D25), not EF `SaveChanges`. Its column mappings are hand-typed: when a mapped RIDB model changes, update the matching mapping; `PopulateTests` fails otherwise. Keep the row order and run the full-export comparison of history/validation/a-w_2026-11-10_to_beta.10.md §M after changing the import.

### ER-05 Failure-safe RIDB refresh
- The RIDB refresh is failure-safe (decision D26, business-rules §8): it builds and validates a staging DB in `ConfigPath/RecreationDotOrg.refresh-<guid>/` and installs it with one `SqliteConnection.BackupDatabase` transaction (`RidbStagedRefresh`). Never install by renaming, replacing or deleting the installed DB. Keep the order: refresh lock → staging build and `Validate` → cache cleared → repair lock + backup → `quick_check` → `LastRidbDataRefresh` written once. The cache step clears the configured `CachePath` (`LocalApplicationData/CampertronCache` on the desktop, `/cache` in a container; TD-05 resolved, decision D27). The cache path comes only from `CampertronInternalConfig.CachePath`; never rebuild it from `LocalApplicationData`, and keep the guards in `Clear.CheckCacheDirectory`/`ClearRefreshCache` (no unset, root or config directory; only top-level files deleted).
  After changing it, run `AtomicRefreshTests`, the kill harness and the full-export comparison (history/validation/a-w_2026-11-10_to_beta.10.md §N). The timestamp is written with `Yaml.GeneralConfigReplaceYaml` (since D40 only that value, edited in the current file and written by `ConfigFileReplace.Replace`); don't write it in place or re-serialize `General.yaml`. The culture-dependent row order (TD-36 part 2) is open.
  Since D61 (V011-1) a refresh runs only through `RidbRefreshService.Run` (the console's `RefreshRidbRecreationData.RefreshData` is its adapter, the GUI's Settings > System > Campground data its other host). Keep the order above, the timestamp written while the lock is held, the token read only at the checkpoints up to the cache step and never from there on, the download in a folder of its own (`CampertronDownload-<guid>`; never a shared file name, TD-58), the stall timeout, the removal of its own files on every end, nothing written to the console but through its log sink, and the console's lines, messages, key wait and rethrown exceptions (only the archive's path in "Extracting …" changed, §BD). After changing it also run `RidbRefreshServiceTests` and the pseudo-terminal comparison of history/validation/ba_v0.1.1.md §BD.
  Since D99 web mode is the refresh's third host (`WebRefresh`, business-rules-settings §36): the web UI's, never a session's; started only by the system page's confirmation POST; one data operation at a time with the results page (`WebResultsRuns`' gate); the monitoring paused before the service starts and started again after it (ER-36); web mode's stop cancels one that can stop and waits for one that installs; no live reload and no restart of the process after an installation (the page says to restart web mode). In the container (`RidbRefreshRequest.InContainer`) the download folder and `CampertronExtract` are in the cache folder (`RidbRefreshService.DefaultWorkRoot`, D85 point 5): folders of their own, which the cache step (files only) never touches; never move the staging database, settings, keys or history there, and never widen the leftover cleanup beyond exact names.
  After changing the web UI's refresh or the container's work folder run `RidbRefreshServiceTests` (its container tests), `SystemPageTests` and the container check of history/validation/bv_v0.2.0.md §CK.

### ER-06 GUI startup
- GUI startup (R8, decision D33): `MainWindowViewModel` runs `Load.GetConfig` on a background task after the window opened and shows "Preparing campground data" or the startup error (message, settings folder, Try again). Never create or bind anything database-backed before it succeeded (`StartupTests` count EF commands on all threads), keep UI changes on the UI thread, keep the attempt/detach guards, post an attempt's completion to the dispatcher `Begin` captured on the UI thread and never ask for `Dispatcher.UIThread` on a worker thread (D49: between two headless tests the first thread that asks becomes the UI thread, and the next test fails before it starts), and keep `Program.Main` waiting for a preparation still running when the window closed (extraction, repair and refresh must not be cut off) and, since D61, for a refresh of the campground data until it stopped at its checkpoint or finished its installation (`App.WaitForPendingRefresh`; never cut off in its installation).
  Since D62 `Program.Main` of a process the automatic restart started takes its one-time token from the environment (and removes it) and claims, deletes and validates the handoff before Avalonia starts; an ordinary start has no token and reads, creates or restores nothing. The window takes the handoff's place before it is shown and opens at Settings > System only once the startup is ready (`MainWindowViewModel.TakeRestartNavigation`, once); never navigate, create view models or skip the startup's checks earlier.
  The loader is the only test seam; don't change `CampertronLibrary` for the GUI, except for a host-neutral service a decision approves for both hosts (D45's search service; D60's `CurrentConfiguration`, the View Config items; D61's `RidbRefreshService`, the RIDB refresh). `--smoke-test` (`SmokeTest.cs`) reports `SMOKE key=value` lines that `check_gui_smoke_report` validates:
  change both together. Capped elements use a capped star column (D28), never `MaxWidth` alone (centers) or left alignment (shrinks).

### ER-07 GUI lookup tabs and theme resources

Take colors only from Fluent theme resources (`Styles/AppStyles.axaml`, `DynamicResource`; the app follows the system Light/Dark theme). Bind each database-backed view-model property exactly once (every getter queries SQLite; `Selections_RunOneQueryEach`). The GUI owns its labels through `Read.GetCampgroundDetailsById` (since D42; `GetCampgroundDetailsByName` is kept unchanged for its tests); leave `Read.GetParkCampgroundByName`'s prefixed contract alone. Keep the Tab-wrap workaround in `MainWindow` for the TabControl keyboard trap reproduced with Avalonia 12.1.6 (TD-39; since D50 on both tab levels);
  reassess it after any Avalonia upgrade or an upstream fix for that exact behavior. Campgrounds are identified by FacilityID, not by name (D42, next rule).

### ER-08 Campground identity
- Campground identity (CM4, decision D42, business-rules §16): a GUI campground is a `CampgroundChoice`; never select, compare or look up a campground by its name or label in the GUI (the label is display text, never parsed). Keep the FacilityID exactly as stored (a string: never parsed as a number or trimmed). One entry per FacilityID; the label shows the location when known and always the ID (`Unnamed campground` for a blank name); order by `CampgroundChoice.ListOrder`. By State and By City keep their location filters (inner joins); By Park lists a park's campgrounds also without an address (outer join); never invent a location. A filter change clears its tab's campground in `ReactiveViewModel`; the details come only from `Read.GetCampgroundDetailsById` (empty state when it returns null); still one query per selection. Keep the campground drop-down capped at its selector's width so the IDs stay visible.
  Keep the name-based `Read` methods unchanged for their callers (`RidbDatabase.Validate`, `ReleaseCheck`, tests). The search editor's picker (CM6, D44) reuses `CampgroundChoice` through `CampgroundPickerEntry` and `Read.CampgroundPickerEntries` (every reservable, enabled campground, one query). After changing any of this run `CampgroundChoiceTests`, `CampgroundIdentityTests` (library and GUI), `CampgroundDetailsTests`, `AddressStateTests`, the GUI suite and the negative controls of history/validation/ad-ax_preview.2.md §AG.

### ER-09 GUI navigation and theme
- GUI navigation and theme (decision D50, business-rules §21): the top-level tabs are exactly Searches, Results, Settings, Campgrounds (`MainWindow.*TabIndex` 0 to 3; the fourth labeled Campgrounds since D55, while its automation IDs `CampsitesTab` and `CampsitesTabControl`, the internal `MainWindow.CampsitesTabIndex` and the smoke line's key `campsites` keep the former label: they are automation IDs, keep them; never relabel campsite text, a campsite is a site within a campground), Searches is shown at the start and is shown to its view model when the startup is ready (it reads the search files and the campground data then); Settings' row is Campertron then System (`SettingsTabControl`), Campgrounds' row is By Park, By City, By State (`CampsitesTabControl`), each opening on its first tab; nested rows use `Classes="nested"` (aligned with the top level, smaller headers).
  Settings > Campertron keeps every CM5 rule (files checked when it is shown, the password masked when it is left, also for System). Settings > System's current configuration (V011-2, D60, business-rules §24) exists only after a successful startup (`SystemSettingsViewModel.Configuration`, set by `MainWindowViewModel`), reads again once when Settings > System is shown and once on activation while it is shown (no watcher, no polling), never writes or creates a file, never shows a value of `Email.yaml`, and acts (Copy, Open settings folder) only when pressed; keep the System tab's DataContext `SystemSettingsViewModel`.

  Since D62 (business-rules §26) a successful refresh restarts Campertron through `RefreshSeams.Restart` (production `AutomaticRestart.Run`: a one-time handoff in `LocalApplicationData/CampertronGUI/restart`, the process's own executable started with a typed argument list and the token only in the environment, a bounded wait for the new process to claim the handoff), keeping the data-operation gate until the restart failed or the process ends.
  Never restart after a failure, a cancellation or a close, with unsaved changes in Settings or Searches, or more than once (no retry); never pass the token on the command line or through a shell, log it or write it to disk; never keep a window position as a preference; a launch that fails leaves the window usable with its fixed words. Only `AutomaticRestart` starts a process (`ResultsViewTests` checks the IL), and no test starts one (`AutomaticRestart.StartForbidden`). After changing any of this also run `AutomaticRestartTests` and the nested-session restart scenarios of history/validation/ba_v0.1.1.md §BD.
  Keep the tabs' `x:Name`s (automation IDs), the content names and the smoke test's `navigation` and `system-tab` lines in step with `check_gui_smoke_report`.
  The TD-39 workaround: a trapped Tab wraps to the top-level header, a trapped Shift+Tab goes to the innermost row's header, a Tab from a header that skips a nested header goes to it. The theme: `ThemeChoice` System/Light/Dark, applied only through Avalonia (`AppTheme`: System is `ThemeVariant.Default`, never platform detection of Campertron's own), read by `App.PrepareTheme` before the window is created and kept by `ThemePreferenceStore` in `LocalApplicationData/CampertronGUI/preferences.json` (a JSON object, `"theme"`; read without creating anything, never the working directory; anything missing, unreadable, malformed, over 64 KiB, with a duplicate member or an unknown name gives System;
  a save goes through a temporary file in the same folder and keeps the object's other members). Never store it in `CampertronConfig`, a YAML file, `CampertronInternalConfig` or the console, and never write it except on the user's choice (the smoke test's `ThemeProbe` uses a temporary folder and restores the application's theme). After changing any of this run `NavigationTests`, `ThemePreferenceTests`, `CurrentConfigurationTests` (library and GUI), since D61 `CampgroundDataTests`, `MainWindowUsabilityTests`, `SettingsEditorTests`, `SearchEditorTests`, `ResultsTabTests`, `StartupTests`, `SmokeTestTests` and the release-policy tests, then the negative controls and the real-window review of history/validation/ad-ax_preview.2.md §AO (for the campground data the nested-session scenarios of history/validation/ba_v0.1.1.md §BD).

### ER-10 GUI settings editing
- GUI settings editing (CM5, decision D43, business-rules §17): the Settings tab (since D50 Settings > Campertron) edits only `General.yaml`, `Email.yaml`, since D69 `Ntfy.yaml` and, since D94, `Web.yaml` (search files: the Searches tab, next rule), only through `ConfigEditSession` (never write a settings file from the GUI another way, never re-serialize, never normalize a file to make it editable: unsupported YAML stays read-only with its reason, unknown keys stay refused). Keep: no edit no write; a value equal to the file's is no edit; Save only when edited, verified by the editor, without blocking validation errors and without a conflict; the read-back must be the reviewed text before the edits are cleared; external changes reload a clean editor and open a conflict for an edited one (never overwrite, never discard silently); `Email.yaml`'s severity follows the General form's outputTo; `outputTo: UnitTest` kept but not offered. The password:
  masked (`SecretTextBox`, whose automation value is always the mask), revealed on screen only until save/revert/reload/resolution/file switch/leaving the tab or window, never in a message, preview line, status, smoke line or exception (the preview masks it with a fixed-length mask). One rolling `.bak` with the file's mode or access rules; a GUI-created `Email.yaml`, `Ntfy.yaml` or `Web.yaml` 0600 on Unix (`ConfigFileReplace.Create`'s mode). No SMTP connection, ntfy publish, search, refresh or vault, except the test email and test notification the user asks for (ER-39, D94).

  Nothing is saved that the monitoring's start would refuse (D71): the General form saves outputTo: Email or Ntfy only when `ConfigValidation.MonitoringStartErrors` (the start's own checks on the saved files) finds nothing; the `Email.yaml` and `Ntfy.yaml` editors follow outputTo shown and saved; a value written but invalid is an error in every output; an empty list row is never written; `Save` checks again. No weaker GUI-only check; the start's refusals stay as they are. Then also run `MonitoringStartCheckTests`, `SettingsRuntimeParityTests` and the negative controls of history/validation/ba_v0.1.1.md §BQ.
  The search files likewise (D73): the General form saves a changed outputTo of Email or Ntfy only when `ConfigValidation.MonitoringSearchErrors` (the start's own `Load.LoadMonitoringSearches`) finds a search to check and no search file it stops on, and warns for a saved one; the Searches tab warns with the same check and never blocks a search's save. Then also run `MonitoringSearchCheckTests`, `MonitoringSearchCheckGuiTests`, `EmailStartTests` and the negative controls of history/validation/ba_v0.1.1.md §BS.

  `--smoke-test` runs `SettingsProbe` in a temporary folder and reports `settings-probe` (since D69 with `ntfy=created,saved`) and `settings-tab` (with `ntfy=new`, since D94 also `web=new`); change `SmokeTest.cs`, `check_gui_smoke_report` and its policy tests together. After changing any of this run `ConfigEditSessionTests`, `ConfigEditEmailTests`, `ConfigEditNtfyTests`, `ConfigEditWebTests`, `SettingsEditorTests`, `NtfySettingsEditorTests`, `WebSettingsEditorTests`, `SettingsPagesFormsTests`, `SmokeTestTests`, the CM1 to CM3 suites and the release-policy tests, then the negative controls of history/validation/ad-ax_preview.2.md §AH and, for `Ntfy.yaml`, of history/validation/ba_v0.1.1.md §BO.

### ER-11 Parallel searches
- Parallel searches (TD-40): `Load.RunConsoleSearch` and `MonitoringService` (D90) run the searches in `Parallel.ForEach`, and a month's availability in `RunData.SiteData` is one object shared by every search of that campground and month. Treat it as read-only once it is cached: derive per-search data into new objects (`CampsitesDataEntry.CalculateAvailableDates`, `AvailabilityApi.AvailableDatesBySite`) and never write into the cached `AvailabilityEntries`/`CampsitesDataEntry` (the kept `GenerateDates` does; the search must not call it). `RunData.FilteredAvailableData` is the run's set of every search's final hits: a search collects its own hits, filters its consecutive nights on those only, and only adds its final hits to the run's set; never read or replace it from a search (TD-04, fixed by D35). Build dates from their numbers, never by parsing culture-dependent text (TD-11, D35), and keep the Email loop's per-check date regeneration quiet and file-free (TD-46, D35).
  After changing the search, run `AvailableDatesTests`, `SharedMonthSearchTests`, `SearchIsolationTests`, `SearchDatesTests` and the parallel-versus-isolated comparison of history/validation/x-ac_preview.1.md §Z (every search, single-night and consecutive, must equal itself run alone: 0 differences).

### ER-12 HTML results page

### ER-13 Console output

Keep these contracts: `--version` (untouched, first in `Main`); View Config's lines are `CurrentConfiguration.Describe`'s items (D60, shared with the GUI), byte for byte as before; a start with `outputTo: UnitTest` writes nothing;
  `Load.GetConfig` writes nothing on a clean first start unless `Load.FirstStartNotice` is set, which only `CampertronConsole` does (the GUI's `--smoke-test` output must hold only `SMOKE` lines); "Config path does not exist" and "Unsupported output type in container" stay in their messages; a handled failure exits with code 1 (`ConsoleUi.ReportFailure` in `Program.Main`; since D37 also equal `StartEndDate` dates and a blocked request), signals keep 130/143/129. Failure messages come from exceptions only: never print a value of `Email.yaml` or, since D67, `Ntfy.yaml` (`Program.Main` reports with `ConsoleUi.ReportFailure(Exception, CampertronInternalConfig)`, which hides the SMTP passwords and ntfy's token and topic).
  Don't add a terminal library, flags or a logging framework. After changing console output run `ConsoleUiTests`, `ConsoleResultsTests`, `ConsoleOutputTests`, `ConsoleFailureTests`, `ConsoleOutputGoldenTests` and, for View Config, `CurrentConfigurationTests`, and for anything touching the terminal the pseudo-terminal, redirection, signal and container checks of history/validation/x-ac_preview.1.md §Y. A plain-mode golden changes only with an intended presentation change, in the same commit.

### ER-14 GUI search-file editing
- GUI search-file editing (CM6, decision D44, business-rules §18): the Searches tab writes a search file only on an explicit user action (Save, Save As, New search) and only through `ConfigEditSession<CampertronConfig>` (Save: `ConfigFileReplace.Replace`; Save As and New search: `SearchFiles`/`SaveAs` → `ConfigFileReplace.Create`, create-only, never over a file, also not over a concurrent winner). - The desktop GUI's layout is responsive (decisions D106, D107, business-rules-gui §38): every tab's content is a `ResponsiveColumns` (`CampertronGUI/Views/ResponsiveColumns.cs`) with the shared sizes of `AppStyles.axaml` (`ReadableColumnMaxWidth` 960, `SideColumnWidth` 400, `WideLayoutMinWidth` 1136, `ReadableGroupMaxWidth` 1376, `TwoColumnsMinWidth` 1344, `TwoColumnsMaxWidth` 1936; the Settings tab's gutter-carrying 416, 976 and 1152) and its page's width category, a style class (readable for forms, data for Results, mixed for Searches and a campground's details; D107): never one maximum for every page and never a cap on the tab control.
  Never put content back into a fixed or left-aligned column, never disable maximize or resizing, never decide the layout from the window or a view model, and never create, drop, duplicate or reorder controls between the layouts: one instance keeps its state and bindings, and the side part comes first in reading and Tab order. No size goes into the shared form layer (ER-37).
  A new card goes into a panel's side or main part, or into a one-child panel over both columns; a new page takes the category of its content (data that is cut short benefits from width, forms and prose don't); a changed size changes the resource and the measured boundary in business-rules-gui §38 together.
  After changing any of this run `ResponsiveLayoutTests`, `MainWindowUsabilityTests`, `ResultsViewTests`, `StartupTests` and every GUI suite, the negative controls of history/validation/co_v0.3.0.md §CS and §CT, and a before-and-after comparison of the window (`maintainer-procedures.md` §Real GUI windows in a nested session) at 720, 1024, 1192, 1920, 2048 and 2560 wide in Light and Dark, Results with a large result set of long campsite details among them.
