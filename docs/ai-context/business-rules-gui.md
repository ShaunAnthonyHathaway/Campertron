# Business rules: GUI

Authority: current. This file is the current authority for the rules of Campertron's GUI and of the library services it uses: campground identity (§16), settings editing (§17), search-file editing (§18), the host-neutral search service (§19), the Results tab (§20), navigation and the theme preference (§21), the filter choices read from the campground data (§22), the filter selectors (§23), since D60 the current configuration (§24), since D61 the campground data refresh with the host-neutral refresh service it uses (§25; the service's rules are business-rules §8) and, since D62, the automatic restart after a refresh (§26).
Section numbers are global and permanent: §1 to §12 are in `business-rules.md`, §13 to §15 in `business-rules-settings.md`, and `business-rules.md` §Section index lists every section; a bare "§N" below names that global section, in whichever file holds it. Roadmap step 9, Phase 4 (2026-11-17) moved these sections here from `business-rules.md` with their numbers and words; lines over 1,000 characters were broken at sentence boundaries (`history/README.md` §Phase 4 migration map). Since D63 (V011-3, roadmap step 10, Phase C) the GUI's words for a search's `autoRun` are "Enabled (autoRun)" and "Not enabled", explained where they are shown (§18 to §20);
the former "runs at startup" wording, which no GUI behavior matched, is recorded in `history/validation/ba_v0.1.1.md` §BE.

## 16. GUI campground identity (decision D42; `CampgroundChoice`, `Read.CampgroundChoicesBy*`, `Read.GetCampgroundDetailsById`)
- [V] **A campground is its FacilityID.** The GUI's campground lists hold `CampgroundChoice` entries (`class/RecDotOrg/CampgroundChoice.cs`, global namespace): the FacilityID exactly as `FacilitiesEntries` stores it (its TEXT primary key, a `string`; never trimmed, parsed as a number or converted, so a leading zero stays; a blank ID is refused), the trimmed name (null for a blank or whitespace-only name) and the City and State of an address (null when there is none). Equality and the hash code use the FacilityID only (ordinal); the label is display text and is never parsed back. Selecting an entry selects that FacilityID; the details are loaded with `Read.GetCampgroundDetailsById`, never by name. The search files' `campgroundID` is a string too; the configuration model is unchanged.
- [V] **Why names were unsafe** (TD-38, resolved). In the shipped database (2026-11-10 export) 4,966 reservable, enabled campgrounds have 4,966 distinct FacilityIDs but 4,936 distinct names (trimmed, case-insensitive): 24 names belong to more than one campground (30 extra rows), one of them the empty name (8 campgrounds), the other 23 pairs; two names are also used by a reservable, enabled facility of another type. The lists showed each name once and the details came from the first facility of that name, of any type. On the shipped data, for example, `GetCampgroundDetailsByName("FISH CREEK CAMPGROUND")`, the lookup the GUI used, returns Utah's campground (10241505) also when Montana's (232493, West Glacier) was selected on the By State tab; since D42 the GUI shows 232493 for it (real-window review, history/validation/ad-ax_preview.2.md §AG).
- [V] **Labels** (`CampgroundChoice.Label`, also the item's `ToString()`, accessible name and tooltip): `<Name> — <City>, <State> — ID <FacilityID>`; `<Name> — <State> — ID <FacilityID>` without a city; `<Name> — ID <FacilityID>` without a state (a city without a state is not shown; the queries never return one); `Unnamed campground` replaces a blank or whitespace-only name, followed by the location if there is one (all 8 blank-name campgrounds of the shipped data have none: "Unnamed campground — ID <FacilityID>"). Only the ends of the name, city and state are trimmed for display; stored values are unchanged. Every entry shows its ID: a list entry shows the name and location (`Title`, trimmed with an ellipsis when long) and the ID (`IdText`, never trimmed) in two columns, and the drop-down is as wide as its selector so the IDs stay visible (it used to grow to the longest name). The details title shows `Unnamed campground` for a blank name;
  the details' context line is still the tab's filters.
- [V] **Order** (`CampgroundChoice.ListOrder`, in managed code): by name (trimmed, case-insensitive ordinal), then state, then city (both case-insensitive, missing first), then FacilityID (shorter first, then ordinal, so digit IDs sort numerically); unnamed campgrounds last. Before D42 the lists were ordered by SQLite's case-sensitive `ORDER BY` of the raw names, so mixed-case names (`Lava Point Campground`) sorted after all upper-case ones.
- [V] **The lists** (each one parameterized query, one entry per FacilityID; a campground with two qualifying addresses is listed once, by its Physical address, else its Default address, then by state and city):
  - **By State** (`CampgroundChoicesByState`) and **By City** (`CampgroundChoicesByStateAndCity`, an empty city included) keep their location filters exactly (the meaning of `UniqueParksByState` and `UniqueParks(state, city)`): a reservable, enabled campground with a Physical or Default address in that state (and city), located by that address, so a campground with addresses in two states shows the one of the selected state. They list the same 3,337 campgrounds of the shipped data as before; only same-name campgrounds, which used to be one entry, are now separate.
  - **By Park** is not a location filter: `ParksWithCampgrounds` lists every recreation area name with a reservable, enabled campground, and `CampgroundChoicesByPark` lists every such campground of the park, also one without a qualifying address (an outer join; it is then shown without a location). Shipped data: 522 parks instead of 463 and 4,937 campgrounds instead of 3,330 (1,607 newly listed, for example Zion's Lava Point Campground, 10138237). A park name shared by two recreation areas (Sardis Lake, 154 and 577) lists the campgrounds of both, as before, each with its own location and ID.
  - **Not listed in the lookup tabs:** 22 reservable, enabled campgrounds of the shipped data have neither a recreation area nor a qualifying address, among them all 8 blank-name ones. Since D44 the Searches tab's campground picker lists them (§18; TD-53 resolved, open question #41 answered); the lookup tabs are unchanged. Nothing is invented for them.
- [V] **Details by ID** (`GetCampgroundDetailsById`): the one reservable, enabled `Campground` facility with exactly that FacilityID (the primary key; `SingleOrDefault`, a parameter, matched exactly by SQLite's binary comparison), with the HTML fields converted to plain text as before; null, without a query, for a blank ID, and null for an unknown ID, another facility type, a disabled or non-reservable facility, or an ID that differs only by spaces or a leading zero. A not-found result shows the tab's empty state (`CampgroundDetails.None`), never a record of the same name and never the previous campground.
- [V] **Selection** (`ReactiveViewModel`): a filter change clears its tab's campground before the new list is raised (also when the new list holds a campground of the same name, or the same campground), so no details of the previous selection remain; a cleared or unknown selection shows the empty state and runs no query. The details are computed from the current selection whenever they are raised (synchronously, no cache), so fast selection changes cannot show earlier details. One query per selection, as before: the dependent list or the details (`Selections_RunOneQueryEach`, `EverySelection_RunsOneParameterizedQuery_AndNoNameLookup`). The selection path refers only to these database reads: no settings file, YAML, writer, web request or search code (checked from the IL by `Selections_ReadAndWriteNoSettingsFile` and `TheLookup_StartsNoCampsiteSearchAndNoWebRequest`).
- [V] **Kept for their callers:** `UniqueStates`, `UniqueCities`, `UniqueParks(state, city)` (`RidbDatabase.Validate`, `ReleaseCheck`), `UniqueParksByState` (`ReleaseCheck`), `UniqueCampgrounds`, `UniqueCampgroundsByPark`, `UniqueParks(path)` and `GetCampgroundDetailsByName` are unchanged (names, `Distinct()`, first match by name); the GUI no longer calls them (TD-22).
- [V] **Reused by CM6** (D44, §18): the search editor's campground picker reuses `CampgroundChoice` (identity, label, optional location) through `CampgroundPickerEntry`. Typed-ID entry, the check of a search file's `campgroundID` against the campground data and saving search files are CM6's, not CM4's.

## 17. GUI settings editing (decision D43; `ConfigEditSession`, the Settings tab)
- [V] **What is edited.** The GUI's Settings tab (since D50 Settings > Campertron, §21; every rule of this section unchanged) edits `General.yaml` and `Email.yaml` in the settings folder `Load.GetConfig` uses (`CampertronInternalConfig.ConfigPath`), each through one `ConfigEditSession` (`function/Base/ConfigEditSession.cs`, internal; the GUI sees the library's internals since D43). Search files are edited by the Searches tab (§18, CM6); deleting files is not part of either. Nothing in it searches, refreshes the campground data, connects to an SMTP server or sends an email (checked from the IL and with an HTTP listener).
- [V] **Opening.** The file's exact bytes and their SHA-256 are read by `ConfigFileReplace.Read` (strict UTF-8, links, size limit; §14), its structure by `YamlDocument.Analyze` (§13) and its settings by `Yaml.LoadSettingsText` (§15). States: **Missing** (Create offered); **Unreadable** (`ConfigFileReplace.Read` refuses it: empty, not UTF-8, too large, a link it can't follow; its message); **ReadOnly** (the editor refuses the document, for example a comment-only file, malformed YAML, a duplicate key, a flow-mapping root, or the loader can't read its settings, for example an unknown key, which stays refused (D20) and is shown as the validation's diagnostic; nothing is changed or normalized to make it editable; Reload after correcting it in a text editor); **Editable**. In an editable file a key whose value uses an anchor, alias or tag, a multi-line text, or a list layout the editor can't edit item by item is locked (shown with the reason); a missing key can be added.
- [V] **Editing.** Values are typed (`OutputType`, numbers, `true`/`false`, a UTC date and time, texts, the recipients as rows). A value equal to the file's is no edit, so a field changed back is clean again; no edit means no write. Every change is applied to the text read by the YAML document editor, step by step (the scalars in one step, then each list operation: removals from the last, one reordering, changed values, insertions), each verified against the settings it should give (§13): comments, blank lines, order, quoting, indentation, a byte-order mark, the line breaks and the final line break stay; nothing is re-serialized. A step the editor refuses is an error at its field, with the editor's reason, and blocks the save.
- [V] **Validation.** `ConfigValidation` (§15) checks the changed text as the loader would read it; its diagnostics are shown at their field (list items at their row), with the severity written out ("Error:", "Warning:", "Info:"), also as the field's accessible help text. Errors block the save, warnings and information don't. `Email.yaml`'s severity follows the outputTo the General form shows (edited or as the file has it): with `Email` what sending needs is an error, otherwise a warning. `outputTo: UnitTest` is kept and shown with its Info diagnostic, but not offered as a choice. Text that is not a value of the field's type (a port that is not a whole number, a date that is not ISO 8601) is the GUI's own error at the field.
- [V] **The preview** (read-only): the lines a save changes, with one line of context (a single unchanged line between two changes is shown instead of the gap marker), line markers `-` and `+`, and a summary of the changed keys. The SMTP password is masked (always six bullets, whatever its length): its value range in the file as it is and as it will be, and any other occurrence of the old or new password in a shown line (a whitespace-only password only by its range); the summary says "smtpPassword (hidden)". A removed recipient that takes comments with it is announced ("Removing item 2 of sendToAddressList also removes 2 comments that belong to it."); mixed line breaks are announced (new lines get the most frequent one).
- [V] **Saving.** Only an editable, edited, verified file without blocking problems and without a conflict is saved. The file is first compared with what was read (a change becomes a conflict); `ConfigFileReplace.Replace` then writes it (temporary file, one rolling `<name>.bak` with the exact previous bytes and the file's mode or access rules, the external-change checks, the rename, the read-back; §14), and the file is read again: only when it is exactly the reviewed text are the edits cleared ("Saved Email.yaml. The previous version is in Email.yaml.bak."). Any failure keeps the edits and shows the writer's message, which names the file and the problem, never a value.
- [V] **External changes** (optimistic, `CheckForExternalChange`; when the Settings tab is shown, when the window is activated, and before every save). The file is read again and compared with what was read: no change; only the permissions, time or links changed (kept as the file's state, the edits stay); the content changed or the file disappeared. A clean editor then shows the new version (or Missing); an edited one keeps its edits and opens a **conflict**: nothing can be saved and the fields are locked until the user chooses. If the other program changed other settings, "Apply my changes to the new version" applies the edits to the new version (the editor proves they apply; a byte-order mark or line-break change is a content change and is kept); if it changed the same setting, the button names it ("Keep my values for smtpServer") and the user's values replace the other program's; "Discard my changes and use the file on disk" reloads.
  A deleted file can be created again with the edits (create-only: a file another program created meanwhile is never written over). A version the editor can't edit can only be taken as it is. Neither version is ever lost silently: until the user chooses, the other program's version stays on disk and the edits stay in the form. Before a save the writer itself checks the file again (§14).
- [V] **The password.** The password box masks the password (`PasswordChar`); its accessibility value is always the mask (`SecretTextBox`: Avalonia's own text-box peer reports the real text once it is revealed), and copying is disabled. "Show password" reveals it on screen only until the next save, revert, reload, conflict resolution, switching files, leaving the tab or deactivating the window; the reveal is never stored. An unchanged password stays byte for byte; a changed one is written only through the editor and the writer. No diagnostic, preview line, status, conflict message, smoke line or exception text holds it (sentinel tests search all of them and the window's texts, tooltips, accessible names, help texts and accessibility values).
- [V] **Backups and permissions.** One rolling `<name>.bak` (no history): for `Email.yaml` it holds the previous password, as an exact backup does, with exactly the file's mode (Unix) or access rules (Windows), never broader. A saved file keeps its mode or access rules (§14). An `Email.yaml` the GUI creates (Create, or created again after a deletion) is owner-only (0600) on Unix; on Windows it takes its folder's inherited access rules, as every new file there does. An existing `Email.yaml` that other users can read keeps its mode; the editor says so (Info, "Other users of this computer may be able to read Email.yaml…"); TD-49.
- [V] **Missing files.** The start still creates the samples (§9); a file removed later can be created from the Settings tab with exactly the start's sample (`Yaml.CreateSampleSettingsFile`, the same sample settings as the start, create-only); if another program created it meanwhile it is opened as it is. No search file is created.
- [V] **Open settings folder** shows the settings folder in the platform's file manager through Avalonia's launcher (`LaunchDirectoryInfoAsync`: a directory to show, no command line, no shell); a failure is shown ("Campertron couldn't open the settings folder. It is …"), never thrown.

## 18. GUI search-file editing (decision D44; `ConfigEditSession<CampertronConfig>`, `SearchFiles`, `SearchFileName`, the Searches tab)
- [V] **Write policy (D37 narrowed).** A search file is written only by an explicit action in the GUI's Searches tab: **Save** (the editing session of §17 and `ConfigFileReplace.Replace`: verified temporary file, one rolling `<name>.bak` with the exact previous bytes and the file's mode or access rules, the external-change checks, the read-back), **Save As** and **New search** (`ConfigFileReplace.Create`: create-only, never over a file, also not over one another program created meanwhile; no backup for a new file). Every write is the YAML document editor's targeted text (§13), checked by the validation (§15) and the editor's own verification; no edit, no write. The console, the Email loop, the start, the RIDB refresh and the validation never write a search file, and nothing deletes one.
- [V] **Which files.** Exactly the console's search files (`ConfigFiles.SearchFiles`: the top-level `*.yaml` files except `General.yaml` and `Email.yaml` in any case, §15), listed by name ignoring case, then ordinally (`ConfigFiles.SortedSearchFileNames`; the same in every culture). Backups (`<name>.bak`) and temporary files (`<name>.<32 hex>.tmp`) never match; `.yml` files and subfolders are not search files. Each file shows its name, its search's `displayName`, its `autoRun` setting ("Enabled (autoRun)" or "Not enabled" since D63; "Enabled" or "Disabled" before), its campground (label, or the ID) and its state (no problems, warnings, errors, read-only, can't be read; unsaved changes; changed on disk while edited).
  A file that can't be edited (malformed, unknown key, unsupported layout, not UTF-8, empty) is listed and opens read-only with a reason that holds no value (§17's states). The list is read when the tab is first shown and compared with the disk when the tab is shown, the window is activated and on "Look for changes on disk":
  a new file is listed, a removed clean file leaves the list, a removed edited file stays with its edits (a conflict); the chosen file stays chosen while it is listed.
- [V] **Settings.** Every setting of `CampertronConfig` (§1): `displayName`, `autoRun` ("Enabled (autoRun)" since D63; "Run this search" before), `campgroundID`, `totalHumans` (empty is no number), `searchBy` (a value that is no search type is kept as the file has it, shown as not a valid choice, until the user picks one), `searchValue`, `searchValueDates`, `showMonday` to `showSunday`, the eight include and exclude lists and `consecutiveDays` (since D51 also `filterMatching`; since D52 the equipment and campsite-type lists are database-backed selectors, §23). Numbers are whole numbers (the GUI's error otherwise); dates are text as the search reads them (`yyyy-MM-dd` recommended; the validation reports other forms). A missing setting stays missing and a null list stays null (not `[]`) until edited. Lists are edited item by item (insert, remove, reorder, change) with the comments that belong to each item; an empty item written `- ~` stays exactly as it is until the user types in it;
  a list written in a form the editor can't edit item by item (for example a bare `-` item) is locked with its reason and the other settings stay editable. New list items that would read as another type (a date) are quoted, as are flow-list items with a colon. Undefined content is never normalized: unknown keys keep the file read-only (D20).
- [V] **Validation.** The search validation (§15, `ValidateSearch`) of the changed text, at its setting and list item, the severity written out; errors (in an enabled search: equal or unreadable `StartEndDate`/`Until` dates, a negative or out-of-range `searchValue`, an empty item in an equipment, attribute or campsite-type filter, an undefined `searchBy`) block Save and Save As, warnings and information don't. The search rules (§1 to §4, the date generation, the filters) are unchanged; the GUI only shows what the validation says. The days-of-the-week warning is shown with the check boxes. Its message about `consecutiveDays` follows the outputTo the General form shows.
- [V] **The campground.** Identity is the FacilityID, a string kept exactly (§16). The picker lists every reservable, enabled campground (`Read.CampgroundPickerEntries`, one query when the tab is first shown: 4,966 in the shipped database, also the 22 without a named park and without a qualifying address, TD-53 resolved, and the 8 unnamed ones), each with its label (name, location if known, ID) and park if it has one; nothing is invented. A filter narrows it to the campgrounds whose name, city, state or park contains each word (ordinal, ignoring case), or whose FacilityID is exactly the text (listed first); part of an ID never matches. A typed ID is used only if a reservable, enabled campground has exactly that ID: blank, surrounding spaces, a partial ID, a number form of another ID and a name are refused with a message that does not repeat the input. A label is never parsed.
  A campgroundID of the file that the campground data does not have is a warning (the data may be older than the file); an entered one is an error.
- [V] **New search** asks for a name and creates `<name>.yaml` in the settings folder with the example search's settings (`Yaml.SearchSampleConfig`, the start's example; since D51 with `filterMatching: Exact`, §9) and `autoRun: false` (not enabled: the Results tab runs it when it is selected, the console's Search and email mode once the user enables it and saves; its message says so since D63), in the serializer's text, create-only, then opens it. **Save As** writes the chosen search, with its edits (the reviewed text; without edits an exact copy), to a new file with the source's mode on Unix (on Windows the folder's inherited access rules), create-only; the source file is not changed and shows what is on disk again; the new file is opened.
- [V] **Names** (`SearchFileName`): `.yaml` is added when it is left out (an upper-case `.YAML` becomes `.yaml`); `.yml` is refused (the console reads `*.yaml` only); the name part has at most 100 characters of letters, digits, spaces and `- _ . ( )`, does not start or end with a space or a dot, has no `/`, `\` or `..`, is not a Windows device name (`CON`, `NUL`, `COM1`, …, also before an extension) and is not `General` or `Email` in any case; a name that a file, folder or link in the settings folder has in any case is refused (one file on Windows and macOS). The file is always directly in the settings folder; no folder is created and no shell is involved.
- [V] **The enabled toggle** edits `autoRun` alone: the preview and the save change exactly that value. The tab warns when no search file on disk is enabled and usable (`ConfigValidation.SearchFolderDiagnostic` with `IsEnabledAndUsable`, named `RunsAtStart` before D63: the counting of the folder validation, `autoRun: true` and no error), with email mode's consequence when the General form's output is Email and, since D63, that the Results tab still runs a search that is not enabled when it is selected; since D64 email mode then stops at its start with an error (business-rules §9; open question #40 answered), and nothing is enabled or created automatically.
  One difference from email mode's start, recorded by §BJ and not changed: an enabled search without a `campgroundID` counts here as enabled and usable (its `CampgroundIdMissing` is a warning), so a folder whose only enabled search has none shows no `NoEnabledSearch` warning, only the file's own ("campgroundID is empty: the search is skipped."), while email mode refuses to start.
- [V] **The words for `autoRun`** (D63, V011-3; `AutoRunWording`): the check box is "Enabled (autoRun)" (access key A) with what it does: "Enabled searches run each time you choose Search in the console and at every check of email mode, which reads the search files when it starts (restart it after a change). The Results tab selects enabled searches by default and runs one that is not enabled when you select it. Enabling a search doesn't make the GUI search by itself, and saving never runs a search."
  It is the check box's help text; for a file that is not enabled the help text is `SearchDisabled`'s Info (§15), which says what that means. The list's accessible name and tooltip add to the state "The console's Search and email mode run it, and the Results tab selects it by default." or "The console's Search and email mode skip it; the Results tab runs it only when you select it.", or for a file with errors "It has errors, so it can't be searched until they are fixed." instead: the setting is never told as whether the search can run.
  With no search file the notice says "There is no search file. Create one with New search. While there is none, the console creates and runs its example search the next time you choose Search or start email mode."; the `NoEnabledSearch` warning ends "To enable a search, check Enabled (autoRun) and save it."; New search's help says the file is not enabled (`autoRun: false`), and its note what that means. No text says that a search runs at a start (`AutoRunWordingTests`).
- [V] **Not part of it:** deleting search files, running a search, showing availability or results, a general YAML or raw-text editor, multi-provider work. The tab's code refers to no availability, download or email code (checked from the IL and with an HTTP listener).

## 19. Interactive searches: the host-neutral search service (decision D45; `CampsiteSearch`, `SearchHost`, `class/Base/SearchRunModel.cs`)
- [V] **What it is.** `CampertronLibrary.function.RecDotOrg.search.CampsiteSearch` (internal) lets a host other than the console (the GUI, GS2) search saved search files and get typed results. `Plan(SearchRunRequest, Now)` reads and checks the chosen files; `Run(Plan, IProgress<SearchProgress>?, CancellationToken, SearchHostOptions?)` searches them, blocking (the caller owns the thread), and returns a `SearchRunResult`. Since GS2 (D46) the GUI's Results tab calls it (§20); nothing else in the GUI does. The console's search, its Email loop and its output are unchanged (below, *Compatibility*).
- [V] **Plan: one file at a time, read once, never written.** The request names the settings folder, the cache folder and the search files by name (as `ConfigFiles.SortedSearchFileNames` lists them). The folders must be full paths, the settings folder must exist and the cache folder must pass the RIDB refresh's guard (`Clear.CheckCacheDirectory`: not unset, not a root, not the settings folder); otherwise every entry is `Invalid` with `InvalidRequest`. Names are taken once each (the first of exact duplicates), in the order asked for. A name must be a file directly in the settings folder that the console would read as a search file (`.yaml`, no folder part, not `General.yaml` or `Email.yaml` in any case): otherwise `NotASearchFile`, and the file is not read. A missing file is `FileMissing`, one that can't be read `FileUnreadable`. The file is read once with the loaders' bounded reader (`Yaml.ReadSettingsText`, D41) and never written:
  no file of the settings folder is created, changed or deleted, `autoRun` included.
- [V] **Plan: checked as a start checks an enabled search, whatever `autoRun` says.** Choosing a file is the explicit request to search it, so a file with `autoRun: false` is searched too. Its diagnostics are the configuration validation's (`ConfigValidation.ValidateSearch`, CM3) for the text read, with their positions, each with the severity it has in an enabled search (the validation run on the same settings with `autoRun` set in memory only); `SearchDisabled` (since D63 "Not enabled (autoRun: false): the console's Search and email mode skip this search. …", about the console's runs) is left out and `SearchPlanEntry.AutoRun` keeps what the file has.
  An Error (what a start refuses: YAML errors, limits, unknown keys, equal, too few or unreadable `StartEndDate`/`Until` dates, a negative or out-of-range window, an empty item of the six filters `FilterData` calls `Contains` on, an undefined `searchBy`) makes the entry `Invalid` (`FileInvalid`, with the diagnostics); warnings never block and reach the result. A blank `campgroundID` is `Skipped` (`CampgroundIdMissing`;
  the console would search a campground with an empty ID). The dates are generated for `Now` as a start generates them (`CampertronConfig.RegenerateSearchData`: the same dates, without the console's warnings, which the diagnostics already hold). No network, no database, no console output. Discovery at a start, the example search and `Yaml.CampertronConfigGetConfigs` are not involved.
- [V] **Run: the console's own search.** Each ready search runs through `AvailabilityApi.GetAvailabilitiesByCampground`, the operation `Load.RunConsoleSearch` runs for each search: the same months (0 to `GetMonthsToCheck` from now that hold a search date), the same month URLs and sharing (one request per campground and month for the whole run, `RunningData.Urls`/`SiteData`), the same availability parsing (`Data.DynamicDeserialize`, `CalculateAvailableDates`), the same filters (§3), the same consecutive nights (§4) and the same output values. Searches run in parallel (`Parallel.ForEach`, as the console). Stages: validating (the months and URLs each search needs; the cache folder created if missing, as a start creates it), preparing campsite details, checking availability, building results.
- [V] **The run's configuration is its own** (the manual-search policy, D8 as refined, §5): `GeneralConfig.OutputTo = HtmlFile`, `EmailConfig = null`, the request's two folders. On the search path that means no calendar values in the output and no notification history (`Load.UsesNotificationHistory` is false, so `FilterData` never looks at `Camp.History`). `Run` never calls `PostProcess`, `ReportResults` or `OutputResults`: nothing is rendered, written, opened or sent. It never reads `General.yaml` or `Email.yaml`, so an Email output setting or an SMTP secret never enters it; it never reads or writes `Camp.History` and never creates it; markers on disk hide nothing, and a later Email check is unaffected (its markers are exactly as they were).
- [V] **Campsite details** (the JSON cache): each campground of the run is prepared once, silently, cancellably and before any request (`Cache.PrepareCampground`, the code `Cache.PreCheckCache` runs for the console, with no status line). A campground whose cache is not complete is built from the campground data only if `RecreationDotOrg.db` exists in the settings folder (opening a missing SQLite file would create an empty one); otherwise its searches fail with `CampsiteDataMissing` and no request is made. A failure to build is `CampsiteDetailsUnavailable` for its searches. **Completion protocol** (unchanged for the console): `{CampgroundID}-Cached.json`, the only file `Cache.CacheExist` looks at, is written last and only after every other file was written; a build that stops (a cancellation between campsites, an exception, a killed process) leaves no cache that looks complete, and the next search builds it again.
  The search itself never builds a cache in an interactive run (`Cache.CheckCache` with `MayBuild` false). A campground ID that is not a reservable campground of the campground data is a warning (`CampgroundNotFound`); the search still runs, as the console's.
- [V] **The per-run host** (`SearchHost`, carried by `RunningData.Host`; null for the console) adds only what an interactive search needs: the run's `CancellationToken`, the transport, the bounds below, the signal of each shared month, the months each search checked, and the progress. `ProcessMonth` asks it for a month (`GetMonth`) instead of the console's fetch-or-poll; the day and campsite loops, the month loop and the consecutive filter check the token (`Host?.ThrowIfCanceled()`, a no-op for the console).
- [V] **Requests of an interactive run**:

| Answer or failure | Interactive run | Console (unchanged, §7) |
|---|---|---|
| A month: JSON with `campsites` (an empty object too) | the month is checked | the same |
| Network failure (`HttpRequestException`, `IOException`, socket, TLS) | `NetworkFailure`, tried again | retried every 30 s without limit |
| No answer within `RequestTimeout` (30 s) | `Timeout`, tried again | no timeout of its own (HttpClient's 100 s, then the 30 s retry) |
| The heavy-traffic message | `HeavyTraffic`, tried again after 1 s | retried every second without limit |
| HTTP 408 or 5xx | `HttpStatus` (the status kept), tried again | the status is not read; the body is parsed |
| Other HTTP errors (4xx) | `HttpStatus`, not tried again | as above |
| Not JSON, empty | `MalformedResponse`, tried again | retried every 30 s without limit |
| JSON of another shape: `{"count":0}`, `{}`, `[]`, `{"error":…}` | `UnexpectedResponse`, tried again | spins (`{"count":0}`, `{}`, `[]`) or retried without limit |
| Body over `MaxResponseBytes` (32 MiB) | `ResponseTooLarge`, not read, not tried again | read whole |
| The block page (`REQUEST BLOCKED`, any case) | `RequestBlocked`: the run is blocked | "Error: Blocked by API …", 5-minute wait, exit code 1 (§7) |
| HTTP 429 | `RateLimited`: the run is blocked | the body is parsed (429 is not read) |
| Cancellation | the request is canceled at once | Ctrl+C ends the process (§12) |

  **At most three requests per month in all** (`SearchHostOptions.MaxAttempts`, a constant), whatever mix of failures, timeouts, heavy traffic and other answers worth another request; there is no separate heavy-traffic path. The wait before another request is the console's (30 s, 1 s after heavy traffic), but it ends at once when the run is canceled or blocked. **A block** (the block page or HTTP 429) is never tried again and stops the run's requests: no request is started after it (a month not yet requested is not checked, with the block as its reason; one already in flight may finish), and what was received before it is kept. The run then ends `Blocked`; it never waits five minutes, never ends the process and writes nothing to the console. The answers are classified as the console reads them (the block page first, then `Data.DynamicDeserialize`), and the status is read as well.
- [V] **Shared months.** The first search that needs a campground's month fetches it (`RunningData.Urls`), the others wait for it. Whoever fetches it always releases every search waiting for it (`finally`): with the month, a final failure, a block or cancellation; a defect in the fetch itself is contained to that month (`InternalError`) and kept. A waiting search waits on that signal, cancellably; nothing polls. The month's outcome is each waiting search's outcome for it.
- [V] **The transport** (`SearchTransport`: a delegate that takes a `SearchRequest`, the URL, campground, month and attempt, and a token that ends at the request timeout or the run's cancellation, and returns a `SearchResponse`, the status, the body as text and whether it was too large). Production is `HttpSearchTransport`: one `HttpClient` for the whole run, created by `Run` when no transport is given and disposed when it ends; no header of its own and the system's proxy settings, like the console; `HttpCompletionOption.ResponseHeadersRead`, a `Content-Length` over the limit refused unread, a body without one read only up to the limit; decoded as the console's `StreamReader` decodes (UTF-8, a byte-order mark honored). Tests give their own transport (`SearchHostOptions.Transport`); no test reaches the network (history/validation/ad-ax_preview.2.md §AJ).
- [V] **Cancellation** is observed before any request, during a request (the request's token), during the wait before another request, while waiting for a shared month, while the campsite details are prepared (between campsites; no completion marker is written), in each month's day and campsite loops, in the consecutive filter, and while the results are built (a search not built yet is `Canceled`). Measured in the tests: well under one second from the cancellation to `Run` returning, at every one of these points (history/validation/ad-ax_preview.2.md §AJ).
- [V] **Run never throws** for a file, network, block, timeout, retry, response or cancellation outcome, and never for a failing progress handler. An unexpected exception on a search's path ends that search (`InternalError`, with the exception's type name; the exception itself in `SearchRunResult.Defects`, for tests and diagnostics only, never shown) and the others go on. `ArgumentNullException` for a null plan is the only exception it throws.
- [V] **Results** (`SearchRunResult`, immutable: records and read-only lists over arrays of its own; no `RunningData` collection, no `ConsoleConfigValue`): the run's status (`Completed`: every search complete; `CompletedWithProblems`; `Blocked`; `Canceled`; `Failed`: nothing could be searched), its start (UTC) and elapsed time, the unique campground-month requests planned, finished (with data or a final failure) and failed, the run's issues (the block, a cancellation, a defect of the run itself) and one `SearchResult` per plan entry, in the plan's order: the file name, display name, `autoRun` as in the file, campground ID, campground and park name, consecutive nights, its state (`Complete`: every month it needed was checked, with or without availability; `Incomplete`: some were; `Failed`: none, or it stopped; `Canceled`; `Skipped`; `Invalid`), its requests planned and finished, its months (`SearchMonthResult`:
  the month's first day, checked or not, and why not), its openings and sites, its issues and its configuration diagnostics.
  - **A month that was not checked is never a month without availability**: it adds nothing to the output (no month header, no "No entries found"), it is listed as not checked with its reason (`NetworkFailure`, `Timeout`, `HttpStatus`, `HeavyTraffic`, `MalformedResponse`, `UnexpectedResponse`, `ResponseTooLarge`, `RequestBlocked`, `RateLimited`, `CampsiteDataMissing`, `CampsiteDetailsUnavailable`, `InternalError` or `Canceled`), and each one except a cancellation is an issue of the search with the month, the requests made and the HTTP status. No availability is a `Complete` search with no opening.
  - **Openings** (`SearchOpening`): one campsite on one night, with the campsite's ID, name, loop, type, equipment, its check-in and check-out times (the campsite's attributes, as the console shows them), its minimum and maximum occupancy (the month's data), and its booking link (`ResultsHtml.BookingUrlPrefix` and the campsite ID escaped with `Uri.EscapeDataString`). They are built from the search's output values by `CampsiteSearch.OpeningsOf`, from their typed metadata only (`Kind` and `Metadata`: the `Availability` values of single nights, the `ConsecutiveDate` values of runs; never `ConfigValue`, the console text, and never the HTML page), so they are exactly what the console and the results page show for the same search: a search with `consecutiveDays` above 1 has only the nights of its runs, one below 1 has none. One opening per campsite and night: the same campsite listed twice for a night (the console lists it twice) is one opening.
    **Order:** by night, then by campsite ID (shorter first, then ordinal, so numeric IDs sort as numbers in every culture); the same in every run. **Sites** (`SearchSite`): the openings by campsite, in the same ID order, with the campsite's details (those of its first night), its nights in date order and their runs of consecutive nights (`SearchStay`: the first night, the number of nights, the checkout date).
  - **Problems are value-free** (`SearchIssue`): a code, a severity, fixed text (`CampsiteSearch.Message`), the file name, the month, the HTTP status, the requests made and, for a defect, the exception's type name. Never a response body, an exception's message, a folder or a value of a settings file; the configuration diagnostics keep CM3's rules (§15).
- [V] **Progress** (`SearchProgress`, immutable snapshots, a sequence number): reported when something changes (a stage, a search's state, a prepared campground, a finished request, the start or end of a wait before another request, a block), never per campsite or day, in order and under one lock; a handler that throws is a defect, never the run's end. Stages: `Validating`, `PreparingCampsiteDetails`, `CheckingAvailability` (`Retrying` while a request waits to be tried again), `BuildingResults`, then the run's status. Counts only where the total is known: campgrounds planned and prepared; unique campground-month requests planned (all of the run's at its start), finished, failed and waiting to be tried again. Each search: `Waiting`, `Searching`, then its state. No percentage. The library does not depend on Avalonia; throttling progress for a window is GS2's.
- [V] **Compatibility** (the console path, `RunningData.Host` null): the stream of every search is the same value for value (kind, write type, color, text, metadata) and the HTML page, each Email page and the console rendering byte for byte as on `master` (history/validation/ad-ax_preview.2.md §AJ); the retries, waits, block handling, exit codes, `Camp.History`, the Email loop and the container are unchanged. Two changes on the console path, both without an observable effect: `ProcessMonth` adds a month's header after the month's fetch instead of before it (nothing is added to the output while a month is fetched, so the output is the same), and the console's download is a replaceable internal step (`AvailabilityApi.ConsoleDownload`, production the former code: a new `HttpClient` per request, the body read whatever the status) so the tests run the console's search without recreation.gov. `OutputMetadata` gained `MinOccupancy` and `MaxOccupancy` (nullable, set by `AvailabilityValues`);
  no renderer reads them.
- [V] **Not part of GS1:** any GUI change (the Results tab is GS2, §20), throttling progress for a window and the GUI's shutdown with a run in progress (both GS2), the console's own bounds (TD-09 stays for the console), the menu (TD-12, TD-15), the parser's fragility (TD-55) and the cache race between processes (TD-54).

## 20. GUI campsite searches and results (decision D46; the Results tab, `ResultsViewModel`, `ResultRows.cs`, `ProgressGate`, `ResultsView`)
- [V] **What it is.** The GUI's sixth tab, Results, after Searches (since D50 the second of four top-level tabs, still right after Searches; §21): it runs saved search files on request through GS1's service (§19: `CampsiteSearch.Plan` and `Run`, the console's own search with manual-search semantics) and shows the typed results. - [V] **Folders.** The settings folder and the cache folder are the ones `Load.GetConfig` returned at the GUI's start (`MainWindowViewModel.ConfigPath`/`CachePath`, carried through the startup's completion; nothing rediscovers them). Without a cache folder nothing can start ("Campertron couldn't find its cache folder, so it can't search. Restart Campertron."). The folders are never shown in the results.
- [V] **The list.** Exactly the console's search files (`ConfigFiles.SortedSearchFileNames`: the same discovery and order as the Searches tab), each read as GS1's plan reads it (`CampsiteSearch.LoadEntry`: the bounded reader and CM3's diagnostics with an enabled search's severities; never written).

- [V] **The choice.** A runnable file that is enabled (`autoRun: true` as the file has it, `ResultsSearchRow.IsEnabled`; `RunsAtStart` before D63) is selected by default; one that is not enabled is listed unselected and runs only when the user selects it (its `autoRun` is never changed: the run's `SearchResult.AutoRun` and the file keep `false`). A file that can't run can't be selected and is unselected when it stops being runnable; a file that is no longer enabled is unselected unless the user selected it; a file that becomes enabled is not selected behind the user's back, and one that could not run and now can gets the default choice.
  Select enabled (named "Select the enabled searches"), Select all that can run and Clear selection change the choice (the first two say in help text that nothing runs until Start); all of them, and the check boxes, are locked while a run goes on. The GUI searches only when Start is selected: never because it starts, a tab is shown or a file is listed (`AutoRunWordingTests`).
- [V] **Start** (enabled only when no run goes on, at least one file is selected, Start is not waiting after a block, both folders are known and, since D61, the campground data is not being refreshed (§25); the command checks the same again): the disk is read again first.
  If that unselects a selected file (it can no longer run, or it is no longer enabled and the user did not select it), nothing starts and the tab says which files changed; a file that appeared meanwhile is listed unselected. A selected file deleted since it was listed is asked for anyway, so the run reports it as a typed missing file while the others are searched. Then GS1's plan reads each selected file once (the bytes searched are those read now) and checks it; if no file can be searched, nothing starts and the previous results stay. Otherwise the run is accepted: the previous results are cleared and `CampsiteSearch.Run` runs on a background thread of its own (`TaskCreationOptions.LongRunning`: never a foreground thread, never the UI thread);
  one file and several files go through the same entry point.
- [V] **One data operation in the window** (since D61, §25): a run holds the window's `DataOperationGate` from its accepted Start to its end, so Settings > System's Refresh campground data… is unavailable meanwhile; while a refresh runs, Start is disabled and the run card says "Start is unavailable while the campground data is refreshed (Settings > System). It is available again when the refresh has finished." (the list, the choice and the results stay usable).
- [V] **One operation at a time.** Each accepted Start is an operation with its own increasing ID, `CancellationTokenSource`, plan, progress gate, start time (the monotonic `TimeProvider`) and task. Every progress publication, the run's end and the elapsed-time ticker check that their operation (or ticker) is still the current one; a callback of an earlier or abandoned run changes nothing. The token is disposed only after the run has ended (Cancel and Dispose are serialized). Since D63 (TD-56 resolved) the progress and the end are posted to the dispatcher Start captured on the UI thread (`ResultsSeams.Post` is null in production), as the startup (D49) and the refresh (D61) do: no worker thread asks for `Dispatcher.UIThread`.
- [V] **Cancel** (enabled while a run goes on and not yet canceled): cancels the operation's token; GS1 stops at its next checkpoint (during a request, the wait before another request, while waiting for a shared month, while campsite details are prepared or results filtered; measured: well under a second, 143 to 148 ms by keyboard in the real window). The button reads "Canceling…" until the run ended; repeating it does nothing; it never starts anything or ends the process. Searches that finished keep their results; a month that was not checked is listed as not checked, never as a month without availability.
- [V] **Progress.** GS1's snapshots reach the UI through `ProgressGate`: `Report` (on GS1's threads, under its lock) only keeps the newest snapshot and queues one job for the UI thread if none is queued or waiting; the UI publishes at most once per 100 ms (a later snapshot waits for the rest of the interval on a one-shot timer), so at most ten publications a second and never more than one job or timer waiting. The run's end is shown at once from its result (the gate is closed and its timer stopped). Shown: the stage ("Reading the searches", "Preparing campsite details", "Checking availability at recreation.gov", "Checking availability; N requests are waiting to be tried again (each month is asked for at most three times)", "Building the results"), the campgrounds ready of planned and the month requests finished of planned (with those not checked and those waiting to be tried again), each file's state in the list (Waiting, Searching, then its end) and the elapsed time (every second).
  The bar is determinate only with GS1's totals (campgrounds while their details are prepared, month requests while availability is checked), otherwise indeterminate; no percentage is shown. GS1 reports no attempt number or wait duration, so none is shown (open question #42 unchanged).
- [V] **A block** (the block page or HTTP 429, `SearchRunStatus.Blocked`): the run is over at once; the searches that completed keep their results, the blocked one is "Stopped: recreation.gov limited the requests…", its months are listed as not checked ("recreation.gov blocked the requests" or "asked for fewer requests"); no answer text or exception message is shown; the application keeps running. Start is disabled for five minutes from the blocked result in this GUI process only ("recreation.gov limited Campertron's requests. Start is available again in m:ss.", every second), measured with the monotonic `TimeProvider`; nothing is written, another window or a restart does not wait, and the console's own block handling (§7) is unchanged.
- [V] **The results** (`ResultSearchViewModel`, `ResultRow` and its kinds), directly from the immutable `SearchRunResult`: the run's status ("Finished: …", "Finished with problems: …", "Stopped: …", "Canceled. …", "Nothing could be searched.") with the openings found and the elapsed time, the run's issues, and a choice of the search to show (the first with openings is shown first). Per search: its status in words, distinct for each end (complete with openings "Complete: N openings found", complete without "Complete: no matching availability in the months checked", "Incomplete: some months were not checked…", "Failed: no month could be checked", "Stopped: recreation.gov limited the requests…", "Canceled before it finished…", "Not searched: no campground is set (campgroundID)" or "Not searched: the file can't be searched"), its counts (openings, campsites, nights; for consecutive nights the campsites with runs and the nights in all), "Months checked:
  …" and "Not checked: <month> (<reason>)" (a month not checked is never shown as without availability), its campground, park and ID, and its issues and warnings with their severity written out ("Error:", "Warning:"), the month, the HTTP status and the requests made (never a response body or an exception's message). Single nights: a heading per night in date order with the number of campsites, then GS1's openings of that night in GS1's order (campsite ID, shorter first); consecutive nights: each campsite in GS1's order with its stays (arrive, leave, nights) in date order. A campsite row shows its name as the results page names it ("Site 086"; a name starting with "Site" as it is), its ID and only the details it has: loop and type as stored, equipment, check-in, checkout, occupancy ("1 to 6 people", "4 people", "up to 6 people"); no empty label. Nothing is truncated in the model; long text is trimmed on screen with the whole text in a tooltip and the accessible name.
- [V] **Large results.** The rows of a search are built once, when it is first shown; the list is a `ListBox` with a `VirtualizingStackPanel` in a bounded star row, so only the rows on screen exist (12,030 rows: under 100 realized, also after scrolling to the end; 17,280 openings from a stand-in run shown in 2.5 s in the real window).
- [V] **Booking links and copies.** The selected campsite's booking link is opened (Avalonia's `ILauncher.LaunchUriAsync`: no shell, no command line, no process) or copied only if it is exactly the link GS1 builds for that campsite (`CampsiteSearch.BookingUrl`: https, host `www.recreation.gov`, the default port, no user information, query or fragment, the path `/camping/campsites/<the escaped campsite ID>`); otherwise "Campertron did not open (copy) this link: it is not a recreation.gov campsite page.". Copy campsite ID and Copy booking link write to the clipboard only on the user's action. A launcher or clipboard failure is reported without its message ("Campertron couldn't open the booking page. …", "Campertron couldn't copy …"). No configuration value is ever copied.
- [V] **Accessibility.** Every interactive control has an accessible name (Start search, Cancel search, the check boxes "<search> (<file>), Enabled (autoRun): selected by default", "<search> (<file>), Not enabled: runs when selected" or "<search> (<file>), <the setting>, can't be searched now" with the reason as help text (since D63), the selection buttons ("Select the enabled searches"), the result choice, the list "Openings found", the actions); the status is a polite live region read as its text; the progress bar is "Search progress" with its value when determinate; each result row reads its date and campsite with its details; every state and problem is said in words, never by color alone. Keyboard: Tab goes Start, the check boxes, the selection buttons (Cancel and disabled buttons skipped), then the result choice, the list (arrow keys choose a row) and the actions, and wraps to the tab header (TD-39's workaround); Enter toggles a check box and presses a button.
- [V] **Window close.** Closing the window detaches the tab (no later callback changes anything), cancels the run and stops its timers; the UI thread never waits for the run. `Program.Main` (and the smoke test) then waits at most `App.SearchShutdownWait` (10 s) for the canceled run to end (measured: a few milliseconds), so a campsite-details build stops at a checkpoint; the run's thread is a background thread either way. - [V] **The theme.** Settings > System offers exactly **System** (the default), **Light** and **Dark**. System is Avalonia's `ThemeVariant.Default`: the window follows the operating system's light or dark setting and its changes while Campertron runs (Avalonia reads it from the platform; on Linux the settings portal's `org.freedesktop.appearance color-scheme`); Light and Dark always use that theme. It applies until Campertron is closed."). The smoke test's theme probe uses a temporary folder and never writes the user's file.

## 22. Filter choices from the campground data (decision D51; `Read.FilterChoicesByCampground`, `CampgroundFilterChoices`, `FilterChoice`)
- [V] **What it is.** The values a search's eight include and exclude lists can be set to for one campground, read from the local campground database only (no network): the permitted equipment names, the campsite types, the campsite names and the attributes (`"Name:Value"`, composed exactly as the search composes them, `Cache.ConvertAttributeValuePairToString`) of the campground's **own campsites** (`CampsitesEntries.FacilityID`, the exact string; never trimmed or parsed: `0232445`, ` 232445` and `2324` give nothing). Each `FilterChoice` holds the value exactly as stored (never trimmed or case-changed; blank names, surrounding spaces, colons in attribute values and case variants are kept as separate values), the number of the campground's campsites that have it (for a campsite name: the campsite records that carry it), and for an attribute its name and value. Lists are ordered by `FilterChoice.ListOrder` (ignoring case, then ordinal: case variants are next to each other;
  the same in every culture). The search editor's selectors use it (§23).
- [V] **How.** Three parameterized queries in one context: the campground's campsite records, then the equipment and the attribute rows of exactly those campsite IDs (an `IN` list of parameters, which Campertron's attribute index serves, §8). Equipment and attribute rows whose campsite is not in `CampsitesEntries` (the shipped data has 4,850 and 1,200 such rows) are never offered, and neither are rows of another campground's campsites: the search never sees them either. A blank ID runs no query (no database is opened or created); an unknown ID and a campground without campsites give no choices after one query. Null names and types are left out (the shipped data has none). Read-only; it reads no settings file and makes no web request.
- [V] **The shipped data** (RIDB export of 2026-11-10; measured 2026-11-16 with read-only SQL, history/validation/ad-ax_preview.2.md §AQ): 130,948 campsite records, 441,779 equipment rows, 2,407,137 attribute rows; 15 equipment names, 39 campsite types, 336 attribute names and 3,489 distinct `Name:Value` pairs overall; per campground at most 14 equipment names, 10 types, 92 attribute names and 270 pairs, and at most 360 campsite records (258830; 232490 has 357). 4,966 reservable, enabled campgrounds, 10 of them without campsite records. 1,115 campsite names occur more than once within their campground (in 120 campgrounds), 3 pairs of names differ only by case within a campground; 14 names are blank and 260 untrimmed; 43,862 attribute rows have a blank value and 48 a whitespace-only one, 376 an untrimmed value (17 distinct pairs); 142 pairs have a colon in the value; 28 groups of pairs differ only by case (35 when also trimmed).
  No equipment name, type or attribute name differs from another only by case. A copy of a real data folder's database refreshed on 2026-11-11 has exactly the same equipment names, types and `Name:Value` pairs, but 130,949 campsite records, 541 of which differ from the shipped ones (`EXCEPT`): the choices of a campground can change with a refresh.
- [V] **Cost** (the product's code, medians of 15): 22 to 34 ms per campground with Campertron's index (Watchman 27 ms, 258830 22 ms, 232490 34 ms), 0.19 to 0.35 s without it.

## 26. GUI automatic restart after a refresh (decision D62; `RestartHandoff.cs`, `AutomaticRestart`, `WindowPlacement`, `MainWindow`, `Program.Main`)
- [V] **What it is.** After a refresh of the campground data that installed new data (§25: refreshed, also without its date), Campertron restarts itself so that a clean process loads the new database, and the new window opens where the old one was, at Settings > System. It is a one-time handoff between two processes, never a preference: nothing about the window is kept for a later, ordinary start.
- [V] **When it doesn't happen.** Not after a failed or canceled refresh (also not after "installed but the check found a problem" or an unexpected problem after the installation); not when the window was closed meanwhile (an ordinary close); not without a desktop lifetime to end this process with; not when Settings > Campertron or the Searches tab hold unsaved changes, which a restart would lose: the card then says "The campground data was refreshed. Campertron didn't restart automatically because Settings or Searches have unsaved changes: save or revert them, then restart Campertron to use the new data." Never more than once, and a restarted process never restarts because it was restarted.
- [V] **Restarting.** The card says "The campground data was refreshed. Restarting Campertron…" (the polite live region), shows neither Refresh campground data… nor Cancel, and keeps the window's data-operation gate, so no search starts meanwhile. Normally the new window appears within about a second and the old process ends cleanly through its desktop lifetime (Program.Main's waits find nothing left).
- [V] **The handoff** (`RestartHandoffStore`): a JSON object of known members only (`version` 1, `binding`, `createdUtc`, `outcome`, `tab`, `settingsTab`, `window`: `x`, `y`, `width`, `height`, `maximized`, or null), at most 4 KiB, never a setting, path, address or secret, in `LocalApplicationData/CampertronGUI/restart/restart-<binding>.json` (the GUI's own folder beside its theme preference; never `CampertronConfig` or a YAML file). The folder is created owner-only (0700 on Unix; on Windows it inherits the per-user folder's rules) and refused if it is a link or others can write to it; the file is created new, 0600 on Unix.
  The new process claims it by an atomic rename to a name of its own (so exactly one of the two processes gets it), reads it within the limit, deletes it and then validates it: the schema version, the binding of its token, its age (at most two minutes, at most 30 seconds ahead), every number within bounds (whole coordinates within a million, sizes from 1 to 100,000), every enumeration by its exact name, no unknown or repeated member. A missing, malformed, oversized, linked, stale, replayed or foreign file is no handoff: the start goes on as an ordinary one. Leftovers of a failure (exact names, older than two minutes) are removed by the next restart.
- [V] **The token** (`RestartToken`): 32 bytes from the system's cryptographic generator, as 64 lowercase hexadecimal digits; its SHA-256 (the binding) names the file, so the token is never on disk. It reaches the new process only in the environment variable `CAMPERTRON_RESTART_HANDOFF`, which `Program.Main` removes at once (nothing the GUI starts later inherits it); it is never on the command line, in a log or in a message. Anything but 64 lowercase hexadecimal digits selects no file at all.
- [V] **The launch** (`RestartTargets`, `AutomaticRestart.Run`): the process's own executable, `Environment.ProcessPath`, as a full path that exists: the apphost (`CampertronGUI`, `CampertronGUI.exe`) of every release archive (self-contained; on macOS a plain program, not an app bundle) and of a local build or `dotnet run` (framework-dependent), with no argument; or the dotnet host (`dotnet CampertronGUI.dll`) with the entry assembly's full path as its one argument. `ProcessStartInfo` with an explicit argument list, `UseShellExecute` false: no shell, no PATH lookup, no working-directory lookup, no elevation, no launcher script.
- [V] **The acknowledgment and its failure.** The new process claims the handoff first thing in `Program.Main`; the old one checks every 50 ms, at most 20 seconds. Claimed: the old process ends. The start throws or returns no process, the new process ends without claiming, or nothing is claimed in time: the old process invalidates the handoff, ends a new process that never claimed it (it has done nothing yet), and stays, usable, with "The campground data was refreshed, but Campertron could not restart automatically. Restart Campertron manually to use the new data." (a warning, not an error; the installed data stays). There is no second attempt. The reason is kept for tests and diagnostics (an exception's type name, never its message or a path).
  The acknowledgment proves that the new process started and took the handoff, not that its whole startup succeeds (a startup failure shows in its own window).
- [V] **The window** (`MainWindow.CaptureForRestart`, `WindowPlacement.Fit`, `MainWindow.ApplyRestartPlacement`): the old window's normal bounds (its position in device pixels and client size in device-independent pixels, kept in memory while it is normal, because Avalonia reports no restore bounds) and whether it is maximized; a minimized or full-screen window restores as a normal one. The new window gets them fitted to its screens: on the screen that holds the window's top-left corner, else the nearest working area (the primary screen on a tie; scale-independent); unchanged when they lie within the working area, otherwise moved and shrunk the least, never below the minimum size (720×540), with room for the title bar; without screen information only the size; invalid values keep the ordinary startup placement.
  They are applied before the window is shown (`WindowStartupLocation.Manual`), the position is asked for once more after it opened, and only then is the window maximized, so it keeps its normal bounds for when it is restored.
- [V] **Window managers.** The position is a request: a window manager or compositor may place a window itself. Avalonia 12.1.6 has no Wayland backend, so on a Wayland desktop the GUI is an XWayland client and the compositor decides. Measured in a nested KWin session with Xwayland (history/validation/ba_v0.1.1.md §BD); Windows and macOS were not run.
- [V] **Navigation and the one-time status.** The new process starts as every start does (`Load.GetConfig` in the background, nothing database-backed before it succeeded); once it is ready, and only then, the window shows Settings > System (`MainWindowViewModel.TakeRestartNavigation`, once; the tabs' own handlers read the current configuration and the last refresh, which shows the new date). Its card says "The campground data was refreshed and Campertron restarted successfully." (or, after a refresh without its date, that the date could not be recorded), until the next refresh; no confirmation opens and nothing starts.
- [V] **Ordinary starts and closes.** A start without the token reads no handoff, keeps the window's startup placement (centered, 1024×768) and opens at Searches; an ordinary close writes nothing.
- [V] **The smoke test** reports `restart=<launcher>` in its `system-tab` line (`apphost` for every release archive), resolved from the process's own executable with the window's capture bound, and never starts a process or writes a handoff; `check_gui_smoke_report` requires `restart=apphost`.
- [V] **Not part of it:** a remembered window position or size, a live reload, a restart after anything but a successful refresh, a watchdog that outlives the acknowledgment, the console (which has no restart).
