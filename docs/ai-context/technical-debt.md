Blocking names what the item blocks. Labels such as §Z name validation records (`history/README.md` §Validation record index). Since Phase 3 each record is a subsection with the former table's column names as labels.

### TD-01
**Issue:** **Tests touch real user state and the network** (config dir, DB extraction, recreation.gov, `Camp.History` markers)

**Evidence:** [V] `LoadUnitTests.cs` calls `Load.GetConfig()`, `RunConsoleSearch(config, true)`. ~~[V] `Load.HasNewEntries` creates markers when `OutputTo != Console`.~~ Since branch `fix/manual-search-notification-history` (2026-11-14) `UnitTest` neither writes nor reads `Camp.History` (Email only, business-rules §5), so the tests no longer create markers (0 in the §T runs); the real config dir, DB extraction and live request remain. **Confirmed by test run 2026-11-10:** 1 live request, DB extraction, 384 cache files, 118 `Camp.History` markers (in an isolated `XDG_DATA_HOME`). **Audit 2026-11-14:** still one live GET per full test run (§T, §Y; CI run 43652516073 included `LoadTests`), so CI and the release `verify` job depend on recreation.gov; a failure or block fails the run safely (nothing is published) and recovery is a separately approved rerun. Disposition: preview.2, with an HTTP seam (R4) that R5 needs anyway;
the preview.1 cleanup tests use the offline technique of `SharedMonthSearchTests` instead. **Network part resolved by D45 (GS1, 2026-11-15):** `LoadTests.RunConsoleSearchTest` runs the console's whole search through the internal download seam `AvailabilityApi.ConsoleDownload` (production: the former download code), the interactive search's tests through its transport seam, and an assembly-wide guard (`NoLiveNetwork`) fails the test run if any test reaches a non-loopback address; the complete suite passes inside a network namespace with only a loopback interface (history/validation/ad-ax_preview.2.md §AJ), so CI and the release `verify` job no longer depend on recreation.gov. **Still open:** `LoadTests` uses the real (isolated) data folder through `Load.GetConfig` and extracts the database (R1); the test commands must keep isolating `XDG_DATA_HOME`

### TD-06
**Issue:** HTML and email output runs once per config item. **`HtmlFile` part resolved on branch `feat/html-visual-polish` (2026-11-12, D29); email part open**

**Evidence:** [V] Before: `PostProcess` looped `ProcessConsoleConfig` per `ConsoleConfigItem`, and each call deleted `*.html`, wrote a new file and opened a browser or sent an email. With several searches, an earlier search's file was deleted before the browser had opened it: in a real run with four searches and a recording opener, 2 of the 4 files were gone when the opener ran (2026-11-12). Now `HtmlFile` writes one page for the run and opens it once (`HtmlResultsOutputTests`). **Still open:** `Email` sends one email per search per cycle (open question #9), each write replacing the previous search's file in `CachePath` after its email was sent. When the gate opens, every search gets an email, including a search with nothing new (its page shows "No new matching availability to display."). Disposition: product direction, stable readiness

### TD-07
**Issue:** Today's availability is never reported

**Evidence:** [V] `FilterData` requires `CampsiteAvailableDate >= DateTime.Now`, and the dates are midnight (`ProcessMonth` `CheckDt.AddDays`). `Until` with a past date yields only today, so it never matches anything. [I] "Now" is the machine's local time: a container without a time-zone setting runs on UTC, so during US evenings (after UTC midnight) it also excludes the date that is still "tomorrow" for the user. Disposition: product direction (open question #7), stable readiness

### TD-09
**Issue:** Unbounded retry and wait loops (since D34 a failed request, heavy traffic and a block are reported with the retry that follows; the loops themselves are unchanged). **Bounded for the interactive search by D45 (GS1, 2026-11-15); unchanged for the console**

**Evidence:** [V] `GetWebApiData` catch-all retries forever every 30 s. Heavy traffic recurses without limit. `ProcessMonth` waits on `SiteData` forever. [I] `while (ReceivedData == false)` spins if the JSON has only `count`. **D45** [V]: an interactive run (`CampsiteSearch.Run`, `SearchHost`) never takes these loops: at most three requests per month in all, cancellable waits, a 30 s request timeout, the answers the console would spin or retry on forever (`{"count":0}`, `{}`, `[]`, an error object, not JSON) classified and bounded, and a waiting search released by a signal instead of polling (`SearchHostTests`, business-rules §19). The console keeps the loops (its retry behavior is a contract until stable readiness)
**D90 (2026-11-23, the monitoring service):** the monitoring's checks keep the console's loops (the same requests and retries, ER-02), but their waits end at once when the monitoring service is stopped (`MonitoringRun.Pause`), and a stopped check leaves the loop at its next checkpoint; a request in flight is not interrupted. The console never stops its monitoring, so for the console nothing changed; the console's Search is untouched.

### TD-10
**Issue:** `Environment.Exit` and `Console.ReadKey` inside library code

**Evidence:** [V] `CampertronConfig.GenerateSearchDates` (StartEndDate equal), `GetWebApiData` (REQUEST BLOCKED), `Menu.Init` (container, and since D34 a start without an interactive terminal), `Menu.ProcessInput` (Exit); `ConsoleUi.WaitForKey` reads keys (only on an interactive terminal). [I] Prevents reuse from the GUI and makes testing hard. Audit 2026-11-14: the two search-path sites are tracked as TD-45 (`GenerateSearchDates`) and TD-44 (`GetWebApiData`). **D37 (P4):** `GenerateSearchDates` no longer reads a key or exits (it throws, TD-45); `GetWebApiData` still ends the process after a blocked request, now with exit code 1 through `AvailabilityApi.ExitProcess` (TD-44), so that site remains for R5. The menu sites, the blocked-request exit and the rest belong with R5 (preview.2). **D45 (GS1, 2026-11-15):** the interactive search service never reaches them:
a block ends its run as `Blocked` (no wait, no exit), and it uses neither the menu nor `ConsoleUi` (checked from the IL and at run time by `CampsiteSearchTests` and `SearchHostTests`). The console's sites are unchanged
**D90 (2026-11-23, the monitoring service):** the monitoring service itself never ends the process: a blocked request does what its host gives (`MonitoringOptions.Blocked`); the console's adapter gives the console's own answer, the error, the five-minute wait and `AvailabilityApi.ExitProcess(1)` (`AvailabilityApi.ConsoleBlocked`), so the console is unchanged, and without a host's handling the monitoring ends as failed and the process goes on. The console's sites are otherwise unchanged.

### TD-54
**Issue:** **Two processes building one campground's cache at the same time can read each other's partial files.** The cache files (`{CampgroundID}-CampInfo.json`, `-Campsites.json`, `-CampsitesByPark.json`, `{CampsiteID}-Equipment.json`, `-Attributes.json`, the marker `-Cached.json`) are written with a truncating `StreamWriter` (`Cache.Serialize`, `CachePermittedEquipmentByCampsite`, `CacheCampSiteAttributesByCampsite`). Within one process the completion protocol holds: the marker is written last and only after a complete build, so a build that stops (a canceled interactive search, an exception, a killed process) leaves no cache that looks complete and is built again (business-rules §19). Between processes there is no lock: when the console and the GUI (or two consoles)
build the same campground at once (after a RIDB refresh cleared the cache, or on a first search), one can truncate a file the other is reading, and a reader that finds the other's marker can read a file still being rewritten

[I] Not observed: it needs two processes building the same campground's cache within the same seconds; the reader then fails with a `JsonException` or reads an empty list (an empty list would make the search miss that campsite's equipment or attributes for that run). The GUI's searches (GS2) make concurrent builds more likely. Severity Low. Disposition: preview.2, to assess with GS2 (options, none decided: write each file through a temporary file and a rename, a lock file per campground, or rebuild on a read failure). **Assessed by GS2 (D46, 2026-11-15), not changed:** within the GUI there is one run at a time, and GS1 prepares each campground once per run, so the race needs two processes (the GUI's Results tab and a console, or two GUIs) preparing the same campground at the same moment: only on a campground's first search or after a refresh cleared the cache.

[I, not run] On Windows, where a file's share mode is enforced, two processes opening the same cache file at the same moment give one of them an `IOException`, so a simultaneous first search can fail once there. ## Migration risks (for example, moving search into the GUI or refactoring)
- [V] The search pipeline writes directly to the console (through `ConsoleUi` in `Load`, `GetWebApiData`, `Cache` and `Yaml` since D34; `Console.WriteLine` in `Clear`, `Populate` and `RidbStagedRefresh`, which since D61 write through a log sink that only the console's refresh gives `Console.WriteLine`) and calls `Menu.Init` from `Load.PostProcess`. A GUI host would need these separated first. D34 moved the result rendering out of the value text (`ConsoleResults` renders the metadata), which a GUI host can reuse the same way. Since D45 (GS1) a host other than the console searches through `CampsiteSearch.Run`, which reaches neither the console, `Menu`, `PostProcess` nor `Environment.Exit` (the per-run `SearchHost` replaces the console's fetch, waits and status lines on that path); the console's own path still writes to the console.
- [V] `Load.GetConfig()` has side effects (dir creation, YAML writes, a 226 MB extraction of about 0.35 s, possible network refresh). Until R8 it was called synchronously in the GUI `MainWindow` constructor, before any window existed; since R8 (D33) `MainWindowViewModel` runs it on a background task after the window has opened and shows its progress or its error.
- [V] Models in the global namespace and static mutable state (`Menu._location`) complicate reuse.
- [V] Changing the filter semantics (§3 of business-rules) changes which notifications users receive. Treat it as a behavior change. **Done deliberately by D51 (2026-11-16):** OR semantics for `excludeEquipment`, `excludeAttributes` and `includeCampsiteType`; files without `filterMatching` keep the containment matching; the preview.2 notes describe it (the curated-notes stage of the selector project).
- [V] Changing the `Camp.History` path format would re-notify every previously suppressed hit.
- [V] The DB schema has no migration path in use. Model changes to `*Recdata` need a new embedded DB or a migration strategy.
