# Console → GUI map

Legend: **[V]** verified · **[I]** inference

GUI facts come from `CampertronGUI/Views/MainWindow.axaml(.cs)`, `Views/CampgroundDetailsView.axaml(.cs)`, `Views/StartupStatusView.axaml(.cs)`, `ViewModels/ReactiveViewModel.cs`, `ViewModels/CampgroundDetails.cs`, `ViewModels/MainWindowViewModel.cs`, `SmokeTest.cs`, `Program.cs` and `App.axaml(.cs)`. The GUI has no `ReactiveCommand` [V]. Its interactions are `ComboBox` selections (with type-ahead) across three lookup tabs, selecting text, scrolling the details, one **Copy ID** button (a `Click` handler in `CampgroundDetailsView`, beta.8), after a failed startup **Try again** (R8) [V], since D43 (CM5) the **Settings** tab, which edits `General.yaml` and `Email.yaml` (business-rules §17; `ViewModels/Settings*.cs`, `Views/Settings*.axaml`, `SecretTextBox`) [V], since D44 (CM6) the **Searches** tab, which creates and edits search files (business-rules §18; `ViewModels/Search*.cs`, `CampgroundPicker.cs`, `Views/Search*.axaml`, `ListFieldView`) [V], and since D46 (GS2) the **Results** tab, which runs saved search files on request through GS1's `CampsiteSearch` and shows their typed results (business-rules §20; `ViewModels/ResultsViewModel.cs`, `ResultRows.cs`, `ProgressGate.cs`, `Views/ResultsView.axaml`) [V]. The lookup tabs stay read-only; only the Results tab searches. Since D50 the window's top-level tabs are Searches, Results, Settings and Campgrounds (labeled Campsites until D55; Searches shown at the start); Settings holds Campertron (the CM5 editors) and System (the theme: System, Light or Dark, saved in the GUI's own preferences file; `ThemePreference.cs`, `ViewModels/SystemSettingsViewModel.cs`, `Views/SystemSettingsView.axaml`), and Campgrounds holds the three lookup tabs [V].

| Console workflow (feature-inventory ID) | GUI status | Evidence |
|---|---|---|
| F1 Startup / first-run bootstrap (dirs, sample YAML, DB extraction, auto-refresh) | **Implemented** (shared code) | Since R8 (D33) `MainWindowViewModel` calls `Load.GetConfig()` on a background task after the window has opened [V]; the same library method as the console, so the side effects are identical. Meanwhile the window shows "Preparing campground data…"; a failure (for example an invalid `General.yaml`) is shown in the window with the message, the settings folder and Try again, instead of aborting the process. The tabs and their database-backed `ReactiveViewModel` exist only after it succeeded, with its `ConfigPath`. Before R8 it ran in the `MainWindow` constructor, before any window existed, and its result was unused |
| F2 Interactive menu | **Not implemented** | No menu equivalent. The GUI is a `TabControl` with "Searches", "Results", "Settings" (Campertron, System) and "Campgrounds" (By Park, By City, By State) since D50 (the last labeled "Campsites" until D55); before, "By Park", "By City", "By State" and later Settings, Searches and Results in one row [V] |
| F3 Search with console output | **Implemented in the GUI as the Results tab (GS2, D46)** | The Results tab runs the chosen saved search files once, on request, through GS1's `CampsiteSearch.Plan`/`Run` (the console's own search: the same months, filters and consecutive nights; business-rules §19) and shows the typed results: per search its status, counts, checked and unchecked months and issues, single nights by date and consecutive nights by campsite, booking links and copies (business-rules §20). Like a manual Console search it shows every current match (no `Camp.History`); unlike the menu it also runs disabled files when they are chosen, and it never writes a file. Still no reference to `RunConsoleSearch`, `AvailabilityApi` or `Preload` in `CampertronGUI/**` [V, IL scan in `ResultsViewTests`] |
| F4 Search with HTML output | **Covered by the Results tab** (no page) | The Results tab shows the same openings the results page would show for the same search (both from the same values' metadata, GS1), in the window; it writes and opens no HTML file |
| F5 Headless email loop | **Not implemented** | No reference to `EmailConfig` or `ProcessConsoleConfig` in the GUI [V] |
| F6 Refresh RIDB data | **Partial** | No user action. It can only happen as a side effect of `Load.GetConfig()` → `DbExistsCheck` when `autoRefresh: true` and the interval has elapsed [V]. That path writes progress to `Console`, which a WinExe does not show [I]. Since D26 it is failure-safe: a failed or interrupted refresh leaves the GUI's DB unchanged, and the GUI's own open or pooled connections need not close for the installation (business-rules §8). Since R8 it runs on a background task while the window shows "Preparing campground data…" (it used to block before any window existed); a failed refresh is shown in the window with Try again, and a refresh still running when the window closes is allowed to finish before the process exits (`Program.Main`). A failed refresh is retried on the next start because the timestamp is no longer written before the refresh |
| F7 View Config | **Partly (D43)** | The Settings tab shows the settings folder and each file's path, opens the folder (Open settings folder) and shows `General.yaml`'s settings, the refresh interval and the last refresh; no refresh age or OS info. Also the settings folder in the startup-error state (R8). Since R8 `ReactiveViewModel.ConfigPath` is `Load.GetConfig`'s path (it replaced `GetConfigPath`) and is not bound in XAML [V] |
| F8 Exit | **Unclear** | No explicit exit action. Window close is handled by Avalonia's classic desktop lifetime (`StartWithClassicDesktopLifetime` in `Program.cs`). Not an equivalent workflow |
| F9 Container mode | **Not implemented** | The GUI is not supported in a container. Since R8 it queries `Load.GetConfig`'s own `ConfigPath` (before R8 it was hard-coded to `LocalApplicationData/CampertronConfig`, which differs from `/config` in container mode) [V] |
| F10 Search-config discovery and editing | **Implemented in the GUI (CM6, D44)** | The Searches tab lists the console's search files (the same discovery, `ConfigFiles.SearchFiles`, sorted by name) with each file's search name, whether it runs (autoRun), its campground and its state, and edits the chosen one: every setting typed, the dates and the eight filters as rows, the validation's problems at their fields and rows, a read-only preview of the changed lines, Save, Revert, Reload, conflicts for changes by another program, New search (the example search, disabled) and Save As (create-only). The campground is chosen from every reservable, enabled campground or by its exact ID (TD-53 resolved). Comments and formatting stay (the CM1 editor, the CM2 writer, D39/D40). Nothing deletes a file or runs a search (business-rules §18). The console still edits search files only in a text editor [V] |
| F11 Duplicate-notification suppression | **Not applicable** | The Results tab is a manual search: it neither reads nor writes `Camp.History` (business-rules §5, §20); there is no notification in the GUI |
