# Console → GUI map

Legend: **[V]** verified · **[I]** inference · **[A]** assumption, not executed (as in `build-and-test.md`)

GUI facts come from `CampertronGUI/Views/MainWindow.axaml(.cs)`, `Views/CampgroundDetailsView.axaml(.cs)`, `Views/StartupStatusView.axaml(.cs)`, `ViewModels/ReactiveViewModel.cs`, `ViewModels/CampgroundDetails.cs`, `ViewModels/MainWindowViewModel.cs`, `SmokeTest.cs`, `Program.cs` and `App.axaml(.cs)`. The GUI has no `ReactiveCommand` [V]. Its interactions are `ComboBox` selections (with type-ahead) across three lookup tabs, selecting text, scrolling the details, one **Copy ID** button (a `Click` handler in `CampgroundDetailsView`, beta.8), after a failed startup **Try again** (R8) [V], since D43 (CM5) the **Settings** tab, which edits `General.yaml` and `Email.yaml` (business-rules §17; `ViewModels/Settings*.cs`, `Views/Settings*.axaml`, `SecretTextBox`) [V], since D44 (CM6) the **Searches** tab, which creates and edits search files (business-rules §18; `ViewModels/Search*.cs`, `CampgroundPicker.cs`, `Views/Search*.axaml`, `ListFieldView`) [V], and since D46 (GS2) the **Results** tab, which runs saved search files on request through GS1's `CampsiteSearch` and shows their typed results (business-rules §20; `ViewModels/ResultsViewModel.cs`, `ResultRows.cs`, `ProgressGate.cs`, `Views/ResultsView.axaml`) [V]. The lookup tabs stay read-only; only the Results tab searches. Since D50 the window's top-level tabs are Searches, Results, Settings and Campgrounds (labeled Campsites until D55; Searches shown at the start); Settings holds Campertron (the CM5 editors) and System (the theme: System, Light or Dark, saved in the GUI's own preferences file; `ThemePreference.cs`, `ViewModels/SystemSettingsViewModel.cs`, `Views/SystemSettingsView.axaml`; since D60 also the current configuration, V011-2: `ViewModels/CurrentConfigurationViewModel.cs`, `Views/CurrentConfigurationView.axaml`; since D61 also the campground data with Refresh campground data…, V011-1: `ViewModels/CampgroundDataViewModel.cs`, `ViewModels/DataOperationGate.cs`, `Views/CampgroundDataView.axaml`; since D62 the automatic restart after a successful refresh: `RestartHandoff.cs`, `AutomaticRestart.cs`, `WindowPlacement.cs`), and Campgrounds holds the three lookup tabs [V].

| Console workflow (feature-inventory ID) | GUI status | Evidence |
|---|---|---|
| F1 Startup / first-run bootstrap (dirs, sample YAML, DB extraction, auto-refresh) | **Implemented** (shared code) | Since R8 (D33) `MainWindowViewModel` calls `Load.GetConfig()` on a background task after the window has opened [V]; the same library method as the console, so the side effects are identical. Meanwhile the window shows "Preparing campground data…"; a failure (for example an invalid `General.yaml`) is shown in the window with the message, the settings folder and Try again, instead of aborting the process. The tabs and their database-backed `ReactiveViewModel` exist only after it succeeded, with its `ConfigPath`. Before R8 it ran in the `MainWindow` constructor, before any window existed, and its result was unused |
| F2 Interactive menu | **Not implemented** | No menu equivalent. The GUI is a `TabControl` with "Searches", "Results", "Settings" (Campertron, System) and "Campgrounds" (By Park, By City, By State) since D50 (the last labeled "Campsites" until D55); before, "By Park", "By City", "By State" and later Settings, Searches and Results in one row [V] |
| F3 Search with console output | **Implemented in the GUI as the Results tab (GS2, D46)** | The Results tab runs the chosen saved search files once, on request, through GS1's `CampsiteSearch.Plan`/`Run` (the console's own search: the same months, filters and consecutive nights; business-rules §19) and shows the typed results: per search its status, counts, checked and unchecked months and issues, single nights by date and consecutive nights by campsite, booking links and copies (business-rules §20). Like a manual Console search it shows every current match (no `Camp.History`); unlike the menu it also runs files that are not enabled when they are chosen, and it never writes a file. Still no reference to `RunConsoleSearch`, `AvailabilityApi` or `Preload` in `CampertronGUI/**` [V, IL scan in `ResultsViewTests`] |
| F4 Search with HTML output | **Covered by the Results tab** (no page) | The Results tab shows the same openings the results page would show for the same search (both from the same values' metadata, GS1), in the window; it writes and opens no HTML file |
| F5 Headless email loop (since D67 also ntfy) | **Not implemented** | No reference to `EmailConfig` or `ProcessConsoleConfig` in the GUI [V]; the GUI never publishes to ntfy. Since D67 Settings > Campertron offers `outputTo: Ntfy` and shows `Ntfy.yaml`'s state, and since D69 it edits `Ntfy.yaml` (created only by Save; the token never read), so the console's monitoring can be set up there (business-rules §17) |
| F6 Refresh RIDB data | **Yes (V011-1, D61)** | Settings > System > Campground data shows when the data was last refreshed and offers **Refresh campground data…**: a confirmation in the card (about 570 MB from Recreation.gov, several minutes, cancel until the installation, then an automatic restart at Settings > System, or a manual one if it can't), then the refresh through the same library service as the console's refresh (`RidbRefreshService`), on a worker thread, with its stage, a bar where the total is known, the counts and the elapsed time, Cancel until the cache step, and the result in words (business-rules §25); after a success Campertron restarts itself and opens at Settings > System, where the old window was, with a one-time status (D62, business-rules §26); with unsaved changes in Settings or Searches, or when the new process can't start, the window stays and asks for a manual restart. The console's refresh never restarts anything. The Results tab's search and the refresh exclude each other in the window; closing the window cancels a refresh that can still stop, and `Program.Main` waits for it to stop or to finish its installation. The start's automatic refresh is unchanged: it can also happen as a side effect of `Load.GetConfig()` → `DbExistsCheck` when `autoRefresh: true` and the interval has elapsed [V]. That path writes progress to `Console`, which a WinExe does not show [I]. Since D26 it is failure-safe: a failed or interrupted refresh leaves the GUI's DB unchanged, and the GUI's own open or pooled connections need not close for the installation (business-rules §8). Since R8 it runs on a background task while the window shows "Preparing campground data…" (it used to block before any window existed); a failed refresh is shown in the window with Try again, and a refresh still running when the window closes is allowed to finish before the process exits (`Program.Main`). A failed refresh is retried on the next start because the timestamp is no longer written before the refresh. Before D61 that side effect was the GUI's only refresh |
| F7 View Config | **Yes (V011-2, D60)** | Settings > System > Current configuration shows the eight items of the console's View Config (Version, Config, Cache, Output, Searches, RIDB refresh, OS, Framework) from the same library summary (`CurrentConfiguration`), read-only; the GUI's Version is "CampertronGUI <version>". Unlike the console, which shows the settings loaded at its start, it reads `General.yaml` again (read-only, "unknown" when it can't be read) when the tab is shown and when the window is activated; Copy copies the items as "Label => value" lines and Open settings folder opens the startup's folder (business-rules §24). The Settings tab (D43) also shows the settings folder and each file's path and opens the folder, and the startup-error state shows the settings folder (R8). Since R8 `ReactiveViewModel.ConfigPath` is `Load.GetConfig`'s path (it replaced `GetConfigPath`) and is not bound in XAML [V] |
| F8 Exit | **Unclear** | No explicit exit action. Window close is handled by Avalonia's classic desktop lifetime (`StartWithClassicDesktopLifetime` in `Program.cs`). Not an equivalent workflow |
| F9 Container mode | **Not implemented** | The GUI is not supported in a container. Since R8 it queries `Load.GetConfig`'s own `ConfigPath` (before R8 it was hard-coded to `LocalApplicationData/CampertronConfig`, which differs from `/config` in container mode) [V] |
| F10 Search-config discovery and editing | **Implemented in the GUI (CM6, D44)** | The Searches tab lists the console's search files (the same discovery, `ConfigFiles.SearchFiles`, sorted by name) with each file's search name, its autoRun setting ("Enabled (autoRun)" or "Not enabled", D63), its campground and its state, and edits the chosen one: every setting typed, the dates and the eight filters as rows, the validation's problems at their fields and rows, a read-only preview of the changed lines, Save, Revert, Reload, conflicts for changes by another program, New search (the example search, not enabled) and Save As (create-only). The campground is chosen from every reservable, enabled campground or by its exact ID (TD-53 resolved). Comments and formatting stay (the CM1 editor, the CM2 writer, D39/D40). Nothing deletes a file or runs a search (business-rules §18). The console still edits search files only in a text editor [V] |
| F11 Duplicate-notification suppression | **Not applicable** | The Results tab is a manual search: it neither reads nor writes `Camp.History` (business-rules §5, §20); there is no notification in the GUI, by email or ntfy |
