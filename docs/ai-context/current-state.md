### V011-1 Settings > System > Refresh database
Expose in the GUI the database refresh that the console offers as "Refresh Ridb Data (slow)". Context: `feature-inventory.md` F6, `console-to-gui-map.md` F6, `business-rules.md` §8 and §9, `engineering-rules.md` ER-05, TD-54, TD-58, open question #43.

Approved design (2026-11-18), implemented by Phase B (D61; `business-rules-gui.md` §25):
- A host-neutral refresh service in `CampertronLibrary`, in the pattern of GS1's search service (D45): progress, cancellation and a typed result, nothing written to the console. This is an explicit exception to ER-06's "don't change `CampertronLibrary` for the GUI", to be recorded by its own decision. `RefreshRidbRecreationData.RefreshData` stays the console's adapter, with its output and exit behavior unchanged.
- A card in Settings > System with an in-window confirmation card (the download is about 570 MB). Cancel is offered only before the installation starts. Closing the window requests a cancel, and `Program.Main` waits for a running refresh.
- ~~After a successful refresh the user restarts Campertron to see the new data~~ **superseded on 2026-11-18, before Phase B was pushed (D62):** after a successful refresh Campertron restarts itself through a one-time handoff and reopens at Settings > System in the old window's place, size and maximized state as far as the window system allows; no persistent window position; a manual restart only if the relaunch fails. There is still no live reload.
- A stalled download must end or be cancellable: today's download has no timeout for the body (§BA). This is a design requirement of the service, not recorded technical debt.
- The smoke test's `system-tab` line is extended for the new card, with `check_gui_smoke_report` and its policy tests changed together.
- Validation includes an isolated real refresh that downloads the RIDB export (it contacts `ridb.recreation.gov`; never against real user data), which needs its own approval when it runs. It ran once, approved, on 2026-11-18 (§BD).

As implemented: the card is titled "Campground data", below Current configuration; Refresh campground data… opens the confirmation, Start refresh starts it. Cancel is offered until the cache step, the refresh's first change a stop could not undo; from there the card says it is finishing safely. A stalled download ends after 60 seconds without data. The console's refresh is the service's adapter: its lines, messages, key wait and exit codes are unchanged, but "Extracting …" names the archive in its new folder (`CampertronDownload-<32 hex>`). The smoke test's `system-tab` line adds `campground-data=shown last-refreshed=shown refresh=bound confirmation=ready refresh-state=idle` and, since D62, `restart=apphost`.

### V011-3 Coordinated correction of the autoRun and "startup" terminology
Correct misleading `autoRun` and "startup" wording consistently, as the implementation evidence supports: GUI labels, tooltips, accessible names, diagnostics, the directly affected tests, README wording, screenshots and the current AI-context records.
**The wording is decided** (the maintainer, 2026-11-18; implemented by Phase C, D63): the canonical term for a search with `autoRun: true` is "Enabled (autoRun)", and its negative is "Not enabled" (instead of "Disabled"). Explanations are specific to their context, following the verified behavior below; no single sentence is forced across the GUI, the interactive console's Search and Email mode. The implementation settles the exact sentences.

Verified behavior that the wording must describe:
1. Starting the interactive console does not itself run searches.
2. Choosing Search in the interactive console reads the search files each time and runs the searches with `autoRun: true`.
3. Email mode reads the search files once, when it starts, and then runs the `autoRun`-enabled searches every minute.
4. A change to the search files after Email mode started needs a restart of Email mode.
5. The GUI runs no search merely because it starts.
6. In the GUI's Results tab, `autoRun`-enabled searches are selected by default.
7. Searches without `autoRun` run when they are selected manually in the GUI.
8. With no search file, the console creates and runs its example search the next time it searches, not at a generic application start. (Since D65, after `v0.1.1`, only the console's Search does; email mode stops with an error.)

Known locations (to be confirmed by the implementation; Phase C confirmed and changed them, `history/validation/ba_v0.1.1.md` §BE):

- `CampertronLibrary/function/Base/ConfigValidation.cs`: `NoSearchFiles`, "Campertron creates and runs its example search at its next start."; also review `SearchDisabled`, "autoRun is false: this search does not run."
- Found by the investigation (§BA): `SearchesViewModel.cs`, "Enable a search with Run this search (autoRun) and save it."; `ConfigValidation.cs`'s `NoEnabledSearch` ("so nothing is searched", wrong in the GUI, where a manual run works); the Searches list's "Enabled"/"Disabled" in `SearchFileViewModel.cs`, also in its accessible name; the New search help text and note in `CampertronGUI/Views/SearchesView.axaml`; `ConfigEditSession.cs`, "It does not run until you enable it (autoRun) and save."

## Open risks

- **The new notification paths met only stand-ins:** the SMTP password's sources (D66) and ntfy (D67) were validated against loopback stand-ins for the SMTP server, ntfy and recreation.gov (§BL, §BM, §BN); no real email or ntfy message was sent by those validations. The `v0.2.0` notes say so. The maintainer reported on 2026-11-22 that the local build of `54d3142` passed the personal test of email, `smtpPasswordFile`, the recipients and ntfy; the results email's new body (D72, §BR) was checked in a browser by the validation, and the maintainer approved it on 2026-11-22 after testing both forms of the email locally ("both look right"). On 2026-11-22 the maintainer's personal test of the released commit's candidate #96 passed email, ntfy and the container too (§BV).
- **TD-49, unresolved:** `Email.yaml` can keep the SMTP password in plain text, and the README's container recipe makes the settings folder writable by every local user. A host-user recipe was verified (D57), but it is tied to open questions #10 and #27 and the choice is the maintainer's. Since D66 (on `master` since PR #103) the password can stay out of `Email.yaml` (a password file, such as a Docker secret, or `CAMPERTRON_EMAIL_PASSWORD`); `smtpPassword` stays the plaintext fallback, and nothing checks the password file's permissions (#45). Since D67 (on `master` since PR #104) `Ntfy.yaml` keeps ntfy's topic, which on a server without access control works like a password, in plain text in the same settings folder; its token is never in a settings file.
  Since D69 (on `master` since PR #106) a `Ntfy.yaml` the GUI creates is owner-only (0600) on Unix, and the editor says when other users can read an existing one. Since D70 (on `master` since PR #107) the GUI recommends the password file over the plain-text password, but never clears or migrates a plain-text password. Since D75 (step 3) the GUI warns when others can read the password or token file, from its metadata only; email mode itself doesn't check.
- **Open question #43, the refresh's free space:** the refresh checks no free space before it starts; the measured peak (§BD) is in the `v0.1.1` notes' known limitations and the README. An accepted known limitation for `v0.1.1`; whether to add such a check is the maintainer's product decision, after it.
- **The automatic restart's platforms:** run in a real window only on Linux under KWin through Xwayland (§BD); on Windows and macOS the native smoke tests only resolve the restart's launcher (`restart=apphost`), never refresh or restart. An accepted known limitation (the notes say so) and a requirement of the maintainer's personal test of the candidate (§BH). No screen reader and no physical multi-monitor setup were tried: accepted, optional checks.
