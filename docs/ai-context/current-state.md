### V011-3 Coordinated correction of the autoRun and "startup" terminology

Verified behavior that the wording must describe:
1. Starting the interactive console does not itself run searches.
2. Choosing Search in the interactive console reads the search files each time and runs the searches with `autoRun: true`.
3. Email mode reads the search files once, when it starts, and then runs the `autoRun`-enabled searches every minute.
4. A change to the search files after Email mode started needs a restart of Email mode.
5. The GUI runs no search merely because it starts.
6. In the GUI's Results tab, `autoRun`-enabled searches are selected by default.
7. Searches without `autoRun` run when they are selected manually in the GUI.
8. With no search file, the console creates and runs its example search the next time it searches, not at a generic application start. (Since D65, after `v0.1.1`, only the console's Search does; email mode stops with an error.)

## Open risks

- **The new notification paths met only stand-ins:** the SMTP password's sources (D66) and ntfy (D67) were validated against loopback stand-ins for the SMTP server, ntfy and recreation.gov (§BL, §BM, §BN); no real email or ntfy message was sent by those validations. The `v0.2.0` notes say so. The maintainer reported on 2026-11-22 that the local build of `54d3142` passed the personal test of email, `smtpPasswordFile`, the recipients and ntfy; the results email's new body (D72, §BR) was checked in a browser by the validation, and the maintainer approved it on 2026-11-22 after testing both forms of the email locally ("both look right").
- **TD-49, unresolved:** `Email.yaml` can keep the SMTP password in plain text, and the README's container recipe makes the settings folder writable by every local user. A host-user recipe was verified (D57), but it is tied to open questions #10 and #27 and the choice is the maintainer's. Since D66 (on `master` since PR #103) the password can stay out of `Email.yaml` (a password file, such as a Docker secret, or `CAMPERTRON_EMAIL_PASSWORD`); `smtpPassword` stays the plaintext fallback, and nothing checks the password file's permissions (#45). Since D67 (on `master` since PR #104) `Ntfy.yaml` keeps ntfy's topic, which on a server without access control works like a password, in plain text in the same settings folder; its token is never in a settings file.
  Since D69 (on `master` since PR #106) a `Ntfy.yaml` the GUI creates is owner-only (0600) on Unix, and the editor says when other users can read an existing one. Since D70 (on `master` since PR #107) the GUI recommends the password file over the plain-text password, but never clears or migrates a plain-text password. Since D75 (step 3) the GUI warns when others can read the password or token file, from its metadata only; email mode itself doesn't check.
- **Open question #43, the refresh's free space:** the refresh checks no free space before it starts; the measured peak (§BD) is in the `v0.1.1` notes' known limitations and the README. An accepted known limitation for `v0.1.1`; whether to add such a check is the maintainer's product decision, after it.
- **The automatic restart's platforms:** run in a real window only on Linux under KWin through Xwayland (§BD); on Windows and macOS the native smoke tests only resolve the restart's launcher (`restart=apphost`), never refresh or restart. An accepted known limitation (the notes say so) and a requirement of the maintainer's personal test of the candidate (§BH). No screen reader and no physical multi-monitor setup were tried: accepted, optional checks.
