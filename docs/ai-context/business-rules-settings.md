# Business rules: settings files

Authority: current. This file is the current authority for the rules of Campertron's settings files (`General.yaml`, `Email.yaml` and the search files): the comment-preserving YAML document editor (§13), how settings files are written (§14) and how they are validated and loaded (§15). Section numbers are global and permanent: §1 to §12 are in `business-rules.md`, §16 to §24 in `business-rules-gui.md`, and `business-rules.md` §Section index lists every section; a bare "§N" below names that global section, in whichever file holds it. Roadmap step 9, Phase 4 (2026-11-17) moved these sections here from `business-rules.md` with their numbers and words; lines over 1,000 characters were broken at sentence boundaries (`history/README.md` §Phase 4 migration map).

Legend: **[V]** verified in source · **[I]** inference (usually standard .NET semantics applied to the code) · **[?]** unknown

## 13. YAML document editor (decision D39; `YamlDocument`, internal; used by the `General.yaml` timestamp write since D40 and by the GUI's editing session since D43)
- [V] **Two callers.** Since D40 (CM2) `Yaml.GeneralConfigReplaceYaml` uses `Edit` to change only `lastRidbDataRefresh` after a RIDB refresh and `VerifyCandidate` on the text before writing, on the temporary file read back and on the file read back after the rename (§8 step 11, §14). Since D43 and D44 the GUI's editing session (`ConfigEditSession`, §17 and §18) uses `Analyze` and `Edit` for every edit of `General.yaml`, `Email.yaml` and the search files. Nothing else calls it: the loaders, the sample writers and the search don't. It is pure: no file, console, environment or network access (CM2's file handling is in `ConfigFileReplace`). Under D39 alone nothing called it.
- [V] **Input.** The text of one settings file as a string; offsets are UTF-16 indexes into it (the units of YamlDotNet's `Mark.Index`); lines and columns are 1-based. A leading U+FEFF counts as the file's byte-order mark: it is not parsed (`File.ReadAllText` drops it before the loader sees the text, and YamlDotNet would read it as part of the first key) and stays at the start of the result.
- [V] **Supported documents.** One YAML document whose root is a plain block mapping (no anchor, tag or flow style) of plain or quoted scalar keys, each at the start of its line; directives, `---` and `...` may be present. Values may be anything YAML allows; only those below are edited. Refused (no edit at all):
  malformed text, an empty or comment-only document (Campertron reports such a file as unusable, §9), more than one document, any other root, a complex key (`?`, a collection or block scalar as key), a key that appears twice in one mapping (the loader would silently take the last), a merge key `<<` (the loader rejects it), a tag that is not a standard YAML tag (`tag:yaml.org,2002:`), a lone UTF-16 surrogate, a NEL, line separator or paragraph separator character (YamlDotNet reads them as line breaks), a `#` that can't be told apart from content, a line outside the properties that holds anything but a comment, the opening directives and `---` or the closing `...`, and anything over the editor's limits (1 Mi UTF-16 units, 100,000 parser events, 32 nesting levels, 100 aliases). Malformed text includes what YamlDotNet 16.3.0's scanner rejects with an `InvalidOperationException` (an unclosed flow list followed by another line), refused since D41 instead of thrown.
  Since D41 the same limits bound the settings loader and the validation (§15).
- [V] **Comments.** A `#` at the start of a line or after a space or tab, outside every scalar, alias, anchor, tag and directive (the parser reports where those are), runs to the end of its line; a block scalar's header can end with one. A `#` directly after a quoted value or a flow mapping, which YamlDotNet reads as a comment although YAML requires a space before it, is refused.
- [V] **What belongs to what.** A property's own lines run from its key's line through the line of its value's last character; for a block scalar that is its last content line, not the line break and blank lines the parser's range includes. A list item owns the comment lines directly above it (after the previous item or the key's line, without a blank line between) and its end-of-line comment.
- [V] **Edits** (one per key per call, planned against the text that was passed in and applied together): `SetScalar` replaces a scalar value (an empty value is filled in after the colon) or adds a missing key; `RemoveProperty` removes the property's own lines and nothing else (a comment above the key stays); `SetSequence` replaces a list's items (a block list's lines after the key, or the inside of a flow list's brackets) or creates the list; `SetItem`, `InsertItem`, `RemoveItem` and `ReorderItems` change items of a list whose items are single-line plain or quoted scalars without anchors or tags (a block list with every `-` at the start of its line and the same indentation, nothing but comments and blank lines between the items; or a flow list on one line). A removed or reordered item takes its own comments along; comments after the last item stay where they are. Removing the only item of a block list writes ` []` after the colon (an empty list, not a missing one)
  and removes the list's lines.
- [V] **Locked and kept.** A property whose key or value uses an anchor, an alias or a standard tag is kept exactly and can't be edited or removed. A block scalar (literal or folded) is kept and can be removed but not rewritten; a list with any other kind of item is kept and can be removed but not edited item by item. Keys Campertron does not know (and their sections) are kept exactly and can be removed.
- [V] **Writing a value.** An edited scalar keeps its style (plain, single-quoted, double-quoted) when the new value can be written in it and reads back unchanged; a text value is never written plain as `null`, `~` or empty, which the loader reads as null. A new text value is written plain only when YAML can't read it as anything but text: nothing YAML reads as a null or a boolean (YAML 1.1's `yes`/`no`/`on`/`off`/`y`/`n` included), nothing that starts like a number, a date, an infinity or NaN (a digit, `+`, `-` or `.`), and no character that would change its meaning, otherwise single-quoted (a `'` doubled), otherwise double-quoted (`\\`, `\"`, `\n`, `\r`, `\t`, and `\uXXXX` for other non-printable characters; an astral character is written as itself). Inside a flow list, a plain value also may not hold `:` or `,[]{}`. A null is written `null`.
  Booleans, numbers, dates and enum values are written as Campertron's writer writes them (the same YamlDotNet serializer configuration), in the old value's quotes if it had them.
- [V] **Where new lines go.** A new property goes after the last property's last line (before any comment lines, blank lines and `...` after it), with the top-level keys' indentation, as `key: value`; several in the order of the edits. A new list is a one-line flow sequence `[a, b]` with `, `. A new block list item goes before the item at its index (before that item's comment lines) or after the last item's line, with the first item's indentation and the text between its `-` and its value; a new flow item uses the list's separator (`, ` if it had fewer than two items). New lines end with the document's most frequent line break (ties: LF, then CRLF, then CR; LF in a document without one); a document with mixed line breaks gets the `MixedLineEndings` warning. After a last line without a line break, the break goes before the new line, so the file still ends without one; removing a last line removes the break before it for the same reason.
- [V] **The check before any text is returned.** The text outside the replacements is unchanged; the result parses as a supported document; its keys are the original ones less the removed and plus the inserted, in order; every untouched property's lines are identical; edited values and items read back as written, kept and moved items with their own text and comments; the comments are the original ones less those the losses name; line breaks, the final line break and a leading U+FEFF are kept. Then `Yaml.SettingsDeserializer`, the deserializer of the three settings loaders, loads the result, which must equal the model the caller intends property by property (strings ordinal, doubles bit for bit, dates with their kind, lists item by item, null not equal to empty). Keys the loader rejects (D20) are left out of that load (the same parsed events without them) and named in an `UnknownKeys` warning: the loader still rejects the file until they are removed.
  A failure returns no text and the reason.
- [V] **Losses.** A removed property, item or list reports the exact range it removed from the text, its lines and the comments in it.
- [V] **Diagnostics** hold a code, a severity, the key, a position and fixed text: never a value of the document or an exception's message, so nothing of `Email.yaml` (the SMTP password) reaches one (§12, Secrets).

## 14. Writing settings files (decision D40; `ConfigFileReplace`, `Yaml.GeneralConfigReplaceYaml`, the sample writers)
- [V] **One writer, three kinds of write, nothing else.** Campertron changes an existing settings file only to set `General.yaml`'s refresh timestamp (`ConfigFileReplace.Replace`, §8 step 11), since D43 when the user saves `General.yaml` or `Email.yaml` in the GUI's Settings tab (§17, the same `Replace`) and since D44 when the user saves a search file in the GUI's Searches tab (§18, the same `Replace`); it creates only the sample files (`ConfigFileReplace.Create`: the three at a start, §9, and `General.yaml` or `Email.yaml` from the Settings tab's Create, §17) and, since D44, a search file by the Searches tab's New search or Save As (§18, the same create-only `Create`). The console, the Email loop, the start, the RIDB refresh and the validation never write a search file (§9). The loaders read with `File.ReadAllText`'s decoding, since D41 within the editor's limits (§15).
  A `General.yaml` that no longer exists when the refresh writes its timestamp is not recreated ("General.yaml does not exist." in the refresh's warning; the next start creates the sample): before D40 the in-memory settings were written as a new file.
- [V] **Strict UTF-8.** A file read for editing (`ConfigFileReplace.Read`) must be UTF-8: invalid bytes are refused ("General.yaml is not valid UTF-8"), never replaced with U+FFFD; a UTF-16 or UTF-32 byte-order mark and NUL bytes (UTF-16 text without a mark) are refused, never converted. A UTF-8 byte-order mark is kept: it is decoded as a leading U+FEFF, which the editor keeps without parsing it (§13), and encoded back as `EF BB BF`; a file without one gets none. The new text is encoded, decoded again and compared before anything is written, so the text that is verified is exactly the text that is written. Files over 3,145,731 bytes (the editor's 1 Mi UTF-16 units, 3 bytes each, plus a byte-order mark) are refused.
- [V] **Replacement**, in this order; every failure before the rename leaves the file exactly as it was and removes the temporary files: (1) the editor's result is checked by the caller's check (`YamlDocument.VerifyCandidate` against the bytes read and the intended settings); (2) on Windows, a read-only file and a file with an access control list of its own are refused; (3) a temporary file `<name>.<32 hex digits>.tmp` is created in the directory of the file (of the link's final target) with create-new semantics, owner-only (0600) on Unix, written and flushed to disk (`Flush(true)`: `fsync`, `F_FULLFSYNC` on macOS), then given the file's mode, which is checked (on Windows: its access rules must equal the file's, compared as SDDL, or nothing is renamed); (4) it is read back: exact bytes, and the caller's check again; (5) the file is compared with what was read (§External changes); (6) the backup is written; (7) the file is compared again; (8)
  the temporary file is renamed over the file (`File.Move(…, overwrite: true)`: `rename(2)`; `MoveFileExW` on Windows); (9) the file is read back through the path the caller gave: exact bytes, the caller's check and the mode (on Windows its access rules). A mismatch there (after the rename) is reported: "General.yaml was replaced, but reading it back did not give what was written; the previous content is in General.yaml.bak."
- [V] **Backup.** One rolling `<name>.bak` next to the file (next to the link's target), holding exactly the bytes that were read, the content just before the replacement. It is written like the new file (a temporary file with the source's mode, so never wider, read back) and renamed over the previous backup, never written in place or through a link. If it can't be written or checked, nothing is replaced. It is never loaded (it is not `*.yaml`). There is one backup, no history, and none for a created sample. A backup of `Email.yaml` holds its previous SMTP password (the GUI's Settings tab saves `Email.yaml` since D43, §17); like every backup it gets the source's mode, never a broader one.
- [V] **Permissions.** On Unix the new file and the backup get exactly the file's mode (0600, 0640, 0644, 0400 and 0444 tested); the temporary file is owner-only until it gets that mode, so nothing is readable by others while it is written, and a restrictive file never becomes broader. A file without write permission (0400, 0444) is still replaced, keeping its mode (as before D40). The owner and group, POSIX ACLs and extended attributes are not carried over: the new file belongs to the user that runs Campertron (a container's `app` user, or the host user when the host updates the file). The created samples get the permissions any new file gets in that directory, as before (their content holds no secret). On Windows the new file and the backup take the access rules their folder gives new files; they must equal the file's own exactly (its DACL compared as SDDL, inheritance flags included)
  before anything is renamed, and are checked again after the rename, so a replacement never gets different, possibly broader rules. A file with access rules of its own (explicit entries or a protected DACL) is refused before anything is written, and so is a read-only file; `Hidden`, `System`, `Archive` and `NotContentIndexed` are copied (a hidden file and its backup stay hidden). **Windows facts** [V, CI on `windows-2025`]: a new file in the runner user's LocalApplicationData has only inherited rules (`D:(A;ID;FA;;;SY)(A;ID;FA;;;BA)(A;ID;FA;;;LA)`, not protected, owner BUILTIN\Administrators), so an ordinary settings file is updated with exactly its rules; a file moved in from another folder, and a file whose folder's DACL was rewritten with `SetFileSecurityW`, end up with a protected DACL of explicit copies (`D:P(A;;FA;;;SY)(A;;FA;;;BA)(A;;FA;;;LA)`) and are refused as files with rules of their own.
  The owner is not carried over (on Windows the default owner of a new file, BUILTIN\Administrators for an administrator).
- [V] **Links and special files.** On Unix a chain of symbolic links is followed to its final target (at most 40 links); the temporary file and the backup go to the target's directory, the target is replaced and every link stays a link. A cycle, a dangling link, a directory (also through a link) and an empty or non-regular file (a FIFO, socket or device reports size 0 and is refused before it is opened) are refused. On Windows any reparse point (symbolic link, junction, cloud placeholder) is refused ("…is a symbolic link, junction or other reparse point, which Campertron does not update on Windows; it was left as it is."); a junction with the file's name is refused as a directory and not followed; neither is ever replaced or written through. A created sample never replaces anything: a dangling link of that name counts as an existing file. A backup name that is a link is replaced by the new backup, never written through (Linux and Windows).
- [V] **External changes** (optimistic concurrency, no lock file). The edit is planned on the bytes read at the start of the write, not on the settings loaded when Campertron started, so an edit saved before the write is kept. Before the backup and again right before the rename, the file is read again and compared with what was read: the link chain and each link's text, the final target, the SHA-256 of the bytes, the length, the last write time, the mode, the attributes and, on Windows, the access rules. Any difference stops the update: "General.yaml was changed by another program while Campertron was updating it; it was left as it is and can be updated again." (the next refresh updates it). **Residual race:** an edit saved after the last comparison and before the rename, a window of a few system calls, is lost (an in-place write goes to the replaced file; a program that saves by renaming replaces Campertron's file instead). No portable API offers a conditional rename:
  `File.Replace` checks nothing either, and Linux's `renameat2` is Linux-only and needs native calls.
- [V] **Creation** (the samples, §9): the text is checked to load as the settings it is, written to a temporary file (create-new, default permissions), flushed, read back and checked, then moved into place only if the name is free (`File.Move(…, overwrite: false)`: `link(2)` and `unlink(2)` on Unix, which fails if the name exists; on a file system without hard links .NET copies with create-new semantics instead, which an interruption can leave partial; `MoveFileExW` without replacement on Windows). A name that exists, also one that appears during the write, is never written over; the caller then loads the file that is there.
- [V] **Temporary files and their cleanup.** Names are `<name>.<32 lowercase hex digits>.tmp` and `<name>.bak.<32 lowercase hex digits>.tmp` (a new GUID each time); no loader picks them up (they are not `*.yaml`). A write removes its own temporary files after any failure; a removal that fails is reported without hiding the failure. Files left by a killed process are removed only if they have exactly such a name for the file being written, are regular files (never a link or a directory) in that file's directory, and were last written more than 10 minutes ago (a write takes well under a second; a younger file may belong to a write in another process, for example the GUI and the console starting together): quietly before every write, and with a message ("Removed …, left by an interrupted update of General.yaml") at the start of a RIDB refresh, as before D40. Nothing else in the folder is touched.
- [V] **Messages** name the file and the problem, never a value of the file; the editor's reasons are its codes and fixed texts (§13), and a YAML error from loading the file is reported by its position only. The refresh shows them inside its existing warning (§8 step 11).
- [V] **What is established.** On Linux x64 (btrfs) a process killed at each of 12 points of a replacement and 6 points of a creation (two passes), and at 100 random moments, left the complete old or the complete new file (a creation: no file or the complete file), never a partial or empty one; the next start loaded it, the next write completed, and old temporary files were removed (history/validation/ad-ax_preview.2.md §AE). **Not established:** power loss (the directory is not fsynced after the rename or link, so the old file or no file may reappear), process interruption on Windows (no kill harness ran there), macOS (not run), a file system without hard links for creation. **Windows** [V, the CI job `Windows settings files (CM1 to CM3, CM5, CM6)` (named `Windows settings files (CM1, CM2)` when this was recorded), history/validation/ad-ax_preview.2.md §AE]: the deterministic suites pass natively:
  replacement and creation through `MoveFileExW`, read-backs, backup, CRLF and BOM, strict decoding, external changes (content, deletion, recreation, access rules), injected failures at every step (the file intact, only the operation's own temporary files removed), read-only and hidden files, access rules, a file or backup held open without delete sharing and a file held open for writing (refused cleanly), a locked temporary file (the rename fails, the file is intact, only that temporary file is left and the stale cleanup removes it later), symbolic links and junctions.

## 15. Configuration validation (decision D41; `ConfigValidation`, `ConfigFiles`, the bounded loader)
- [V] **Which file is which** (`ConfigFiles`). `General.yaml` and `Email.yaml` are recognized by an ordinal, case-insensitive comparison of the file name (`EMAIL.yaml` is `Email.yaml` in every culture; a dotted or dotless Turkish I is never a match); every other top-level `*.yaml` file of the settings folder is a search file. The search loader, View Config, the failure messages and the validation all use this rule. Before D41 the search loader lower-cased the path with the current culture, so in Turkish `EMAIL.yaml` became `emaıl.yaml` and was loaded (and refused) as a search file. Discovery is unchanged: `Directory.GetFiles(ConfigPath, "*.yaml", TopDirectoryOnly)` (no `.yml`, no subfolder; case-sensitive on Linux as before); CM2's `<name>.bak` and `<name>.<32 hex>.tmp` never match. On Linux `File.Exists("General.yaml")` stays case-sensitive (a file named `general.yaml` is not read as the general settings and is not a search file either), as before.
- [V] **Bounded loading** (TD-52). Every settings file is read by `Yaml.ReadSettingsText` and `Yaml.LoadSettingsText` within the editor's limits (§13): at most 3,145,731 bytes (`ConfigFileReplace.MaxBytes`, checked from the file's length before it is read, and again while reading), 1,048,576 characters (`YamlDocument.MaxDocumentLength`; a byte-order mark counts as one, as in the editor), 100,000 YAML events, 32 nested collections (the root mapping is level 1) and 100 aliases. YamlDotNet's own parser counts them before anything is deserialized, and the deserializer reads exactly the counted events, so the recursive deserializer never sees a document over a limit. Rationale: settings files are a few hundred characters and 2 levels deep (the sample search is about 700 characters); the limits are the editor's, so the loader, the validation and the editor accept and refuse the same documents at the same boundaries.
  Over a limit the file is "could not be used" with a message that names the limit, never the content ("The file is larger than Campertron reads (at most 1048576 characters and 3145731 bytes).", "The file has more than 100000 YAML events.", "The file nests lists or mappings more than 32 levels deep.", "The file has more than 100 aliases."), exit code 1. **Aliases**: an alias is a reference to the object already read, never a copy, so a document within the alias limit can't expand; YamlDotNet reads an alias to a list or mapping, used where a text is expected, as the text `(Collection)` (no error), which the validation reports as a warning. **Decoding** is unchanged (`File.ReadAllText`'s rules: a byte-order mark selects UTF-8, UTF-16 or UTF-32; otherwise UTF-8 with invalid bytes read as U+FFFD); the validation warns about a file that is not strict UTF-8, which the CM2 writer and the editor can't update.
  **YamlDotNet 16.3.0's scanner** throws `InvalidOperationException` for an unclosed flow list followed by another line; the loader reports it as the `YamlException` ("Exception during deserialization") its deserializer gave before D41, and the editor refuses it as `Malformed` (before D41 the editor threw it).
- [V] **Diagnostics** (`ConfigDiagnostic`): a stable code (below), a severity, the file kind, the file's name (never its folder), the top-level key, the 0-based list item and the 1-based line and column of the key or item (0 when there is none). Messages are fixed text, key names and numbers only: never a value of the file and never an exception's message (YamlDotNet's messages can quote the file); an unknown key of `Email.yaml` is not named (it could be a mistyped value). **Severity**: Error, Campertron refuses the file (for `Email.yaml` with `outputTo: Email`, the Email loop refuses to start); Warning, it uses the file but probably not as intended; Info, a fact. An Error about the YAML (limits, syntax, unknown keys, unreadable values) is exactly what the loader refuses:
  the validation runs the loader's deserializer on the same events, and when the whole document fails it runs each top-level key alone to report every refused key (not in a document with aliases, where only the loader's first error is reported).
- [V] **At run time** the loaders refuse, through `ConfigValidation.ThrowIfRefused` (the failure path of §12, exit 1), only the errors marked "refused at start" below: they would otherwise take a dangerous path. The other errors were refused by the loaders before D41 and keep their messages; warnings and information are not printed (they are for a caller that shows settings: the GUI's Settings and Searches tabs since D43 and D44, §17 and §18).
- [V] **Unknown keys** stay refused (D20; no `IgnoreUnmatchedProperties`): "Campertron can't use the file until the key is removed or corrected". Keys are case-sensitive as the loader reads them (`searchby` is unknown). The editor keeps unknown text when it edits (§13); nothing is deleted or normalized.
- [V] **`General.yaml`**: `outputTo` must be `Console`, `Email` or `HtmlFile` (any case; a defined number such as `1` still loads; an undefined number is an error refused at start); `UnitTest` loads and is reported as test-only (Info), so the GUI's Settings tab keeps it but does not offer it (§17). `refreshRidbDataDayInterval` must be a number; a non-finite one (`.nan`, `.inf`) or one too large to count back from today is an error refused at start when `autoRefresh: true` (with `.nan` the refresh ran on every start, with `.inf` the start failed) and a warning otherwise (the value is unused); 0 or less with `autoRefresh: true` is a warning (the campground data is downloaded and rebuilt on every start). With `autoRefresh: true` a missing `lastRidbDataRefresh` (never refreshes automatically) and one in the future are warnings. Missing settings take their defaults. An empty or comment-only file is an error (as since D37).
- [V] **`Email.yaml`**: what sending needs (`CampsiteConfig.SendWithSmtp`, `CreateResultsEmail`): `smtpServer` not empty, `smtpPort` from 1 to 65535, `sendFromAddress` not empty and accepted by `MailAddress`, `sendToAddressList` with at least one entry and every entry accepted by `MailAddressCollection.Add` (as sending adds it; one entry may hold several comma-separated addresses). These are **errors with `outputTo: Email` and warnings otherwise**, so a file that is incomplete for a mode that doesn't send never stops a start; an empty `Email.yaml` is likewise an error only with `outputTo: Email`. An empty `smtpUsername` or `smtpPassword` is always a warning (a relay may accept mail without signing in). **The Email output's start check** (TD-51): `Load.RunConsoleSearch` calls `Load.CheckEmailOutputSettings` first in its Email branch, before the start line, `Preload` (search files, the example search, the campground data) and any request; it refuses with "Email.yaml could not be used:
  the Email output can't start: {each problem}." (for example "smtpServer is empty. smtpPort is not between 1 and 65535. sendFromAddress is empty. sendToAddressList has no address."), "File: …" and "Fix the file, or delete it and Campertron creates a new one.", exit code 1. Nothing is connected, signed in or sent. Before D41 the sample `Email.yaml` failed only at the first send, after a whole search ("unexpected problem: ArgumentException"). Other output types, `Load.GetConfig` and the GUI do not check it.
- [V] **Search files** (business-rules §1 to §4). A disabled search (`autoRun: false`) is reported (Info) and its problems are only warnings (it never runs). For an enabled search: **errors refused at start**: `searchValue` below 0 for `DaysOut` or `MonthsOut` (the dates ran toward the end of the calendar, about 2.9 million days, then failed), a `DaysOut`/`MonthsOut` window past the last date of the calendar, an empty (null) item of `includeEquipment`, `excludeEquipment`, `includeAttributes`, `excludeAttributes`, `includeCampsiteType` or `excludeCampsiteType` (`FilterData` threw on it during the search; since D51 the search no longer throws, a null value matches nothing, and the item stays refused as the mistake it is), an undefined numeric `searchBy`, and (since D51, in an enabled or a disabled search, like a value the loader can't read) `filterMatching` written as anything but `Exact` or `Contains` or written twice (`FilterMatchingInvalid`, below).
  **Errors the loader already refused**: `StartEndDate` with no date or one date, `Until` with an empty list, an unreadable `StartEndDate` or `Until` date, equal `StartEndDate` dates (§2). **Warnings**: an empty `campgroundID` (the search is skipped), a campground ID that is not a number (whether it is in the campground data is checked when the search runs, by its scope lines, and is CM4's), `totalHumans` missing or not positive, an empty `displayName`, no day of the week, `consecutiveDays` below 1 (no result is shown;
  with `outputTo: Email` its openings are recorded as reported although no email shows them, §4), `searchValue` 0 (today only, never matched), a search reaching 12 months or more (results limited to 12 months out), a missing or empty date list, an empty `StartEndDate`/`Until` date, extra dates, a reversed range, dates in the past, an unreadable `SpecificDates` date (ignored), a date not written `yyyy-MM-dd` (read with the computer's date format), a `yyyy-MM-dd` date the current calendar reads as another day (th-TH, fa-IR), an empty item of `includeSites`/`excludeSites` or a blank item of any filter. Missing (null) lists are no filter. Nothing changes the date generation or the filters.
- [V] **The settings folder** (`ValidateFolder`): `General.yaml` (its `outputTo` decides how `Email.yaml` is judged), `Email.yaml`, each search file, then whether any search runs: no search file is Info (the example is created at the next start); search files of which none is usable and enabled is `NoEnabledSearch` (Warning; with `outputTo: Email` the message says the Email loop checks 0 searches every minute). **Open question #40 stays open**: the loop is unchanged.
- [V] **Codes** (`ConfigCode`; stable, checked by `TheCodes_AreTheDocumentedOnes`):

| Code | File | Severity | Meaning |
|---|---|---|---|
| `FileMissing` | any | Info (Error for `Email.yaml` in Email output, or a file asked for by name) | the file does not exist (created at the next start) |
| `FileTooLarge`, `TooManyEvents`, `TooDeep`, `TooManyAliases` | any | Error | over a loader limit |
| `NotUtf8`, `InvalidUtf8` | any | Warning | UTF-16/32 text, or invalid UTF-8 bytes: read, but the writer and the editor can't update it |
| `Empty` | any | Error (`Email.yaml` outside Email output: Warning) | no settings |
| `Malformed`, `MultipleDocuments`, `NotAMapping` | any | Error | not one YAML mapping of settings |
