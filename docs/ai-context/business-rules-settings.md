# Business rules: settings files

Authority: current. This file is the current authority for the rules of Campertron's settings files (`General.yaml`, `Email.yaml`, `Ntfy.yaml` and the search files): the comment-preserving YAML document editor (§13), how settings files are written (§14), how they are validated and loaded (§15), where the SMTP password comes from (§27, D66), the ntfy notifications with their settings and token (§28, D67) and the monitoring service with the monitoring lock in the settings folder (§29, D90). Section numbers are global and permanent: §1 to §12 are in `business-rules.md`, §16 to §26 in `business-rules-gui.md`, and `business-rules.md` §Section index lists every section; a bare "§N" below names that global section, in whichever file holds it. Roadmap step 9, Phase 4 (2026-11-17) moved these sections here from `business-rules.md` with their numbers and words; lines over 1,000 characters were broken at sentence boundaries (`history/README.md` §Phase 4 migration map).

Legend: **[V]** verified in source · **[I]** inference (usually standard .NET semantics applied to the code) · **[?]** unknown

## 13. YAML document editor (decision D39; `YamlDocument`, internal; used by the `General.yaml` timestamp write since D40 and by the GUI's editing session since D43)
- [V] **Two callers.** Since D40 (CM2) `Yaml.GeneralConfigReplaceYaml` uses `Edit` to change only `lastRidbDataRefresh` after a RIDB refresh and `VerifyCandidate` on the text before writing, on the temporary file read back and on the file read back after the rename (§8 step 11, §14). Since D43 and D44 the GUI's editing session (`ConfigEditSession`, §17 and §18) uses `Analyze` and `Edit` for every edit of `General.yaml`, `Email.yaml` and the search files. Nothing else calls it: the loaders, the sample writers and the search don't. It is pure: no file, console, environment or network access (CM2's file handling is in `ConfigFileReplace`). Under D39 alone nothing called it.
- [V] **Input.** The text of one settings file as a string; offsets are UTF-16 indexes into it (the units of YamlDotNet's `Mark.Index`); lines and columns are 1-based. A leading U+FEFF counts as the file's byte-order mark: it is not parsed (`File.ReadAllText` drops it before the loader sees the text, and YamlDotNet would read it as part of the first key) and stays at the start of the result.
- [V] **Supported documents.** One YAML document whose root is a plain block mapping (no anchor, tag or flow style) of plain or quoted scalar keys, each at the start of its line; directives, `---` and `...` may be present. Values may be anything YAML allows; only those below are edited. Refused (no edit at all):
  malformed text, an empty or comment-only document (Campertron reports such a file as unusable, §9), more than one document, any other root, a complex key (`?`, a collection or block scalar as key), a key that appears twice in one mapping (the loader would silently take the last), a merge key `<<` (the loader rejects it), a tag that is not a standard YAML tag (`tag:yaml.org,2002:`), a lone UTF-16 surrogate, a NEL, line separator or paragraph separator character (YamlDotNet reads them as line breaks), a `#` that can't be told apart from content, a line outside the properties that holds anything but a comment, the opening directives and `---` or the closing `...`, and anything over the editor's limits (1 Mi UTF-16 units, 100,000 parser events, 32 nesting levels, 100 aliases). Malformed text includes what YamlDotNet 16.3.0's scanner rejects with an `InvalidOperationException` (an unclosed flow list followed by another line), refused since D41 instead of thrown.
  Since D41 the same limits bound the settings loader and the validation (§15).
- [V] **Comments.** A `#` at the start of a line or after a space or tab, outside every scalar, alias, anchor, tag and directive (the parser reports where those are), runs to the end of its line; a block scalar's header can end with one. A `#` directly after a quoted value or a flow mapping, which YamlDotNet reads as a comment although YAML requires a space before it, is refused.
- [V] **What belongs to what.** A property's own lines run from its key's line through the line of its value's last character; for a block scalar that is its last content line, not the line break and blank lines the parser's range includes. A list item owns the comment lines directly above it (after the previous item or the key's line, without a blank line between) and its end-of-line comment.
- [V] **Edits** (one per key per call, planned against the text that was passed in and applied together): `SetScalar` replaces a scalar value (an empty value is filled in after the colon) or adds a missing key; `RemoveProperty` removes the property's own lines and nothing else (a comment above the key stays); `SetSequence` replaces a list's items (a block list's lines after the key, or the inside of a flow list's brackets) or creates the list; `SetItem`, `InsertItem`, `RemoveItem` and `ReorderItems` change items of a list whose items are single-line plain or quoted scalars without anchors or tags (a block list with every `-` at the start of its line and the same indentation, nothing but comments and blank lines between the items; or a flow list on one line). A removed or reordered item takes its own comments along; comments after the last item stay where they are. Removing the only item of a block list writes ` []` after the colon (an empty list, not a missing one)
  and removes the list's lines.
- [V] **Locked and kept.** A property whose key or value uses an anchor, an alias or a standard tag is kept exactly and can't be edited or removed. A block scalar (literal or folded) is kept and can be removed but not rewritten; a list with any other kind of item is kept and can be removed but not edited item by item. Keys Campertron does not know (and their sections) are kept exactly and can be removed.
- [V] **Writing a value.** An edited scalar keeps its style (plain, single-quoted, double-quoted) when the new value can be written in it and reads back unchanged; a text value is never written plain as `null`, `~` or empty, which the loader reads as null. A new text value is written plain only when YAML can't read it as anything but text: nothing YAML reads as a null or a boolean (YAML 1.1's `yes`/`no`/`on`/`off`/`y`/`n` included), nothing that starts like a number, a date, an infinity or NaN (a digit, `+`, `-` or `.`), and no character that would change its meaning, otherwise single-quoted (a `'` doubled), otherwise double-quoted (`\\`, `\"`, `\n`, `\r`, `\t`, and `\uXXXX` for other non-printable characters; an astral character is written as itself). Inside a flow list, a plain value also may not hold `:` or `,[]{}`. A null is written `null`.
  Booleans, numbers, dates and enum values are written as Campertron's writer writes them (the same YamlDotNet serializer configuration), in the old value's quotes if it had them.
- [V] **Where new lines go.** A new property goes after the last property's last line (before any comment lines, blank lines and `...` after it), with the top-level keys' indentation, as `key: value`; several in the order of the edits. A new list is a one-line flow sequence `[a, b]` with `, `. A new block list item goes before the item at its index (before that item's comment lines) or after the last item's line, with the first item's indentation and the text between its `-` and its value; a new flow item uses the list's separator (`, ` if it had fewer than two items). New lines end with the document's most frequent line break (ties: LF, then CRLF, then CR; LF in a document without one); a document with mixed line breaks gets the `MixedLineEndings` warning. After a last line without a line break, the break goes before the new line, so the file still ends without one; removing a last line removes the break before it for the same reason.
- [V] **The check before any text is returned.** The text outside the replacements is unchanged; the result parses as a supported document; its keys are the original ones less the removed and plus the inserted, in order; every untouched property's lines are identical; edited values and items read back as written, kept and moved items with their own text and comments; the comments are the original ones less those the losses name; line breaks, the final line break and a leading U+FEFF are kept. Then `Yaml.SettingsDeserializer`, the deserializer of the three settings loaders, loads the result, which must equal the model the caller intends property by property (strings ordinal, doubles bit for bit, dates with their kind, lists item by item, null not equal to empty). Keys the loader rejects (D20) are left out of that load (the same parsed events without them) and named in an `UnknownKeys` warning: the loader still rejects the file until they are removed.
  A failure returns no text and the reason.
- [V] **Losses.** A removed property, item or list reports the exact range it removed from the text, its lines and the comments in it.
- [V] **Diagnostics** hold a code, a severity, the key, a position and fixed text: never a value of the document or an exception's message, so nothing of `Email.yaml` (the SMTP password) reaches one (§12, Secrets).

## 14. Writing settings files (decision D40; `ConfigFileReplace`, `Yaml.GeneralConfigReplaceYaml`, the sample writers)
- [V] **One writer, three kinds of write, nothing else.** Campertron changes an existing settings file only to set `General.yaml`'s refresh timestamp (`ConfigFileReplace.Replace`, §8 step 11), since D43 when the user saves `General.yaml` or `Email.yaml` in the GUI's Settings tab (§17, the same `Replace`; since D69 also `Ntfy.yaml`) and since D44 when the user saves a search file in the GUI's Searches tab (§18, the same `Replace`); it creates only the sample files (`ConfigFileReplace.Create`: the three at a start, §9, and `General.yaml` or `Email.yaml` from the Settings tab's Create, §17; since D69 `Ntfy.yaml` when its editor's Save creates it, owner-only, §17) and, since D44, a search file by the Searches tab's New search or Save As (§18, the same create-only `Create`). The console, the Email loop, the start, the RIDB refresh and the validation never write a search file (§9). The loaders read with `File.ReadAllText`'s decoding, since D41 within the editor's limits (§15).
  A `General.yaml` that no longer exists when the refresh writes its timestamp is not recreated ("General.yaml does not exist." in the refresh's warning; the next start creates the sample): before D40 the in-memory settings were written as a new file.
- [V] **Strict UTF-8.** A file read for editing (`ConfigFileReplace.Read`) must be UTF-8: invalid bytes are refused ("General.yaml is not valid UTF-8"), never replaced with U+FFFD; a UTF-16 or UTF-32 byte-order mark and NUL bytes (UTF-16 text without a mark) are refused, never converted. A UTF-8 byte-order mark is kept: it is decoded as a leading U+FEFF, which the editor keeps without parsing it (§13), and encoded back as `EF BB BF`; a file without one gets none. The new text is encoded, decoded again and compared before anything is written, so the text that is verified is exactly the text that is written. Files over 3,145,731 bytes (the editor's 1 Mi UTF-16 units, 3 bytes each, plus a byte-order mark) are refused.
- [V] **Replacement**, in this order; every failure before the rename leaves the file exactly as it was and removes the temporary files: (1) the editor's result is checked by the caller's check (`YamlDocument.VerifyCandidate` against the bytes read and the intended settings); (2) on Windows, a read-only file and a file with an access control list of its own are refused; (3) a temporary file `<name>.<32 hex digits>.tmp` is created in the directory of the file (of the link's final target) with create-new semantics, owner-only (0600) on Unix, written and flushed to disk (`Flush(true)`: `fsync`, `F_FULLFSYNC` on macOS), then given the file's mode, which is checked (on Windows: its access rules must equal the file's, compared as SDDL, or nothing is renamed); (4) it is read back: exact bytes, and the caller's check again; (5) the file is compared with what was read (§External changes); (6) the backup is written; (7) the file is compared again; (8)
  the temporary file is renamed over the file (`File.Move(…, overwrite: true)`: `rename(2)`; `MoveFileExW` on Windows); (9) the file is read back through the path the caller gave: exact bytes, the caller's check and the mode (on Windows its access rules). A mismatch there (after the rename) is reported: "General.yaml was replaced, but reading it back did not give what was written; the previous content is in General.yaml.bak."
- [V] **Backup.** One rolling `<name>.bak` next to the file (next to the link's target), holding exactly the bytes that were read, the content just before the replacement. It is written like the new file (a temporary file with the source's mode, so never wider, read back) and renamed over the previous backup, never written in place or through a link. If it can't be written or checked, nothing is replaced. It is never loaded (it is not `*.yaml`). There is one backup, no history, and none for a created sample. A backup of `Email.yaml` holds its previous SMTP password (the GUI's Settings tab saves `Email.yaml` since D43, §17); like every backup it gets the source's mode, never a broader one.
- [V] **Permissions.** On Unix the new file and the backup get exactly the file's mode (0600, 0640, 0644, 0400 and 0444 tested); the temporary file is owner-only until it gets that mode, so nothing is readable by others while it is written, and a restrictive file never becomes broader. A file without write permission (0400, 0444) is still replaced, keeping its mode (as before D40). The owner and group, POSIX ACLs and extended attributes are not carried over: the new file belongs to the user that runs Campertron (a container's `app` user, or the host user when the host updates the file). The created samples get the permissions any new file gets in that directory, as before (their content holds no secret). On Windows the new file and the backup take the access rules their folder gives new files; they must equal the file's own exactly (its DACL compared as SDDL, inheritance flags included)
  before anything is renamed, and are checked again after the rename, so a replacement never gets different, possibly broader rules. A file with access rules of its own (explicit entries or a protected DACL) is refused before anything is written, and so is a read-only file; `Hidden`, `System`, `Archive` and `NotContentIndexed` are copied (a hidden file and its backup stay hidden). **Windows facts** [V, CI on `windows-2025`]: a new file in the runner user's LocalApplicationData has only inherited rules (`D:(A;ID;FA;;;SY)(A;ID;FA;;;BA)(A;ID;FA;;;LA)`, not protected, owner BUILTIN\Administrators), so an ordinary settings file is updated with exactly its rules; a file moved in from another folder, and a file whose folder's DACL was rewritten with `SetFileSecurityW`, end up with a protected DACL of explicit copies (`D:P(A;;FA;;;SY)(A;;FA;;;BA)(A;;FA;;;LA)`) and are refused as files with rules of their own.
  The owner is not carried over (on Windows the default owner of a new file, BUILTIN\Administrators for an administrator).
- [V] **Links and special files.** On Unix a chain of symbolic links is followed to its final target (at most 40 links); the temporary file and the backup go to the target's directory, the target is replaced and every link stays a link. A cycle, a dangling link, a directory (also through a link) and an empty or non-regular file (a FIFO, socket or device reports size 0 and is refused before it is opened) are refused. On Windows any reparse point (symbolic link, junction, cloud placeholder) is refused ("…is a symbolic link, junction or other reparse point, which Campertron does not update on Windows; it was left as it is."); a junction with the file's name is refused as a directory and not followed; neither is ever replaced or written through. A created sample never replaces anything: a dangling link of that name counts as an existing file. A backup name that is a link is replaced by the new backup, never written through (Linux and Windows).
- [V] **External changes** (optimistic concurrency, no lock file). The edit is planned on the bytes read at the start of the write, not on the settings loaded when Campertron started, so an edit saved before the write is kept. Before the backup and again right before the rename, the file is read again and compared with what was read: the link chain and each link's text, the final target, the SHA-256 of the bytes, the length, the last write time, the mode, the attributes and, on Windows, the access rules. Any difference stops the update: "General.yaml was changed by another program while Campertron was updating it; it was left as it is and can be updated again." (the next refresh updates it). **Residual race:** an edit saved after the last comparison and before the rename, a window of a few system calls, is lost (an in-place write goes to the replaced file; a program that saves by renaming replaces Campertron's file instead). No portable API offers a conditional rename:
  `File.Replace` checks nothing either, and Linux's `renameat2` is Linux-only and needs native calls.
- [V] **Creation** (the samples, §9): the text is checked to load as the settings it is, written to a temporary file (create-new, default permissions), flushed, read back and checked, then moved into place only if the name is free (`File.Move(…, overwrite: false)`: `link(2)` and `unlink(2)` on Unix, which fails if the name exists; on a file system without hard links .NET copies with create-new semantics instead, which an interruption can leave partial; `MoveFileExW` without replacement on Windows). A name that exists, also one that appears during the write, is never written over; the caller then loads the file that is there.
- [V] **Temporary files and their cleanup.** Names are `<name>.<32 lowercase hex digits>.tmp` and `<name>.bak.<32 lowercase hex digits>.tmp` (a new GUID each time); no loader picks them up (they are not `*.yaml`). A write removes its own temporary files after any failure; a removal that fails is reported without hiding the failure. Files left by a killed process are removed only if they have exactly such a name for the file being written, are regular files (never a link or a directory) in that file's directory, and were last written more than 10 minutes ago (a write takes well under a second; a younger file may belong to a write in another process, for example the GUI and the console starting together): quietly before every write, and with a message ("Removed …, left by an interrupted update of General.yaml") at the start of a RIDB refresh, as before D40. Nothing else in the folder is touched.
- [V] **Messages** name the file and the problem, never a value of the file; the editor's reasons are its codes and fixed texts (§13), and a YAML error from loading the file is reported by its position only. The refresh shows them inside its existing warning (§8 step 11).
- [V] **What is established.** On Linux x64 (btrfs) a process killed at each of 12 points of a replacement and 6 points of a creation (two passes), and at 100 random moments, left the complete old or the complete new file (a creation: no file or the complete file), never a partial or empty one; the next start loaded it, the next write completed, and old temporary files were removed (history/validation/ad-ax_preview.2.md §AE). **Not established:** power loss (the directory is not fsynced after the rename or link, so the old file or no file may reappear), process interruption on Windows (no kill harness ran there), macOS (not run), a file system without hard links for creation. **Windows** [V, the CI job `Windows settings files (CM1 to CM3, CM5, CM6)` (named `Windows settings files (CM1, CM2)` when this was recorded), history/validation/ad-ax_preview.2.md §AE]: the deterministic suites pass natively:
  replacement and creation through `MoveFileExW`, read-backs, backup, CRLF and BOM, strict decoding, external changes (content, deletion, recreation, access rules), injected failures at every step (the file intact, only the operation's own temporary files removed), read-only and hidden files, access rules, a file or backup held open without delete sharing and a file held open for writing (refused cleanly), a locked temporary file (the rename fails, the file is intact, only that temporary file is left and the stale cleanup removes it later), symbolic links and junctions.

## 15. Configuration validation (decision D41; `ConfigValidation`, `ConfigFiles`, the bounded loader)
- [V] **Which file is which** (`ConfigFiles`). `General.yaml`, `Email.yaml` and, since D67, `Ntfy.yaml` are recognized by an ordinal, case-insensitive comparison of the file name (`EMAIL.yaml` is `Email.yaml` in every culture; a dotted or dotless Turkish I is never a match); every other top-level `*.yaml` file of the settings folder is a search file. The search loader, View Config, the failure messages and the validation all use this rule. Before D41
  the search loader lower-cased the path with the current culture, so in Turkish `EMAIL.yaml` became `emaıl.yaml` and was loaded (and refused) as a search file.
  Since D67 `Ntfy.yaml` is no search file, and a search can't be named so ("General.yaml, Email.yaml and Ntfy.yaml are Campertron's settings files, not search files; choose another name."); versions 0.1.1 and older load it as a search file (§28). Discovery is unchanged: `Directory.GetFiles(ConfigPath, "*.yaml", TopDirectoryOnly)` (no `.yml`, no subfolder; case-sensitive on Linux as before); CM2's `<name>.bak` and `<name>.<32 hex>.tmp` never match. On Linux `File.Exists("General.yaml")` stays case-sensitive (a file named `general.yaml` is not read as the general settings and is not a search file either), as before.
- [V] **Bounded loading** (TD-52). Every settings file is read by `Yaml.ReadSettingsText` and `Yaml.LoadSettingsText` within the editor's limits (§13): at most 3,145,731 bytes (`ConfigFileReplace.MaxBytes`, checked from the file's length before it is read, and again while reading), 1,048,576 characters (`YamlDocument.MaxDocumentLength`; a byte-order mark counts as one, as in the editor), 100,000 YAML events, 32 nested collections (the root mapping is level 1) and 100 aliases. YamlDotNet's own parser counts them before anything is deserialized, and the deserializer reads exactly the counted events, so the recursive deserializer never sees a document over a limit. Rationale: settings files are a few hundred characters and 2 levels deep (the sample search is about 700 characters); the limits are the editor's, so the loader, the validation and the editor accept and refuse the same documents at the same boundaries.
  Over a limit the file is "could not be used" with a message that names the limit, never the content ("The file is larger than Campertron reads (at most 1048576 characters and 3145731 bytes).", "The file has more than 100000 YAML events.", "The file nests lists or mappings more than 32 levels deep.", "The file has more than 100 aliases."), exit code 1. **Aliases**: an alias is a reference to the object already read, never a copy, so a document within the alias limit can't expand; YamlDotNet reads an alias to a list or mapping, used where a text is expected, as the text `(Collection)` (no error), which the validation reports as a warning. **Decoding** is unchanged (`File.ReadAllText`'s rules: a byte-order mark selects UTF-8, UTF-16 or UTF-32; otherwise UTF-8 with invalid bytes read as U+FFFD); the validation warns about a file that is not strict UTF-8, which the CM2 writer and the editor can't update.
  **YamlDotNet 16.3.0's scanner** throws `InvalidOperationException` for an unclosed flow list followed by another line; the loader reports it as the `YamlException` ("Exception during deserialization") its deserializer gave before D41, and the editor refuses it as `Malformed` (before D41 the editor threw it).
- [V] **Diagnostics** (`ConfigDiagnostic`): a stable code (below), a severity, the file kind, the file's name (never its folder), the top-level key, the 0-based list item and the 1-based line and column of the key or item (0 when there is none). Messages are fixed text, key names and numbers only: never a value of the file and never an exception's message (YamlDotNet's messages can quote the file); an unknown key of `Email.yaml` or, since D67, `Ntfy.yaml` is not named (it could be a mistyped value, a password or a topic). **Severity**: Error, Campertron refuses the file (for `Email.yaml` with `outputTo: Email`, the Email loop refuses to start); Warning, it uses the file but probably not as intended; Info, a fact. An Error about the YAML (limits, syntax, unknown keys, unreadable values) is exactly what the loader refuses:
  the validation runs the loader's deserializer on the same events, and when the whole document fails it runs each top-level key alone to report every refused key (not in a document with aliases, where only the loader's first error is reported).
- [V] **At run time** the loaders refuse, through `ConfigValidation.ThrowIfRefused` (the failure path of §12, exit 1), only the errors marked "refused at start" below: they would otherwise take a dangerous path. The other errors were refused by the loaders before D41 and keep their messages; warnings and information are not printed (they are for a caller that shows settings: the GUI's Settings and Searches tabs since D43 and D44, §17 and §18).
- [V] **Unknown keys** stay refused (D20; no `IgnoreUnmatchedProperties`): "Campertron can't use the file until the key is removed or corrected". Keys are case-sensitive as the loader reads them (`searchby` is unknown). The editor keeps unknown text when it edits (§13); nothing is deleted or normalized.
- [V] **`General.yaml`**: `outputTo` must be `Console`, `Email`, `HtmlFile` or, since D67, `Ntfy` ("outputTo must be one of Console, Email, HtmlFile or Ntfy."; any case; a defined number such as `1` still loads; an undefined number is an error refused at start);
  `UnitTest` loads and is reported as test-only (Info), so the GUI's Settings tab keeps it but does not offer it (§17). `refreshRidbDataDayInterval` must be a number; a non-finite one (`.nan`, `.inf`) or one too large to count back from today is an error refused at start when `autoRefresh: true` (with `.nan` the refresh ran on every start, with `.inf` the start failed) and a warning otherwise (the value is unused); 0 or less with `autoRefresh: true` is a warning (the campground data is downloaded and rebuilt on every start). With `autoRefresh: true` a missing `lastRidbDataRefresh` (never refreshes automatically) and one in the future are warnings. Missing settings take their defaults. An empty or comment-only file is an error (as since D37).
- [V] **`Email.yaml`**: what sending needs (`CampsiteConfig.SendWithSmtp`, `CreateResultsEmail`): `smtpServer` not empty, `smtpPort` from 1 to 65535, `sendFromAddress` not empty and accepted by `MailAddress`, `sendToAddressList` with at least one entry and every entry accepted by `MailAddressCollection.Add` (as sending adds it; one entry may hold several comma-separated addresses). A missing value (an empty server or sender, port 0, no recipient, an empty recipient item) is an **error with `outputTo: Email` and a warning otherwise**, so a file that is incomplete for a mode that doesn't send never stops a start; an empty `Email.yaml` is likewise an error only with `outputTo: Email`. Since D71 a value written but invalid (a port outside 1 to 65535 other than 0, a sender or recipient entry that is no address, an unusable `smtpPasswordFile`) is an **error in every output**, so the GUI never saves one; the start is unchanged (it checks `Email.yaml` only for `outputTo: Email`).
  Since D71 an empty recipient item is `RecipientEmpty` ("sendToAddressList item N is empty."), an entry with an address an earlier entry has is `RecipientDuplicate` (a warning, compared without case), and a list without a non-empty entry is `RecipientsMissing` ("sendToAddressList has no address: add at least one recipient."). An empty `smtpUsername` or `smtpPassword` is always a warning (a relay may accept mail without signing in). **The Email output's start check** (TD-51): `Load.RunConsoleSearch` calls `Load.CheckEmailOutputSettings` first in its Email branch, before the start line, `Preload` (search files, the example search, the campground data) and any request; it refuses with "Email.yaml could not be used:
  Since D66 a written `smtpPasswordFile` counts as a password, and its form is checked (§27: the codes `PasswordFilePathEmpty`, `PasswordFilePathNotAbsolute`, `PasswordFileSet`, `PasswordNotUsed`; the file itself is never opened by the validation).
  the Email output can't start: {each problem}." (for example "smtpServer is empty. smtpPort is not between 1 and 65535. sendFromAddress is empty. sendToAddressList has no address: add at least one recipient."), "File: …" and, since D71, "Fix the file in a text editor or in the GUI (Settings > Campertron > Email.yaml). Don't delete it to start over: Campertron would create an empty one, without your email settings or smtpPasswordFile." (before: "Fix the file, or delete it and Campertron creates a new one.", which would lose the settings and `smtpPasswordFile`), exit code 1. Nothing is connected, signed in or sent. Before D41 the sample `Email.yaml` failed only at the first send, after a whole search ("unexpected problem: ArgumentException"). Other output types, `Load.GetConfig` and the GUI do not check it.
- [V] **The monitoring's start check of a settings folder** (D71; `ConfigValidation.MonitoringStartErrors(folder, outputTo, now)`): the errors the unattended monitoring's start would refuse in the folder's `Email.yaml` and `Ntfy.yaml`, read as the loaders read them: for `outputTo: Email`, `Email.yaml`'s as `ThrowIfEmailOutputRefused` judges them (a missing or unreadable file too); for `outputTo: Email` or `Ntfy`, `Ntfy.yaml`'s as `ThrowIfNtfyOutputRefused` judges them (nothing while ntfy is off and not required; a missing file only for `Ntfy`, with the start's words). Nothing for another outputTo. It reads no password or token source and no search file (the search files are the next check's, D73). `MonitoringStartCheckTests` shows it finds errors exactly when the start refuses, in the start's words. The GUI's General form uses it before it saves outputTo (business-rules-gui §17).
- [V] **The monitoring's search check** (D73, open question #48 answered; `ConfigValidation.MonitoringSearchErrors(folder, outputTo, editedText)`): for `outputTo: Email` or `Ntfy` (nothing for another outputTo), the start's own check of the search files: `Load.LoadMonitoringSearches`, the one function email and ntfy mode's start calls (`Yaml.CampertronConfigGetConfigs` without the example search, then D64's `CheckSearchesToCheck`), here with no warning about a search's dates written and nothing created.
  `MonitoringNoSearch` (Error) when the start would have no search to check: "Campertron needs at least one enabled search before it can monitor. ## 27. SMTP password sources (decision D66; `SmtpPassword`, `EmailConfig.SmtpPasswordFile`, email mode's start)
- [V] **The sources, in order** (`SmtpPassword.SelectedSource`): (1) the file `smtpPasswordFile` names, when `Email.yaml` has that key with any value (the setter records the key even for `smtpPasswordFile:`, `~` or `null`, which YAML reads as null); (2) `CAMPERTRON_EMAIL_PASSWORD`, when it is set, even to nothing; (3) `smtpPassword`, exactly as before D66 (null or empty signs in with an empty password; §15's `CredentialsMissing` stays a warning). The first configured source is the only one used: a problem of that source is never a reason to use a later one.
- [V] **The file** (`SmtpPassword.ReadFile`): the path must be fully qualified (`Path.IsPathFullyQualified`: `/run/secrets/smtp_password`, `C:\Secrets\pw.txt`; never `pw`, `./pw`, `~/pw`, `\pw` or `C:pw` on Windows); nothing is resolved against the working directory or another folder. A folder (also through a link) is `FileIsFolder`; a missing file, a missing folder on the path or a link to nothing is `FileMissing`.
  Links are followed to the final file (`ResolveLinkTarget(true)`), as Docker and Kubernetes secrets use them. A file that reports no length is `FileEmpty` and is never opened: a FIFO or a device reports 0, and opening a FIFO waits for a writer. More than 4,096 bytes is `FileTooLarge`; the read is bounded to 4,097 bytes, so a file that grows is caught too. Permissions or a sharing lock are `FileNotReadable` (the exception's message, which names the path, is never shown).
  The file is opened read-only with `FileShare.Read`; its folder is never listed, and nothing is written, copied, moved, deleted or chmodded. The buffer is cleared after the read.
- [V] **The content** (`SmtpPassword.FromFileBytes`): a leading UTF-8 byte-order mark is `FileHasByteOrderMark`; a NUL byte is `FileHasNul` (UTF-16 text has them); bytes that are not strict UTF-8 are `FileNotUtf8`. One terminal LF, or CR LF, is removed; nothing else (spaces and tabs are part of the password). Only a line break is `FileOnlyLineBreak`; any other CR or LF (a second line, a lone CR) is `FileHasLineBreak`.
- [V] **The variable** (`SmtpPassword.FromEnvironment`): used as it is, nothing trimmed; set but empty is `EnvironmentEmpty`, a CR or LF is `EnvironmentHasLineBreak`. [I] On Windows a variable set to an empty string is removed, so `EnvironmentEmpty` occurs on Unix only.
- [V] **When it is read:** only by email mode, once, at its start (`Load.SmtpPasswordStartProblem` → `SmtpPassword.ResolveOnce`; the start is the monitoring service's since D90, §29), after the `Email.yaml` check (§15, which refuses an unusable path first) and the start line, and before the search files and D64's gate. The password is kept on the `EmailConfig` (`ResolvedPassword`, never serialized) for every send of the process: a changed file or variable needs a restart (the load-once policy). The console's Search, HtmlFile and `outputTo: UnitTest` starts, View Config (§24), the GUI (§17; since D70 it edits `smtpPasswordFile`'s path, never the file) and the validation never read the file or the variable.
- [V] **A problem stops email mode at its start:** one error on standard error, `Error: email mode can't start: the SMTP password can't be used: <problem>`, then what to do and the line "Campertron never uses another password source when the one configured can't be used (the order is smtpPasswordFile, then CAMPERTRON_EMAIL_PASSWORD, then smtpPassword)."; the console exits with code 1. Nothing is searched, requested, sent or written; standard output has only the start line. The words name keys and the variable only: never the password, the file's path or the variable's value.
- [V] **The send** (`CampsiteConfig.SmtpCredential`): the user name of `Email.yaml` and the start's password; a send without it (no start) resolves once through `SmtpPassword.ForSending`, and a problem throws `SmtpPasswordException` before any connection (reported with the start's words).
- [V] **A failure report** (`ConsoleUi.ReportFailure(Exception, EmailConfig)`, called by `CampertronConsole`'s `Program.Main` since D66) hides every password the process knows (the resolved one and `smtpPassword`, the longest first) as `[hidden]`, and a failed send says where to check the password: "Check the server, port and user name in Email.yaml, and the password in the file that smtpPasswordFile names." or "… in CAMPERTRON_EMAIL_PASSWORD.", or the former "Check the server, port, user name and password in Email.yaml." for `smtpPassword`.
- [V] **The problems** (`SmtpPasswordProblem`, in this order): `FilePathEmpty`, `FilePathNotAbsolute`, `FileMissing`, `FileIsFolder`, `FileNotReadable`, `FileEmpty`, `FileTooLarge`, `FileHasByteOrderMark`, `FileNotUtf8`, `FileHasNul`, `FileOnlyLineBreak`, `FileHasLineBreak`, `EnvironmentEmpty`, `EnvironmentHasLineBreak` (`SmtpPasswordTests` pins the list and that each has its own words).
- [V] **Compatibility:** no migration: an `Email.yaml` without `smtpPasswordFile` and a process without the variable behave as before, and nothing rewrites `Email.yaml`. The sample `Email.yaml` keeps its bytes (`OmitNull`, D40). [V] Versions 0.1.1 and older refuse an `Email.yaml` with `smtpPasswordFile` (an unknown key, D20), so a rollback removes that line first (the README says so).
- [V] **What it protects** (the README's threat model): with the password in a file or the variable, `Email.yaml` and the settings folder no longer hold it. It is not encrypted: whoever can read the file, the process's environment (for example `docker inspect` of a container started with `-e`) or its memory, or administers the computer, can read it. Campertron keeps it in memory as plain text while it runs and checks no permission of the password file (TD-49, open question #45).
- [V] **The GUI's check of the file** (D75; business-rules-gui §17): metadata only, through `SecretFileCheck` (its `Locate` is the start of `SecretFile.Read`, shared): a missing file, a folder, an unreadable, empty or too large file is an error at `smtpPasswordFile`'s field while outputTo is Email (shown or saved), else a warning, and a file others can read a warning (chmod 600); none blocks Save. The file is never opened and the variable never read; email mode's own reading is unchanged. Since D77 General.yaml's outputTo says the same while Email is chosen or saved, as an error (others can read it: a warning), never blocking Save.

## 28. ntfy notifications (decision D67; `Notifications`, `NtfyConfig`, `NtfyEndpoint`, `NtfyToken`, `NtfyPublisher`, `SecretFile`, the unattended monitoring's start)
- [V] **Providers and modes** (`Notifications`). The unattended monitoring is `outputTo: Email` or, since D67, `outputTo: Ntfy` (`IsMonitoring`); both run the loop of §5 to §7 and D64's gate. Email is enabled by `outputTo: Email`; ntfy by `Ntfy.yaml`'s `enabled: true` in either mode (`NtfyEnabled`). So: email only (`Email` without `Ntfy.yaml`, or with `enabled: false`); ntfy only (`Ntfy`); both (`Email` and `enabled: true`); neither: the console's Search, HtmlFile and the GUI, which need no provider and never read `Ntfy.yaml` (`Load.GetConfig` loads it only for the monitoring).
  `outputTo: Ntfy` without an enabled ntfy has no provider and stops at the start. A disabled provider is not usable; an enabled one that can't be used stops the start and is never skipped. The messages name the mode "email mode" (`outputTo: Email`, with or without ntfy) or "ntfy mode" (`ModeName`); the start line's output is `Email`, `Email and ntfy` or `Ntfy` (`OutputText`).
- [V] **`Ntfy.yaml`** (`NtfyConfig`, `ConfigFiles.NtfyFileName`; read by `Yaml.NtfyConfigGetConfig` through the bounded loader, §15, null when it does not exist). It has no sample: the start, the console and the monitoring never create or write it. Since D69 the GUI's `Ntfy.yaml` editor (business-rules-gui §17) creates it, owner-only, when the user saves a new one, and edits it with a backup through §14's writer; before D69 nothing in Campertron wrote it. Keys (`NtfyConfigTests` pins them): `enabled` (default false), `server`, `topic`, `tokenFile` (written only when set, `OmitNull`; the setter records the key even with an empty value), `priority` (`NtfyPriority`: `Min`, `Low`, `Default`, `High`, `Max` in any case, or 1 to 5; default `Default`), `tags` (a list; without the key the message carries `tent`) and `timeoutSeconds` (default 30).
  Unknown keys are refused (D20) and not named. There is no key for the token itself.
- [V] **Its validation** (`ConfigValidation.CheckNtfy`; §15's codes): a missing value (server, topic, an empty tag) is an error while `enabled: true` or with `outputTo: Ntfy` (`Required`) and a warning otherwise; since D71 a value written but invalid is an error also while ntfy is off (the start's `ThrowIfNtfyOutputRefused` still looks at the file only when ntfy is on or required, so it refuses what it refused before); `NtfyDisabled` is Info, or an Error with `outputTo: Ntfy`; an empty file is an Error with `outputTo: Ntfy`, else a Warning. `server` (`NtfyEndpoint.TryServer`) must be an absolute `http` or `https` address of a host with an optional port and nothing else: no user name or password, no path but a single `/`, no query or fragment, no blank or control character, `?`, `#` or `@`.
  The raw text is checked before .NET normalizes it (so `%2e%2e` is refused), and the publish uses a root rebuilt from the scheme, host and port. A server under a path (`https://example.net/ntfy`) is refused: whether ntfy's JSON publishing works there was not verified, and a path could hold a topic. `http` is `NtfyServerNotHttps`, a warning only (it is allowed, as a deliberate choice). `topic` must match ntfy's rule, `^[-_A-Za-z0-9]{1,64}$`; each tag `^[A-Za-z0-9_+-]{1,64}$`, and the tags together at most 512 bytes (ntfy's limit, counted with a comma between tags).
  `timeoutSeconds` must be from 1 to 120. `tokenFile` must not be empty and must be fully qualified (`NtfyTokenFilePathEmpty`, `NtfyTokenFilePathNotAbsolute`); `NtfyTokenFileSet` is Info. The validation never contacts a server and never opens the token file. `ValidateNtfyFile` gives the GUI's General form the file's diagnostics, or null without the file; since D69 the `Ntfy.yaml` editor validates its edited text with `ValidateNtfy`, and its form refuses a timeout outside 1 to 120 also while ntfy is off.
- [V] **The start** (since D90 the service's, §29), in this order: `Email.yaml`'s check when email is enabled (§15); `Ntfy.yaml`'s check when ntfy is enabled or required (`CheckNtfyOutputSettings` → `ThrowIfNtfyOutputRefused`: "Ntfy.yaml could not be used: the ntfy output can't start: {each problem}", the file and, since D71, "Fix the file in a text editor or in the GUI (Settings > Campertron > Ntfy.yaml). To turn ntfy off, set enabled: false (with outputTo: Ntfy, choose another outputTo too); don't delete the file, which holds the server, the topic and tokenFile." (before: "Fix the file, or delete it to turn ntfy off …", which would lose its settings); with `outputTo: Ntfy` and no file: "The file does not exist, and outputTo: Ntfy needs it with enabled: true, the server and the topic." and "Create it in the settings folder with enabled: true, the server and the topic (see the README), or choose another outputTo."); the start line; the SMTP password when email is enabled (§27);
  ntfy's token when ntfy is enabled (`Load.NtfyTokenStartProblem`); then the search files and D64's gate, whose words name the mode; then, since D90, the monitoring lock (§29).
  Each refusal is one error and exit code 1, before anything is searched, requested or sent. Nothing is published to test ntfy. A `Ntfy.yaml` that can't be loaded (YAML, unknown keys) stops the monitoring's start with the loader's error, also when ntfy would be off.
- [V] **The token** (`NtfyToken`). Sources in order (`SelectedSource`): (1) the file `tokenFile` names, when `Ntfy.yaml` has the key (any value); (2) `CAMPERTRON_NTFY_TOKEN`, when it is set, even to nothing; (3) none: the publish carries no `Authorization` header. Only the first configured source is used; a problem of it never leads to a later source or to publishing without the token.
  The file is read by `SecretFile`, the reader D66's password file uses since D67 (`SmtpPassword` delegates to it, unchanged: §27's file and content rules, 4,096 bytes, strict UTF-8 without a byte-order mark or NUL, one terminal LF or CR LF removed). A token must be visible ASCII (U+0021 to U+007E): anything else is `FileInvalidCharacters` or `EnvironmentInvalidCharacters`; the variable is used as it is, and set but empty is `EnvironmentEmpty`.
  The problems (`NtfyTokenProblem`, in order): `FilePathEmpty`, `FilePathNotAbsolute`, `FileMissing`, `FileIsFolder`, `FileNotReadable`, `FileEmpty`, `FileTooLarge`, `FileHasByteOrderMark`, `FileNotUtf8`, `FileHasNul`, `FileOnlyLineBreak`, `FileHasLineBreak`, `FileInvalidCharacters`, `EnvironmentEmpty`, `EnvironmentInvalidCharacters`.
  It is resolved once, at the start (`ResolveOnce`), and kept on `NtfyConfig.ResolvedToken` (internal, never serialized) for every publish of the process: a changed file or variable needs a restart. A problem stops the start: "Error: ntfy mode can't start: the ntfy access token can't be used: <problem>" ("email mode" with `outputTo: Email`), what to do, and "Campertron never publishes without the token, or with another token source, when the one configured can't be used (the order is tokenFile, then CAMPERTRON_NTFY_TOKEN, then none)."; exit code 1.
- [V] **The publish** (`NtfyPublisher.Publish`; ntfy's JSON publishing, docs.ntfy.sh/publish/, checked 2026-11-22): one `POST` of a JSON object (`topic`, `title`, `message`, `priority` as a number, `tags`, `click`) with `Content-Type: application/json` to the server's root, never to a topic URL; `Authorization: Bearer <token>` only when a token was resolved.
  No token, topic, user name or password is ever put in a URL (ntfy's `?auth=` is not used). The handler follows no redirect (`AllowAutoRedirect = false`, so `Authorization` never reaches another address) and keeps no cookies; `HttpClient.Timeout` is `timeoutSeconds`; the system's proxy settings apply as for every .NET request. A delivery is a 2xx answer whose body (read up to 64 KiB) is a JSON object with a non-empty string `id`, ntfy's message; anything else fails. Nothing is retried within a check.
- [V] **Failures** (`NtfyFailure`, `NtfyException`): a 3xx answer is `Redirect`; 401 `Unauthorized`; 403 `Forbidden`; 404 `NotFound`; 413 `TooLarge`; 429 `RateLimited`; other 4xx `ClientError`; 5xx `ServerError`; any other status `UnexpectedStatus`; a 2xx without ntfy's message `MalformedResponse`; and `Dns`, `ConnectionRefused`, `Network`, `Tls`, `Timeout`, `Canceled`, `ServerInvalid`, `Unexpected`.
  The report (`NtfyPublisher.Describe`) is "the ntfy notification could not be sent: <reason>" (with the status, or the timeout's seconds) and one line of what to check; it never holds the topic, the server, the token or an exception's message. ntfy's documentation lists no error codes, so this mapping is Campertron's.
- [V] **The message** (`NtfyMessages.Build`), for a search whose results show at least one opening (`ResultsHtml`'s model, as the email's page; otherwise no message): the title "N new opening(s) at <campground name, or campground ID, or the campground>", at most 200 characters (cut with "…"); a plain-text body: the search's name, the campground and park, "N openings at N sites on N dates." (", in runs of at least N nights" for `consecutiveDays` above 1), a blank line and one line per date, "ddd yyyy-MM-dd: <sites>" (invariant culture, by date, at most ten sites by name, then "and N more").
  The body stays below 3,800 bytes (ntfy turns a message over 4,096 bytes into an attachment): the dates that don't fit become "…and N more dates; recreation.gov shows them all.". The click URL is `https://www.recreation.gov/camping/campgrounds/<ID>` when the ID is digits, else none; priority and tags are `Ntfy.yaml`'s. Nothing of the settings files is sent.
- [V] **One check, both providers** (`Notifications.Deliver`, called by `Load.OutputResults`): the check's single search run and result set go to every enabled provider. Its line counts both ("Check 1: 1 search, 7 new openings; sending 1 email and 1 ntfy notification.", `Load.CheckText`). For each search in order: its email (one per search of a check with news, as before, D57), unless an email of this check failed; its ntfy message, if it has one, unless a publish of this check failed ("ntfy notification sent: <search> (N openings)").
  The search's openings are recorded in `Camp.History` once any provider delivered them (the maintainer's decision of 2026-11-22; ER-03): a provider that failed misses what the other delivered, and nothing is sent twice by a provider. When no provider failed, `Load.ReportResults` then records the run's other hits too (§5: those no message shows, such as a search with `consecutiveDays` below 1, which never gets an ntfy message). After the check, one failure is thrown as it is (a failed email exactly as before D67) and both as a `NotificationException` ("the notifications could not be sent: both the email and the ntfy notification failed.", then an "Email: …" and an "ntfy: …" line); the run ends with exit code 1 (§12), and a restart reports only what no provider delivered.
- [V] **Secrets in output.** The topic counts as a secret (ntfy's FAQ: without access control the topic is the password). `ConsoleUi.ReportFailure(Exception, CampertronInternalConfig)`, which `Program.Main` calls since D67, hides the SMTP passwords (§27) and ntfy's token and topic (`NtfyToken.KnownSecrets`) as `[hidden]`; no message, diagnostic or log line holds the topic, the token, the token file's path or the server. View Config and Current configuration (business-rules-gui §24) never read `Ntfy.yaml`; the GUI shows its values only in its `Ntfy.yaml` editor (since D69; elsewhere only its state) and never the token (business-rules-gui §17).
- [V] **Not supported** (D67): basic authentication (a user name and password; ntfy supports it, but a token covers the need without another secret), a server under a path, attachments, delays, actions, Markdown, icons, ntfy's email forwarding, a server, topic or token per search, subscriptions, creating accounts or topics, running a server, a test message, reloading or watching the files. Other providers (webhooks, Gotify, Apprise, Discord, Telegram, Pushover) are not implemented; their version is unassigned since D68 (before it, a tentative 0.2.x; `current-state.md`).
- [V] **Compatibility.** Without `Ntfy.yaml`, every mode behaves as before D67, and `outputTo: Email`'s emails, lines and failures are unchanged. Versions 0.1.1 and older load `Ntfy.yaml` as a search file (their console stops with its error, their GUI lists it with problems) and refuse `outputTo: Ntfy`; a rollback moves the file out of the settings folder first (the README says so).
- [V] **The GUI's check of the token file** (D75; business-rules-gui §17): as `smtpPasswordFile`'s (§27), at `tokenFile`'s field in the `Ntfy.yaml` editor: an error while ntfy is in use (on, shown or saved, with outputTo Email or Ntfy, shown or saved), else a warning; never blocking Save; the setting's and the file's names only (the topic stays a secret, ER-34). Since D77 also at General.yaml's outputTo (Email or Ntfy, while ntfy is on) and in its ntfy line.

## 29. The monitoring service and the monitoring lock (decisions D83, D90; `MonitoringService`, `MonitoringConsole`, `MonitoringLock`, `MonitoringRun`)
The unattended monitoring (`outputTo: Email` or `Ntfy`, §28) runs as a library service since D90; the console's email and ntfy mode are its adapter. What a check finds, sends and records is unchanged and stays where it was: §5 (the history), §6 (the gate and the email), §7 (the retries), §9 and §15 (the start's checks), §27 and §28 (the secrets and the providers).
- [V] **The service** (`MonitoringService`, an instance; nothing static, so two services share nothing but the files they are given). `Start(settings, hostToken)` checks, in this order: outputTo is a monitoring; `Email.yaml` (email enabled) and `Ntfy.yaml` (ntfy enabled or required), which throw as before; then the event `Starting`; the SMTP password and ntfy's token from their sources, once (§27, §28); the search files, read once and never created, with D64's gate (`Load.LoadMonitoringSearches`); the monitoring lock (below); each campground's cache (`Load.PrepareRun`); then the event `SearchesLoaded`.
  It returns a `MonitoringStartResult`: started, or the problem (`AlreadyRunning`, `NotMonitoring`, `StartFailed` with the exception that was thrown, `SmtpPassword`, `NtfyToken`, `NoSearchToCheck`, `LockHeld`, `LockUnavailable`) and its words. A start that is refused has searched, sent, written and created nothing, the lock's file included.
- [V] **The checks** run on a thread of the service's own: before each one `Load.RequireSearchesToCheck`, from the second on `Load.RegenerateSearchDates`; the searches in `Parallel.ForEach`, as before; then the report (`MonitoringService.ReportCheck`: the gate `Load.HasUnreportedEntries`, the event `CheckReported`, and with news `Notifications.Deliver`, the remaining hits' markers and the event `DeliveriesFinished`); then the run's collections are cleared and the service waits `CheckInterval`, one minute. The search files are not read again.
- [V] **Stop** asks the run to end and waits until it has. The wait between two checks ends at once. A check that is searching ends at its next checkpoint (before a request, between months, in the waits before a retry, after heavy traffic and for another search's month, and after the searches) and nothing of it is sent or recorded: its openings are found again by the next start. A request that is in flight is not interrupted.
  A check that is sending is never interrupted: every notification of the check is sent and recorded first. Stop saves nothing, and nothing starts the monitoring again by itself. A host's token stops it the same way, without waiting; a stop asked for from one of the service's own events only asks.
- [V] **Restart** is Stop and Start with the settings given: the search files are read again, and every start counts its checks from 1.
- [V] **A check that fails** ends the run as `Failed`, with the exception and the console's words for it (`ConsoleUi.DescribeFailure`, the secrets removed) in the status: a failed send (D76: what was not delivered is not recorded; what another provider delivered is, §28), an unexpected problem, or a blocked request when the host gave no handling of its own (`MonitoringBlockedException`; the other searches of the check stop instead of asking again). The lock is released. A new start is a new monitoring.
- [V] **The status** (`GetStatus`, a snapshot): the state (`NotStarted`, `Starting`, `Checking`, `Sending`, `Waiting`, `Stopped`, `Failed`), whether a stop was asked for, when the run started, how many searches it checks, the number and the time of the last check it reported, when the next one starts, the last error, the last start's result, and whether the search files changed since the start: a search file added or removed, or one whose size or time of writing changed (metadata only; the contents are never read for it, and no other file counts).
- [V] **The events** (`MonitoringOptions.Report`, in order, on the thread they happen on): `Starting`, `Status` (a campground's details are prepared), `Warning` (a search's dates; a request that is tried again), `SearchesLoaded`, `CheckReported` (number, searches, new openings, the emails and ntfy notifications it sends), `EmailSent`, `NtfySent`, `DeliveriesFinished`. The service itself writes nothing to a console, waits for no key and ends no process.
- [V] **The console** (`MonitoringConsole.Run`, called by `Load.RunConsoleSearch` for a monitoring's outputTo) starts one service and waits for its end, which only a failure brings: it writes each event through `ConsoleUi` with the calls the loop made before D90 (the start line, "Running N searches:", "Check N: …", "Email sent: …", "ntfy notification sent: …", "Next check …", the warnings on standard error), writes a refused start's words as one error and returns false (exit code 1), and rethrows a start's or a check's exception unchanged for `Program.Main` (exit code 1).
  A blocked request keeps the console's answer (`AvailabilityApi.ConsoleBlocked`: the error, the five-minute wait, exit code 1, §7). The console never stops or restarts its monitoring; its process ends instead.
- [V] **The monitoring lock** (`MonitoringLock`): the file `Campertron.monitoring.lock` in the settings folder, opened without sharing by a start that passed every other check and kept open until the run has ended. A second monitoring of the same settings folder, in this process or another one (a console, a container that uses the same folder), is refused; another settings folder has its own lock.
  The lock is the open handle, not the file: it ends when the monitoring closes it or its process ends in any way, so there is no stale lock to detect or clear, and a lock file that was left behind, whatever it holds, locks nothing. The file is never deleted, nothing is written to it or read from it, and it is created for its owner only (0600 on Unix); an existing file keeps its rights. It is no settings file and no search file, and it is separate from the refresh lock and the repair lock (§8): a refresh and a monitoring do not lock each other out.
- [V] **The lock's words** (one error after the start line, the mode named, exit code 1): "email mode can't start: another Campertron is already monitoring this settings folder." with "Only one monitoring runs for a settings folder, so that every opening is notified once. Stop the other one first (another CampertronConsole in email or ntfy mode, or a container that uses the same settings folder), or give this one its own settings folder." and "Nothing was searched or sent.";
  for a settings folder that can't hold the file (missing, read-only, not this user's): "email mode can't start: the monitoring's lock file can't be created or opened in the settings folder." with "Campertron keeps the file Campertron.monitoring.lock open there while it monitors, so that only one monitoring runs for a settings folder. Let the user that runs Campertron write to the settings folder." and "Nothing was searched or sent.". No path and no value.
- [V] **Limits.** On Linux and macOS the lock is the advisory lock .NET takes for an open without sharing (`flock`): it holds between Campertron's processes on one host, also across containers that use the same folder, but not on a file system without such locks (some network shares). Windows refuses the second open itself; since §CD CI's Windows job runs the lock's tests natively, with a second process. Not run on macOS (open question #49). The lock does not make the campground cache safe for two processes (TD-54).
- [V] **Not implemented yet** (D83, D79's later pull requests): web mode's use of the service (its own start, Start, Stop and Restart from the browser, the monitoring paused by a refresh). Nothing but the console uses the service today.
- [V] **Tests:** `MonitoringServiceTests`, `MonitoringLockTests`, `MonitoringConsoleTests` (`test-coverage.md`); the console's behavior is pinned, as before, by `EmailStartTests`, `NtfyStartTests`, `SmtpPasswordEmailModeTests`, `EmailOutputValidationTests`, `MonitoringSearchCheckTests`, `NotificationDeliveryTests`, `EmailDeliveryHistoryTests` and `NotificationHistoryTests`.
