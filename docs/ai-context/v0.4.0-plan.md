# `v0.4.0` plan: application parity and settings mobility (Phase 0 audit)

Authority: current for the `v0.4.0` implementation plan that the Phase 0 audit proposes: the architecture inventory, the console, desktop GUI and web audits, the threat model, the test plan, the phases with their dependencies and sizes, the risks and the release fit. The maintainer accepted the audit and its phases with D115 (Phase 1, 2026-11-26; §Phase 1's decisions), which answers open questions #56 to #58, and phase 2 is done (D116, §DI); the plan authorizes nothing by itself: each phase starts only with its own approval (D114). What each application does today is `v0.4.0-capability-matrix.md`'s; the open questions still open are `open-questions.md`'s (#59 to #64); the records are §DG (the audit), §DH (Phase 1) and §DI (phase 2).

## Scope and method

`v0.4.0` is D114: a formal capability-matrix audit first (this file and the matrix), then separate reviewed pull requests through shared services, validation, words and business rules. It extends D76's Beam settings and Export and Import and D95's rule that every application sends and receives.
The audit read the entry points (`CampertronConsole/Program.cs`, `Menu.cs`, `Load.RunConsole*`, `MonitoringConsole`, `WebArguments`, `CampertronGUI/Program.cs`, `MainWindow.axaml`, `CampertronWebHost`, the pages), the shared form layer (`CampertronLibrary/function/Forms`), the services and the tests of the three test projects. It changed no product file.
Not looked at (data safety): any real Campertron data, the candidate and personal-test packages, their data and container folders.

## Principles every phase keeps

- **One rule, three adapters.** A capability's rules, words, validation, secrets, backups, version checks and state live once in `CampertronLibrary` (the form layer or a host-neutral service, ER-37); each application is an adapter that shows them. A phase that writes a rule or a sentence in one application's project is refused by review and by the controls below.
- **Platform-appropriate, not identical.** The console stays terminal-oriented: line-oriented prompts and numbered choices, no full-screen terminal UI framework (D114 point 4; a later decision could change that). The GUI keeps its tabs and responsive layout (ER-42); the web UI its pages, sessions and security (ER-38).
- **The Full UI rule moves with D114.** `CLAUDE.md` §Product rules lists the monitoring's control and the guided setup's orchestration as web-only; D114 (the maintainer's approval) gives both to the desktop GUI and gives the console every capability of point 4. The phase that implements each one updates the rule's text, ER-09's tab list, ER-21's menu contract and the console-to-GUI map in the same pull request. Desktop-only and web-only exceptions that D114 does not touch stay (the theme's storage, the automatic restart, window placement, opening folders; the sign-in and password).
- **Scope lock** (`CLAUDE.md` §Product rules): D114 is the approved scope; anything else found on the way (for example a free-space check, open question #43, or a one-shot search, open question #39) is recorded, not added.
- **Unchanged contracts:** the send-failure behavior (D76), `Camp.History` as runtime state (ER-03; never transferred, D114 point 2), the search semantics (ER-01, ER-11, ER-20, ER-22), the safe writers (ER-18), the secret sources (ER-33, ER-34) and the release safeguards (ER-25 to ER-31).

## Phase 1's decisions (D115)

The maintainer's decisions of 2026-11-26, after Microsoft 365 Copilot's review of the audit (the complete record is D115's; §DH). They bind every phase below.
- **The phases:** the audit and its 25 phases are accepted. No phases are combined merely to reduce the number of pull requests; adjacent phases may be combined later only when repository evidence shows that keeping them apart would create artificial duplication and the combined pull request stays focused and reviewable.
- **The console's entry** (open question #56): `--interactive` explicitly opens the guided terminal workflow. The no-argument operation stays unchanged: its outputTo rule, its monitoring, its exit codes and its four-item menu with the menu's bytes (ER-21). Interactive mode is never inferred from a terminal, so scripts and containers never enter it unexpectedly. Help and the answer to an invalid argument must eventually describe it clearly (phase 6; today any other argument is ignored [V]); room is kept for future targeted non-interactive commands.
- **The console's search engine** (open question #57): the console moves to `CampsiteSearch`, only after the new console workflow is implemented, validated and personally tested (PT1). The no-argument monitoring, the search semantics and the manual results' history rules are preserved: a manual search never notifies and never reads, writes, suppresses or re-arms `Camp.History`. The old engine stays until the replacement passes PT1 and is retired in phase 14, a focused phase of its own with regression coverage and negative controls.
  [V] The old engine is the no-argument menu Search's loop (`Load.RunConsoleSearch(config, true)`), its only caller; its per-search operation, `AvailabilityApi.GetAvailabilitiesByCampground`, is also `CampsiteSearch`'s and the monitoring service's and stays. Phase 14's pull request names every difference a user of the no-argument menu would see (a block is one error, a five-minute wait and exit code 1 today [V]; the waits; the requests) for the maintainer's review against the entry's rule.
- **The desktop GUI's monitoring lifetime** (open question #58): it starts only on the user's explicit action (unless a later approved setting adds a desktop auto-start); it is the application's, not the Monitoring view's, and goes on when the user leaves the view; it coordinates with a search, a refresh, the settings, the shutdown, the locks and cancellation through shared rules.
  Closing the window while it runs says so clearly and lets the user cancel the close, or stop the monitoring and exit; no monitoring work is left orphaned after the GUI's shutdown; the notification-failure behavior is kept (D76). It resumes only after an automatic restart that an already approved operation requires (D62's, after a refresh), and only if it was running immediately before it. No operating-system login start, background service or persistence across an ordinary exit in `v0.4.0` (D93's service is `v0.7.0`'s).
- **The release fit:** the complete scope stays in `v0.4.0` for now; Beam stays last; the checkpoint after phase 20 is mandatory, open question #64 is decided there, and evidence that Beam would compromise security, release quality or reasonable reviewability stops the work for options. No version number is assigned.
- **Still open:** #59, #60 and #63 before phase 15; #61, #62 and #64 before phase 20. No cryptographic primitive, no Beam transport detail beyond this plan's recommendation, and nothing about Beam leaving `v0.4.0` is decided.

## Console audit

**Today** [V]: `CampertronConsole` reads its arguments only for `--version` and web mode's `--web`, `--listen`, `--port` and `--healthcheck` (`WebArguments`); every other argument is ignored. Without them, `General.yaml`'s outputTo decides: Console or HtmlFile opens the four-item menu (Search, Refresh Ridb Data (slow), View Config, Exit), which needs a terminal on standard input and output and refuses in a container; Email or Ntfy starts the unattended monitoring (`MonitoringConsole`).
Ctrl+C ends the process with "Stopped." and the terminal restored (`ConsoleUi.InstallTerminalHandlers`). The menu redraws by cursor arithmetic (ER-21) and nests one menu per Enter action (TD-12). Settings, search files, notifications and the monitoring's control need a text editor or another application (the matrix's File-only cells).

**Contracts to keep** [V]: `--version`'s output and touching nothing (business-rules §11); web mode's arguments and words; `--healthcheck`; the no-argument start and its outputTo rule; exit codes (0, and 1 with one error on standard error: a refused start, no search to check, a held lock, a block, a failure); standard output for results and lines, standard error for errors; no value of `Email.yaml` or `Ntfy.yaml` printed (ER-13); the container's start (email or ntfy mode, or `--web`); the menu's refusal without a terminal.

**Interaction model** (accepted with the audit, D115; the exact words, items and layout are phase 6's, reviewed there):
- **Entry** (D115): the no-argument start stays exactly as it is, its four-item menu for outputTo Console and HtmlFile included. `--interactive` opens the interactive console for any outputTo (so a user whose outputTo is Email or Ntfy can still configure and control it); it needs a terminal and is refused without one in the menu's words (exit code 1); a terminal alone never opens it. Scripts that pass no new argument see no change.
- **Main menu** (`--interactive`'s only): numbered items with the arrow selection: Search now, Search files, Settings, Campgrounds, Campground data, Monitoring, Guided setup, Transfer settings (Export, Import, Beam), Current configuration, Help, Exit. The no-argument menu keeps its items and bytes (ER-21, `MenuKeysTests`); phase 6 adds the new menu beside it and extends the rule to it.
- **Screens:** line-oriented, never cursor arithmetic below the main menu, so a dumb terminal, `NO_COLOR`, a screen reader and a recorded session read the same text; every state in words (the severity word before a message, ER-35's rule for text); the width from `ConsoleUi.Detect` (20 to 500 columns, wrapped by `ConsoleUi.Wrap`).
- **Forms:** the shared forms hosted on the console's thread through a console `FormHost`; each field kind has one prompt: text, a masked secret, yes or no, a numbered choice, a list (add, remove, move), the campground picker (find, then choose by number; by FacilityID, ER-08), a filter selector (numbered values, find, select all shown, clear shown; ER-23). Each form offers Check changes (the preview), Save, Revert, Reload and its tests, with the form's own words.
- **Secrets:** typed without echo when standard input is a terminal (`Console.ReadKey` with interception); refused, with the password file recommended, when it is not; never printed, never in a preview, never in history; Replace and Remove as the web UI's (D82). The ntfy topic is shown only on request in the ntfy form (ER-34), since a terminal is easily seen (shoulder-surfing).
- **Ctrl+C and Esc:** inside an interactive operation (a search, a refresh before its cache step, a monitoring screen, a receive, a send) the first Ctrl+C or Esc cancels that operation by its own rule and returns to the menu; at the menu, or a second Ctrl+C, ends the process as today. The unattended email or ntfy mode keeps today's Ctrl+C.
- **Confirmations:** an action that writes, sends, starts or applies asks once with No as the default (Save, Apply, Start the monitoring, Send a test, Refresh, Beam send); the words are the form's.
- **Tests:** the console adapters are driven through a seam (scripted input lines and keys, the `ConsoleUi` lines captured without control sequences) and judged by the shared words and the files written, not by terminal snapshots; `ConsoleOutputGoldenTests` keeps pinning the renderers only; a pseudo-terminal run (`maintainer-procedures.md` §The console on a pseudo-terminal) checks the keys and the masked entry once per phase.
- **No framework:** no terminal UI package is added (D114 point 4); the prompts are a small set of `ConsoleUi` functions.

**Gap by D114 point 4** (each a phase below): guided setup (phase 12); settings and their management (phases 6, 7); search-file management (phase 8); the lookup (phase 9); searches now and their results (phase 10); email and ntfy with their tests and the random topic (phase 7); the refresh with progress and cancellation (phase 9); a redacted current configuration (exists; phase 6 adds the status summary); the monitoring's controls (phase 11); Beam's send and receive (phase 22); Export and Import (phase 17).

## Web audit

The web UI is the behavioral reference for the monitoring and the guided setup, not a template for the other two.
- **Flows that define shared rules** (move to the library or stay there): the guided setup's status and step order (D100), the monitoring's start, stop and restart rules, its refresh pause and resume, its block hold and last check (D83, D98), the test notification (D86, D88), the settings and searches forms (D94, D96), the results run's start and outcome (D97).
- **Web-session-specific** (stay in `CampertronWeb`): workspaces per session, revisions and tokens, the start page's lead per session, the live script and its observation rule (ER-43), Razor forms, rate limits, antiforgery, the theme cookie.
- **Words to share:** most of `WebMonitoringWording` (what the monitoring does, its states, its failures in fixed words; since phase 2 `MonitoringWording`, D116) and the guided setup's step words (already shared); `WebSystemWording`'s restart words stay the web UI's (D61, D84).
- **Security that stays web-only:** the sign-in and password, the setup code, Host and Origin checks, CSP, rate limits, trusted proxies, fixed safe errors, the session's idle time.
- **Beam in a web host** (phase 23): a receive is a signed-in POST that opens a one-use receiver for a fixed time; the receiver ends with the transfer, the timeout, Cancel, a sign-out or web mode's stop; how a sender reaches it (the web UI's own port behind its checks, or another port) is open question #61. A send is the web host's outbound connection on the user's POST.
- **Export and Import in a browser** (phase 19): an export is a POST that answers with a download (`Content-Disposition: attachment`, `no-store`, never kept on the server); an import is a multipart POST within the host's limits (`MaxRequestBytes` 1 MiB, 256 form values, 64 KiB a value [V]), read in memory, never written to disk before it passed its checks, previewed on a page with the preview's revision, applied by a second POST; antiforgery, its own rate limit, the CSP unchanged.
- **Ownership:** the monitoring and the results run stay the web UI's; an apply needs the same rule as in the other applications (§Settings transfer).
- **No secrets in HTML, logs or downloads:** a secret is never put in a page; a download that holds an opted-in secret is protected (open question #63).

## Settings transfer (Export and Import, Beam): the shared model to design

Phase 15 decides these with the maintainer's answers; they are the audit's recommendations, grounded in the rules named.
- **Content, allow-listed:** `General.yaml`, `Email.yaml`, `Ntfy.yaml`, the search files, and `Web.yaml` as open question #59 decides. Never: `Camp.History` (D114 point 2), `RecreationDotOrg.db` with its backups, staging and locks, the cache, `Web.password`, `Web.keys`, `*.bak`, `*.tmp`, the monitoring lock, `preferences.json`, the restart handoff, the theme cookie.
- **Host-specific values:** `smtpPasswordFile` and `tokenFile` hold the sender's absolute paths and are never carried (the receiver keeps its own, or gets a protected file of an opted-in secret, open question #60); `lastRidbDataRefresh` is the receiver's own; outputTo is carried but named in the preview, because it decides whether the receiver monitors (open question #59).
- **Secrets:** the SMTP password (whatever its source: `smtpPasswordFile`, `CAMPERTRON_EMAIL_PASSWORD`, `smtpPassword`), ntfy's token, and the ntfy topic as #59 decides. Left out by default; each opted into one by one; an option disabled with a note when the secret is not in use or comes from an environment variable (D76); written only to protected files on the receiver (open question #60); never shown, logged or put in a preview.
- **Text, not re-serialization:** a file travels as its text; a key left out (a secret, a path) is removed by `YamlDocument`'s text-range edit (ER-16), never by serializing the model again (ER-14).
- **Apply pipeline (one for Import and Beam):** read within limits (count of files, bytes per file, `YamlDocument.MaxDocumentLength`, names by `SearchFileName`'s rules and `ConfigFiles.MaxNameLength`) → the format's version and the sender's Campertron version checked → each file through the bounded loader and `ConfigValidation` → the preview (each file added, replaced or unchanged, with its lines; never a secret) → an explicit confirmation → a refusal while an editor of this process holds an unsaved change to a file it would change, or a file changed since the preview → a backup set of every file it changes (owner-only, secrets left out as D111 and D112) → each file through `ConfigFileReplace` → each opted-in secret through the protected writer → a read-back → the result in fixed words. A failure after the first write restores the set.
- **Search files:** added or replaced by their listed name; the receiver's other search files never deleted (ER-14); a name the receiver's platform refuses is refused in the preview.
- **The monitoring and an apply:** an apply never stops or restarts a running monitoring by itself; it says that the monitoring reads the settings again only at its next start, as an editor's save does today (business-rules-settings §35). [I] the rule follows the editors'; phase 15 confirms it.
- **Compatibility:** a package format version (a whole number); a newer format refused; an older one read by its own reader; a file the receiver's loader refuses (an unknown key of a newer Campertron) refused by name, never dropped silently.

## Security and threat model

Each threat with the control required before its phase can merge; "design" marks a control that phase 15 or phase 20 decides.

| Threat | Applies to | Required control |
|---|---|---|
| Beam discovery | Beam | no broadcast or announcement by default; the receiver shows an address the user gives the sender (open question #61) |
| Pairing-code guessing | Beam | an offline guess must not be possible from a recorded transfer; online guesses bounded (attempts per receiver, then off); the code's strength set by the design (open question #62) |
| Replay | Beam | each receiver's code and keys are one-use and bound to that session; a recorded transfer can't be applied again |
| Man in the middle | Beam | the key agreement is authenticated by the pairing code (or a compared code); no trust on first use without it (design) |
| Eavesdropping | Beam | authenticated encryption of everything after the first message, the package's names included |
| Receiver exposure | Beam | off by default; enabled only by the user; listens only while enabled; the web UI's own checks still apply to its pages |
| Receiver timeout | Beam | a fixed timeout ends it, with or without a sender |
| Unauthorized re-enablement | Beam | a receiver is enabled only by a user action in that application, never by a setting, a start, a request or a remote message |
| Multiple senders | Beam | the first authenticated sender owns the session; others refused; a failed pairing counts toward the limit |
| Duplicate apply | Beam, Import | a preview is applied once (its revision); a second confirmation of it is refused |
| Corrupt transfer | Beam, Import | authenticated encryption or an integrity check refuses it before the preview |
| Truncated transfer | Beam, Import | the package's declared size and file list checked; nothing applied from a partial one |
| Downgrade | Beam | the format and protocol versions are inside the authenticated part; no fallback to a weaker version |
| Version mismatch | Beam, Import | the compatibility check before the preview, in fixed words |
| Package tampering | Import | integrity protection when the package is protected (open question #63); every file validated as any file is |
| Secret inclusion | both | out by default, each opted in, the option disabled with a note when it doesn't apply (D76) |
| Secret display | both | never shown in a preview, a status, a page or a line (ER-10, ER-33, ER-34) |
| Secret logging | both | fixed words only; no exception's message, server text or value (ER-13, ER-38) |
| Secret persistence | both | an opted-in secret written only to a protected file; nothing kept in memory after the apply or the send (ER-39's pattern) |
| Secret backup | both | the backup set never holds a secret a transfer replaced or removed (D111, D112) |
| Secret-file permissions | both | owner-only on Unix (0600) and Windows (an ACL for the user alone); refused where that can't be set (design) |
| Temporary files | both | none outside the settings folder; created owner-only, removed on every end (`ConfigFileReplace`'s pattern) |
| Cancellation | both | before the apply nothing is written; during it, the set is restored |
| Crash recovery | both | the set restores at the next start, or the files are each complete (`ConfigFileReplace`); the design names which |
| Export package theft | Export | a package with a secret is protected at rest (open question #63); the preview says what a package holds |
| Malicious paths | Import, Beam | names only, never paths: one level, the search-file name rules, no separator, no drive, no `..` |
| Zip slip and path traversal | Import, Beam | a package format with no paths, or one read only through a name allow-list; never extracted to disk |
| Symbolic links | Import, Beam | none in a package; the writer's link rules (`ConfigFileReplace`) for the receiver's own files |
| Oversized packages | Import, Beam | limits on the count of files, each file's bytes and the whole; the web host's request limit too |
| Resource exhaustion | Import, Beam | bounded parsing (`YamlDocument`'s limits), bounded compression ratio if compressed, one transfer at a time |
| Cross-platform paths | both | names normalized by one rule; a name one platform refuses is refused everywhere |
| Unknown fields | both | refused by the receiver's loader as any file would be, by name |
| Future-version fields | both | the format version gates them; never silently dropped |
| `Camp.History` inclusion | both | never in the allow-list; a control test |
| Web upload security | Import (web) | antiforgery, the request limits, a rate limit, in memory only, CSP unchanged, fixed error pages |
| Console shoulder-surfing | console | masked entry; the topic and the pairing code shown only when needed; the code's screen cleared after use where a terminal allows |
| Clipboard exposure | GUI, web | no secret is ever put on the clipboard; the pairing code may be (it is one-use) |
| Browser download exposure | Export (web) | `no-store`, an attachment, a protected package when it holds a secret, never cached by the server |

**Design decisions that need a focused phase before code:** the transport and reachability (open question #61), the pairing and encryption approach and whether a new package may be added (#62), the export's protection at rest (#63), the content model (#59), the secrets' destination (#60), the package format and its limits, the apply's crash recovery, and the Windows owner-only rules for a new secret file.
**Beam needs its own protocol and threat-model decision pull request before any code** (phase 20): it adds the first network listener to the desktop GUI and the interactive console and a new one to the web UI, with cryptography chosen for its properties, not by preference; it is reviewed and approved before phase 21.

## Test and validation plan

**Every implementation phase** runs what the repository requires: `dotnet build` with no new warning identity, the three test projects (with `XDG_DATA_HOME` isolated), `test-release-policy.sh`, `check-docs.sh` and `test-check-docs.sh`, the vulnerability scan, natural CI, and the Release dry run that starts by itself for a change of a shipped input (the product folders, the project files, the Dockerfile, the release policy, `assets/icon/`; D105), not for tests or documents alone; never a dispatch or a rerun.
Each adds the tests of its own area:
- **Unit:** the shared service or form; failure injection through the existing seams (`ConfigFileReplace`'s steps, the transports' stand-ins); negative controls in a scratch copy, each recorded.
- **Console:** the scripted seam (input, `ConsoleUi` lines, files written); exit codes; non-terminal refusals; masked entry on a pseudo-terminal.
- **GUI:** the headless suites (`CampertronGUITests`), the smoke test's lines (`--smoke-test`, `check_gui_smoke_report`) for a new tab, `ResponsiveLayoutTests`, real windows under a nested session for the screenshots.
- **Web:** the page tests, the accessibility tests, the live-page tests where an operation goes on (ER-43), the browser suites; the request checks for every new POST.
- **Integration and security:** loopback only (`NoLiveNetwork`); Beam between two processes on loopback; the stand-ins for recreation.gov, email and ntfy; no real server, recipient or topic.
- **Cross-platform:** the Windows job's class list extended to each new writer, lock or secret-file test (open questions #49, #50); macOS stays unrun natively (a known limitation).
- **Container:** the image's start unchanged; a receiver or an import in web mode through the image's checks (D102's smoke test) when phase 23 lands.
- **Accessibility and responsive:** the GUI's names and keyboard order, the web UI's axe checks at 320 and 1280 pixels in both themes, the console's text without color.

### Controls against superficial parity

Each control is a test or a check a later phase adds and the parity audit (phase 24) runs again; the matrix's cells are re-derived from the code, never copied.

| Superficial parity | Control that catches it |
|---|---|
| A service exists but one application has no workflow | the matrix re-derived from each application's entry points; an IL-reference test per adapter that it calls the shared form or service (`IlReferences`, `GuiTestHelpers`' scanner, a console one) |
| Create works, edit, revert or reload doesn't | one parity scenario (create, edit, save, reload, revert, a conflict) run against each application's adapter |
| Validation differs between applications | the same invalid file through the three adapters gives the same diagnostics (the layer's) |
| A secret leaks in one interface | a canary secret in every scenario, searched for in every line, page, preview, log and backup |
| One application is send-only or receive-only | a Beam scenario for each of the six ordered pairs of applications, both directions |
| The console depends on files the GUI made | the console's scenarios start from an empty settings folder |
| The web UI depends on the console's setup | the web scenarios use only the web UI's pages after the setup code |
| The desktop depends on the web guided setup | the GUI's guided setup scenarios start from an empty folder, no web process |
| One application can't recover from a failure | failure injection at each write of an apply, in each application |
| One application silently loses settings | a byte comparison of untouched files and of the backup set after every scenario |
| One application writes different YAML | the same edit through three adapters gives identical bytes |
| One application bypasses the backup rules | the backup's absence or its secret is a failure in every writer test |
| Different words for the same decision | the words are the layer's constants; IL checks that no adapter defines its own |
| `Camp.History` transfers | a `Camp.History` in every sender's folder; the package and the receiver checked for it |
| An export holds a secret by default | the default export of a folder with every secret, searched for each |
| A Beam receiver stays enabled | the receiver's listener checked closed after a transfer, a timeout, a cancel and a failure |
| A pairing code can be replayed | a recorded transfer replayed against a new receiver and the same one: refused |
| An import writes outside the settings folder | crafted names (`..`, separators, drives, links, reserved names) refused; the folder's file list compared |

## Risks

- **Size:** 25 phases, three of them design-only, three high-risk; `v0.4.0` is the largest release so far. Mitigated by the order (shared rules first) and by the checkpoint of open question #64.
- **Refactoring released behavior:** phases 2 and 3 move `v0.3.0`'s web code; the web suites must pass unchanged, and a byte-for-byte check of the pages before and after is part of their records.
- **A desktop process that monitors:** a sleeping laptop, a closed window, two GUIs and a web mode on one folder (the lock), a refresh's restart; D115 sets the lifetime (§Phase 1's decisions).
- **The console's contracts:** ER-21's menu bytes, the golden tests, `--version`, the exit codes and the container's start; D115 keeps the no-argument operation unchanged, so phase 6 adds `--interactive` and its own menu beside it, and phase 14 is the one phase that moves the no-argument menu's Search, with its differences named for review.
- **Cryptography and a new listener:** the first network listener in the GUI and the interactive console; Windows and macOS firewalls ask the user (an [I] expectation, not run); a design error is a security defect in all three applications.
- **Secrets written by Campertron for the first time:** no writer exists today; Windows owner-only rules have no test yet.
- **Platform coverage:** the web UI and its browser checks run on Linux only (open questions #50, #52); the lock on macOS not run (#49); the GUI not looked at on Windows or macOS (#29).
- **TD-54:** two processes building one campground's cache at once stays a known limitation; more hosts that search make it likelier.

## Recommended decisions

Decisions that follow from approved rules, recorded for review and accepted with the audit by D115; each phase applies its part, and its review checks it:
- The extractions (phases 2 and 3) move behavior without changing it, proven by the web suites, as D91 did for the forms.
- The console hosts the shared forms through a console `FormHost` (ER-37's "a form's thread only through `FormHost`"), with no terminal framework (D114 point 4).
- The desktop GUI's Monitoring tab hosts both Status and Guided setup; the guided setup uses the window's own forms (ER-37, ER-40).
- Export and Import precede Beam; one transfer package and one apply pipeline serve both (D114 point 2).
- `Camp.History`, the database, the cache, `Web.password`, `Web.keys`, backups, locks and preferences are never in a package (D114 point 2, ER-03, ER-38).
- Search files are added or replaced by name and never deleted by an import (ER-14); a file travels as its text (ER-16).

## Release fit

[I] The approved scope is coherent as one release: every part serves D114's two aims (each application can do what the others do, and settings move safely), and the parity work is a prerequisite of a three-way transfer (an application can't apply a package it can't edit and validate).
It is also the largest and riskiest scope so far, and Beam alone brings a protocol, cryptography and listeners into all three applications. The audit does not split it: it orders Beam last and proposes a checkpoint after Beam's design phase (open question #64), where the maintainer decides with the design in hand whether Beam stays in `v0.4.0`. No version number is assigned to anything here.
D115 keeps the complete scope in `v0.4.0` for now, Beam last, and makes the checkpoint mandatory: if the evidence then shows that Beam would compromise security, release quality or reasonable reviewability, the work stops and the maintainer is given options.
