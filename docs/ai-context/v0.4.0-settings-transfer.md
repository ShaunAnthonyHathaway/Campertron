# `v0.4.0` settings transfer: the design of Export and Import (phase 15)

Authority: current for the design of `v0.4.0`'s settings transfer: the package, its plain and encrypted envelopes, what it carries and never carries, the secrets, the receiver's apply pipeline with its lock, backup set, write order and rollback, the permission rules, what each application's adapter may do, the threat model, the tests and negative controls phases 16a and 16b owe, and the boundaries of those phases and of Beam.
It records the maintainer's decision D132 (2026-11-28), which answers open questions #59, #60 and #63, as a design; it holds no code and authorizes none. Since D133 (`v0.4.0`'s phase 16a, §EE) its package part is implemented in `CampertronLibrary/function/Transfer`, with no settings write and no UI (business-rules-settings §44, ER-46, the authority for what is implemented); since D134 (phase 16b, §EF) its apply in `function/Transfer/Apply`, with no UI (business-rules-settings §45, ER-47); the adapters (17 to 19) are not. Each phase that implements a part starts only with its own approval (D114), and that phase moves its part into the business rules, the engineering rules and the test inventory, where the behavior's authority then is.

Legend: **[V]** verified in the code at `5487906` · **[D]** decided by D132 · **[B]** bound by this design from the repository's evidence, named beside it, for review · **[O]** open (§Open items that do not block phase 16a).

## Purpose and non-goals

**Purpose.** A user moves Campertron's saved settings and search files from one settings folder to another: Export writes one package file; Import reads one, shows what it would change, and applies it only after the user confirms. Each of the three applications (the interactive console, the desktop GUI, the web UI) exports and imports by itself, and a package one of them wrote is read by every one of them, on every platform (D95, D114).

**Non-goals** in `v0.4.0`:
- Beam: no transport, discovery, pairing or receiver is designed here (§Deferred Beam boundary).
- No noninteractive Export or Import command [D]; open question #66 is not decided and does not block this design.
- No backup or restore of an installation (`v0.8.0`, D103), no migration between versions, no synchronization, no merge of two search files' contents.
- No transfer of state: `Camp.History`, the campground data, the cache, the web UI's access settings, password, keys and sessions, preferences (§Never-carried files and state).
- No secure deletion, no operating-system credential vault, no encryption of the settings folder (TD-49 stays as it is).
- No recovery at a start: no application's start reads, replays or undoes anything of an import [D].

D132 in short [D]: (1) the ntfy topic is a secret, opted in one by one; (2) `Web.yaml` is never transferred; (3) outputTo is transferred, named, and applied only when the result passes the readiness checks of D71 and D73, `General.yaml` last, and an import never starts the monitoring; (4) an opted-in password or token is written to a new owner-only file of Campertron's in the receiver's settings folder, never to the plain-text `smtpPassword`; (5) a secret that comes only from an environment variable is not offered and its value never read; (6) a package with a secret is encrypted (PBKDF2-SHA256, 600,000 iterations, AES-GCM, the header authenticated), a package without one may be readable with a SHA-256 checksum that detects corruption only; (7) Export and Import exist only in the interactive console, the desktop GUI and the web UI; (8) phase 16 is two phases, 16a and 16b; (9) no startup recovery journal.

## Shared package model

One model for Export, Import and, later, Beam [D]: a **package** is one UTF-8 JSON document, never compressed, never an archive, at most 1 MiB, that holds a short header and a list of **entries**. An entry is a kind, a name, a text and the SHA-256 of that text. Names are names, never paths; the package holds no folder, link, permission, owner, time or other file-system metadata, and nothing is ever extracted from it to a disk: a reader builds everything in memory and hands texts to the apply pipeline.

The package has two forms that share the header and the payload: the **plain envelope**, whose payload is readable, and the **encrypted envelope**, whose payload is the same document encrypted. A package that holds a secret entry is always the encrypted form [D]. The model lives once in `CampertronLibrary` (the transfer core, phases 16a and 16b); no application's project reads, writes or interprets a package.

**Reader and writer** [B]: the base class library's JSON reader and writer, no package added (as PBKDF2 was chosen for `Web.password`, D92). The reader is strict: exactly the members this design names, each once, in any order; no duplicate member, unknown member, comment, trailing comma, byte-order mark, `NaN` or text after the document; numbers are whole and in range; a depth of at most four. The writer is deterministic: the members in this design's order, entries in the order of §Entry kinds, the same input always the same bytes but for the encrypted envelope's random salt and nonce.

## Plain envelope

The form of a package without a secret [D]. Members of the document, in the writer's order:

| Member | Value |
|---|---|
| `campertronSettingsPackage` | the format version, a whole number (§Format versioning); its presence is also what identifies the document as a package |
| `protection` | the text `none` |
| `exportedBy` | the exporting Campertron's version (§Exporting Campertron version) |
| `payload` | the payload: an object with `entries` (the list) and `manifestSha256` (§Integrity and authenticated encryption) |

A plain envelope with a secret kind among its entries is refused, whatever else it holds. Its checksums detect corruption; they prove nothing about who wrote the package or whether someone changed it and recomputed them, and no word shown to a user may suggest otherwise [D].

## Encrypted envelope

The form of a package that holds at least one secret entry [D]; the reader also accepts it for a package without one, so that encrypting a secret-free package can be offered later without a new format [D]. Members, in the writer's order:

| Member | Value |
|---|---|
| `campertronSettingsPackage` | the format version |
| `protection` | the text `passphrase` |
| `exportedBy` | the exporting Campertron's version |
| `kdf` | an object: `name` the text `pbkdf2-sha256`, `iterations` the number 600000, `salt` 16 random bytes as base64 |
| `cipher` | an object: `name` the text `aes-256-gcm`, `nonce` 12 random bytes as base64 |
| `ciphertext` | the encrypted payload as base64 |
| `tag` | AES-GCM's 16-byte tag as base64 |

The plaintext is the payload object of the plain envelope, written as UTF-8 JSON by the same writer. Base64 is the standard alphabet with padding, read strictly (it must encode back to the same text).

## Header fields

The header is every member but `payload`, `ciphertext` and `tag`. Every header value is checked before anything else is done with the package:
- `campertronSettingsPackage`: a whole number of 1 or more;
- `protection`: exactly `none` or `passphrase`, and the members that follow must be exactly that form's;
- `exportedBy`: 1 to 64 characters, each a letter, a digit or one of `.`, `-`, `+`;
- in the encrypted form `kdf.name`, `kdf.iterations`, `cipher.name` exactly the values above, the salt exactly 16 bytes, the nonce exactly 12, the tag exactly 16.

For format 1 the iteration count is the constant 600,000 [D]: a header that asks for any other number is refused before a key is derived, so a package can ask neither for a weaker derivation nor for one that would stall the reader.

## Format versioning

- The format version is a whole number; this design is format **1** [B].
- A reader refuses a format newer than the ones it knows, in fixed words that say the package was made by a newer Campertron [D]. It never reads such a package "as far as it can".
- A reader reads each older format by that format's own rules; with format 1 there is none.
- The format changes (a new number) when a member, an entry kind, a cryptographic choice or the meaning of a value changes. The limits of §Limits are the reader's policy, not the format: changing one needs no new format number, only a release note.
- In the encrypted form the format version is part of the authenticated header, so it can't be changed without the tag failing.
- A package of a known format whose settings text the receiver's own loader refuses (a key a newer Campertron wrote) is refused by that file's name; nothing is dropped silently.

## Exporting Campertron version

`exportedBy` is the application version of the exporting program, without its build's commit hash [B] (`RuntimeInfo` reads the same informational version; the hash is left out because a package is passed around). It is information: the preview shows it, and nothing is accepted or refused because of it. Compatibility is decided by the format version and by the receiver's own loader and validation.

## Entry kinds

An entry has exactly four members: `kind`, `name`, `text` and `sha256` (64 lower-case hexadecimal digits: the SHA-256 of the text's UTF-8 bytes) [D]. The kinds are an allow-list [D]; an entry of any other kind makes the whole package refused, never skipped:

| Kind | Name | Text | Form |
|---|---|---|---|
| `general` | exactly `General.yaml` | the file's text after the export's edits (§Text-preserving YAML edits) | both |
| `email` | exactly `Email.yaml` | likewise | both |
| `ntfy` | exactly `Ntfy.yaml` | likewise | both |
| `search` | a search file's name (§Strict name model) | the file's text, unchanged | both |
| `secret-smtp-password` | exactly `smtpPassword` | the SMTP password | encrypted only |
| `secret-ntfy-token` | exactly `ntfyToken` | ntfy's access token | encrypted only |
| `secret-ntfy-topic` | exactly `ntfyTopic` | ntfy's topic | encrypted only |

At most one entry of each kind but `search`. A secret entry needs the entry of the file it belongs to in the same package (`email` for the password, `ntfy` for the token and the topic), so a secret never arrives without its settings [B]. A package has at least one entry. The writer's order: `general`, `email`, `ntfy`, the searches by name (ignoring case, then ordinally, as `ConfigFiles.SortedSearchFileNames` orders them [V]), then the secrets in the table's order.

A text is the file's text as the safe writers read it [V] (`ConfigFileReplace.Read`: strict UTF-8, a leading byte-order mark kept as its one character, the line endings as they are), so the receiver writes the bytes the sender had, apart from the edits this design names.

## Strict name model

- A name is never a path: no separator, no drive, no parent folder. The three settings names are compared exactly; a different spelling or case of them is refused.
- A search entry's name is what `SearchFileName.Check` returns for it [V], and the name in the package must equal that result exactly: it ends in `.yaml`, has at most 100 characters before it (`SearchFileName.MaxNameLength` [V]), only letters, digits, spaces and `- _ . ( )`, no leading or trailing space or dot, nothing Windows reserves, and never one of the settings files' names in any case. The rule is the same on every platform, so a name one platform would refuse is refused everywhere.
- Two entries whose names are equal ignoring case are refused, also when they differ in case only [D].
- On the receiver a search entry whose name equals an existing file's name exactly replaces that file; one that matches no existing entry of the settings folder in any case creates a file; one that differs from an existing entry in case only refuses the import (`SearchFileName.CheckFree`'s rule [V]) [D].
- Export offers the search files the applications list (`ConfigFiles.SortedSearchFileNames` [V]); one whose name the check refuses (a file made by hand) is not offered and is said by name.

## Limits

Each is enforced before the work it bounds, and each refusal is one fixed sentence [D]. The numbers are the reader's policy (§Format versioning).

| Limit | Value | Evidence and where it is enforced |
|---|---|---|
| The complete package | 1,048,576 bytes (1 MiB) [D] | the web host's request limit `MaxRequestBytes` [V]; from the file's length or the upload's declared length before reading, and again while reading (never more than the limit and one byte are read) |
| Entries | at most 256, secrets included [B] | the web host's `MaxFormValues` and `YamlDocument.MaxEdits`, both 256 [V]; counted while the list is read, before any entry is hashed or parsed |
| One settings or search text | at most 65,536 bytes of UTF-8 (64 KiB) [B] | the web host's `MaxFormValueLength` [V], a sixteenth of the loader's `YamlDocument.MaxDocumentLength` of 1,048,576 characters [V] (Campertron's files are a few hundred characters); before its hash and before the YAML loader |
| One secret | 1 to 4,096 bytes of UTF-8, no line break, no NUL, no byte-order mark [D] | `SecretFile.MaxFileBytes` and `SecretFile.FromBytes`' rules [V], so that a secret Import writes is one the monitoring's start reads |
| A name | the settings names exactly; a search name by `SearchFileName.Check` (at most 100 characters before `.yaml`) | [V] |
| `exportedBy` | 1 to 64 characters | §Header fields |
| Nesting | at most four levels | the reader |
| The passphrase | 10 to 128 characters (§Passphrase rules) | `WebPasswordHash.MinLength`, `MaxLength` [V] |
| Key derivations | one for each passphrase the user enters, never before the header passed | §Header fields |

Export applies the same limits: a file over the text limit is not exported and is named; a selection that would exceed the entry or package limit is refused before anything is written.

**The order of a read** [B]: the length; the bytes within the limit; strict UTF-8 without a byte-order mark; the strict JSON document; the header; for the encrypted form the passphrase, one derivation and the decryption with its tag; the payload's strict JSON; the entry count; each entry's kind, name and length; each text's SHA-256; the manifest's SHA-256; the secrets' rules. Only a package that passed all of it reaches the YAML loader and the validation (§Validation).

## Integrity and authenticated encryption

**Plain envelope** [D]: each entry's `sha256` covers its text. `manifestSha256` covers the list as a whole [B]: the SHA-256 of the UTF-8 bytes of these lines, each ended by a line feed: the format version; the number of entries; then for each entry, in the package's order, its kind, its name and its `sha256`. A changed text, name or kind, a missing or added entry and a changed order are each detected. This is corruption detection, said so wherever it is named; a person who changes a plain package can recompute both, and every text is validated as any file is.

**Encrypted envelope** [D]:
- the key: PBKDF2-HMAC-SHA256 over the passphrase's bytes (§Passphrase rules), the header's 16-byte salt, 600,000 iterations, 32 bytes of output, used as the AES-256 key (`Rfc2898DeriveBytes.Pbkdf2`, as `WebPasswordHash` uses it [V]);
- the cipher: AES-GCM (`System.Security.Cryptography.AesGcm`) with the header's 12-byte nonce and a 16-byte tag; .NET's own cryptography only, no package;
- the associated data [B]: the complete header, as the UTF-8 bytes of these lines, each ended by a line feed: the text `campertron-settings-package`; the format version; `passphrase`; `exportedBy`; `pbkdf2-sha256`; the iteration count; the salt as base64; `aes-256-gcm`; the nonce as base64. It is built from the values read, not from the file's bytes, so the same header always gives the same data, and any changed header value fails the tag;
- the salt and the nonce are new random bytes for every package (`RandomNumberGenerator`); a key is derived for one package and encrypts once, so a key and nonce pair is never used twice;
- the payload inside still carries each entry's `sha256` and the `manifestSha256`, checked after the decryption like a plain package's;
- a wrong passphrase, a changed header, a changed ciphertext and a changed tag all end in the same fixed sentence, which does not say which it was [D];
- the key and the passphrase's bytes are cleared from memory after use (`CryptographicOperations.ZeroMemory`), as far as managed memory allows; no claim beyond that.

**Availability** [D]: if the running platform does not support AES-GCM (`AesGcm.IsSupported`), an encrypted export or import is refused in fixed words; there is never another cipher and never an unencrypted package with a secret. That it is available on every release target is confirmed before phase 16a merges (§Phase 16a boundary).

## Passphrase rules

The established rules of the web UI's password, where they fit [D] (`WebPasswordHash` [V]):
- the bytes are the UTF-8 of the passphrase's Unicode NFKC form, so the same passphrase typed on another keyboard or system gives the same key; nothing is trimmed;
- 10 to 128 characters, not only spaces, valid Unicode; Export asks for it twice and refuses two that differ; Import asks once;
- chosen by the user for one export, never generated, remembered, stored, written to a file, logged, echoed, shown, put on the clipboard by Campertron or kept in any evidence;
- typed without echo in the console (refused where the input is no terminal), in a password box in the desktop GUI and in a password field in the web UI, sent only in the protected POST's body;
- a wrong passphrase costs one derivation; the web UI counts each attempt against the import's rate limit (§Web adapter), the other two wait for the user.

Campertron cannot recover a forgotten passphrase, and says so where it asks for one.

## Allow-list

Exactly this is transferable in `v0.4.0` [D]:

| Content | Carried | Left out of its text at export |
|---|---|---|
| `General.yaml` | its settings, outputTo among them | `lastRidbDataRefresh` |
| `Email.yaml` | its settings | `smtpPassword`, `smtpPasswordFile` |
| `Ntfy.yaml` | its settings | `topic`, `tokenFile` |
| each search file the user chooses | its text, unchanged | — |
| the SMTP password, ntfy's token, ntfy's topic | only as a secret entry, each after its own opt-in | — |

The user chooses what a package holds: any of the three settings files and any of the search files; a secret only with its file. A file that does not exist is not offered. Nothing outside this table is ever read for a package, and the writer takes its entries from this allow-list, never from a listing of the folder.

## Never-carried files and state

Never in a package, never read for one and never written by an import [D]: `Web.yaml` and every value of it (`passwordProtection`, `networkListening`, `allowedHosts`, `trustedProxies` and any other); `Web.password`, `Web.keys`, setup codes, sessions and password records; `preferences.json` and the web UI's theme cookie; `Camp.History`; the campground database with its backups, staging files and lock files; the cache; `*.bak` and `*.tmp` files; the restart handoff; process, monitoring and guided-setup state; logs; any file of the user's that is not a settings or search file; any path; a secret file's contents unless that secret was opted in; an environment variable's value.

`Web.yaml` is not an advanced or off-by-default category, and reconsidering it needs a later, separately reviewed decision [D]. A package that names `Web.yaml`, or any name outside the allow-list, is refused as a whole (an unknown kind, or a search name the check refuses: `SearchFileName.Check` refuses the four settings names in any case [V]).

## Secret classification

Three values are secrets in a transfer [D]:

| Secret | Where it is on the sender | Its sources, in the established order |
|---|---|---|
| The SMTP password | the file `smtpPasswordFile` names, the variable `CAMPERTRON_EMAIL_PASSWORD`, or `Email.yaml`'s `smtpPassword` | ER-33: the file, then the variable, then the plain text; never a fallback from a configured source |
| ntfy's token | the file `tokenFile` names, or the variable `CAMPERTRON_NTFY_TOKEN` | ER-34: the file, then the variable, else none |
| ntfy's topic | `Ntfy.yaml`'s `topic`; the schema has no topic file, and `v0.4.0` adds none | ER-34, D112 |

The paths `smtpPasswordFile` and `tokenFile` are the sender's and are never carried; they are not secrets but are treated as host-specific (§Receiver-kept keys). The email addresses, server names and campground choices a package holds are ordinary content: a secret-free package is readable, and Export says so before it writes one.

## Secret opt-in

- Every secret is left out by default and opted into one by one, each with its own choice, at export [D]. No choice selects them together.
- A choice is offered only when it applies; otherwise it is disabled with a note in fixed words [D]: the secret's file is not part of the export; no value or source is configured; its only source is an environment variable (§Environment-variable handling); its configured file can't be used (the problem's kind, never the path).
- Opting in is what allows the read: the configured file (through `SecretFile.Read`, the one reader [V]) or the plain-text value is read once, when the user starts the export, never while the choices are shown and never for a secret that was not chosen (ER-39's rule for the test notification, applied to Export) [D]. The value goes into the package's secret entry and is dropped as soon as the package is built.
- A value that is not a usable secret by `SecretFile`'s rules (empty, over 4,096 bytes, a line break inside, a NUL, a byte-order mark) is not exported; the export stops with that secret's fixed words.
- Any opted-in secret makes the package the encrypted form and asks for the passphrase [D].
- On the receiver the preview names each secret the package carries, by its kind only, and what importing it does (§Preview); a carried secret is imported with the package unless a rule refuses it (§Candidate-state construction), and the user may cancel.
- No value of a secret is ever in a preview, a status, a page, a console line, a log, a screenshot, an error, a test's output or an evidence file [D]. Every test scenario of the transfer carries canary secrets and searches for them (§Test obligations).

## Environment-variable handling

A secret whose only source is an environment variable is not offered for export [D]: its choice is disabled, with a note that the receiver must set the variable itself. Export never reads the variable's value; it looks only at whether the variable is set, yes or no, as the web UI's settings pages already do [V] (ER-33, ER-34), and only to word the note. This stays outside the user-action read exception of §Secret opt-in. The established precedence is kept: a configured file is the source even when the variable is also set, and a configured file that can't be used never falls back to the variable.

On the receiver nothing reads or changes a variable. A receiver that uses a variable keeps using it when the package carries no secret; when an imported secret's file is written, the file is that secret's source from then on (the established precedence), and the preview says the source changes.

## Receiver-kept keys

Keys whose value belongs to one computer [D]. Export removes them from the text; Import puts the receiver's own value back:

| File | Key | At import |
|---|---|---|
| `General.yaml` | `lastRidbDataRefresh` | the receiver's value, or left out when the receiver has none |
| `General.yaml` | outputTo | carried; replaced by the receiver's value only when the user leaves its change out after the gate refused it (§outputTo gate) |
| `Email.yaml` | `smtpPassword` | always the receiver's own (left out when it has none); an import never writes this key's value [D] |
| `Email.yaml` | `smtpPasswordFile` | the path of Campertron's new password file when the SMTP password is imported; else the receiver's own, or left out |
| `Ntfy.yaml` | `tokenFile` | the path of Campertron's new token file when the token is imported; else the receiver's own, or left out |
| `Ntfy.yaml` | `topic` | the imported topic when it is carried and the file's protection allows it; else the receiver's own, or left out |

The preview says of each kept value that it is kept from this computer and never shows it. Where a kept key is absent and the result needs it (an enabled ntfy without a topic, email without a password source), the preview says in safe words what stays incomplete, in the validation's own words.

## Text-preserving YAML edits

Every change of a settings text is a text-range edit of `YamlDocument` (`RemoveProperty`, `SetScalar` [V]; ER-16), on a copy in memory; nothing is ever serialized from a model again (ER-14) [D].
- **Export:** the keys of §Allow-list's third column are removed from a copy of each file's text; comments, order, quoting, line endings and a byte-order mark stay. The edited text must load by Campertron's own loader as the file's settings without those keys, and is checked the way a secret-free backup is (`SecretFreeBackup`'s verification, D111 and D112 [V]): it must hold the removed secret nowhere else, for example in a comment. A file that fails either check is not exported and is named.
- **Import:** the receiver's values of §Receiver-kept keys are set in, or removed from, the package's text the same way, and the result must load as the intended settings.
- **A text the editor refuses to edit** (it refuses instead of normalizing: an alias, a duplicate key, a layout it can't change safely) is not exported, or refuses the import, by its file's name; it is never sent unfiltered and never rewritten.
- **Search files** are never edited: their text travels and is written as it is.

## Candidate-state construction

The candidate is the receiver's settings folder as it would be after the apply, built in memory and never written before the confirmation [D]. For each name it is the package's text (with the receiver-kept values), or the receiver's present text for a file the package does not touch. Building it:
1. read the receiver's present state within the loaders' limits: the three settings files and, for each name the package touches, the file of that name or the fact that no entry of the folder has it in any case;
2. for each settings entry, the text of §Text-preserving YAML edits; for each search entry, its text;
3. for each carried secret, its rule:
   - **the SMTP password and the token:** a new file of Campertron's in the settings folder, `Email.password` or `Ntfy.token` [B] (the naming of `Web.password` and `Web.keys` [V]), and its fully qualified path as `smtpPasswordFile` or `tokenFile`. The file is only ever created: if any entry of the folder has that name in any case, that secret is not imported, the receiver's own setting is kept, and the preview says so [B][O];
     since D134 (2026-11-28, the approval's secret-replacement policy) the names are `Email.password.<id>` and `Ntfy.token.<id>`, `<id>` the transaction's 128 random bits as 32 lower-case hexadecimal digits, so every import creates a new file and a later import supersedes an earlier one; a taken name fails the apply rather than refusing the secret (business-rules-settings §45);
   - **the topic:** written into `Ntfy.yaml` only if the resulting file is owner-only (§Unix permissions, §Binding Windows owner-only ACL rule); otherwise that secret is not imported and the receiver's topic is kept [D];
   - a secret the platform can't protect (§Unix permissions, §Binding Windows owner-only ACL rule) is not imported;
4. the outputTo of §outputTo gate.

A refused secret never refuses the rest of the package: the preview names it and the remaining package can be applied [D]. Whenever a choice or a refusal changes the candidate, it is built again and previewed again; an apply is always of the candidate last shown.

## Validation

Nothing of the validation is written again for the transfer [D]:
- each candidate text goes through the bounded loader (`Yaml`'s limits: the characters, events, depth and aliases [V]; ER-17) and `ConfigValidation`, with the resulting outputTo, exactly as that file's editor judges it before a save;
- what an editor's Save of that text would refuse, the import refuses, by the file's name and in the validation's own value-free words; what it would only warn about, the preview shows as a warning;
- a file the loader refuses (an unknown key, a wrong type, a document over a limit) refuses the import by name; unknown keys are never dropped, and an unknown file never becomes a search file (an entry's kind and name decide what it is, and both were checked);
- Export validates too: a file the sender's own loader refuses is not exported and is named.

## outputTo gate

`General.yaml`'s outputTo decides whether a start monitors, so its change is gated by the checks of D71 and D73 on the candidate, not on the folder as it is [D].

**The candidate-text seam** (phase 16b) [B]: `ConfigValidation.MonitoringStartErrors` and `MonitoringSearchErrors` read the settings folder today; `MonitoringSearchErrors` and the search loader below it (`Load.LoadMonitoringSearches`, `Yaml.CampertronConfigGetConfigs`) already take a search file's unsaved text from the caller (`EditedText` [V]), and the file validation already has a form that judges a text (`ValidateText` [V]). Phase 16b extends that one seam so that the same two checks judge a complete candidate: a source that gives, for `Email.yaml`, `Ntfy.yaml` and every search file name, the candidate's text or that the file is absent, search files that do not exist yet included. The checks, their decisions and their words stay exactly these functions'; no rule of them is copied, and with no source they read the folder as before.

**The gate:**
- outputTo changes to Email or Ntfy (the package's value differs from the receiver's): both checks run on the candidate for that outputTo. If they find nothing, the change is part of the candidate. If they find something, the change can't be applied: the preview shows the checks' own words, and the user may apply the remaining package without changing outputTo, which builds the candidate again with the receiver's outputTo [D], or cancel.
- outputTo changes to Console or HtmlFile: applied; no start monitors with it.
- outputTo stays what the receiver has (the package carries none, carries the same, or its change was left out) and it is Email or Ntfy: the same checks run on the candidate, and what they find is shown as a warning in their own words, as the editors warn about a saved outputTo (D73).
- Campertron never chooses another outputTo by itself and never changes one silently [D].

**What the preview says of the resulting outputTo** [D]: its value, prominently; and which future starts would monitor with it: with Email or Ntfy the console started without arguments, a container that starts it so, and web mode at its start monitor by themselves, while the desktop app and the interactive console monitor only after the user's Start. An import starts, stops and restarts no monitoring (§Monitoring, refresh, search and editor coordination), and `General.yaml` is written last (§Write order).

## Preview

Built from the candidate, by the transfer core; an adapter only shows it [D]:
- the package: the exporting version, its format, whether it was encrypted, and for a plain one that its checksum detects damage only;
- each file: created, replaced or unchanged; for a settings file the lines that change, with every secret's and kept key's value left out; for a search file its name and whether it is new;
- the resulting outputTo and what it means (§outputTo gate);
- each receiver-kept value, as kept from this computer, never shown;
- each carried secret by its kind: imported into a new owner-only file of Campertron's, or into `Ntfy.yaml`; the change of a secret's source kind (from a file, the variable, the plain text or nothing to Campertron's file) without a path and without a value; or why it is not imported;
- what stays incomplete, and every warning and refusal of §Validation and §outputTo gate;
- that the receiver's other search files are not touched and nothing is deleted;
- what a backup is kept of, and that the monitoring reads the settings only when it next starts.

Where an application must not show a path (the web UI, ER-38), the preview holds none; it never holds a secret anywhere. A preview has a **revision** [B]: a digest of the package, of every piece of the receiver's state it was built from (each file's SHA-256 or absence) and of the user's choices. An apply names the revision it applies.

## Confirmation

An apply needs the user's explicit confirmation of the preview shown, with No as the default wherever a default exists [D]: a question in the console, a button in the desktop GUI, a protected POST in the web UI. The confirmation carries the preview's revision; a revision is applied at most once, and a second confirmation of it is refused.

## Apply lock

One lock for every apply of a settings folder, shared by the three applications and by every process [D]: a file `Campertron.transfer.lock` [B] in the settings folder, held as an open handle without sharing for the whole apply, modeled on the monitoring lock [V] (`MonitoringLock`: the lock is the handle, so it is never stale; the file is never deleted, stays empty and is created for its owner only). It is separate from the monitoring, refresh and repair locks and is never taken while holding one of them.

After the confirmation and before any write, in this order, each refusal in fixed words and with nothing written:
1. this process has an unsaved change in an editor of a settings or search file (the web UI: in the importing session's forms): refused; the user saves or reverts first [D];
2. a refresh of the campground data is running in this process: refused [D];
3. this process's monitoring is starting: refused; a monitoring that is running, stopped or held is not a reason (§Monitoring, refresh, search and editor coordination) [D];
4. the lock is held, by this or another process: refused; an apply is never queued [D];
5. under the lock, the receiver's state is read again and compared with the preview's revision; any difference (a file changed, appeared or disappeared, a name now taken) refuses the apply as stale and asks the user to look at the preview again [D].

Another process's unsaved editor is not known here: its own save then meets the changed file and is refused by the editing session's established check (ER-18).

## Backup set

Before the first write to a settings, search or secret file, the apply writes a backup set of every file it will replace [D]:
- **where:** a folder `Campertron.transfer.backup` [B] in the settings folder. No loader reads it: the search files are the top-level `*.yaml` files only [V], and its files are named `<name>.bak`. A file `Contents.txt` in it lists, by name only, what the apply replaced and what it created, with the time and the Campertron version; it holds no value and no path, and no program reads it;
- **protection:** the folder and its files are owner-only, by the rules of §Unix permissions and §Binding Windows owner-only ACL rule; where that can't be established, the apply is refused before any write;
- **no secret:** each backed-up `Email.yaml` and `Ntfy.yaml` holds `smtpPassword: ''` and `topic: ''` in place of a value, whether or not the apply changes it (the text edit of D111 and D112); a set never holds a secret file's contents. The same holds for the rolling `<name>.bak` the safe writer keeps beside each replaced file: every replacement of an apply, forward or back, gives the writer the secret-free backup text [D];
- **bounded:** one set is kept, the last apply's [B] (as the safe writer keeps one rolling backup [V]). A new set is written under a temporary name, read back, and only then takes the old set's place, before the first settings write; if it can't, the apply is refused;
- **not a journal:** no start and no program reads the set; it is for the user [D].

The set is not what the rollback restores from (§Rollback): it is what is left for the user when a rollback fails or the process dies. Because it holds no secret, a file restored from it by hand needs its password or topic entered again; the recovery words say so.

## Write order

Fixed [D]:
1. the backup set;
2. the search files, by name: each created or replaced;
3. `Ntfy.token`, if the token is imported, then `Ntfy.yaml`;
4. `Email.password`, if the password is imported, then `Email.yaml`;
5. `General.yaml`, last.

A secret file is always written before the settings file that names it, and `General.yaml`, which alone decides whether a start monitors, changes only after everything it needs is in place. A file whose candidate text equals its present text is not written.

## Atomic replacement

Every settings and search file is written by the safe writers and by nothing else (ER-18): `ConfigFileReplace.Replace` for a file that exists (a verified temporary file, the rolling backup, the mode and links kept, the re-read before the rename) and `ConfigFileReplace.Create` for a new one (create-only, so a name taken since the preview fails; a new `Email.yaml` or `Ntfy.yaml` owner-only, as the editors create them) [V]. A process that dies at any moment therefore leaves each file complete, old or new. The secret files are written by the protected secret writer (§Unix permissions, §Binding Windows owner-only ACL rule), to a temporary file created with its protection and moved into place only if the name is free.

## Read-back verification

After each write the file is read again and must be exactly the candidate's bytes (its SHA-256), with the protection its rule requires; a secret file is compared with the value in memory, which is never written anywhere else. After the last write every file the apply wrote is checked once more. Any difference is a failure of the apply and starts the rollback [D].

## Rollback

On any failure after the first write, in the same process and under the same lock [D], in the reverse of §Write order:
- each replaced file is put back to its exact previous bytes, which the apply holds in memory from its read under the lock, through the safe writer, and read back against the SHA-256 it had;
- each file the apply created is removed only if it is still exactly what the apply wrote (the same regular file, not a link, the same bytes): a created search file, and a created secret file after the settings file that named it is restored. This is the one case in which Campertron removes a search file (ER-14 says never): phase 16b records it there as an exception limited to a file this apply created moments before and nobody changed;
- anything else is left as it is and named in the result.

After a successful rollback the folder's settings, search and secret files are byte for byte what they were, and the result says in fixed words that nothing was changed. The backup set and the rolling backups remain; they hold no secret.

## Rollback failure

If a file can't be put back or removed, the rollback goes on with the others and then stops [D]. The backup set is kept, and the result says, in fixed words and by names only: which files are as before, which could not be restored, that the backup set holds the earlier settings without their passwords and topic, and that Campertron does nothing more about it by itself. Nothing is retried in the background, and no start looks for an unfinished import.

## Cancellation boundary

- Before the confirmation everything can be cancelled, and nothing was written: Export before its file is written, Import at the choice of the file, the passphrase and the preview.
- From the moment the apply holds the lock there is no cancellation [D]: Esc, Ctrl+C, a closed window, a sign-out, the input's end and a stop signal are answered only after the apply ended, applied or rolled back, as a check that sends is never interrupted (ER-36). An apply takes moments; each host waits for it at its end as it waits for a search or a refresh.
- A process killed during an apply leaves every file complete, old or new, perhaps a mix of both, the backup set in place and `General.yaml` unchanged unless everything before it was written (§Write order). Nothing repairs it automatically [D]. A secret file left without a setting that names it stays until the user removes it; it is owner-only.

## Restart requirements

An import changes saved files and nothing else, so nothing has to restart for it to be complete [D]. What reads the files when:
- the editors of the three applications show the saved files again after an apply (nothing unsaved was open, §Apply lock);
- a monitoring that is running keeps the settings it started with and reads the new ones at its next start, as after an editor's save [V] (business-rules-settings §35); the result says so;
- web mode decides at its own start whether it monitors (D83), so a changed outputTo takes effect at web mode's next start, and the result says so; the campground data and the web UI's access settings are not touched.

## Monitoring, refresh, search and editor coordination

- **The monitoring:** an import never starts, stops, restarts or pauses a monitoring, in any process [D]. It is refused only while this process's monitoring is starting, because a start reads the files at that moment. A monitoring another process starts during an apply reads complete files that may be a mix of old and new; its own start checks judge what it reads, and the write order keeps outputTo for last. The monitoring lock is never taken by an apply.
- **`Camp.History`** is never read, written or re-armed (ER-03).
- **A refresh:** an apply is refused while this process refreshes, and a refresh is not started while this process applies; another process's refresh writes only `General.yaml`'s `lastRidbDataRefresh` through the safe writer, whose re-read refuses the one that comes second.
- **A search and a test notification** that already run have read their files and are not affected; none is started by an import. The database, the cache and the campground data are never touched, and no example search is created (ER-15).
- **Editors:** §Apply lock.
- **One operation:** each host shows an apply as its own busy state, apart from a search, a refresh and the monitoring; the web UI allows one at a time for all sessions.

## Cross-platform paths

- A package holds names only, judged by one rule on every platform (§Strict name model); line endings and a byte-order mark travel as they are.
- The only path an import writes is the fully qualified path of Campertron's own secret file in the receiver's settings folder, built by the receiver. Where one settings folder is used through two paths (a folder a container mounts as `/config` and the host uses under its own path), the path is right only for the application that imported; the preview says that the path is this computer's (the editors' note on a secret file that exists only where Campertron runs, D75).
- No path of the sender is carried, shown or compared, and the web UI shows no path of the receiver either (ER-38).

## Unix permissions

On Linux and macOS [D]:
- a secret file is created with mode 0600 at its creation (never created wider and narrowed), by the current user, and must read back as exactly 0600 before it is moved into place and after; otherwise it is removed and that secret is not imported (a file system that keeps no modes refuses every secret);
- the backup set's folder is 0700 and its files 0600, checked the same way; otherwise the apply is refused before any write;
- the topic is imported only if the resulting `Ntfy.yaml` has no permission for its group or others: a new one is created 0600 (as the editors create it, D69), an existing one keeps its mode (ER-18), so an existing file that others can read refuses the topic;
- an existing file's mode is never changed, wider or narrower, by an import;
- a new `Email.yaml` or `Ntfy.yaml` is created 0600; a replaced one keeps its mode; a search file as the editors write it.

## Binding Windows owner-only ACL rule

For `v0.4.0`'s per-user applications [D]; binding on phase 16b:
- **A new secret file and the backup set's folder** are created with their access control already in place, never created with the folder's inherited rules and changed afterwards: a protected access control list (inheritance disabled, no inherited entry) with exactly one entry, which allows full control to the current user's own account, and that account as the owner. No entry for Users, Authenticated Users, Everyone, or any other group or account; none for Administrators or the system account either, because the per-user application needs none. The backup set's files take their rules from that folder only.
- **Proof before use:** the file's or folder's rules are read back and must be exactly that (protected, one entry, the current user, the owner the current user), and the object must be no link or other reparse point. If the rules can't be set or don't read back so, the object is removed and the secret is not imported, or the apply is refused before any write: Campertron refuses rather than writes [D].
- **`Email.yaml`, `Ntfy.yaml`, `General.yaml` and the search files never get rules of their own:** the safe writer refuses to replace a file with a protected or explicit access control list [V] (`ConfigFileReplace`), so an import leaves these files to the rules their folder gives them, and no existing rule is weakened or tightened [D].
- **The topic** is imported only if the resulting `Ntfy.yaml`'s rules, which it inherits, allow access to nobody but the current user, the system account and the Administrators group [B]: the rules a folder below the user's own profile has. Any entry for another account or group refuses the topic. Those two system identities read every file of the computer in any case; an inherited rule can't exclude them without giving the file rules of its own, which the safe writer forbids.
- **Service accounts are deferred** [D]: which other identity, if any, needs access (a background service, an installer's account) is `v0.7.0`'s installer design (D93); until then no other identity is granted anything.
- **Validation on Windows itself** is owed by phase 16b (§Test obligations): these rules are checked natively, never only reasoned about.

## Console adapter

The interactive console only (`--interactive`; ER-45), through a choice of its main menu [D]; no argument exports or imports:
- **Export:** numbered choices of the files and of each secret (a disabled one shown with its note); the passphrase asked twice without echo when a secret is chosen; a typed path for the package. An existing file is never written over: the user types another name. The file is created for its owner only on Linux and macOS.
- **Import:** a typed path; the passphrase without echo for an encrypted package; the preview as text, a part at a time; the choice to leave outputTo's change out when the gate refused it; the confirmation asked, No by default; the result in fixed words.
- Line-oriented prompts as every screen of it; Esc and Ctrl+C cancel before the apply and are answered after it (§Cancellation boundary); a secret, the topic and the passphrase never echoed or written back.

## Desktop GUI adapter

- **Where:** in the window, at a place phase 18 proposes with its frames; a layout choice, reviewed there.
- **Export:** check boxes for the files and each secret (a disabled one with its note in a severity block, ER-35); a password box twice for the passphrase; Avalonia's `StorageProvider` save picker for the file, whose own question covers an existing name.
- **Import:** the `StorageProvider` open picker; a password box; the preview in the window; the outputTo choice; a confirmation; progress while it applies and the result in a severity block.
- A close of the window during an apply waits for it, as for a search or a refresh (ER-06); the forms show the saved files again afterwards; nothing of a secret is put on the clipboard.

## Web adapter

- **Export:** a protected POST (the request checks of ER-38 in their order, antiforgery) that answers with the package as a download: `Content-Disposition: attachment`, `Cache-Control: no-store`, a type no browser renders; nothing of it is kept on the server or written to its disk.
- **Import:** an upload in a protected POST, read in memory, never written to disk; the preview on a page, held only in the session's memory with its revision; a second protected POST applies it. A sign-out, the session's end or a restart discards the preview.
- **Limits:** the upload is refused above the package limit before it is read; because the host's request limit equals the package limit [V], the upload's own request limit is the package limit plus a bounded allowance for the form's other fields, set by phase 19, and no other request's limit changes [O]. Its own rate limit, counted per client like the tests', covers uploads, passphrase attempts and applies; one import at a time for all sessions.
- **No path:** no page, error or console line holds a path of the server, a file name of the upload, a secret or the passphrase; the passphrase is a password field sent in the POST's body only. The fixed pages and console lines stay the only ones (ER-38), and the CSP is unchanged.

## Interface parity

The same in all three, because it is the transfer core's [D]: what is offered and why a choice is disabled, the package's bytes for the same choices (but the random salt and nonce), every limit and refusal, the candidate, the preview's content, the gate, the lock, the order, the rollback and every word of a result. An adapter owns only its layout, its input (a typed path, a picker, an upload) and how it shows text.

No adapter owns a business rule, a validation rule, an allow-list rule, a cryptography rule, the apply order or a secret rule [D]. Each adapter's phase adds the reference tests that prove it (the existing IL-reference checks: `IlReferences`, the GUI's scanner, the console's): the adapter calls the transfer core, defines no word, limit, kind or name of its own, and reaches no file or cryptographic API for a package itself.

## Logging and redaction

- Campertron has no log; the transfer adds none. What an application writes is its usual output: `ConsoleUi` lines, the web host's fixed console lines, the GUI's severity blocks.
- Every line is a fixed sentence with, at most, a settings or search file's name, a count, a kind of secret and the exporting version. Never: a value of a settings file, a secret, the passphrase, a path, the package's own file name in the web UI, an exception's message or an operating system's or server's text.
- The transfer core's failures are its own fixed sentences: it never passes on the safe writers' or the system's message. Open question #65 (a save's failure showing the system's own message) is about the editors and stays open; the transfer must not add a second place for it.
- Evidence of a test or a validation (logs, transcripts, screenshots, records) is searched for the canaries before it is kept.

## Safe errors

Each failure has one fixed sentence in the transfer core; the final words are settled by the phase that implements them and reviewed there, and each says only what its row allows:

| Failure | May name |
|---|---|
| Not a Campertron settings package; damaged; too large; too many entries | nothing |
| Made by a newer Campertron | nothing |
| The passphrase is wrong, or the package was changed or damaged (one sentence for all of it) | nothing |
| Encryption is not available on this computer | nothing |
| An entry that can't be used (an unknown kind, a name that is refused, two names that differ in case only) | nothing of the entry's text; a name only after it passed the name rules |

| A secret that is not exported or imported | the secret's kind and the reason's kind |
| outputTo can't be applied | the readiness checks' own words |
| Unsaved changes; a refresh running; the monitoring starting; another import running; a stale preview | nothing |
| The apply failed and nothing was changed | nothing |

## Test obligations

Every scenario carries canary secrets (a unique synthetic SMTP password, token and topic, and for encrypted packages a canary passphrase), searched for afterwards in every output, package that should not hold them, backup and evidence file. No test reaches the network or a real settings folder (`NoLiveNetwork`, isolated temporary folders).

**Phase 16a** (the package; no settings write):
- a plain package's round trip; an encrypted package's round trip; deterministic parsing and writing (the same choices the same bytes, the encrypted form apart from its salt and nonce);
- a wrong passphrase; a tampered header (each member); a tampered ciphertext and tag; truncated input at several lengths; an oversized package, entry and entry count;
- a newer format; an unknown kind; a duplicate name and a duplicate JSON member; names that differ in case only; invalid names (separators, parent folders, drives, reserved names, the settings names in other cases, `Web.yaml`); invalid UTF-8 and a byte-order mark; a hash mismatch of an entry and of the manifest;
- the KDF parameters (the count, the salt's and key's lengths, another count refused before any derivation); nonce and salt uniqueness; AES-GCM's availability on every release target (§Phase 16a boundary);
- the secrets' rules (size, line breaks, an environment-only secret not offered and never read); canary secrets absent from a default export and from every plain package;
- no settings writes: no test of the phase, and no code path of it, writes a settings, search or secret file.

**Phase 16b** (the apply):
- an empty receiver; an existing receiver; every transferable file; a search added; a search replaced by its exact name; the receiver's other searches never deleted; an invalid search;
- every receiver-kept key, present and absent; the topic omitted, with and without a topic on the receiver; the topic opted in, allowed and refused; the SMTP password opted in; the token opted in; an environment-only secret unavailable;
- outputTo accepted; outputTo left out after the gate refused it; a stale preview; an unsaved editor; a refresh active; the monitoring starting; the apply lock held by this and by another process;
- a failure injected at every write step (through `ConfigFileReplace`'s steps and the secret writer's); a read-back failure; a successful rollback, byte for byte; a failed rollback and its retained set;
- the secret files' permissions; the Windows access rules, natively; Unix 0600; the backups' sanitization; the fixed safe errors; no path in the web output;
- no monitoring started, stopped or restarted; no access to `Camp.History`; no change of the database or the cache; no example search created;
- compatibility with TD-65 and TD-66: a search file is carried and applied as text, whatever those corrections add to it.

**The adapters' phases** (17, 18, 19): each application's workflow from an empty folder; the same choices giving the same package and the same preview in all three; the reference tests of §Interface parity; the console's hidden entry on a pseudo-terminal; the GUI's headless suites and frames; the web UI's request checks, limits, rate limit, `no-store` download and accessibility checks. PT2 follows phase 19.

**Windows:** the transfer's lock, writer, permission and apply tests run natively only when the Windows job's class list names them, which is a separately approved workflow pull request after phase 16b (§Phase 16b boundary); until it merges they are recorded as run on Linux only. Since D135 it has merged into the plan's sequence: the Windows job runs every transfer class natively.

## Phase 16a boundary

**In** [D]: the package model; the strict reader and the deterministic writer; the format version; the limits; the hashes; the encryption and the passphrase handling; the validation of a package up to its entries; the export's choice of content from the allow-list with its text edits and its secrets (their applicability, the read on the user's action); the fixed sentences of these failures; the tests and controls above. It may read settings and secret files, as an export must.

**Out:** any write of a settings, search or secret file, of a backup or a lock; the candidate, the gate, the preview and the apply; every application's project. Its tests prove that it writes nothing in the settings folder.

**Before it merges** [D]: AES-GCM's availability on every release target is confirmed and recorded. The release targets are the eight runtime identifiers and the two image platforms (`release-process.md` §Platforms and what a release run shows); six archives and both images run natively in a Release dry run, `win-x86` as compatibility execution, and `linux-arm` is built but never run (ER-28). How the dry run exercises the cipher, and what stands for `linux-arm`, is settled with phase 16a's approval [O]; a claim is never wider than what ran.
  Since D133 (2026-11-28): no release smoke test and no Windows CI class runs the transfer code without a change phase 16a's approval excludes, so AES-GCM ran on Linux x64 only (the unit tests' self-test); the merge records that, and every other target's run is owed before `v0.4.0`'s candidate, by a separately approved workflow, native or emulated validation (TD-69). Since D135 the release workflow runs the self-test on every release target's console archive and in both images (native, win-x86 compatibility, linux-arm emulated), and every check passed (TD-69 resolved).

## Deferred Beam boundary

Phase 15 designs only what Beam will reuse: the transport-neutral package and the receiver's apply pipeline [D]. Not decided here, and left to phase 20 with open questions #61, #62 and #64: Beam's transport, discovery, port, pairing protocol, key agreement, receiver lifecycle, timeout, replay defense, guessing limits and remote-session behavior. The encrypted envelope protects a file at rest with a passphrase; it is not Beam's transport protection and decides nothing about it.

A future Beam receiver must [D]: use this package and this apply pipeline; never apply without the receiving user's preview and confirmation; keep every secret rule and the outputTo gate.

## Open items that do not block phase 16a

Recorded so that none is decided by accident; each is settled with the approval of the phase named, and none is an open question of `open-questions.md`:
- **A later import's secret file** (phase 16b): this design only creates `Email.password` and `Ntfy.token`, so a second import of the same secret is refused while the first file exists. Replacing it would need the earlier secret kept for a rollback, which the backup rules forbid; whether and how a later import may supersede it is not decided.
  Settled by D134 (2026-11-28): a transaction-named new file each time, the earlier one left in place until the commit and then removed only when provably Campertron's and unneeded, else kept with a fixed warning; no earlier secret is kept for a rollback, because none is ever replaced.
- **AES-GCM on `linux-arm` and the dry run's check** (phase 16a): settled by D133: the run is recorded by target, Linux x64 only, and every other release target's run is owed before `v0.4.0`'s candidate (TD-69); since D135 it ran on every target, linux-arm emulated under QEMU user mode (TD-69 resolved).
- **The web upload's request limit** (phase 19): one request's limit above the host's, or a package limit lowered so that an upload fits the host's; either keeps every package importable by every application.
- **The package file's default name and extension, the menu's and the pages' words, the GUI's place** (phases 17 to 19): user-facing terminology, reviewed there. A package is recognized by its content, never by its name.
- **The limits' values** (§Limits) are bound here from the repository's constants and may be changed on review before phase 16a without changing the format.
